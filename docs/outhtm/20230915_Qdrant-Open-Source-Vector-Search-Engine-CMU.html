📋 บทสรุปย่อ

บทสรุปย่อ: การบรรยายในชุดสัมมนา ML⇄DB ของ CMU Database Group (11 กันยายน 2023) โดย อังเดรย์ วาสเนตซอฟ CTO และผู้ร่วมก่อตั้ง Qdrant เขาเล่าว่า vector search ไม่ใช่เรื่องใหม่ แต่เพิ่งใช้ง่ายสำหรับทุกคน แล้วอธิบายสถาปัตยกรรมของ Qdrant: collection → shard → segment (metadata ของคลัสเตอร์ เช่น ตำแหน่งของ collection/shard และสถานะ node เก็บด้วย Raft) ซึ่งบางส่วนเป็นแบบ immutable เพื่อให้ optimize ได้ (และต้องมีอย่างน้อยหนึ่ง segment ที่แก้ไขได้สำหรับรับข้อมูลใหม่) และใช้ copy-on-write กับ proxy segment ให้ผู้ใช้เห็นว่าทุกอย่างแก้ไขได้ตลอด เขาย้ำว่า Qdrant ควรถูกมองเป็น search engine (แบบ BASE) ไม่ใช่ database แบบ ACID จากนั้นลงลึกเรื่อง HNSW, ปัญหา random access, binary quantization (บีบอัด 32 เท่า แล้ว rescore ด้วยเวกเตอร์ต้นฉบับ) และ filterable HNSW: filter ระหว่างเดินกราฟ (in-place), ปัญหากราฟขาดตาม percolation theory และการสร้างลิงก์เพิ่มตาม payload ปิดด้วยการถามตอบเรื่อง Postgres, DiskANN, time series และโจทย์ที่ยังไม่แก้คือ "ทำให้การให้บริการเวกเตอร์พันล้านตัวมีราคาถูก"

โหมดของเนื้อหา: แปลคำต่อคำฉบับเต็ม เพราะคลิปใช้สัญญาอนุญาต Creative Commons Attribution (CC BY, ตรวจในหน้าคลิป 2026-10-10) ส่วนที่ 1–13 คือคำแปลของทุกประโยคตามลำดับ แยกตามผู้พูด ตัดเฉพาะคำเติม แก้คำที่ caption ฟังผิดตามบริบทและสไลด์ จุดที่ฟังไม่ออกเขียน [ฟังไม่ชัด] ส่วนที่ผู้จัดทำเพิ่มเองอยู่ในส่วนที่ 14 และ 15

vector search และตำแหน่งของ Qdrant: โมเดล (encoder) แปลงข้อมูลเป็นเวกเตอร์ (embedding) ที่วัตถุคล้ายกันจะอยู่ใกล้กัน ความคล้ายแบบไหนและฟังก์ชันระยะแบบไหนขึ้นกับโมเดล แต่ส่วนใหญ่ใช้ dot product สิ่งที่ใหม่คือโมเดลสำเร็จรูปหาง่าย ขั้นถัดไปคือทำให้ใช้งานจริงได้สะดวกและเชื่อถือได้เหมือน search engine และ database แบบดั้งเดิม ซึ่งเป็นสิ่งที่ Qdrant ทำ Qdrant เป็นโอเพนซอร์ส (Apache 2.0) เขียนด้วย Rust มีผู้ร่วมพัฒนาภายนอกกว่า 60 คน (ตอนนั้น) และผู้บรรยายชอบคำว่า vector search engine มากกว่า vector database

สถาปัตยกรรม: collection (คล้าย table) → shard (ข้อมูลไม่ซ้อนกัน ย้ายและ replicate ได้; metadata ของคลัสเตอร์เก็บด้วย Raft) → segment (แยก index กับ storage ทำงานได้ครบเหมือน collection เล็ก ๆ) Qdrant ยึดหลัก BASE (Basically Available, Soft state, Eventual consistency) เหมือน Elasticsearch ซึ่ง scale ได้ดีแต่ consistency อ่อนกว่า Postgres ที่เป็น ACID ผู้บรรยายจึงมองว่าในอุดมคติไม่ควรใช้เป็นที่เก็บข้อมูลหลัก โดยเฉพาะเมื่อการอัปเดตเวกเตอร์ทั้งหมด (เช่น เปลี่ยนเวอร์ชันโมเดล) เป็นเรื่องปกติ

ทำไมต้องมีหลาย segment: (1) immutable ทำให้ optimize ได้มาก: ข้อมูลกะทัดรัด cache miss น้อย รู้สถิติล่วงหน้า จองหน่วยความจำพอดี โหลดเร็ว (copy หรือ mmap) บีบอัดได้ รวมกันอาจทำให้มีประสิทธิภาพดีกว่าแบบ mutable ระดับ order of magnitude (2) แลก latency กับ throughput: segment เป็นหน่วยของการขนาน หลาย segment ช่วย latency ของคำขอเดียว segment ใหญ่ segment เดียวช่วย throughput การอัปเดตใช้ copy-on-write และระหว่างสร้าง index ใช้ proxy segment ที่ห่อ segment เดิมและเก็บรายการแก้ไขไว้

vector index: ต่างจาก index ดั้งเดิมสองข้อ คือเป็นค่าประมาณ (ผลอาจต่างกันถ้าสร้าง index ใหม่ เพราะขึ้นกับลำดับการใส่) และทุกเวกเตอร์อาจเป็นผลลัพธ์ได้ จึงขีดเส้นแบ่งเกี่ยวข้อง/ไม่เกี่ยวข้องจากคะแนนอย่างเดียวไม่ได้ Qdrant ใช้ HNSW (proximity graph ค้นแบบ greedy ปรับ precision ด้วยขนาด beam) ความท้าทายคือ การใส่เวกเตอร์ใหม่แพงกว่าการค้นราว 2 เท่าและกิน CPU และการเข้าถึงแบบสุ่มและเป็นลำดับ ทำให้ต้องใช้ RAM มากและขนานได้ยาก ทางแก้คือค้นด้วยเวกเตอร์ที่บีบอัดใน RAM เช่น binary quantization (1 บิตต่อมิติ บีบอัด 32 เท่า เทียบด้วย XOR + popcount) แล้ว rescore ผู้สมัคร (เช่น 100 อันดับแรก) ด้วยเวกเตอร์ต้นฉบับซึ่งดึงจาก disk แบบขนานได้ด้วย async I/O

filtering: post-filtering ง่ายแต่อาจกลายเป็น linear scan หรือได้ผลไม่ครบ pre-filtering ต้องสร้างรายการผู้สมัครซึ่งอาจแพง Qdrant ใช้ in-place filtering คือตรวจเงื่อนไขระหว่างเดินกราฟ (HNSW ที่ปรับเอง) แต่ถ้า filter เข้มมาก กราฟจะขาด ตาม percolation theory ค่าวิกฤตคือ 1/k (k = จำนวนลิงก์เฉลี่ย) เช่น 10 ลิงก์ ถ้าตัดออก 90% กราฟจะขาด ทางแก้คือสร้างลิงก์เพิ่มจาก payload ที่ index ไว้ (subgraph ต่อค่า keyword, ช่วงที่ซ้อนกันสำหรับตัวเลข, geohash สำหรับตำแหน่ง) แล้วรวมเข้ากราฟหลักโดยตัดลิงก์ซ้ำ ไม่เพิ่มความซับซ้อนตอนค้น ใช้กับหลายฟิลด์ได้ และในกรณีใช้งานจริงส่วนใหญ่ precision ที่ลดลงสังเกตไม่ได้เมื่อเทียบกับความเป็นค่าประมาณของ HNSW เอง

ถามตอบที่สำคัญ: ขนาด segment ไม่ได้กำหนดตรง ๆ แต่กำหนดจำนวน segment; สำหรับ customer ID ให้สร้าง HNSW เฉพาะ subgraph ตาม payload ได้; มิติเพิ่มสองเท่า การเทียบเวกเตอร์ช้าลงราวสองเท่า และการค้น/สร้างกราฟราว logarithmic; segment แบ่งแบบสุ่ม ไม่ทำ clustering; Postgres เหมาะเมื่อพอใจกับข้อจำกัดด้าน scale และระบบจริงมักมี Postgres เป็นแหล่งความจริงคู่กับ search engine; time series ใช้ได้ถ้ามีโมเดลที่แปลงเป็นเวกเตอร์; โจทย์ใหญ่ที่สุดคือทำให้การให้บริการเวกเตอร์พันล้านตัวมีราคาถูก

ตรวจทาน (เสริมจากผู้จัดทำ): ค่าวิกฤต 1/k ในสไลด์คือ "สัดส่วนของ node ที่เหลือ" ดังนั้นสัดส่วนที่ filter ออกได้ก่อนกราฟขาดคือ 1 − 1/k (ตรงกับตัวอย่าง 10 ลิงก์ → 90% ที่ผู้บรรยายยก) โมเดล OpenAI ที่พูดถึง (ปี 2023) ให้เวกเตอร์ 1,536 มิติ (ผู้บรรยายพูดว่าราว 1,500) และคำอธิบายเรื่อง DiskANN ที่ผู้บรรยายบอกเองว่าอาจผิด ควรอ่านคู่กับหมายเหตุในส่วนที่ 14

~5:13 อังเดรย์: แนวคิดพื้นฐานคือ คุณมีโมเดลบางตัว หรือที่เราเรียกอีกอย่างว่า encoder ซึ่งโดยทั่วไปเป็นโครงข่ายประสาทเทียม (neural network) มันสามารถแปลงข้อมูลอินพุตบางอย่างให้เป็นการแทนค่าในรูป dense vector และการแทนค่าในรูป vector เหล่านั้น ซึ่งเราเรียกอีกอย่างว่า embedding มีคุณสมบัติที่น่าสนใจมาก คือ คู่ของ vector ใน vector space ที่อยู่ใกล้กัน มักจะสอดคล้องกับวัตถุที่มีความคล้ายกันในบางแง่มุมด้วย ในกรณีของข้อความ อาจเป็นความคล้ายคลึงของความหมาย ในกรณีของรูปภาพ อาจเป็นความคล้ายคลึงทางภาพ และอื่น ๆ และจริง ๆ แล้วโมเดลเป็นตัวกำหนดว่าเราต้องการจับความคล้ายคลึงประเภทไหน [ฟังไม่ชัด] และฟังก์ชันระยะห่างระหว่าง vector ก็ถูกกำหนดโดยโมเดลเช่นกัน แต่กรณีการใช้งานส่วนใหญ่ก็เป็นแค่ dot product ธรรมดาระหว่าง vector

~7:05 อังเดรย์: งั้นตอนนี้มาดูกันว่า Qdrant ทำสิ่งนี้ได้อย่างไร นี่คือภาพรวมระดับบนสุดของส่วนประกอบของ Qdrant แต่ละระดับในลำดับชั้นนี้แทนการแยกส่วน (isolation) แบบพิเศษบางอย่าง ในระดับบนสุดคือ collection ซึ่ง collection จะแยกประเภทของข้อมูลออกจากกันในเชิงตรรกะ มันคล้ายกับ table ในฐานข้อมูลเชิงสัมพันธ์ หรือ collection ในฐานข้อมูลเชิงเอกสารอย่างเช่น MongoDB ถัดจาก collection ก็เป็นขั้นต่อไป ซึ่งก็คือ shard โดย shard จะแยกชุดย่อยของข้อมูลออกจากกัน รับประกันได้ว่า shard จะมีเฉพาะชุดย่อยของ record ที่ไม่ซ้อนทับกัน และ shard สามารถย้ายไปมาระหว่าง node ได้ shard สามารถทำ replicate เพื่อ availability ที่สูงขึ้น และอื่น ๆ

~7:59 อังเดรย์: และสุดท้าย ระดับต่ำสุดของการแยกส่วนคือ segment โดย segment จะแยก index และที่เก็บข้อมูล ดังนั้นแต่ละ segment สามารถทำงานทุกอย่างได้เหมือนกับทั้ง collection ด้วยตัวเอง แต่ทำบนชุดย่อยเล็ก ๆ ของข้อมูลเท่านั้น และต่อไปผมจะอธิบายว่าทำไมเราจึงทำ segment และมันทำงานอย่างไร แต่ก่อนหน้านั้น ขอพูดเพิ่มอีกนิดเกี่ยวกับระดับบนสุด คุณอาจสังเกตว่าในระดับบนสุด สถาปัตยกรรมของ Qdrant ค่อนข้างเป็นมาตรฐาน เรามี collection ซึ่งประกอบด้วย shard โดย shard สามารถ replicate และย้ายไปมาระหว่าง node ได้ เราใช้โปรโตคอล Raft consensus เพื่อติดตาม metadata นี้ เช่น collection อยู่ที่ไหน สถานะของ node เป็นอย่างไร การตั้งค่าของ collection เป็นอย่างไร และอื่น ๆ ดังนั้น metadata ทั้งหมดนี้จึงถูกจัดเก็บแบบ distributed consensus

~9:01 อังเดรย์: และนี่ก็ค่อนข้างเป็นมาตรฐานสำหรับระบบแบบกระจายหลาย ๆ ระบบ และที่จริงนี่เป็นเพราะ Qdrant เป็นตัวอย่างที่เป็นแบบฉบับของระบบที่สร้างบนหลักการ BASE ซึ่ง BASE ในที่นี้ย่อมาจาก Basically Available, Soft state, Eventual consistency โดยทั่วไปมันมักถูกนำไปเปรียบเทียบกับหลักการ ACID ซึ่งพบได้บ่อยกว่าในฐานข้อมูลเชิงสัมพันธ์ ถ้าคุณอยากเข้าใจแบบเห็นภาพว่า BASE คืออะไรและ ACID คืออะไร คุณลองนึกถึง Postgres กับ Elasticsearch ได้ Postgres เป็นตัวอย่างที่เป็นแบบฉบับของฐานข้อมูลแบบ ACID มันมีการรับประกันด้าน transaction ที่เข้มงวดมาก ให้ความสำคัญกับ consistency ของข้อมูลมาก แต่ scalability ของ Postgres จริง ๆ แล้วมีจำกัดมาก โดยพื้นฐานแล้วก็ได้แค่ขนาดของเครื่องเดียว ในทางกลับกัน Elasticsearch เป็นตัวอย่างที่เป็นแบบฉบับของระบบแบบ BASE มัน scale ได้สูง แต่การรับประกันด้าน consistency อ่อนกว่ามาก

~10:08 อังเดรย์: และนั่นเองคือเหตุผลที่ผมชอบใช้คำว่า vector search engine มากกว่า vector database และสำหรับระบบอย่าง Qdrant ในความเห็นของผม scalability และประสิทธิภาพสำคัญกว่า consistency เชิงธุรกรรม (transactional consistency) มาก ดังนั้นจึงควรมองมันเป็น search engine มากกว่าเป็นฐานข้อมูล ในอุดมคติผมคิดว่ามันไม่ควรถูกใช้เป็นที่เก็บข้อมูลหลัก (primary storage) ด้วยซ้ำ โดยเฉพาะเมื่อพิจารณาว่าการอัปเดต vector ทั้งหมด เช่น เนื่องจากมีโมเดลเวอร์ชันใหม่ เป็นเพียงการดำเนินการปกติทั่วไปในโลกของ vector database คุณต้องเขียนฐานข้อมูลใหม่ทั้งหมดและสร้างขึ้นมาใหม่ เพียงเพราะ encoder ของคุณเปลี่ยนไป ใช่ไหมครับ และนี่เป็นสิ่งที่ไม่เคยเกิดขึ้นในฐานข้อมูลแบบดั้งเดิม

~11:01 อังเดรย์: สิ่งที่เกิดขึ้นภายใน shard นั้นน่าสนใจกว่าสักหน่อยสำหรับการบรรยายครั้งนี้ เพราะมันมีลักษณะเฉพาะที่เกี่ยวข้องกับ vector search จริง ๆ ในระดับบนสุด เราเห็นองค์ประกอบที่ค่อนข้างเป็นมาตรฐาน คือ write-ahead log (WAL) ซึ่งรับผิดชอบให้ Qdrant โดยปกติแล้วไม่ทำข้อมูลสูญหายเมื่อข้อมูลถูก commit แล้ว ย้ำอีกครั้งว่ามันเป็นองค์ประกอบที่ค่อนข้างมาตรฐานสำหรับฐานข้อมูลทุกตัว สิ่งที่ไม่มาตรฐานคือการแบ่งแยกข้อมูลระดับที่สองภายใน shard และระดับที่สองนี้ก็คือ segment แล้วทำไมเราถึงต้องมีหลาย segment ตั้งแต่แรก ทำไมเราไม่ใส่ข้อมูลทั้งหมดลงใน segment เดียวแล้วก็จบ

~11:44 อังเดรย์: ซึ่งจริง ๆ แล้วมีเหตุผลสำหรับเรื่องนี้ เหตุผลแรกคือความสามารถในการเปลี่ยนแปลง (mutability) ใน Qdrant เราชอบโครงสร้างข้อมูลที่เปลี่ยนแปลงไม่ได้ (immutable) มาก แต่สมมติฐานง่าย ๆ ที่ว่าโครงสร้างถูกสร้างเพียงครั้งเดียวและไม่ถูกขยายอีกเลยนั้น เปิดช่องให้ทำ optimization ได้หลายรูปแบบ โครงสร้างข้อมูลสามารถกะทัดรัดขึ้นได้ เราไม่ต้องกระโดดไปมาระหว่างตำแหน่งต่าง ๆ ในหน่วยความจำ จึงเกิด cache miss น้อยลง สถิติของข้อมูลทั้งหมดเป็นที่รู้ล่วงหน้า ดังนั้นจากข้อมูลนั้นเราก็สามารถทำ optimization ต่าง ๆ ได้เช่นกัน ตัวอย่างเช่น เราสามารถคำนวณ histogram ไว้ล่วงหน้า เราสามารถคำนวณการกระจายตัวของข้อมูลไว้ล่วงหน้า และอื่น ๆ แน่นอนว่าในกรณีนี้เรายังสามารถจองหน่วยความจำในปริมาณที่พอดีกับที่เราต้องการได้ เราจึงไม่ต้องกังวลเรื่อง memory fragmentation ด้วย

~12:41 อังเดรย์: การโหลดโครงสร้างข้อมูลแบบ immutable ก็เร็วกว่ามากเช่นกัน เพราะคุณไม่ต้องทำ deserialization ใด ๆ คุณแค่คัดลอกก้อนหน่วยความจำดิบ (raw chunk) จากดิสก์แล้วก็จบ หรือคุณจะทำ memory mapping ก็ได้ ซึ่งเร็วกว่าอีก นอกจากนั้น เรายังสามารถบีบอัดข้อมูลเพิ่มเติมโดยใช้เทคนิคต่าง ๆ เช่น delta encoding, variable byte encoding และอื่น ๆ และผลรวมทั้งหมดของ optimization เหล่านี้สามารถทำให้โครงสร้างข้อมูลแบบ immutable มีประสิทธิภาพมากกว่าแบบ mutable ในระดับ order of magnitude

~13:20 อังเดรย์: เหตุผลที่สองคือ trade-off ระหว่าง latency กับ throughput และเหตุผลของเรื่องนี้คือ การทำงานพร้อมกัน (concurrency) ของ request เดียวนั้นมีประสิทธิภาพได้แค่ถึงจุดหนึ่งเท่านั้น และยิ่งเราเข้าใกล้ index ระดับล่างมากเท่าไร concurrency ก็ยิ่งมีประสิทธิภาพน้อยลงเท่านั้น สิ่งนี้จึงทำให้ segment เป็นหน่วยตามธรรมชาติของการทำงานแบบขนาน (parallelization) ใน Qdrant ตัวอย่างเช่น ถ้าเรากำลังจัดการกับแอปพลิเคชันที่ต้องการ latency ต่ำมากสำหรับ request เดี่ยว เราสามารถ optimize การใช้งาน CPU (CPU utilization) ได้โดยแค่กำหนดให้ CPU core แต่ละ core ดูแล segment หนึ่ง segment ด้วยวิธีนี้มันจะใช้ CPU ให้ได้มากที่สุดเท่าที่จะเป็นไปได้ในเพียง request เดียว ในทางกลับกัน ถ้าเรามีแอปพลิเคชันที่ต้องรับมือกับ throughput สูง และต้องทำ request แบบขนานจำนวนมาก เราสามารถมี segment ขนาดใหญ่เพียง segment เดียว และในกรณีนี้มันจะทำให้ throughput ของทั้งระบบสูงสุด โดยแค่ให้บริการแต่ละ request บน core เฉพาะของมัน โดยใช้ทั้ง segment ในโหมดอ่าน

~14:36 แอนดี (ผู้ดำเนินรายการ): เรามีคำถามจากโรฮัน ถามว่าขนาดของ segment ใน [ฟังไม่ชัด] instance เป็นเท่าไร ค่าเริ่มต้นของพวกคุณคือเท่าไร

~14:53 อังเดรย์: ค่าเริ่มต้นคือศูนย์ ใช่ไหมครับ ถ้าคุณไม่มีข้อมูลเลยมันก็เป็นศูนย์ ถ้าคุณใส่ข้อมูลเข้าไป มันก็จะโตขึ้นไปจนถึงขนาดที่... คือ สิ่งที่เราชอบกำหนดค่า (configure) ไม่ใช่ขนาดของ segment แต่เป็นจำนวน segment ที่เราต้องการมี

~15:12 โรฮัน: [ฟังไม่ชัด] โอเค

~15:15 อังเดรย์: และคุณสามารถทำให้มันใหญ่เท่าไรก็ได้ตามที่ต้องการ ถ้าคุณมีทรัพยากรเพียงพอสำหรับเรื่องนี้

~15:19 โรฮัน: ถ้าอย่างนั้น ตามตรรกะนี้ สมมติว่าคุณมี segment จำนวน n segment สิ่งที่คุณกำลังจะบอกคือ ในกรณีสูงสุด storage ทั้งหมดอาจถูกใช้โดย segment เพียง segment เดียว อันนั้นเกิดขึ้นได้ไหมครับ

~15:34 อังเดรย์: เป็นไปได้ครับ ใช่ ถ้าคุณต้องการ ถ้าแอปพลิเคชันของคุณเน้นการอ่านมาก (read heavy) ถ้าคุณมี write request ในปริมาณต่ำมาก และคุณต้องการเพิ่ม throughput ให้สูงสุด ใช่ครับ เป็นไปได้ที่จะรวมข้อมูลทั้งหมดไว้ใน segment เดียวแล้วทำงานกับมัน

~16:03 โรฮัน: โอเค ขอบคุณครับ

~16:05 แอนดี (ผู้ดำเนินรายการ): มีใครอีกไหมครับ คำถามถัดไป: มีข้อได้เปรียบอะไรไหมในการมี segment หลายขนาดภายใน shard หรือ collection เดียวกัน

~16:12 อังเดรย์: ครับ คือไม่มีข้อได้เปรียบในเรื่องนี้ เพราะเราต้องการให้มีการกระจายที่สม่ำเสมอ แต่ในทางปฏิบัติมันอาจเกิดขึ้นได้ เพราะ segment ถูกรวมกัน ในระหว่างการแทรกข้อมูล segment สามารถถูกรวมเข้าด้วยกันได้ และคุณจำเป็นต้องมี segment อย่างน้อยหนึ่ง segment ที่ไม่ใช่ immutable อยู่เสมอ ซึ่งเราสามารถใส่ข้อมูลใหม่ลงไปได้ ดังนั้นในทางปฏิบัติก็ไม่ใช่ว่าจะไม่เกิดขึ้น แต่เราต้องการให้มันมีขนาดสม่ำเสมอที่สุดเท่าที่จะเป็นไปได้

6. การจัดการ segment: copy-on-write และ proxy segment

~17:05–20:30

~17:05 อังเดรย์: ได้ครับ แต่ก็มีอีกหนึ่งสไลด์เกี่ยวกับการจัดการ segment นะครับ ประเด็นก็คือ เรามี segment จำนวนมากภายใน shard บางส่วนเป็น immutable ส่วนอื่น ๆ ใช้เพื่อแทรกข้อมูลใหม่ แต่เราจะรักษาภาพลวงตาให้ผู้ใช้เห็นว่า collection ทั้งหมดเปลี่ยนแปลงได้อย่างสมบูรณ์ได้อย่างไร และใน Qdrant ผู้ใช้สามารถแทรก ลบ อัปเดตข้อมูลใด ๆ ได้ทุกเมื่อ ดังนั้นในอุดมคติ ผู้ใช้ไม่ควรรู้ด้วยซ้ำว่ามี segment เหล่านี้อยู่ มันเป็นเรื่องภายในล้วน ๆ และเพื่อแก้ปัญหานี้ เราต้องแก้ปัญหาสองข้อ ข้อแรกคือจะอัปเดตข้อมูลในโครงสร้างข้อมูลแบบ immutable ได้อย่างไร และข้อที่สองคือจะได้มาซึ่งโครงสร้างข้อมูลแบบ immutable ตั้งแต่แรกได้อย่างไร

~18:01 อังเดรย์: ปัญหาแรกแก้ได้โดยใช้กลไก copy-on-write ง่าย ๆ คือทุกครั้งที่ผู้ใช้แทรกข้อมูลใหม่เข้าไป หรือเปลี่ยนแปลงข้อมูลใน segment ที่เป็น immutable เราก็แค่คัดลอกข้อมูลชิ้นนั้นไปยัง segment ที่เป็น mutable ทำเครื่องหมายว่าถูกลบแล้วใน segment เดิม แล้วทุกอย่างก็ทำงานได้ ปัญหาที่สองซับซ้อนกว่าเล็กน้อย เพราะเราต้องทำ optimization ที่ใช้เวลานานบน segment การสร้าง index ใช้เวลาค่อนข้างนาน นั่นคือเหตุผลที่เราต้องทำให้ segment ยังพร้อมใช้งานสำหรับการอ่านและการอัปเดตของผู้ใช้ ในขณะเดียวกันเราก็ต้องสร้าง index จากมัน

~18:44 อังเดรย์: และเพื่อทำเช่นนั้น เราใช้สิ่งที่เรียกว่า proxy segment ซึ่งเป็น segment ชนิดพิเศษที่ห่อหุ้ม segment ที่กำลังถูก optimize อยู่ไว้ภายใต้ interface เดียว และมันยังเก็บรายการการแก้ไขที่ต้องนำไปใช้เพื่อแก้ความขัดแย้ง ซึ่งเกิดขึ้นเมื่อคุณคัดลอกข้อมูลจาก segment เดิมไปยัง segment ใหม่ มีโครงสร้างข้อมูลพิเศษที่จัดการการแทรกทั้งหมดนี้ และเมื่อ optimization เสร็จสิ้น มันก็แค่แปลงกลับเป็น segment ปกติ หรือจริง ๆ แล้วเป็น segment คู่หนึ่ง คือ segment ที่ถูก optimize แล้ว และ segment copy-on-write ขนาดเล็ก ซึ่งกลายเป็น segment ที่ mutable

~19:32 อังเดรย์: ภายใน segment มีองค์ประกอบเชิงนามธรรมอยู่จำนวนหนึ่ง ผมตั้งใจจะไม่อธิบายว่าแต่ละตัวทำงานอย่างไรอย่างละเอียดในระดับล่าง แต่ผมจะเน้นที่ vector index เป็นหลัก และเหตุผลก็คือ การเลือก implementation ที่เป็นรูปธรรมนั้นขึ้นอยู่กับการกำหนดค่าเท่านั้น ตัวอย่างเช่น vector storage เรามี implementation ของ vector storage ใน Qdrant อย่างน้อยสามแบบ

~20:01 อังเดรย์: และค่อนข้างเป็นไปได้ว่าในอนาคตอันใกล้เราจะเพิ่มแบบที่สี่เข้าไป และมันก็ไม่ได้สำคัญจริง ๆ Qdrant สามารถทำงานกับ abstraction แบบไหนก็ได้ อาจเป็นแค่ไฟล์ อาจเป็น memory storage และอื่น ๆ มันไม่ได้สำคัญจริง ๆ แต่สิ่งที่สำคัญคือ vector index และในที่สุดเรามาพูดถึงองค์ประกอบหลักของ vector search กัน

7. vector index และ HNSW

~20:31–23:40

~20:31 อังเดรย์: vector index มีคุณลักษณะหลักสองประการที่ทำให้ vector search แตกต่างจาก index แบบดั้งเดิมอย่าง inverted index หรือ B-tree หรืออะไรทำนองนี้ ประการแรกคือธรรมชาติที่เป็นการประมาณ (approximate) ของมัน ซึ่งหมายความว่ามันไม่ได้รับประกันว่าผลลัพธ์จะแม่นยำตรงทุกประการ หรือแม้แต่ว่าผลลัพธ์จะเหมือนเดิมสำหรับข้อมูลพื้นฐานชุดเดียวกัน หากคุณสร้าง index หลายครั้ง เพราะผลลัพธ์จริง ๆ แล้วขึ้นอยู่กับลำดับที่คุณใส่ข้อมูลเข้าไปใน index ดังนั้นนี่จึงเป็นเรื่องที่ค่อนข้างเป็นพื้นฐาน และประการที่สองคือ vector ใด ๆ ก็สามารถเป็นผลลัพธ์ของคำขอค้นหาใด ๆ ได้ หรือพูดอีกอย่างคือ เอกสารใด ๆ ใน collection ของคุณก็คล้ายกับเอกสารอื่นใดใน collection ของคุณอยู่บ้างไม่มากก็น้อย ดังนั้นจึงเป็นไปไม่ได้ที่จะขีดเส้นแบ่งที่ชัดเจนระหว่างเอกสารที่เกี่ยวข้องกับเอกสารที่ไม่เกี่ยวข้อง โดยอาศัยเพียงคะแนนความคล้ายคลึงของ vector (vector similarity score) เท่านั้น

~21:41 อังเดรย์: และแน่นอนว่ามีแนวทางที่แตกต่างกันมากมายในการ implement vector index แต่ไม่ว่าคุณจะเลือกแนวทางไหน ทุกแนวทางก็จะต้องรับมือกับคุณสมบัติเหล่านี้ที่ผมเพิ่งอธิบายไป และที่จริงมันทำลายสมมติฐานหลายอย่างที่คุณตั้งไว้ในฐานข้อมูลแบบดั้งเดิม ดังนั้นผมจึงเชื่อว่ามันต้องการการดูแลเป็นพิเศษจริง ๆ และต้องการสถาปัตยกรรมเฉพาะที่สร้างขึ้นรอบ ๆ มัน

~22:10 อังเดรย์: [ฟังไม่ชัด] เราใช้สิ่งที่เรียกว่า HNSW index ที่นี่ HNSW ย่อมาจาก hierarchical navigable small world ใช่ครับ มันเป็นชื่อที่ค่อนข้างซับซ้อน แต่ผมจะพยายามอธิบายในเวอร์ชันที่ง่ายมาก ๆ เพียงเพื่อให้พอเห็นภาพ (intuition) ว่ามันทำงานอย่างไร

~22:35 อังเดรย์: ภายใน HNSW มีลักษณะเป็น proximity graph ซึ่งหมายความว่าแต่ละ vector ถูกแทนด้วย node ใน graph และ node เหล่านั้นเชื่อมต่อกับเพื่อนบ้านที่ใกล้ที่สุดจำนวนหนึ่ง ก็คือ vector อื่น ๆ จำนวนหนึ่งในฐานข้อมูล และการค้นหาใน proximity graph ทำในลักษณะ greedy หมายความว่าในแต่ละขั้นเราจะเลือก node ที่ใกล้กับเป้าหมาย (target) ที่สุด แล้วทำขั้นตอนการค้นหาซ้ำกับ node ที่ถูกเลือกใหม่นี้ กระบวนการนี้ทำซ้ำไปเรื่อย ๆ จนกว่าเราจะไม่สามารถทำให้ระยะห่างระหว่าง node กับเป้าหมายดีขึ้นได้อีก และแน่นอนว่าไม่มีการรับประกันว่าการค้นหานี้จะได้ผลลัพธ์ที่ใกล้ที่สุดอย่างแท้จริง นั่นคือเหตุผลที่มันถูกเรียกว่า approximate แต่เราสามารถควบคุม precision ได้ และเราสามารถแลก (trade off) ระหว่าง precision กับความเร็วของการค้นหาได้ โดยการเปลี่ยนพารามิเตอร์ beam size ของการค้นหา

8. ความท้าทายของ HNSW, binary quantization และ rescoring

~23:41–29:02

~23:41 อังเดรย์: ใช่ครับ แต่แน่นอนว่า HNSW index ก็มีความท้าทายในตัวของมันเอง อย่างแรกคือเวลาในการสร้าง การแทรก vector ใหม่เข้าไปใน index มีต้นทุนสูงกว่าการค้นหาใน index เพียงอย่างเดียวประมาณสองเท่า และมันยังใช้ CPU หนักมากด้วย ดังนั้นถ้าเราต้องการทำ index โดยไม่ให้กระทบกับกระบวนการอื่น ๆ ของเรา เช่น ถ้าเราทำ index และค้นหาไปพร้อม ๆ กัน ก็จำเป็นต้องมี thread pool เฉพาะสำหรับการสร้าง index ในเบื้องหลัง หรือในอุดมคติ เราอาจถึงขั้นต้องการย้ายกระบวนการสร้าง index นี้ไปไว้บนอีกเครื่องหนึ่งโดยสิ้นเชิง

~24:31 อังเดรย์: index ไม่ได้ใช้ CPU หนักเพียงอย่างเดียว แต่ยังมีรูปแบบการเข้าถึงข้อมูลแบบสุ่ม (random data access pattern) ซึ่งหมายความว่ามันอ่อนไหวมากต่อ latency ของ storage ที่อยู่ข้างใต้ และเทคนิคอย่าง prefetching หรือ block reading ก็ไม่ได้มีประสิทธิภาพจริง ๆ สำหรับ HNSW นั่นคือเหตุผลที่โดยปกติแล้วมันต้องการ RAM จำนวนมาก และไม่ได้ทำงานได้ดีจริง ๆ กับดิสก์ และยิ่งไปกว่านั้น รูปแบบนี้ไม่ได้เป็นแบบสุ่มเท่านั้น แต่ยังเป็นแบบลำดับต่อเนื่อง (sequential) ด้วย จำไว้ว่าเราเดินจาก node หนึ่งใน graph ไปยังอีก node หนึ่ง ซึ่งหมายความว่าเราไม่สามารถทำ parallelization ของการค้นหาได้อย่างมีประสิทธิภาพ และประสิทธิภาพของมันส่วนใหญ่ถูกจำกัดด้วย latency ของ storage มากกว่า throughput

~25:25 อังเดรย์: เพื่อเอาชนะความท้าทายเหล่านี้ ใน Qdrant เราทำสิ่งต่อไปนี้ ทางออกคือการใช้การแทน vector แบบบีบอัดใน memory (compressed in-memory representation) และใช้มันเพื่อสร้างชุดของ candidate ที่ถูกคัดเลือก ตัวอย่างเช่น หนึ่งในสิ่งที่เพิ่มเข้ามาล่าสุดใน engine ของ Qdrant คือ binary quantization ซึ่งช่วยให้เราบีบอัด vector ได้ถึงระดับที่หนึ่งมิติถูกแทนด้วยเพียงบิตเดียว ซึ่งให้การบีบอัด vector รวมทั้งหมด 32 เท่า และนอกจากนั้น มันยังช่วยให้เราใช้การคำนวณบน CPU ที่เร็วมาก คือโดยพื้นฐานแล้วมันช่วยให้เราเปรียบเทียบ vector ได้ด้วยคำสั่ง CPU เพียงสองคำสั่ง คือ bitwise XOR และ popcount และมันทำงานได้มีประสิทธิภาพเป็นพิเศษกับ vector ขนาดใหญ่ อย่างเช่น vector ที่ได้จากโมเดลของ OpenAI ซึ่งเรามี 1,500 มิติสำหรับ vector เดียว

~26:31 อังเดรย์: ใช่ครับ หลังจากได้รายการ candidate นี้มาแล้ว เราสามารถ rescore พวกมันโดยใช้ vector ต้นฉบับ และส่งผลลัพธ์สุดท้ายกลับไปให้ผู้ใช้ และเป็นเรื่องสำคัญที่ต้องรู้ว่ากระบวนการ rescoring นี้ ต่างจากการ traverse graph ของ HNSW ตรงที่มันสามารถทำแบบขนาน (parallelize) ได้อย่างมีประสิทธิภาพจริง ๆ เพราะเรารู้ offset หรือ ID ของ candidate ทั้งหมดอยู่แล้ว ดังนั้นเราจึงสามารถใช้ประโยชน์จาก asynchronous I/O ได้ที่นี่ และใช้ประโยชน์ได้แม้กระทั่งจากดิสก์ที่ mount ผ่านเครือข่ายซึ่งช้าและมี latency สูงมาก

~27:06 แอนดี (ผู้ดำเนินรายการ): คุณบอกว่า rescoring นี่คือคุณเอา vector ที่ถูก quantize แล้ว จากนั้นคุณก็ทำอะไรนะ เทียบมันกับ vector ต้นฉบับอีกครั้งใช่ไหม

~27:15 อังเดรย์: คือเราทำการค้นหา เหมือนการค้นหาปกติโดยใช้ HNSW กับการแทนแบบ quantize ดังนั้นมันจึงเร็วมาก ประหยัด memory มาก และหลังจากที่เราได้ สมมติว่า ผลลัพธ์ top 100 มาแล้ว เราก็ทำ rescoring โดยใช้การแทนแบบต้นฉบับ เราจำเป็นต้องดึง vector 100 ตัวนั้นจากดิสก์ แต่ขณะที่เราทำแบบนี้ เรารู้ offset ทั้งหมดอยู่แล้ว ดังนั้นเราก็แค่ส่งคำขอแบบขนานไปยังดิสก์ด้วย asynchronous IO อะไรทำนองนี้ และก็ได้ vector ต้นฉบับทั้งหมดมาค่อนข้างเร็ว

~28:13 อังเดรย์: ใช่ครับ อันนี้ต่างกันเล็กน้อย ผมไม่คิดว่า DiskANN ทำ quantization ใด ๆ มี implementation อื่นที่ทำ ดังนั้นผมไม่คิดว่าแนวทางนี้จะเป็นอะไรที่ค่อนข้างปฏิวัติวงการ แต่ใช่ครับ มันถูกบรรจุมาให้พร้อมใช้ (out of the box) ซึ่งคุณสามารถใช้มันได้โดยไม่ต้องตั้งค่าเพิ่มเติมใด ๆ คุณไม่จำเป็นต้อง quantize ข้อมูลหรือ vector ของคุณล่วงหน้า คุณแค่อัปโหลดทุกอย่างเข้าไปใน Qdrant และมันก็ทำงานได้ทันที ดังนั้น Qdrant ดูแลเรื่อง quantization นี้เอง มันดูแลเรื่อง rescoring และใช่ครับ คุณก็ได้ผลลัพธ์

9. ค้นหาพร้อม filter: post-filtering, pre-filtering และ in-place filtering

~29:03 อังเดรย์: ครับ ได้เลย ความท้าทายอีกอย่างหนึ่งที่เกี่ยวข้องกับ HNSW คือความจำเป็นที่จะต้องรวม vector search เข้ากับเงื่อนไข filtering เพิ่มเติม ตัวอย่างเช่น คุณอาจต้องการค้นหาสินค้าบางประเภทในร้านค้า e-commerce และราคาของสินค้านี้ควรจะน้อยกว่าหนึ่งร้อยดอลลาร์ และเราต้องการค้นหาในสถานที่เฉพาะเจาะจง เช่น ใกล้ตัวคุณ หาอะไรสักอย่างใกล้ฉัน อะไรทำนองนี้ เงื่อนไขเพิ่มเติมเหล่านี้จำเป็นจริง ๆ สำหรับแอปพลิเคชันในโลกจริง แต่การ implement HNSW แบบพื้นฐาน (naive) หรืออัลกอริทึม ANN อื่นใด ก็ไม่มีสิ่งนี้เลย และในบางงานตีพิมพ์ คุณอาจพบว่ามีสองวิธีในการแก้ปัญหานี้

~30:50 อังเดรย์: อีกแนวทางหนึ่งคือกลับกัน มันเสนอ — ผมหมายถึง pre-filtering — มันเสนอให้สร้างรายการ candidate ขึ้นมา แล้วจากรายการ candidate นี้ เราจึงทำ vector search และปัญหาของมันคือ การสร้างรายการ candidate โดยตัวมันเองอาจเป็นการดำเนินการที่มีต้นทุนสูงมาก ในกรณีที่แย่ที่สุด มันอาจต้องตรวจสอบเงื่อนไขกับ vector ถึงครึ่งหนึ่งใน collection และนั่นอาจเพิ่ม latency ของการค้นหาอย่างมาก และอื่นๆ อีก ดังนั้นสิ่งที่เราเสนอคือแนวทางที่ใช้ใน Qdrant ซึ่งเราเรียกว่า in-place filtering หมายความว่าเงื่อนไข filtering จะถูกตรวจสอบระหว่างการท่อง graph ซึ่งทำให้เราต้องทำ implementation แบบกำหนดเอง ต้องปรับแต่ง HNSW เอง ดังนั้นเราจึงไม่ได้ใช้ implementation แบบ vanilla อีกต่อไป เราใช้ implementation แบบกำหนดเองใน Qdrant แต่ด้วยวิธีนี้ เราสามารถรับประกันได้ว่าเราต้องตรวจสอบเงื่อนไข filtering เพียงเท่าจำนวนครั้งที่จำเป็นจริงๆ ในการทำการค้นหาเท่านั้น

~32:06–39:46

Key Takeaways

  1. Qdrant ควรถูกมองเป็น search engine แบบ BASE ไม่ใช่ database แบบ ACID และผู้บรรยายมองว่าในอุดมคติไม่ควรใช้เป็นที่เก็บข้อมูลหลัก
  2. segment ที่ immutable เปิดทางให้ optimize ได้มาก ส่วน copy-on-write และ proxy segment ทำให้ผู้ใช้เห็นว่าแก้ไขได้ตลอด
  3. HNSW แพงตอนสร้างและต้องการ RAM เพราะเข้าถึงแบบสุ่มและเป็นลำดับ ทางแก้คือค้นด้วยเวกเตอร์ที่บีบอัดไว้ใน RAM (เช่น binary quantization บีบอัด 32 เท่า) แล้ว rescore ด้วยเวกเตอร์ต้นฉบับ
  4. filter ระหว่างเดินกราฟ (in-place) ดีกว่า post/pre-filtering แต่ filter เข้มทำให้กราฟขาดตาม percolation theory จึงต้องสร้างลิงก์เพิ่มตาม payload
  5. โจทย์ที่ยังไม่แก้คือราคา ทำให้การให้บริการเวกเตอร์พันล้านตัวมีราคาถูก
