บทสรุปย่อ

งานนี้เสนอ RGDC (Reference-Grounded Data Curation) วิธีสร้างข้อมูลฝึกสองเฟสสำหรับงานแปลที่ต้องทำตามกฎในคำสั่ง (instruction-following MT) เช่น ศัพท์บังคับ รูปแบบ ระดับภาษา ความยาว แนวคิดหลักคือดึง "กฎ" ออกมาจากคำแปลอ้างอิงที่ทำตามกฎนั้นอยู่แล้ว กฎทุกข้อจึงเป็นไปได้แน่นอนตั้งแต่ต้น ได้ชุดข้อมูล Grounded 1.97 ล้านระเบียน แล้วใช้ fine-tune ได้โมเดลแปลไทย-อังกฤษ ChindaMT ขนาด 4B, 2B, 0.8B (ฐาน Qwen3.5) และรุ่นทดสอบบน Qwen3-4B ผลหลักวัดด้วย length-controlled win rate (LC%) แบบให้ LLM ตัดสินเป็นคู่ ChindaMT ชนะหรือเสมอคู่แข่งขนาดเดียวกันทุกระดับ ทั้งแปลธรรมดาและแปลตามกฎ สูงสุด 68.4% เทียบคู่แข่งที่ยากที่สุด และมีการตรวจซ้ำด้วย metric ภายนอก judge อีกสองตระกูล และผู้ประเมินคนไทยสามคน

สรุปเชิงลึก

ปัญหา โมเดลที่เน้นแปลเก่งมักทำตามคำสั่งเสริมได้ไม่ดี ส่วนโมเดลที่ทำตามคำสั่งเก่งมักแปลไม่ถึง ผู้เขียนยกตัวอย่างฝั่งไทยว่า Typhoon ทำตามคำสั่งได้แต่คุณภาพแปลไม่เฉพาะทาง ขณะที่ Hunyuan-MT แปลดีแต่ไม่ได้รองรับกฎในคำสั่ง และบอกว่ายังไม่มีโมเดลไทย-อังกฤษแบบเปิดตัวไหนปิดช่องว่างนี้ได้ วิธีสร้างข้อมูล instruction-following ทั่วไป (AutoIF, UltraIF) สร้างกฎขึ้นจากคำสั่งก่อนแล้วกรองทิ้งส่วนที่ทำไม่ได้ ซึ่งไม่ได้คิดมาสำหรับงานแปล

วิธีการ เฟส 1 คัด "cherry" จากคลังคู่ขนาน 17.85 ล้านระเบียน (10 คลัง ทั้งสองทิศ) ด้วยคะแนน IFD = loss ของคำตอบเมื่อมีคำสั่ง หารด้วย loss เมื่อไม่มีคำสั่ง ทิ้งตัวที่ IFD ตั้งแต่ 1 ขึ้นไป แล้วเก็บ 10% ที่ IFD สูงสุด (ยากแต่ยังเรียนได้) ได้ 1,751,962 ระเบียน เฟส 2 ใช้ LLM ช่วย Qwen3.5-35B-A3B-FP8 ตัวเดียว ทำ 5 ขั้น: ดึงกฎจากคำแปลอ้างอิง (5 หมวด) → แปลงกฎเป็นคำถามใช่/ไม่ใช่ → แปลใหม่ภายใต้กฎ 2 แบบ (สุ่ม 1–3 ข้อ และครบทุกข้อ) → ให้ LLM ตัดสินทีละกฎ → เก็บเฉพาะที่ผ่านครบทุกข้อ ได้ 1,973,358 ระเบียน (รอด 56.5% ของผู้สมัคร 3,495,704) เฉลี่ย 3.7 กฎต่อระเบียน คำตอบที่ใช้ฝึกคือคำแปลที่ LLM สร้างใหม่ ไม่ใช่คำแปลอ้างอิงเดิม การตรวจด้วย CometKiwi บอกว่าคำแปลใหม่ได้คะแนนไม่ต่ำกว่าคำแปลอ้างอิงของคลังใน 85.9% ของ 20,000 ตัวอย่าง

การฝึก SFT เต็มพารามิเตอร์ 1 epoch, lr 2e-5, inverse-sqrt, batch จริง 64, cutoff 1024, packing, NEFTune α=2 ไม่มี preference optimization หรือ RL ใช้ H100 สองใบ ประมาณ 25 / 10 / 8 ชั่วโมงสำหรับ 4B / 2B / 0.8B

ผล บน CoreEval ChindaMT-4B ชนะ Typhoon-Translate-4B ที่ 61.8 (Plain) และ 68.4 (Constrained) ชนะ HY-MT-1.5-7B ใน Constrained ถึง 97.9 และ Plain (own template) ยังเกิน 50 กับทุกคู่ metric ภายนอกบน FLORES-200 ให้ 4B เสมออันดับหนึ่งที่ 90.7 แต่บน WMT24++ ตามหลัง HY-MT-1.5-7B (87.8 กับ 89.4) judge อีกสองตัวเห็นทิศทางตรงกันทุกคู่ใน Constrained และ Plain (shared) ผู้ประเมินคนไทยให้ ChindaMT-4B ชนะ Typhoon ที่ win rate 0.64 (Plain) / 0.69 (Constrained) (นับเสมอเป็นครึ่ง; κ ระหว่างผู้ประเมิน 0.73 แต่ κ คนกับ judge 0.41) ablation ชี้ว่าการฝึกด้วย Rules block ช่วยมากที่สุด (+12.63 / +9.53) การคัด IFD ช่วยเฉพาะ Plain ในโดเมน (+8.24) และตัวกรอง all-pass ช่วยเล็กน้อย (+1.09 / +1.06)

สิ่งที่ควรระวัง (ผู้จัดทำ) (1) judge หลักเป็นตระกูล Qwen เดียวกับโมเดล ผู้เขียนยอมรับเองและตรวจซ้ำแล้ว (2) "คำแปลที่ซื่อตรงทุกข้อ" ยังไม่ได้วัดตรง ๆ: ตรวจแค่ CometKiwi แบบไม่ใช้ reference ไม่มีคนตรวจข้อมูลฝึก (3) ChindaMT-0.8B อยู่ท้ายกลุ่มบน metric ภายนอกทั้งสองชุด ซึ่งบทความไม่ได้พูดถึงตรง ๆ (4) prompt ตอนประเมินไม่ตรงตัวกับแม่แบบตอนฝึกในโค้ด (5) ไม่มีการวัด metric ภายนอกของโมเดลฐาน คำว่า "ไม่เสียคุณภาพแปล" จึงเทียบกับคู่แข่งเท่านั้น ตารางตรวจข้อเท็จจริงมี 15 ข้อ: ยืนยัน 9, ยืนยันบางส่วน 6, ไม่พบหรือขัดแย้ง 0

ใช้ทำอะไรต่อ (ผู้จัดทำ) สูตร IFD, ขั้นตอน all-pass และชุดประเมิน (LC%, cross-judge, κ) เป็นตัวอย่างจริงที่สอนเรื่อง post-training และ LLM-as-judge ได้ดี ส่วนการเอาโมเดลมาใช้บนเว็บเป็นเรื่องที่เจ้าของต้องตัดสินใจแยก (ดูหัวข้อ 15)

1. ปัญหา: แปลเก่งกับทำตามกฎมักได้อย่างเสียอย่าง (§1–2)

ผู้เขียนเปิดว่า LLM แปลได้ใกล้ระบบ MT เฉพาะทางแล้ว และคำขอแปลจริงมักพ่วงกฎ เช่น ศัพท์ที่ต้องใช้ รูปแบบ ระดับภาษา ความยาว ปัญหาคือการ fine-tune ให้แปลเก่งทำให้ความสามารถทำตามคำสั่งจางลง ส่วนโมเดลทำตามคำสั่งทั่วไปก็แปลไม่ถึงขั้นเฉพาะทาง ฝั่งไทย Typhoon ทำตามคำสั่งได้แต่คุณภาพแปลไม่เฉพาะทาง และ Hunyuan-MT แปลดีแต่ไม่ได้จำลองกฎในคำสั่ง ผู้เขียนสรุปว่ายังไม่มีโมเดลแปลไทย-อังกฤษแบบ open-weight ที่ปิดช่องว่างนี้

งานที่เกี่ยวข้องสี่สาย (1) การคัดข้อมูลสำหรับ instruction tuning: LIMA แสดงว่าข้อมูลน้อยแต่ดีสู้ข้อมูลมากที่ไม่คัดได้ IFD คัดตัวอย่างที่คำสั่งช่วยลด loss แต่ไม่ถึงกับทำให้ง่ายเกิน วิธีใกล้เคียงคือ Deita, Humpback, SuperFiltering ผู้เขียนเลือก IFD เพราะวัดความยากด้วย loss ของโมเดลฐานที่จะฝึกจริง ไม่ต้องมี scorer อื่น (SuperFiltering ใช้โมเดลเล็กกว่าแทนเพื่อประหยัด, Deita วัดความซับซ้อนและคุณภาพซึ่งแยกตัวอย่างในคลังงานเดียวแบบนี้ได้น้อย) (2) การเสริมข้อมูล instruction-following: Self-instruct และ WizardLM ขยายคำสั่งจากชุด seed ส่วน AutoIF และ UltraIF สร้างกฎที่ตรวจได้จาก prompt แล้วกรองแบบ rejection sampling RGDC กลับด้าน คือดึงกฎจากคำแปลที่มีอยู่ ตัวกรองขั้น 2E จึงเป็นแค่ "สุขอนามัยของข้อมูล" ไม่ใช่ตัวบังคับว่าทำได้ (3) MT ด้วย LLM: Typhoon, SeaLLMs, Hunyuan-MT; BLEU, chrF, COMET วัดคุณภาพแต่ไม่วัดการทำตามกฎ (4) LLM-as-judge: สอดคล้องกับคนดีแต่มี length bias และ position bias; AlpacaEval v2 แก้ length bias ด้วย GLM ผู้เขียนใช้ judge แบบเปิดขนาด 35B และตรวจซ้ำด้วย judge อีกสองตระกูลกับคน

ผู้เขียนชี้ว่ารูปแบบ "เก่งแปลแล้วเสียการทำตามคำสั่ง" ปรากฏในคู่แข่งด้วย MM-46-4B, TranslateGemma-4B และ GemmaX2 เท่ากับ ChindaMT ในการแปลธรรมดา แต่แพ้ทุกคู่ Constrained ภายใต้ judge ทั้งสาม ส่วน Typhoon-Translate-4B อยู่อีกมุม คือแปลธรรมดาอ่อนกว่าแต่ช่องว่างใน Constrained เล็กกว่า RGDC เลี่ยงทั้งสองแบบเพราะการสอนกฎและการสอนแปลมาจาก "แหล่งความจริงเดียว" คือคำแปลอ้างอิงที่ผ่านการคัด หลักฐานคือ ablation ที่ตัด Rules แล้ว Plain ลดมากกว่า Constrained และการที่ Plain เท่ากับผู้เชี่ยวชาญที่แข็งที่สุดในขนาดเดียวกัน บน metric ภายนอก ChindaMT "เท่า" ไม่ใช่ "ครอง" จุดเดียวที่ผู้เชี่ยวชาญยังนำคือข่าวในโดเมน (HY-MT 7B ที่ WMT24++ th→en) จุดที่ ChindaMT นำคือการทำตามกฎและความทนทานข้ามโดเมนที่ขนาดเท่ากัน

13. ข้อจำกัด จริยธรรม และ license (§7–9)

บทสรุปของผู้เขียน ChindaMT ชนะหรือเสมอผู้เชี่ยวชาญการแปลขนาดเดียวกันทุกระดับบน CoreEval และ BroadEval "โดยไม่เสียคุณภาพแปลดิบ" บน FLORES-200 หรือ WMT24++ judge ข้ามตระกูลและคนไทยยืนยัน สูตรใช้ได้กับสี่ฐานและ Qwen สองรุ่น ปล่อย weights ชุดข้อมูล ชุดประเมิน และโค้ดภายใต้ license เปิด

ข้อจำกัดที่ผู้เขียนเขียนเอง (1) กฎถูกจำกัดด้วยคำแปลอ้างอิง กฎที่ไม่มีคำแปลไหนแสดง หรือที่ตรวจแบบใช่/ไม่ใช่ไม่ได้ อยู่นอกขอบเขต ครอบคลุมศัพท์ ความยาว ระดับภาษา รูปแบบผลลัพธ์ แต่ glossary บังคับและ placeholder token อยู่นอกขอบเขตโดยการออกแบบ การขยายด้วยทรัพยากรของโดเมนหรือการสร้างกฎสังเคราะห์เป็นงานอนาคต (2) judge หลักตัวเดียว ค่า LC และ GEMBA ทั้งหมดพึ่ง Qwen3.6-35B ค่าสัมบูรณ์จึงอาจสะท้อนการตั้งค่าของ judge นั้น บรรเทาด้วย metric ภายนอก การคุมความยาวและตำแหน่ง judge สามตระกูล และคน (3) ครอบคลุมแค่อังกฤษ-ไทยสองทิศ การขยายไปคู่ภาษาทรัพยากรน้อยอื่น โดยเฉพาะภาษาในเอเชียตะวันออกเฉียงใต้ และระดับภาษาที่กว้างขึ้นเป็นงานอนาคต (4) รูปแบบ prompt ไม่สมมาตร รูปแบบฝึกของ Grounded ตรงกับแม่แบบ Typhoon-Translate แต่ต่างจาก HY-MT และ GemmaX2 ใน Plain จึงประเมินทั้งแม่แบบกลางและของตัวเอง ส่วน Constrained ใช้แม่แบบกลางเท่านั้น (5) ฐานเป็น Qwen ทั้งหมด ยังไม่ได้ทดลองคัดใหม่ด้วยฐานเป้าหมายและสถาปัตยกรรมอื่น

จริยธรรมและ license ใช้คลังสาธารณะ 10 คลัง หลายคลังมีเงื่อนไข ShareAlike จึงปล่อย Grounded และชุดประเมินเป็น CC-BY-SA 4.0 ชุดประเมินมีต้นฉบับและผลของโมเดลแต่ ไม่มีคำแปลอ้างอิง และไม่มีข้อมูลระบุตัวบุคคล หนึ่งรายการใน BroadEval คงเงื่อนไข CC-BY-NC-4.0 ของต้นทาง ผู้ประเมินสามคนเป็นอาสาสมัครไม่รับค่าตอบแทน ให้ความยินยอม บันทึกเฉพาะความชอบ ไม่ต้องผ่านคณะกรรมการจริยธรรมของสถาบัน ผลแปลอาจลื่นไหลแต่ผิดหรือมีอคติจากข้อมูล ควรมีคนตรวจในงานสำคัญ weights และโค้ดเป็น Apache-2.0 (weights สืบ license ของฐาน Qwen) ผู้เขียนระบุว่าใช้ผู้ช่วย AI ช่วยขัดภาษา ร่าง และ LaTeX/โค้ด และตรวจเนื้อหาเองทั้งหมด

15. ข้อคิดสำหรับ ZVect (ผู้จัดทำ)

หัวข้อนี้เป็นของผู้จัดทำทั้งหมด เชื่อมบทความเข้ากับแผนของ ZVect

Token ภาษาไทย (gap G12) ChindaMT ใช้ tokenizer ของ Qwen3.5 ตามที่เห็นใน config ในเครื่อง: vocab 248,320 (ตรงกับสเปกสาธารณะของ Qwen3.5-0.8B) ตาราง embedding จึงมีขนาด 248,320 × 1,024 ≈ 254 ล้านพารามิเตอร์ (0.8B) และ × 2,560 ≈ 636 ล้าน (4B) ผูกกับชั้น output เป็นตัวอย่างจริงของ "ตาราง embedding = จำนวน vocab × มิติ" ในบทเรียนเรื่อง embedding บทความเองไม่ได้วัดว่าภาษาไทยใช้กี่โทเค็นต่ออักษร ตัวเลขนี้ยังต้องวัดเองจาก tokenizer.json ในเครื่อง

Post-training และการคัดข้อมูล (gap G2) บทความเป็นตัวอย่าง SFT ที่ครบและเปิด: รูปแบบ Alpaca, คิด loss เฉพาะคำตอบ, packing, cutoff 1024, ไม่มี RL/DPO แต่ชนะฐานได้ในงานแคบ สูตร IFD เป็นอัตราส่วนของ cross-entropy สองค่า สอนต่อจากบท loss ได้ทันที และ ablation ให้ตัวเลขจริงว่าแต่ละขั้นช่วยเท่าไร

การประเมิน MT และ LLM-as-judge (gap G5) มีครบในงานเดียว: rubric ที่มีลำดับเกณฑ์และกฎลงโทษ, win rate กับ LC% (GLM คุมความยาว), judge สามตระกูล, κ ระหว่างคนและคนกับ judge, QE แบบไม่ใช้ reference (CometKiwi) กับแบบใช้ reference (MetricX-24) และ GEMBA ที่ใช้ LLM ให้คะแนน เหมาะเป็น "บทความประเมินผล" หนึ่งเรื่องที่แผนคู่มือต้องการ พร้อมตัวอย่างจุดอ่อนจริง (judge ตระกูลเดียวกัน, κ 0.18 ในกรณีที่ใกล้กัน)

ChindaMT ใช้กับเนื้อหาไทยของ ZVect ได้ไหม หน้า Q&A บนเว็บตั้งใจไม่ใช้ LLM ภายนอก ใช้แค่การค้นคืน (BM25 + latent space ของเราเอง + RRF) ChindaMT เป็นโมเดลภาษาที่รันในเครื่องได้ (ไฟล์ checkpoint ของ 0.8B ≈ 2.2 GB ใน bf16 ซึ่งรวม vision tower ด้วย) แต่การนำโมเดลใด ๆ มารันตอนผู้ใช้ถาม เป็นการตัดสินใจแยกของเจ้าของ และขัดกับหลัก zero-dependency ของเว็บ ทางที่ไม่ขัดแผนคือใช้ตอนสร้างเนื้อหา (offline) เช่น ร่างคำแปลศัพท์หรือคำค้นอังกฤษ-ไทยให้คนตรวจ แล้วเก็บผลเป็นข้อมูลนิ่ง บทความเองเตือนว่าผลแปลควรมีคนตรวจในงานสำคัญ

Key Takeaways

1.RGDC ดึงกฎจากคำแปลอ้างอิงที่ทำตามกฎอยู่แล้ว กฎทุกข้อจึงทำได้แน่นอน แต่ครอบคลุมได้เฉพาะกฎที่คำแปลอ้างอิงแสดงให้เห็น
2.ข้อมูลฝึกคือคำแปลที่ Qwen3.5-35B-A3B สร้างใหม่ภายใต้กฎและผ่านการตัดสินครบทุกข้อ (1,973,358 ระเบียน, รอด 56.5%) ไม่ใช่คำแปลของคนโดยตรง
3.ใน ablation ที่ 4B การฝึกให้เห็นบล็อก Rules ช่วยมากที่สุด (+12.63 / +9.53 LC) และช่วยแม้งานแปลธรรมดา การคัด IFD ช่วยเฉพาะ Plain ในโดเมน
4.ChindaMT-4B ชนะ Typhoon-Translate-4B ที่ 61.8 / 68.4 LC% บน CoreEval และชนะคู่แข่งชัดที่สุดเมื่อมีกฎ แต่บน metric ภายนอกเป็นระดับ "เท่า" ไม่ใช่ "ครอง" และ 0.8B อยู่ท้ายกลุ่ม
5.การประเมินมีหลายชั้น (LC%, judge สามตระกูล, κ, คน, metric ภายนอก) แต่ judge หลักเป็นตระกูลเดียวกับโมเดล และคนกับ judge ตรงกันน้อยเมื่อสองระบบใกล้กัน
