บทสรุปย่อ

ผู้พูด (ประสบการณ์ 22 ปีในงานเทคโนโลยีองค์กร ตามที่เล่าเอง) บอกว่า TabFM ทำให้เขาเลิกยึดกฎข้อแรกของ ML ที่ว่า classification และ regression ต้องใช้โมเดลที่เราเทรนเองจากข้อมูลของเรา เขาสร้างหน้าจอสาธิตของตัวเองเพื่อเปิดดูว่า TabFM ทำงานอย่างไร (column attention, row compression, ICL transformer) ให้ดูตัวอย่างทำนายความเสี่ยง แล้วสรุปว่า "พื้นยกขึ้น แต่เพดานไม่ขยับ" ผู้จัดทำตรวจแล้วพบว่าหน้าจอเป็นภาพประกอบ (บางส่วนระบุเองว่า simulated) ตัวเลข attention ในหน้าจอไม่ใช่ผลของ softmax จริง ข้ออ้างเรื่องไม่ต้อง spin up GPU รองรับได้เพียงบางส่วน และข้ออ้างว่าชนะ XGBoost ที่จูนแล้วต้องอ่านอย่างระวัง

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึก (license มาตรฐานของ YouTube; transcript เป็น ASR ภาษาอังกฤษ)

สรุปเชิงลึก

ข้อโต้แย้งของคลิป ผู้พูดเปิดว่า TabFM คือโมเดลพื้นฐานสำหรับข้อมูลตารางที่ทรงพลังที่สุดที่ Google เคยสร้าง พอที่จะชนะโมเดล ML ที่นักวิทยาการข้อมูลต้องใช้เวลาจูนนานเป็นสัปดาห์ ทำนายงานอย่าง churn, fraud, credit risk ได้ในรอบเดียว โดยไม่ต้องเทรนบนข้อมูลของเรา กฎที่เขาเชื่อมาสองทศวรรษคือโมเดลทำนายต้องเทรนเอง ซึ่งมีราคาคือ ล้างข้อมูล ทำ feature engineering เลือกโมเดล จูน แล้วตั้งค่าใหม่ ราว 3 สัปดาห์ของนักวิทยาการข้อมูลก่อนที่ใครฝ่ายธุรกิจจะเห็นคำทำนายแรก ส่วน TabFM ข้ามทั้งหมดนี้ด้วย forward pass เดียว เพราะ weights ถูกตรึง ไม่ต้องเทรน และตามที่เขาว่าไม่ต้อง "spin up GPU"

สิ่งที่เขาแสดง หน้าจอที่เขาสร้างเองชื่อ Google TabFM Engine ใช้ตัวอย่างความเสี่ยงส่วนบุคคล: ตาราง context 5 แถวมี age, job, income และ label ความเสี่ยง แล้วถามอีก 3 แถวที่ไม่มี label ได้คำตอบ low, low, high ภายใน session ที่รัน forward pass ครั้งเดียว จากนั้นเขาเปิดดู 3 ขั้นของโมเดล คือ column attention (attention วิ่งตามคอลัมน์ ค่า age ทุกค่าดูค่า age อื่น ๆ เพื่อรู้ว่า $80,000 หมายถึงอะไรในตารางนี้), row compression (attention วิ่งข้ามแถว บีบทั้งแถวเป็นเวกเตอร์เดียว จึงเร็ว) และ ICL transformer (ใช้แถวที่มี label เป็น context และแถวที่ไม่มี label เป็น "คำถาม" เหมือน LLM อ่าน prompt แต่ prompt คือสเปรดชีต) เขาชี้ว่า Transformer ทั่วไปอ่านทางเดียว ตารางเป็นสองมิติ โมเดลนี้อ่านสองทางสลับกัน

ปิดท้าย ผู้พูดยกตัวอย่างอุตสาหกรรมอื่น (B2B SaaS, healthcare, fintech) เปิดโค้ด 6 บรรทัดที่ใครในทีมก็ใช้ได้ แล้วสรุปว่านี่ไม่ใช่จุดจบของ ML อาจเป็นจุดจบของงานเฉพาะอย่างหนึ่ง คือการจูน feature engineering และสัปดาห์ที่ใช้เพื่อไปถึง baseline ส่วนที่เหลือ (ข้อมูลดีพอไหม คำทำนายผิดแล้วเสียอะไร เมื่อไหร่โมเดลมั่นใจแต่ผิด) ไม่มี foundation model ตัวไหนตอบให้ "พื้นยกขึ้น แต่เพดานไม่ขยับ"

ผลตรวจของเรา (ดูตารางตรวจข้อเท็จจริง 11 ข้อ: ยืนยัน 3 · ยืนยันบางส่วน 5 · ขัดแย้ง 1 · ยังไม่พบ 0 · ไม่ได้ตรวจ 2) (1) พื้นฐานถูก: TabFM ทำนายด้วย forward pass เดียวโดยไม่ปรับพารามิเตอร์ และโครงสร้างสามขั้นตรงกับ blog และการ์ดของ weights (2) หน้าจอสาธิตเป็นของผู้พูด ไม่ใช่ผลจาก Google: แท็บกราฟ scaling มีป้าย "Simulated — Illustrative" ผู้พูดเรียกเองว่า "simulation" และเวลา 18.4 ms เป็นเวลาใน sandbox ของเขา (3) เมทริกซ์ "cross-attention" ที่ผู้พูดว่าเป็นของจริง มีแถวที่รวมกันได้ 4.57 ไม่ใช่ 1 จึงไม่ใช่แถวของ softmax ตัวเลขอย่าง "94% attention" ใช้เป็นคำอธิบายผลทำนายไม่ได้ (4) ข้ออ้างว่าชนะ XGBoost ที่จูนแล้วในโหมด zero-shot: blog ของ Google พูดกว้าง ๆ ว่า TabFM ชนะอัลกอริทึม supervised ที่จูนหนัก โดยไม่ระบุว่า XGBoost และไม่ระบุว่าเป็นรุ่นไหนของ TabFM (5) "ไม่ต้อง spin up GPU" ยืนยันได้บางส่วน: README ระบุว่ารันได้ทั้ง CPU และ GPU และหน้าจอสาธิตของผู้พูดรันบน PyTorch CPU แต่ไม่มีตัวเลขความเร็วบน CPU จาก Google และ blog ไม่ได้พูดเรื่องฮาร์ดแวร์

ใช้คลิปนี้อย่างไร (ข้อเสนอของผู้จัดทำ) อ่านเป็นภาพรวมแนวคิดและไกด์โครงสร้างสามขั้นเท่านั้น ไม่ควรอ้างตัวเลขจากหน้าจอ (94%, 0.88, 18.4 ms) เป็นผลของ TabFM

ตรวจข้อเท็จจริง

ข้ออ้างในคลิปผลตรวจรายละเอียดอ่านจาก
Google ปล่อย TabFM ซึ่งเป็นโมเดลพื้นฐานสำหรับตารางที่ทรงพลังที่สุดที่ Google เคยสร้างยืนยันบางส่วนการปล่อย (blog 2026-06-30) ยืนยัน แต่คำว่า "ทรงพลังที่สุดที่เคยสร้าง" เป็นคำเปรียบเปรยที่ตรวจไม่ได้blog (ผ่าน WebFetch สรุป)
zero-shot ชนะ gradient boosted trees ที่จูนหนัก "ไม่ใช่ XGBoost ค่าเริ่มต้นแต่เป็นที่จูนแล้ว"ยืนยันบางส่วนblog สรุปกว้าง ๆ ว่า TabFM ชนะอัลกอริทึม supervised ที่จูนหนักอย่างสม่ำเสมอ (ถอดความจากสรุปของ WebFetch) แต่ไม่ระบุคู่เทียบ (ไม่ได้ระบุ XGBoost) และไม่ระบุว่าหมายถึง TabFM ธรรมดาหรือ TabFM-Ensemble; abstract ของ paper บอกว่า zero-shot TabFM ชนะ AutoML ที่จูนแล้วblog, arXiv 2609.37959
ทำนายด้วย forward pass เดียว weights ตรึง ไม่ต้องเทรนบนข้อมูลของเรายืนยันblog: "single forward pass" ไม่มีการเทรนต่อชุดข้อมูลblog

โครงสร้างสามขั้น: column attention, row compression, ICL transformer และอ่านสองทางสลับกันยืนยันblog อธิบาย alternating row and column attention, row compression, ICL; การ์ดรุ่น 1.0.0 ระบุ row attention 3 block (8 head, 8 CLS token) และ ICL 24 blockblog, Hugging Face

ตัวเลข 18.4 ms คือเวลาใน sandbox ของผู้พูด ไม่ใช่ benchmark ของ Googleไม่ได้ตรวจผู้พูดบอกเอง ตรวจซ้ำไม่ได้ และไม่ทราบว่าหน้าจอเรียกโมเดลจริงหรือไม่ (ผู้พูดบอกว่าเรียกโมเดล TabFM)คลิป
เมื่อเพิ่ม context ผลใต้เส้น ROC ดีขึ้นยืนยันบางส่วนหน้าจอระบุกราฟนี้ "Simulated — Illustrative" ผู้พูดเรียกเองว่า simulation แนวโน้มทั่วไปสอดคล้องกับคลิป 8vW6gi5vRes ที่ F1 สูงขึ้นจาก 50 เป็น 500 แถวแต่ไม่ได้ขึ้นทุกตัวชี้วัดทุกขั้น (recall 0.525 เป็น 0.508 ระหว่าง 100 กับ 200 แถว)หน้าจอ; คลิปที่เกี่ยวข้อง

  4. 4. ใต้ฝา: สามขั้นของโมเดลและเมทริกซ์ attention (~2:54–5:03)

  6. 6. โค้ด 6 บรรทัด (~6:06–6:27)
  7. 7. ความหมายจริง ๆ ของเรื่องนี้: พื้นยกขึ้น เพดานไม่ขยับ (~6:27–7:15)

1. กฎเก่าของ ML และสิ่งที่ TabFM เปลี่ยน (~0:00–0:55)

ผู้พูดเปิดคลิปด้วยข้ออ้างว่า Google เพิ่งปล่อย TabFM ซึ่งเป็นโมเดลพื้นฐานที่ทรงพลังที่สุดที่ Google เคยสร้างสำหรับข้อมูลตาราง แรงพอที่จะเอาชนะโมเดลแมชชีนเลิร์นนิงที่นักวิทยาการข้อมูลใช้เวลาจูนนานเป็นสัปดาห์ เขายกปัญหาตัวอย่างอย่าง churn, fraud และ credit risk และบอกว่าโมเดลนี้ทำได้ในรอบเดียว โดยไม่ต้องเทรน และไม่ใช้แม้แต่แถวเดียวของข้อมูลของเรา (ผู้จัดทำตีความว่าหมายถึงไม่ใช้ข้อมูลของเราเพื่อเทรน เพราะแถวที่มี label ยังต้องป้อนเป็น context ตามที่ผู้พูดแสดงในหน้าจอภายหลัง)

ผู้พูดเล่าว่าเขาอยู่ในวงการเทคโนโลยีองค์กรมา 22 ปี ส่วนใหญ่ของเวลานั้นสร้างระบบ ML แบบดั้งเดิม และตอนนี้กำลังสร้าง agentic AI กฎข้อแรกที่เขาเรียนรู้ใน ML คือ classification และ regression เป็นหน้าที่ของโมเดลที่เราเทรนเองบนข้อมูลของเรา เขาเชื่อแบบนั้นมาสองทศวรรษ และ TabFM "ทำลายความเชื่อมั่น" ข้อนั้นของเขา

2. ต้นทุนของ ML แบบเดิม และสิ่งที่ TabFM ข้าม (~0:55–1:51)

ผู้พูดอธิบายว่ากฎเก่ามีราคาอะไรบ้าง เริ่มจากล้างข้อมูล สร้างตัวแปร (feature) เลือกโมเดลที่เหมาะจากหลายตัว จูนโมเดล แล้วตั้งค่าใหม่ เขาเปรียบว่านี่คือ 3 สัปดาห์ในชีวิตของนักวิทยาการข้อมูลก่อนที่ฝ่ายธุรกิจจะเห็นคำทำนายแรกสักตัว

ส่วน TabFM เขาว่าข้ามทั้งหมดนี้ ทำ forward pass เดียว เพราะมี frozen weights จึงไม่มีขั้นเทรน และ "ไม่ต้อง spin up GPU" เขาย้ำว่า TabFM แบบ zero-shot เอาชนะ gradient boosted trees ที่จูนหนัก ไม่ใช่ XGBoost ค่าเริ่มต้นแต่เป็น XGBoost ที่จูนแล้ว จากภายนอกเราเห็นแค่ว่ายื่นตารางให้แล้วได้คำทำนายกลับมา ผู้พูดจึงสร้างหน้าจอ (UI) เพื่อเปิดกล่องให้เห็นการทำงาน และเตือนว่าความเห็นทั้งหมดเป็นของเขาเอง ไม่ใช่ของนายจ้าง

เสริมจากผู้จัดทำ

ผู้จัดทำแนะนำให้อ่านข้ออ้าง "ชนะ XGBoost ที่จูนแล้ว" พร้อมตารางตรวจข้อเท็จจริง blog ของ Google ไม่ได้ระบุชื่อ XGBoost ในผล benchmark และไม่ระบุว่าหมายถึงรุ่น TabFM ใด ส่วน "ไม่ต้อง spin up GPU" รองรับได้เพียงบางส่วน (README ระบุว่ารันได้ทั้ง CPU และ GPU แต่ไม่มีตัวเลขความเร็วบน CPU)

3. สาธิต: ทำนายความเสี่ยงส่วนบุคคลบนหน้าจอของผู้พูด (~1:51–2:54)

ผู้พูดบอกว่าสิ่งที่เห็นคือ UI ที่เขาสร้างเพื่อให้เข้าใจว่าเกิดอะไรขึ้นภายใน และเข้ากับอุตสาหกรรมต่าง ๆ อย่างไร เขาเริ่มจากความเสี่ยงส่วนบุคคล ซึ่งอาจเป็นประกัน หรือการผิดนัดชำระบัตรเครดิต หรืออะไรทำนองนั้น ข้อมูลฝั่ง context ใส่ได้ 5, 10 หรือ 15 แถว เหมือนป้อนข้อมูลให้ LLM ในกรณีนี้มี age, job, income และ label ความเสี่ยงที่มีอยู่ ซึ่งคือตัวอย่างที่เราให้ ขั้นที่สองคือระเบียนที่ยังไม่มี label ซึ่งเป็นที่ที่เราคาดหวังคำตอบ

เมื่อกดเริ่ม UI จะเรียกโมเดล TabFM และโมเดลทำ in-context scoring แล้วให้คะแนนออกมา คนแรกเสี่ยงต่ำ คนที่สองเสี่ยงต่ำ และคนที่สามเสี่ยงสูง

เสริมจากผู้จัดทำ

ข้อสังเกตจากภาพ (ผู้จัดทำ ไม่ใช่คำพูดของผู้พูด): แถวคำถามที่ 3 ทำนายว่า high risk แต่ "Top Attention Match" ในหน้าต่างเดียวกันชี้ไปที่ Context Row 1 ซึ่งมี label low risk ดังนั้นการดูแถวที่ attention สูงสุดอย่างเดียวอธิบายคำทำนายของแถวนี้ไม่ได้ ตารางตัวอย่างมีเพียง 5 แถว และ label ในตัวอย่างแยกได้ด้วยรายได้ (แถวเดียวที่ high risk มีรายได้ต่ำสุด) จึงเป็นตัวอย่างประกอบเท่านั้น

4. ใต้ฝา: สามขั้นของโมเดลและเมทริกซ์ attention (~2:54–5:03)

ผู้พูดบอกว่าเบื้องหลังคือวิธีแบบ Transformer เพราะนี่เป็นโมเดลพื้นฐานที่ Google สร้าง มีสามขั้นที่จะเห็น ขั้นแรกคือ column attention ขั้นสองคือ row compression และขั้นสามคือ ICL transformer

ขั้นที่ 1 column attention attention วิ่งตามคอลัมน์ ค่า age ทุกค่าดูค่า age อื่นทั้งหมด และนี่คือวิธีที่โมเดลรู้ว่า $80,000 หมายถึงอะไรในตารางนั้น โดยมองทั้งคอลัมน์ ไม่ใช่เซลล์เดียว

ขั้นที่ 2 row compression attention "พลิก" ไปวิ่งข้ามแถวแล้วบีบทั้งแถวเป็นเวกเตอร์เดียว คือรายการตัวเลขหนึ่งชุดที่แทนลูกค้าทั้งคน และนี่คือเหตุผลที่ยังเร็วอยู่ เพราะ attention วิ่งบนแถวไม่ใช่ทุกเซลล์

ขั้นที่ 3 ICL transformer รับแถวที่ถูกบีบแล้ว ใช้แถวที่มี label เป็น context และแถวที่ไม่มี label เป็นคำถาม นี่คือ in-context learning กลไกเดียวกับที่ LLM อ่าน prompt เพียงแต่ prompt คือสเปรดชีตของเรา

ผู้พูดอธิบายต่อว่า Transformer มาตรฐานอ่านทิศทางเดียว แต่ตารางเป็นสองมิติ โมเดลนี้จึงอ่านทั้งสองทางสลับกัน ในหน้าจอเขาแสดงเมทริกซ์ cross-attention ระหว่างคำถามกับตัวอย่าง แถวคือคนที่ไม่มี label (แถว 1, 3, 4, 5) และคอลัมน์คือตัวอย่างที่มี label ทุกเซลล์เป็นน้ำหนัก attention ว่าคำถามนั้นให้ความสำคัญกับตัวอย่างนั้นมากแค่ไหน และเขาชี้ว่านี่คือฟังก์ชัน softmax โดยมีมิติ embedding ตามภาพ เขายกตัวอย่างว่าวิศวกรอายุ 30 ปีให้ attention 94% กับวิศวกรอายุ 25 ปี ซึ่งเป็นที่มาของการทำนายความเสี่ยงต่ำ ผู้พูดสรุปว่านี่จึงไม่ใช่กล่องดำ เพราะน้ำหนัก attention คือคำอธิบาย

ข้อที่ควรเข้าใจให้ตรง

ข้อที่ควรเข้าใจให้ตรง (ผลตรวจของเรา): ตัวเลขในเมทริกซ์ไม่ใช่ผลของ softmax จริง เพราะแถวแรกรวมกันได้ 0.941 + 0.882 + 0.914 + 0.871 + 0.963 = 4.571 ขณะที่แถวของ softmax ต้องรวมเป็น 1 ดังนั้น "94%" ในหน้าจอเป็นตัวเลขประกอบภาพ ไม่ใช่ attention จริงของ TabFM นอกจากนี้ ICL transformer จริงมี 24 block และ 8 head ไม่มีเมทริกซ์ Q·K^T เดียวที่อธิบายคำทำนายได้ทั้งหมด (ข้อสรุปเรื่องนี้ของผู้จัดทำอ้างจากโครงสร้างในการ์ดรุ่น 1.0.0)

เสริมจากผู้จัดทำ

ข้อมูลเสริม (ผู้จัดทำ): ข้อความบนการ์ดสามขั้นในหน้าจอสอดคล้องกับการ์ด weights รุ่น 1.0.0 ใน Hugging Face (embedding 256 มิติ, row attention 3 block 8 head 8 CLS token, ICL 24 block) และกับ blog ของ Google ที่อธิบาย alternating row and column attention แล้ว row compression แล้ว ICL

5. ตัวอย่างอุตสาหกรรมอื่น เวลาตอบสนอง และกราฟ scaling (~5:03–6:06)

ผู้พูดบอกว่าเพราะ weights ถูกตรึง จึงเห็นการตอบสนองเป็นมิลลิวินาที และ 18.4 มิลลิวินาทีที่เห็นคือเวลาใน sandbox ของเขาเอง ไม่ใช่ benchmark ของ Google เขาย้ำให้ผู้ชมรู้ จากนั้นเขาให้ดูอุตสาหกรรมอื่น: B2B SaaS, healthcare ซึ่งเลือกตามกรณีใช้งานแล้วรันได้เช่นกัน และ fintech เช่นข้อพิพาท เขาสรุปว่านี่คือโมเดลภาษาขนาดใหญ่ที่ทำงานข้ามอุตสาหกรรมและข้อมูลตารางใดก็ได้ (ตามคำพูดของเขา; TabFM เป็นโมเดลพื้นฐานสำหรับตาราง ไม่ใช่ LLM)

เขายังบอกว่าเมื่อให้ context มากขึ้น พื้นที่ใต้เส้น ROC จะดีขึ้นมาก ซึ่งเขาให้ดูและเรียกว่าเป็นการจำลองแบบหนึ่ง (a kind of simulation) และเห็นความแม่นยำเท่ากันเมื่อเทียบกับงานที่นักวิทยาการข้อมูลต้องทำ เขาว่านี่คือวิธีประหยัดต้นทุนได้มาก

ข้อที่ควรเข้าใจให้ตรง

ข้อที่ควรเข้าใจให้ตรง: ในกราฟเขียนไว้เองว่า "Simulated — Illustrative" ผู้พูดก็เรียกว่า simulation จึงไม่ควรอ่านเส้นโค้งหรือค่า 0.88 เป็นผลวัดจริงของ TabFM และคลิปไม่ได้แสดงการเทียบกับงานของนักวิทยาการข้อมูลด้วยตัวเลขที่ตรวจได้ (ตัวเลขที่วัดจริงเรื่องจำนวนแถวกับคุณภาพมีในคลิปอื่นในชุดเดียวกัน)

6. โค้ด 6 บรรทัด (~6:06–6:27)

ผู้พูดบอกว่าแม้ไม่เคยเขียนโค้ดสักบรรทัดก็ขอให้ดูต่อ เพราะข้อนี้บอกอะไรบางอย่าง ถ้าคนในทีมอยากใช้ Tabular FM วันนี้ ทั้งหมดคือหกบรรทัด: สอง import โหลดโมเดล เตรียมตาราง แล้วทำนาย

from tabfm import tabfm_v1_0_0
from tabfm import TabFMClassifier
model = tabfm_v1_0_0.load()
clf = TabFMClassifier(model=model)
clf.fit(X_train, y_train)
preds = clf.predict(X_test)
เสริมจากผู้จัดทำ

ผู้จัดทำเสริม: ASR ได้ยินว่า "annotate your table" ซึ่งตรงกับบรรทัด clf.fit(...) บนสไลด์ (คำว่า fit ในที่นี้ไม่ได้ปรับพารามิเตอร์ของโมเดลในความหมายของการเทรนปกติ ตามที่ blog และการ์ดอธิบายว่าเป็น ICL) หน้า Hugging Face ของรุ่น 1.1.0 ใช้รูปแบบ tabfm_v1_1_0.load(model_type=...) จึงต้องดูรุ่นก่อนคัดลอกโค้ด

7. ความหมายจริง ๆ ของเรื่องนี้: พื้นยกขึ้น เพดานไม่ขยับ (~6:27–7:15)

ผู้พูดปิดว่าสิ่งนี้ไม่ใช่จุดจบของ machine learning แน่นอน บางทีอาจเป็นจุดจบของงานเฉพาะด้านหนึ่ง คือการจูน feature engineering และสัปดาห์ที่เคยใช้ไปเพียงเพื่อให้ถึง baseline หกบรรทัดนั้นแทนที่สิ่งเหล่านี้ ทุกอย่างหลังจาก baseline ยังคงเป็นส่วนที่ยาก: ข้อมูลของเราดีพอหรือไม่ คำทำนายที่ผิดมีต้นทุนเท่าไร และเมื่อไหร่ที่โมเดลมั่นใจแต่ผิด ไม่มี foundation model ตัวไหนตอบสามข้อนี้แทนเราได้

ผู้พูดเสนอว่าอาจมองได้ว่า "พื้นยกขึ้น แต่เพดานไม่ขยับ" (the floor just came up, the ceiling did not move) ก่อนปิดคลิปด้วยการขอให้คอมเมนต์ ถ้ามีคำถาม และกดไลก์กับติดตามช่อง (ส่วนเชิญชวนนี้ตัดออกจากรายงาน)

Key Takeaways

1.TabFM ทำนายตารางด้วย forward pass เดียว weights ตรึง ไม่ปรับพารามิเตอร์ตามข้อมูลของเรา แถวที่มี label ทำหน้าที่เป็น context
2.โครงสร้างสามขั้นที่ผู้พูดอธิบายตรงกับ blog และการ์ดของ weights: column attention, row compression (แถวเป็นเวกเตอร์เดียว), ICL transformer
3.หน้าจอสาธิตเป็นของผู้พูด: กราฟ scaling ระบุว่า simulated, เมทริกซ์ attention รวมแถวไม่ได้ 1 จึงไม่ใช่ softmax จริง และ 18.4 ms เป็นเวลาใน sandbox ของเขา อย่าอ้างตัวเลขเหล่านี้เป็นผลของ TabFM
4.ข้ออ้างว่า "ไม่ต้อง spin up GPU" รองรับได้เพียงบางส่วน (README ระบุว่ารันได้ทั้ง CPU และ GPU แต่ไม่มีตัวเลขความเร็วบน CPU) และ "ชนะ XGBoost ที่จูนแล้ว" ยังไม่มีหลักฐานตรงตามที่ผู้พูดพูด (blog พูดกว้าง ๆ ไม่ระบุ XGBoost)
5.ข้อสรุปของผู้พูด "พื้นยกขึ้น เพดานไม่ขยับ": คุณภาพข้อมูล ต้นทุนของคำทำนายที่ผิด และความมั่นใจที่ผิด ยังเป็นงานของเรา
