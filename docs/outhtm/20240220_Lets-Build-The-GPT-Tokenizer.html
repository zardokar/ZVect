📋 บทสรุปย่อ

บทสรุปย่อ: Karpathy สร้าง tokenizer แบบ GPT ตั้งแต่ศูนย์ใน Jupyter notebook: ข้อความ → ไบต์ UTF-8 (คลังเริ่มต้น 256 ค่า) → BPE นับคู่ที่ติดกันบ่อยที่สุดแล้วรวมเป็น token ใหม่ id 256, 257, … จนได้ขนาดคลังที่ต้องการ → ได้ merges (กฎการรวม) กับ vocab (id → ไบต์) ที่ใช้ encode และ decode ได้ จากนั้นต่อยอดเป็นของจริง: regex แบ่งข้อความก่อนรวม (GPT-2 / GPT-4), ไลบรารี tiktoken, special token เช่น <|endoftext|>, sentencepiece ของ Llama 2, การเลือกขนาดคลัง และปิดท้ายด้วยการอธิบายว่าความแปลกของ LLM (สะกดคำไม่ได้ เลขคณิตพลาด ภาษาที่ไม่ใช่อังกฤษแย่กว่า SolidGoldMagikarp, JSON กิน token มากกว่า YAML) ล้วนย้อนกลับไปที่ tokenization

โหมดของเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ (license มาตรฐานของ YouTube, ตรวจ 2026-10-11) อ่านจาก caption อังกฤษอัตโนมัติ ตัวเลขเทียบกับภาพบนจอ จุดที่ caption ผิดรวมไว้ในส่วนที่ 16 · คลิปเผยแพร่ 2024 อยู่ในช่วงความรู้ของผู้จัดทำ จึงไม่ได้ค้นเว็บเพิ่ม ข้อความที่ผู้จัดทำเติมเองติดป้าย "ผู้จัดทำ" ทุกจุด

🧭 สรุปเชิงลึก

ภาพใหญ่: tokenizer คือชั้นแปลภาษาที่แยกจาก LLM มีชุดข้อความฝึกของตัวเอง ฝึกครั้งเดียวก่อนฝึกโมเดล แล้วแปลงข้อความทั้งหมดเป็นเลข token ให้โมเดลอ่าน โมเดลไม่เคยเห็นตัวอักษรตรง ๆ เห็นแต่เลข token แต่ละเลขเปิดแถวในตาราง embedding (แถวละหนึ่ง token) และที่ปลายโมเดลมีชั้น lm_head ที่ให้คะแนนทุก token ในคลังเพื่อทายตัวถัดไป ขนาดคลังจึงไปโผล่สองที่นี้เท่านั้น

ทำไมเริ่มจากไบต์: สตริงของ Python คือลำดับ Unicode code point (ราว 150,000 ตัว 161 ระบบเขียน) ใช้เป็นคลังตรง ๆ ไม่ได้เพราะใหญ่และมาตรฐานยังเปลี่ยนเรื่อย ๆ UTF-8 แปลงแต่ละ code point เป็น 1–4 ไบต์ (UTF-16 / UTF-32 เปลืองเพราะมีศูนย์เยอะ) แต่ถ้าใช้ไบต์ดิบ 256 ค่าเป็นคลัง ลำดับจะยาวเกินไปสำหรับ context ที่จำกัด คำตอบคือ BPE บนไบต์: ได้คลังขนาดที่ปรับได้ (GPT-2 ราว 50k, GPT-4 ราว 100k) (ผู้จัดทำ: และไม่มีวันเจอตัวที่ไม่รู้จัก เพราะทุกข้อความแตกเป็นไบต์ได้เสมอ)

ขั้นตอนหลักที่คลิปสร้าง (ส่วนที่ 5–8): (1) get_stats นับทุกคู่ที่ติดกัน (2) เลือกคู่ที่บ่อยที่สุด ให้ id ใหม่ (3) merge แทนคู่นั้นทุกจุด (4) วนจนครบจำนวนรอบ = ขนาดคลัง − 256 (5) decode: ต่อไบต์ของแต่ละ id แล้วถอด UTF-8 ด้วย errors="replace" (6) encode: แปลงเป็นไบต์ แล้วรวมคู่ที่มีลำดับกฎต่ำสุดก่อน จนไม่มีคู่ไหนรวมได้ ตัวอย่างในคลิป: 20 merges ทำให้ข้อความ 24,597 ไบต์เหลือ 19,438 token (บีบได้ 1.27 เท่า)

ของจริงซับซ้อนกว่า: GPT-2 ใช้ regex แบ่งข้อความเป็นชิ้น (ตัวอักษร / ตัวเลข / เครื่องหมาย / ช่องว่าง) แล้ว BPE ภายในแต่ละชิ้น เพื่อไม่ให้ได้ token อย่าง "dog." "dog!" แยกกัน GPT-4 (cl100k_base) เปลี่ยน regex: ไม่สนตัวพิมพ์เล็กใหญ่ของ 's 't, รวมช่องว่างได้ และตัวเลขยาวสุด 3 หลักต่อชิ้น นอกจากนี้มี special token ที่ไม่ผ่าน BPE เช่น <|endoftext|> = 50256 (GPT-2) และ token สำหรับแชตกับ fill-in-the-middle การเพิ่ม token ใหม่ต้องผ่าตัดโมเดลเล็กน้อย (เพิ่มแถว embedding และแถวใน lm_head)

ข้อสรุปของผู้สอน: อย่ามองข้าม tokenization เพราะเป็นต้นเหตุของปัญหาจำนวนมาก (รวมถึงเรื่องความปลอดภัย) ถ้าทำได้ให้ใช้ token ของ GPT-4 ผ่าน tiktoken ถ้าต้องฝึกคลังเองให้ใช้ BPE ของ sentencepiece อย่างระวัง (ลอกค่าของ Meta) และของที่อยากได้จริงคือ "tiktoken ที่ฝึกได้" ซึ่ง minbpe เป็นตัวต้นแบบ

1. ทำไมต้องลงรายละเอียดเรื่อง tokenization (~0:00–5:50)

ผู้สอนบอกตรง ๆ ว่า tokenization เป็นส่วนที่ไม่ชอบที่สุดในงาน LLM แต่จำเป็นต้องเข้าใจ เพราะมี "กับดัก" ซ่อนอยู่มาก และความแปลกของ LLM จำนวนมากย้อนกลับไปที่ขั้นนี้

ทบทวนคลิปก่อน (Let's Build GPT): ชุดข้อมูล Shakespeare เป็นสตริงยาวหนึ่งก้อน สร้างคลังจากตัวอักษรที่เจอได้ 65 ตัว ทำตารางแปลงตัวอักษร ↔ เลข ข้อความ 1,000 ตัวอักษรจึงได้ 1,000 token จากนั้นเลข token แต่ละตัวใช้เปิดแถวใน ตาราง embedding (65 แถว) แถวนั้นเป็นพารามิเตอร์ที่ฝึกด้วย backpropagation แล้วส่งเข้า Transformer ของจริงไม่ทำระดับตัวอักษร แต่ทำเป็น "ชิ้น" ที่สร้างด้วยอัลกอริทึมอย่าง Byte Pair Encoding

เปเปอร์ GPT-2 (ส่วน Input Representation ผู้สอนบอกว่า "น่าจะ" เป็นเปเปอร์แรกที่ใช้ BPE ระดับไบต์กับ LLM): คลัง 50,257 token และ context 1,024 token ผู้สอนเรียก token ว่าเป็น "อะตอม" ของ LLM ทุกอย่างวัดเป็น token ส่วนเปเปอร์ Llama 2 พูดถึง token 63 ครั้ง เช่นฝึกด้วยข้อมูล 2 ล้านล้าน token

รายการความแปลกที่จะกลับมาอธิบายตอนท้าย (ส่วนที่ 15): สะกดคำไม่เก่ง · งานจัดการสตริงง่าย ๆ ทำได้ยาก · ภาษาที่ไม่ใช่อังกฤษแย่กว่า · เลขคณิตง่าย ๆ พลาด · GPT-2 เขียน Python ได้ไม่ดีเท่าที่ควร · คำเตือนเรื่องช่องว่างท้ายข้อความ · ถามถึง "SolidGoldMagikarp" แล้วโมเดลเพี้ยน · คำแนะนำให้ใช้ YAML แทน JSON ผู้สอนย้ำว่าอย่าปัดทิ้ง เพราะหลายปัญหาที่ดูเหมือนเป็นปัญหาของสถาปัตยกรรม จริง ๆ แล้วเป็นปัญหาของ tokenization

2. ลองเล่นใน tiktokenizer: GPT-2 เทียบ GPT-4 (~5:50–15:00)

เว็บ tiktokenizer ตัด token สดในเบราว์เซอร์ ผู้สอนวางข้อความตัวอย่างหลายแบบแล้วดูผลทีละจุด (ข้อสังเกตทั้งหมดเป็นของ GPT-2):

  • คำอังกฤษ: "tokenization" กลายเป็น 2 token (3,642 และ 1,634) · " is" = 318 · " at" = 379 · " the" = 262 สังเกตว่าช่องว่างติดไปกับคำที่ตามมา
  • ตัวเลข: 127 เป็น token เดียว แต่ 677 แตกเป็น 2 token (" 6" กับ "77") 804 ก็แตกเป็น 2 ตัวเลข 4 หลักแตกแบบไม่มีกฎ บางทีหลายหลักรวมเป็นหนึ่ง บางทีหลักเดียวเป็นหนึ่ง
  • Egg: "Egg" ต้นประโยคเป็น 2 token แต่ " Egg" (มีช่องว่างหน้า) เป็น token เดียว "egg" ตัวเล็กเป็นอีก token และ "EGG" เป็น 2 token แนวคิดเดียวกันได้เลขต่างกันหมด โมเดลต้องเรียนรู้เองจากข้อมูลว่าเป็นสิ่งเดียวกัน
  • ภาษาเกาหลี: ประโยคแนะนำ ChatGPT ใช้ token มากกว่าภาษาอังกฤษที่ความหมายเดียวกัน เพราะชุดฝึกของ tokenizer มีอังกฤษมากกว่า อังกฤษจึงได้ชิ้นยาว ภาษาอื่นแตกเป็นชิ้นเล็ก ลำดับยืดออก กิน context ของ Transformer
  • Python (FizzBuzz): ช่องว่างย่อหน้าแต่ละตัวเป็น token แยก (220 ซ้ำ ๆ) ทำให้เปลือง context มาก GPT-2 จึงเขียน Python ได้ไม่ดี ไม่ใช่เพราะตัวโมเดลอย่างเดียว

เปลี่ยนเป็น cl100k_base (GPT-4): ข้อความเดิมเหลือ 185 token จาก 300 เพราะคลังโตจากราว 50k เป็นราว 100k ข้อความเดิมจึงอัดแน่นขึ้นราวครึ่งหนึ่ง โมเดลมองย้อนได้ยาวขึ้นราวสองเท่า แต่คลังใหญ่ขึ้นไม่ได้ดีขึ้นเรื่อย ๆ เพราะตาราง embedding และ softmax ที่ปลายโมเดลโตตาม ต้องหาจุดพอดี (ส่วนที่ 14) อีกจุดคือ GPT-4 รวมช่องว่างของ Python: ย่อหน้า 4 ช่องกลายเป็นช่องว่าง 3 ตัวรวมเป็น token เดียว + " if" และช่องว่าง 7 ตัวรวมเป็น token เดียว เป็นการตัดสินใจโดยตั้งใจของ OpenAI และความสามารถเขียนโค้ดที่ดีขึ้นจาก GPT-2 ถึง GPT-4 ส่วนหนึ่งมาจากการออกแบบ tokenizer นี้

3. Unicode, UTF-8 และทำไมไม่ใช้ไบต์ดิบตรง ๆ (~15:00–23:30)

ขั้น 1 — สตริงคืออะไร: ตามเอกสาร Python สตริงคือ "ลำดับของ Unicode code point" ที่แก้ไม่ได้ Unicode Consortium กำหนดตัวอักษรราว 150,000 ตัว ใน 161 ระบบเขียน (มาตรฐาน 15.1 ออกกันยายน 2023) ฟังก์ชัน ord() ให้เลข code point เช่น ord("h") = 104 อีโมจิได้เลขราว 128,000 ตัวอักษรเกาหลีได้ราว 50,000 (ใส่ได้ทีละตัวอักษรเท่านั้น)

ขั้น 2 — ทำไมไม่ใช้ code point เป็นคลัง: คลังจะใหญ่ราว 150,000 และมาตรฐานยังมีชีวิตอยู่ เปลี่ยนเรื่อย ๆ ไม่ใช่ตัวแทนที่นิ่งพอ

ขั้น 3 — encoding: Unicode กำหนด 3 แบบคือ UTF-8, UTF-16, UTF-32 UTF-8 ใช้มากที่สุด แปลงแต่ละ code point เป็น 1–4 ไบต์ (ยาวไม่เท่ากัน) UTF-32 ยาวคงที่แต่มีข้อเสียอื่น ผู้สอนแนะนำบทความ "UTF-8 Everywhere Manifesto" ข้อดีเด่นของ UTF-8 คือเข้ากันได้กับ ASCII เดิม ลองใน Python: list("…".encode("utf-8")) ได้ไบต์ดิบ ส่วน UTF-16 / UTF-32 เห็นศูนย์คั่นเต็มไปหมด (0, ค่า, 0, ค่า …) สำหรับตัวอักษรอังกฤษ จึงเปลืองสำหรับงานนี้

ขั้น 4 — ทำไมไม่ใช้ไบต์ดิบ: ไบต์มีแค่ 256 ค่า คลังเล็กมาก ตาราง embedding และชั้นทายผลจะเล็ก แต่ลำดับยาวมาก ขณะที่ attention รองรับ context ได้จำกัด โมเดลจึงมองย้อนข้อความได้สั้นลง ต้องการคลังที่ใหญ่กว่านี้และปรับได้เป็น hyperparameter แต่ยังยึด UTF-8 → คำตอบคือ BPE ที่บีบลำดับไบต์ลงตามต้องการ

ทางเลือกในอนาคต: มีเปเปอร์ (ฤดูร้อนปีก่อนคลิป) เสนอ Transformer แบบลำดับชั้นที่รับไบต์ดิบได้เลย สรุปว่าการทำโมเดลไม่มี tokenizationที่สเกลใหญ่ "ทำได้" ผู้สอนอยากให้เป็นจริงแต่ไม่แน่ใจว่าถูกพิสูจน์แล้วโดยหลายกลุ่มที่สเกลพอ ตอนนี้จึงต้องบีบด้วย BPE ไปก่อน (ผู้จัดทำ: คลิปไม่ได้เอ่ยชื่อ เปเปอร์ที่ตรงคำอธิบายคือ MEGABYTE ของ Meta ปี 2023)

ผู้จัดทำ (ไม่ได้มาจากคลิป): ตัวอักษรไทยอยู่ช่วง U+0E00–U+0E7F ใน UTF-8 จึงใช้ 3 ไบต์ทุกตัว เช่น "สวัสดี" มี 6 code point = 18 ไบต์ ทุกตัวขึ้นต้นด้วยไบต์ 224, 184 (ตัวตั้งแต่ U+0E40 เช่น เ แ โ ไ และเลขไทย ขึ้นต้นด้วย 224, 185)

4. BPE ทีละรอบ: ตัวอย่างบน Wikipedia (~23:30–27:00)

ผู้สอนบอกว่า BPE ไม่ซับซ้อน และหน้า Wikipedia อธิบายได้ดี สมมุติคลังมีแค่ 4 ตัว (a, b, c, d) และมีลำดับยาว 11 ตัว ที่อยากบีบให้สั้นลง:

  1. หาคู่ที่ติดกันบ่อยที่สุด — aa เจอบ่อยสุด
  2. สร้าง token ใหม่ ชื่อ Z = aa เพิ่มเข้าคลัง (คลังเป็น 5)
  3. แทนทุกจุด — ลำดับเหลือ 9 ตัว
  4. ทำซ้ำ — คู่ที่บ่อยสุดรอบถัดไปคือ ab → Y (เหลือ 7 ตัว คลัง 6) แล้ว ZY → X (เหลือ 5 ตัว คลัง 7)

สุดท้ายลำดับ 11 ตัวด้วยคลัง 4 กลายเป็นลำดับ 5 ตัวด้วยคลัง 7 สังเกตว่า token ที่เพิ่งสร้าง (Z, Y) ก็ถูกรวมต่อได้ในรอบหลัง

ใช้กับไบต์: ทำแบบเดียวกันทุกอย่าง แต่เริ่มจากคลัง 256 (ไบต์) แล้วสร้าง token ใหม่ต่อท้ายไปเรื่อย ๆ ผลที่ได้มีสองอย่าง: ชุดข้อมูลฝึกที่ถูกบีบแล้ว และอัลกอริทึมสำหรับ encode ข้อความใดก็ได้ด้วยคลังนี้ และ decode กลับเป็นสตริง

5. เขียนเอง ขั้นที่ 1–3: ไบต์ → get_stats → merge (~27:00–34:40)

ขั้น 1 — เตรียมข้อมูล: ใช้ย่อหน้าแรกของบล็อกโพสต์เรื่อง Unicode ที่ผู้สอนชอบ ยาว 533 code point แปลงเป็น UTF-8 ได้ 616 ไบต์ (ยาวขึ้นเพราะตัวอักษรที่ซับซ้อนกินหลายไบต์ สูงสุด 4) แปลง bytes เป็น list ของเลขจำนวนเต็มเพื่อจัดการง่าย

ขั้น 2 — get_stats: รับ list ของเลข ใช้ dict นับทุกคู่ที่อยู่ติดกัน (วนคู่ด้วย zip(ids, ids[1:])) เรียงจากมากไปน้อยแล้วพบว่าคู่ (101, 32) เจอบ่อยที่สุด 20 ครั้ง chr(101) = "e" และ 32 = ช่องว่าง คือคำจำนวนมากลงท้ายด้วย e ใน Python เลือกคู่บนสุดได้ด้วย max(stats, key=stats.get)

ขั้น 3 — merge(ids, pair, idx): เดินจากซ้ายไปขวา ถ้าตำแหน่งนี้กับตำแหน่งถัดไปตรงกับคู่ ให้ใส่ idx แล้วกระโดด 2 ช่อง ไม่ตรงก็คัดลอกตัวเดิมแล้วไป 1 ช่อง ต้องระวังไม่ให้ดูเกินท้าย list ตอนอยู่ตัวสุดท้าย ตัวอย่างเล็ก: [5, 6, 6, 7, 9, 1] แทน (6, 7) ด้วย 99 ได้ [5, 6, 99, 9, 1]

token ใหม่ได้ id 256 (เพราะไบต์ใช้ 0–255 ไปแล้ว) เมื่อแทน (101, 32) ด้วย 256 list ยาว 596 จาก 616 ลดลง 20 ตรงกับจำนวนครั้งที่เจอ และไม่เหลือคู่ 101, 32 ติดกันอีก

# ผู้จัดทำเขียนใหม่ ทำงานแบบเดียวกับในคลิป
def get_stats(ids):
    counts = {}
    for pair in zip(ids, ids[1:]):          # ทุกคู่ที่ติดกัน
        counts[pair] = counts.get(pair, 0) + 1
    return counts

def merge(ids, pair, idx):
    out, i = [], 0
    while i < len(ids):
        if i + 1 < len(ids) and (ids[i], ids[i + 1]) == pair:
            out.append(idx); i += 2           # เจอคู่: ใส่ token ใหม่ ข้าม 2 ช่อง
        else:
            out.append(ids[i]); i += 1
    return out

6. ขั้นที่ 4: วนฝึกจนได้ขนาดคลัง และอัตราบีบ (~34:40–39:40)

จำนวนรอบเป็น hyperparameter: ยิ่งรวมมาก คลังยิ่งใหญ่และลำดับยิ่งสั้น มีจุดพอดีที่หาจากการทดลอง (GPT-4 ใช้ราว 100,000 token) คราวนี้ใช้ทั้งบล็อกโพสต์เป็นข้อความยาวบรรทัดเดียว เพื่อให้สถิติของคู่ไบต์น่าเชื่อถือขึ้น

  1. ตั้ง vocab_size = 276 → num_merges = 276 − 256 = 20
  2. คัดลอก list ไว้ก่อน (list(tokens)) จะได้ไม่ทำลายต้นฉบับ
  3. สร้าง dict merges เก็บ (ลูกตัวที่ 1, ลูกตัวที่ 2) → id ใหม่
  4. วน 20 รอบ: get_stats → เลือกคู่บ่อยสุด → id = 256 + i → merge → จดลง merges

ผลคือป่าต้นไม้ไบนารี (ไม่ใช่ต้นเดียว): ใบล่างสุดคือ 256 ไบต์ แล้วรวมทีละสอง ไบต์ 101 กับ 32 ยังโผล่เดี่ยว ๆ ได้ จะกลายเป็น 256 เฉพาะตอนที่อยู่ติดกัน และ token ใหม่ก็ถูกรวมต่อได้ เช่นรอบที่ 20 รวม (259, 256) เป็น 275

อัตราบีบ: ข้อความ 24,597 ไบต์ เหลือ 19,438 token หลังรวม 20 รอบ = บีบได้ 1.27 เท่า ยิ่งเพิ่มคลัง อัตรานี้ยิ่งสูง ทั้งหมดนี้คือ "การฝึก tokenizer"

7. Tokenizer เป็นขั้นตอนแยกจาก LLM (~39:40–42:50)

ผู้สอนย้ำว่าทั้งหมดที่ทำมายังไม่ได้แตะ LLM เลย tokenizer เป็นวัตถุแยก มีชุดข้อความฝึกของตัวเองซึ่งอาจต่างจากชุดฝึกของ LLM ฝึกด้วย BPE ครั้งเดียวตอนเริ่ม เมื่อได้ vocab กับ merges แล้วก็ทำได้สองทาง: encode (ข้อความ → token) และ decode (token → ข้อความ) เป็นชั้นแปลระหว่างข้อความดิบ (ลำดับ code point) กับลำดับ token

LLM ถูกฝึกเป็นขั้นที่สอง ระบบระดับแนวหน้ามักแปลงข้อมูลฝึกทั้งหมดเป็นลำดับ token ยาวมหาศาลเก็บลงดิสก์ แล้วทิ้งข้อความดิบ LLM อ่านเฉพาะ token ตอนฝึก

ส่วนผสมของชุดฝึก tokenizer สำคัญ: ต้องคิดถึงหลายภาษาและโค้ด เพราะปริมาณของแต่ละภาษาในชุดฝึกกำหนดว่าภาษานั้นจะได้ merges มากแค่ไหน เช่นถ้าใส่ภาษาญี่ปุ่นเยอะ ภาษาญี่ปุ่นจะได้ token ที่รวมแล้วมากขึ้น ลำดับสั้นลง ซึ่งดีต่อ LLM ที่มี context จำกัด

ผู้จัดทำ: ข้อนี้อธิบายตัวอย่างภาษาเกาหลีในส่วนที่ 2 และภาษาไทยได้เหมือนกัน ถ้าชุดฝึก tokenizer มีภาษาไทยน้อย ตัวอักษรไทยแต่ละตัวที่กิน 3 ไบต์จะรวมกันได้น้อย

8. ขั้นที่ 5–6: decode และ encode (~42:50–57:00)

decode (id → ข้อความ):

  1. สร้าง vocab: dict จาก id → bytes เริ่มที่ vocab[i] = bytes([i]) สำหรับ 0–255 แล้วไล่ merges ตามลำดับที่ใส่ vocab[idx] = vocab[p0] + vocab[p1] (ต่อ bytes) ผู้สอนเตือนว่าต้องวนตามลำดับที่ใส่ ซึ่ง dict ของ Python รับประกันตั้งแต่ 3.7
  2. เอา bytes ของทุก id มาต่อกัน แล้ว .decode("utf-8") กลับเป็นสตริง

กับดัก: decode([97]) ได้ "a" แต่ decode([128]) พัง: invalid start byte เพราะ 128 ในเลขฐานสองคือ 1 ตามด้วยศูนย์ทั้งหมด ซึ่งไม่ตรงรูปแบบใด ๆ ของ UTF-8 (ผู้จัดทำ: ไบต์นำของตัวหลายไบต์ต้องขึ้นต้นด้วย 11…) ลำดับไบต์ไม่ใช่ทุกลำดับที่เป็น UTF-8 ที่ถูกต้อง ถ้า LLM ทาย token ออกมาแปลก ๆ ก็อาจถอดไม่ได้ วิธีมาตรฐานคือ errors="replace" ซึ่งแทนด้วยตัว � (โค้ดที่ OpenAI ปล่อยก็ทำแบบนี้) ถ้าเห็น � ในผลลัพธ์แปลว่าโมเดลออก token ที่ไม่ถูกต้อง

encode (ข้อความ → id):

  1. แปลงเป็นไบต์ UTF-8 แล้วเป็น list ของเลข
  2. วนไปเรื่อย ๆ: ใช้ get_stats เอาแค่ชุดของคู่ที่มีอยู่ (ไม่สนจำนวน)
  3. เลือกคู่ที่มีลำดับใน merges ต่ำสุด: min(stats, key=lambda p: merges.get(p, float("inf"))) เพราะกฎยุคแรกต้องใช้ก่อน (กฎหลังอาจอ้าง token เช่น 256 ที่เกิดจากกฎแรก) คู่ที่ไม่อยู่ใน merges ได้ค่าอนันต์ จึงไม่ถูกเลือก
  4. ถ้าคู่ที่ได้ไม่อยู่ใน merges แปลว่าไม่เหลืออะไรให้รวม → หยุด ไม่งั้น merge ด้วย id ของคู่นั้นแล้ววนต่อ
  5. กรณีพิเศษ: ถ้ามีไม่ถึง 2 token (ตัวเดียวหรือว่าง) ไม่มีคู่ให้นับ ให้คืนค่าเลย ไม่งั้น min ของ dict ว่างจะพัง

ทดสอบ: encode แล้ว decode ควรได้สตริงเดิม (ผู้สอนคิดว่าน่าจะจริงในกรณีทั่วไป) ใช้ได้ทั้งข้อความที่ใช้ฝึกและข้อความ "validation" ที่ tokenizer ไม่เคยเห็น แต่ทางกลับกัน (decode แล้ว encode) ไม่จำเป็นต้องได้เดิม เพราะไม่ใช่ทุกลำดับ token ที่ถอดเป็น UTF-8 ได้ พารามิเตอร์ทั้งหมดของ tokenizer คือ dict merges เท่านั้น

# ผู้จัดทำเขียนใหม่ ทำงานแบบเดียวกับในคลิป
def decode(ids, vocab):
    return b"".join(vocab[i] for i in ids).decode("utf-8", errors="replace")

def encode(text, merges):
    ids = list(text.encode("utf-8"))
    while len(ids) >= 2:
        stats = get_stats(ids)
        pair = min(stats, key=lambda p: merges.get(p, float("inf")))   # กฎที่เก่าที่สุดก่อน
        if pair not in merges:
            break                                                       # ไม่มีคู่ไหนรวมได้แล้ว
        ids = merge(ids, pair, merges[pair])
    return ids

9. GPT-2: ใช้ regex แบ่งชิ้นก่อนรวม (~57:00–1:11:40)

เปเปอร์ GPT-2 (2019) อธิบายเหตุผลของ BPE ระดับไบต์ตรงกับที่ทำมา แต่เพิ่มอีกชั้น: คำที่เจอบ่อยอย่าง dog อยู่ติดกับเครื่องหมายหลายแบบ (dog. dog! dog?) BPE แบบตรง ๆ อาจรวมเป็น token แยกกันหลายตัว ซึ่งปนความหมายกับเครื่องหมาย ไม่ดีตามการทดลองของเขา จึงบังคับจากบนลงล่างว่าอักขระบางประเภทห้ามรวมกัน

ในไฟล์ encoder.py (ผู้สอนบ่นว่าชื่อไม่ตรง เพราะมันคือ tokenizer ทั้งตัว) มี regex ที่ใช้แพ็กเกจ regex (import เป็น re) ซึ่งรองรับ \p{L} ได้:

's|'t|'re|'ve|'m|'ll|'d| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+
  1. re.findall เดินจากซ้ายไปขวา ลองแต่ละทางเลือก (คั่นด้วย |) "Hello world how are you" ได้ 5 ชิ้น: "Hello", " world", " how", " are", " you"
  2. แต่ละชิ้น encode แยกกัน แล้วเอาผลมาต่อกัน → รวมได้เฉพาะภายในชิ้น เช่น e ท้ายคำจะไม่มีวันรวมกับช่องว่างที่ตามมา
  3. ?\p{L}+ = ช่องว่างไม่บังคับ + ตัวอักษรภาษาใดก็ได้ · ?\p{N}+ = ตัวเลข → "world123" แยกเป็น " world" กับ "123"
  4. apostrophe: 's 't 're 've 'm 'll 'd แยกออก แต่ใช้ได้แค่ apostrophe แบบ ASCII ถ้าใช้ apostrophe ของ Unicode จะไม่ตรง และเพราะไม่ได้ใส่ ignore case "HOUSE'S" แบบตัวใหญ่จึงแยกไม่เหมือนตัวเล็ก (ในโค้ดเองก็มีคอมเมนต์ว่าควรใส่ re.IGNORECASE) ผู้สอนยังสงสัยว่ากฎนี้เจาะจงภาษาอังกฤษเกินไป
  5. ?[^\s\p{L}\p{N}]+ = เครื่องหมายวรรคตอน (ไม่ใช่ตัวอักษร ตัวเลข หรือช่องว่าง)
  6. \s+(?!\S) = ช่องว่างหลายตัวยกเว้นตัวสุดท้าย (negative lookahead) ช่องว่างตัวสุดท้ายจึงไปติดกับคำถัดไปเป็น " you" ซึ่งเป็น token ที่พบบ่อย GPT-2 ชอบรูปแบบ "ช่องว่าง + ตัวอักษร/ตัวเลข" อย่างสม่ำเสมอ · \s+ สุดท้ายจับช่องว่างท้ายข้อความที่เหลือ

ไม่ได้มีแค่ regex + BPE: ในโค้ด Python ช่องว่างหลายตัวกลายเป็นชิ้นเดียว แต่ใน tiktokenizer ทุกช่องว่างยังเป็น 220 แยกกัน ผู้สอนคิดว่า OpenAI มีกฎเพิ่มที่ไม่บอก ห้ามรวมช่องว่าง และ OpenAI ไม่เคยปล่อยโค้ดฝึก ของ GPT-2 tokenizer ปล่อยแค่โค้ด inference ที่เอา merges ไปใช้กับข้อความใหม่ จึงไม่รู้แน่ว่าฝึกอย่างไร

10. tiktoken, regex ของ GPT-4 และ encoder.py ของ GPT-2 (~1:11:40–1:18:40)

tiktoken คือไลบรารีทางการของ OpenAI (pip install tiktoken) ใช้ได้เฉพาะ inference ไม่มีโค้ดฝึก เรียกใช้ง่าย ได้ token ของ GPT-2 หรือ GPT-4 ตัวอย่างเดิม: ช่องว่างใน GPT-2 ไม่ถูกรวม แต่ใน GPT-4 ถูกรวม

ไฟล์ tiktoken_ext/openai_public.py เก็บนิยามของ tokenizer แต่ละรุ่น (ต้องเปิดเผย regex เพราะใช้ตอน inference) regex ของ GPT-2 ในไฟล์นี้หน้าตาต่างแต่ทำงานเหมือนเดิม แค่เร็วกว่า ส่วน cl100k_base (GPT-4) เปลี่ยน regex หลัก ๆ คือ:

  • (?i:…) — จับ 's 'd 'm … ทั้งตัวเล็กและตัวใหญ่ แก้ปัญหาที่คอมเมนต์ของ GPT-2 พูดไว้
  • จัดการช่องว่างต่างไป (ผู้สอนไม่ลงรายละเอียด แนะนำให้เปิดเอกสาร regex ไล่ดูเอง)
  • \p{N}{1,3} — ตัวเลขรวมได้ไม่เกิน 3 หลักต่อชิ้น ป้องกัน token ที่เป็นเลขยาว ๆ
  • คลังโตจากราว 50k เป็นราว 100k · ทั้งหมดนี้ไม่มีเอกสาร รู้แค่ pattern

encoder.py ของ GPT-2: โหลดสองไฟล์ encoder.json กับ vocab.bpe สองไฟล์นี้คือ tokenizer ที่บันทึกไว้ทั้งตัว encoder ของเขา = vocab ของเรา (แต่กลับทิศ: สตริง → id) และ vocab.bpe = merges ของเรา มีแค่สองตัวแปรนี้ก็ encode / decode ได้ สิ่งที่สับสนคือมี byte_encoder / byte_decoder ซ้อนอีกชั้น (ทำก่อน encode และหลัง decode) ผู้สอนบอกว่าเป็นรายละเอียดที่ไม่จำเป็นและไม่น่าสนใจ ข้ามได้ แกนกลางคือฟังก์ชัน bpe ที่วนหาคู่ (bigram) ที่ควรรวมถัดไปแล้วรวมจนหมด เหมือน while loop ของเรา โค้ดรก แต่อัลกอริทึมเหมือนกัน

11. Special token และการผ่าตัดโมเดลเมื่อเพิ่ม token (~1:18:40–1:25:40)

นอกจาก token จากไบต์และ merges ยังแทรก special token เพื่อคั่นส่วนต่าง ๆ ของข้อมูลหรือสร้างโครงสร้างของลำดับ token ได้

นับเลข GPT-2: encoder มี 50,257 รายการ = 256 ไบต์ + 50,000 merges + 1 special token คือ <|endoftext|> (id 50256 ตัวสุดท้าย) ใช้คั่นระหว่างเอกสารในชุดฝึก บอกโมเดลว่าเอกสารจบแล้ว สิ่งที่ตามมาไม่เกี่ยวกัน โมเดลต้องเรียนรู้เองจากข้อมูลว่าเจอ token นี้แล้วควร "ล้างความจำ" ใน tiktokenizer พิมพ์ <|endoftext|> ยังไม่ครบก็ยังเป็นหลาย token พอพิมพ์ครบจึงกลายเป็น 50256 เพราะไม่ได้ผ่าน BPE โค้ดของ tiktoken (เขียนด้วย Rust) มีการจัดการพิเศษสำหรับ token เหล่านี้ ซึ่งไม่มีใน encoder.py

แชต: นอกจากคั่นเอกสาร ยังใช้คั่นบทสนทนาระหว่างผู้ใช้กับผู้ช่วยตอน fine-tune เช่น tokenizer ของ GPT-3.5-turbo มี <|im_start|>, <|im_end|> (im = imaginary monologue) คั่นต้นและท้ายทุกข้อความ tiktoken ยอมให้ fork cl100k_base แล้วเพิ่ม special token ของเราเองด้วย id ใหม่

GPT-4 (cl100k_base): มี endoftext เหมือนเดิม (100257) เพิ่ม FIM_PREFIX / FIM_MIDDLE / FIM_SUFFIX (100258–100260, FIM = fill in the middle มาจากเปเปอร์หนึ่ง ผู้สอนไม่ลงรายละเอียด) และ ENDOFPROMPT (100276)

เพิ่ม special token = ผ่าตัดโมเดลเล็กน้อย: (1) ตาราง embedding ต้องเพิ่มแถว เริ่มด้วยค่าสุ่มเล็ก ๆ (2) ชั้นสุดท้ายที่ฉายไปยังคลังต้องเพิ่มอีกหนึ่งช่อง เป็นงานทั่วไป โดยเฉพาะตอนแปลงโมเดลพื้นฐานเป็นโมเดลแชตอย่าง ChatGPT

12. แบบฝึก minbpe: สร้าง tokenizer ของ GPT-4 เอง (~1:25:40–1:28:50)

ระหว่างทำคลิป ผู้สอนเขียนโค้ดไว้ใน repo minbpe (จะปรับต่อเรื่อย ๆ) และเขียน exercise.md แบ่งงานเป็น 4 ขั้น ที่ไต่ขึ้นไปจนเป็น tokenizer แบบ GPT-4 ติดตรงไหนให้ดูเทสต์หรือโค้ดใน minbpe ซึ่งพยายามเขียนให้อ่านง่าย

  • เป้าหมาย: encode สตริงแล้วได้ token ตรงกับ tiktoken ของ GPT-4 และ encode → decode กลับได้สตริงเดิม
  • เขียนฟังก์ชัน train เอง (ซึ่ง tiktoken ไม่มี) เพื่อฝึกคลังของตัวเองได้

เทียบคลัง: 256 ตัวแรกเป็นไบต์เดี่ยว merge แรกของ GPT-4 คือช่องว่างสองตัวรวมเป็น token 256 ผู้สอนฝึก minbpe บนหน้า Wikipedia ของ Taylor Swift (เพราะเป็นหน้าที่ยาวที่สุดหน้าหนึ่ง) แล้วเทียบ: GPT-4 รวม i + n เป็น "in" และ minbpe ก็รวมเหมือนกันที่ id 259 " t" ก็เกิดในทั้งสองแต่คนละลำดับ ความต่างมาจากชุดข้อมูลฝึกเป็นหลัก เช่น GPT-4 มีการรวมช่องว่างเยอะ ผู้สอนเดาว่าชุดฝึก tokenizer ของ GPT-4 มีโค้ด Python มาก

13. sentencepiece ที่ Llama 2 ใช้ (~1:28:50–1:43:30)

sentencepiece (Google) นิยมเพราะทั้งฝึกและ inference ได้และเร็ว รองรับหลายอัลกอริทึมรวมถึง BPE ใช้ในโมเดลตระกูล Llama และ Mistral

ต่างจาก tiktoken ตรงลำดับขั้น: tiktoken แปลง code point เป็นไบต์ UTF-8 ก่อนแล้วรวมไบต์ ส่วน sentencepiece รวมบนระดับ code point โดยตรง code point ที่หายาก (กำหนดด้วย character_coverage) จะกลายเป็น <unk> หรือถ้าเปิด byte_fallback จะถูกแปลงเป็นไบต์ UTF-8 แล้วใช้ byte token แทน ผู้สอนเห็นว่าแบบ tiktoken สะอาดกว่ามาก

  1. ตั้งค่า: เตรียม toy.txt (คำอธิบายของ sentencepiece เอง) ตัวเลือกเยอะมากเพราะไลบรารีอยู่มานานและมี "ภาระทางประวัติศาสตร์" บางตัวไม่เกี่ยวกับ BPE (เช่น shrinking_factor) ผู้สอนเปิดไฟล์ tokenizer.model ที่ Meta ปล่อยด้วย protobuf แล้วลอกค่าที่เกี่ยวข้องให้เหมือน Llama 2 ที่สุด: model_type BPE, vocab_size 400
  2. normalization: สมัยก่อน NLP นิยมทำตัวเล็ก ตัดช่องว่างซ้ำ ฯลฯ แต่ในงาน LLM ผู้สอนอยากเก็บข้อมูลดิบไว้มากที่สุด จึงพยายามปิด
  3. แนวคิด "ประโยค": sentencepiece มองว่าฝึกบนประโยคอิสระหลายประโยค (จำนวนประโยค ความยาวสูงสุด สับลำดับ) ผู้สอนเห็นว่าไม่สมเหตุสมผลกับ LLM เพราะนิยาม "ประโยค" ยาก อยากมองไฟล์เป็นสายไบต์ยาวก้อนเดียว · มีกฎแยกตัวเลข แยกช่องว่าง คล้าย regex ของ tiktoken
  4. คลังที่ได้เรียงแบบนี้: special token ก่อน (<unk> = 0, <s> = 1, </s> = 2, pad = −1 คือไม่ใช้) → byte token 256 ตัว (เพราะ Llama เปิด byte_fallback) → merges (เห็นแต่ตัวพ่อ) → code point เดี่ยวที่เจอในชุดฝึก (ตัวที่หายากมากถูกทิ้ง) · <unk> ต้องมีเสมอ
  5. encode ภาษาเกาหลี: ไม่อยู่ในชุดฝึก จึงไม่มี token แต่ byte_fallback ทำให้กลายเป็นไบต์ UTF-8 (id เลื่อนไป 3 เพราะ special token 3 ตัวแรก) ถ้าปิด byte_fallback แล้วฝึกใหม่ byte token หายไป ได้ merges เพิ่ม แต่ข้อความเกาหลีทั้งก้อนกลายเป็น 0 (unk) ซึ่งไม่ดีต่อโมเดล ผู้สอนคิดว่า Llama เปิดไว้ถูกแล้ว
  6. ช่องว่างแสดงเป็น ▁ (ผู้สอนไม่แน่ใจว่าทำไม อาจเพื่อให้มองเห็น) และมีช่องว่างเกินหน้า "hello" มาจาก add_dummy_prefix · เหตุผล: ใน tiktoken "world" ต้นประโยคกับ " world" กลางประโยคเป็นคนละ token ตัวเลือกนี้เติมช่องว่างหน้าข้อความให้ทั้งสองกลายเป็น " world" เหมือนกัน Llama 2 เปิดใช้

สรุปของผู้สอน: ใช้กันแพร่หลายเพราะมีประสิทธิภาพ แต่มีภาระเก่าเยอะ (เช่นเรื่องประโยคและความยาวสูงสุด) มีจุดแปลก (ต้องมี unk, วิธีทำ byte fallback) และเอกสารไม่ดี ผู้สอนต้องใช้เวลามากในการลองเองจึงเข้าใจ แนบค่า protobuf ของ Llama 2 ไว้ใน notebook ให้ลอกได้

14. ขนาดคลัง, การเพิ่ม token และข้อมูลหลายรูปแบบ (~1:43:30–1:51:40)

กลับไปดู gpt.py จากคลิปก่อน: vocab_size (ตอนนั้นราว 65) โผล่แค่สองที่ คือ ตาราง embedding (vocab_size แถว แถวละ n_embd ค่า) และ lm_head ชั้น linear สุดท้ายที่ให้ logits → ความน่าจะเป็นของทุก token ที่อาจมาถัดไป token ยิ่งมาก ยิ่งต้องทำ dot product มากขึ้นในชั้นนี้

ทำไมคลังใหญ่ไม่ได้ไม่จำกัด:

  1. ตาราง embedding และ lm_head โต → คำนวณแพงขึ้น
  2. พารามิเตอร์มากขึ้น แต่ละ token โผล่ในข้อมูลฝึกน้อยลง → เวกเตอร์ของ token เหล่านั้นอาจฝึกไม่พอ (ตัวอย่างคลังหนึ่งล้าน token)
  3. ลำดับสั้นลง (ดี ได้มองข้อความยาวขึ้น) แต่ถ้าอัดข้อความยาวเกินไปลงใน token เดียว โมเดลอาจมีเวลาคิดต่อจำนวนตัวอักษรไม่พอ การส่งผ่านหนึ่งรอบประมวลผลได้ไม่พอ

เป็น hyperparameter ที่หาจากการทดลอง ระบบระดับแนวหน้าตอนนั้นอยู่ที่หลักหมื่นปลาย ๆ ถึงราว 100,000

เพิ่ม token ให้โมเดลที่ฝึกแล้ว: ทำกันบ่อย เช่นตอน fine-tune เป็น ChatGPT ต้องมี special token ใหม่สำหรับโครงสร้างบทสนทนา หรือการใช้เครื่องมืออย่างเบราว์เซอร์ วิธี: เพิ่มแถว embedding (ค่าสุ่มเล็ก ๆ) และขยายน้ำหนักของ lm_head เป็นการผ่าตัดเบา ๆ มักแช่แข็งโมเดลเดิม แล้วฝึกแค่พารามิเตอร์ใหม่

gist token: เปเปอร์ที่บีบ prompt ยาวให้เหลือ token ใหม่ไม่กี่ตัว: แช่แข็งโมเดลทั้งตัว ฝึกเฉพาะ embedding ของ token ใหม่ด้วย distillation ให้พฤติกรรมเหมือนตอนใส่ prompt ยาว ตอนใช้งานทิ้ง prompt เดิมแล้วใส่ token เหล่านี้แทน ได้ผลเกือบเท่าเดิม เป็น parameter-efficient fine-tuning แบบที่ไม่แตะน้ำหนักโมเดลเลย (ไม่ใช่ LoRA)

หลายรูปแบบข้อมูล (ภาพ วิดีโอ เสียง): แนวโน้มคือไม่เปลี่ยนสถาปัตยกรรม ใช้ Transformer เดิม แค่แปลงข้อมูลอื่นเป็น token แล้วทำทุกอย่างเหมือนข้อความ token อาจเป็นแบบ "แข็ง" (บังคับเป็นจำนวนเต็ม) หรือ "อ่อน" (ไม่บังคับ แต่ผ่านคอขวดแบบ autoencoder) ตัวอย่าง Sora ของ OpenAI: LLM มี text token, Sora มี visual patch ใช้ได้ทั้งกับ autoregressive model (token แข็ง) และ diffusion model (token อ่อน)

15. ย้อนดูความแปลกของ LLM ที่มาจาก tokenization (~1:51:40–2:10:20)

  • สะกดคำ: ".DefaultCellStyle" เป็นtoken เดียวใน GPT-4 ถาม "มี l กี่ตัว" ได้ 3 (จริง 4) ให้กลับลำดับตัวอักษร (โมเดลพยายามใช้ code interpreter แต่ผู้สอนสั่งให้ทำเอง) ก็ได้ผลมั่ว แต่ถ้าสั่งให้ (1) พิมพ์ทีละตัวคั่นด้วยช่องว่างก่อน แล้ว (2) กลับลำดับ ทำได้ถูก เพราะพอแตกเป็นตัวเดี่ยวแล้วโมเดลเห็นทีละตัว
  • ภาษาที่ไม่ใช่อังกฤษ: นอกจากข้อมูลฝึกโมเดลน้อยกว่า tokenizer ก็ฝึกด้วยภาษาอื่นน้อย "hello how are you" 5 token แต่คำแปลเกาหลี 15 token (3 เท่า) "안녕하세요" ซึ่งเป็นคำทักทายพื้นฐานยังใช้ 3 token ขณะที่ "hello" ใช้ 1
  • เลขคณิต: การบวกเป็นอัลกอริทึมระดับหลัก (หลักหน่วย สิบ ร้อย) แต่ตัวเลขถูกตัดตามที่บังเอิญรวมได้ บทความ "Integer tokenization is insane" สำรวจเลข 4 หลัก (ผู้สอนเข้าใจว่าเป็นของ GPT-2) บางตัวเป็น token เดียว บางตัวแตก 1+3, 2+2, 3+1 แบบไม่มีกฎ Llama 2 (sentencepiece) จึงแยกตัวเลขทีละหลัก ส่วนหนึ่งเพื่อช่วยเลขคณิต
  • Python ใน GPT-2: ช่องว่างตัวละ token ทำให้ context หดมาก เกือบเป็น "บั๊กของ tokenizer" ที่ GPT-4 แก้แล้ว
  • <|endoftext|> ใน prompt: สั่ง GPT-4 ให้พิมพ์สตริงนี้ แล้วโมเดลเหมือนมองไม่เห็นหรือพิมพ์ไม่ออก ผู้สอนไม่รู้ว่าข้างในทำอะไร แต่เดาว่าอาจ parse ข้อความผู้ใช้ โดยอนุญาต special token ซึ่งไม่ควร เพราะข้อความผู้ใช้เป็นสิ่งที่ผู้โจมตีควบคุมได้ ความรู้เรื่อง special token จึงเป็นช่องโจมตีได้
  • ช่องว่างท้ายข้อความ: ใน Playground ของ gpt-3.5-turbo-instruct (โมเดล completion) ใส่ "Here's a tagline for an ice cream shop" แล้วเว้นวรรคท้าย จะมีคำเตือน เพราะใน GPT ช่องว่างอยู่หน้า token เช่น " o" = 8840 ถ้าเราใส่ช่องว่างเอง มันกลายเป็น token 220 ตัวเดี่ยวที่โมเดลแทบไม่เคยเห็น → หลุดจากการกระจายของข้อมูล ผลแย่
  • token ครึ่งตัว: ใส่ ".DefaultCellSta" (ตัดท้าย) ให้เติม โมเดลตอบ stop sequence ทันที (ไม่มีผลลัพธ์) ลองอีกครั้งเติมได้แต่ถูก flag ว่าอาจผิดนโยบาย เพราะผู้สอนเชื่อว่าในชุดฝึกคำนี้แทบจะเป็น token เดียวเสมอ ใน Rust ของ tiktoken มีโค้ดจัดการ "unstable tokens" จำนวนมากที่ไม่มีเอกสาร สิ่งที่ API completion ควรทำจริงคือค้นหาตัวอักษรที่ต่อแล้วน่าจะเป็น ไม่ใช่ต่อ token เต็มตัวถัดไป ผู้สอนบอกว่าเรื่องนี้ยุ่งมาก อาจทำเป็นคลิปแยก
  • SolidGoldMagikarp (ที่ผู้สอนชอบที่สุด): บล็อกโพสต์หนึ่งจับกลุ่ม token ตามเวกเตอร์ embedding แล้วเจอกลุ่ม token แปลก ๆ (เช่น " SolidGoldMagikarp", "StreamerBot") ถามโมเดลง่าย ๆ ให้พูดซ้ำสตริงนี้ โมเดลเลี่ยง หลอน หรือถึงขั้นด่ากลับ ฝ่าแนวทางความปลอดภัย คำอธิบายที่เชื่อกัน: เป็นชื่อผู้ใช้ Reddit ที่โพสต์เยอะ ชุดฝึก tokenizer มีข้อมูล Reddit มาก จึงได้ token เฉพาะ แต่ชุดฝึก LLM ไม่มีข้อมูลนั้น token นี้จึงไม่เคยถูกใช้ แถว embedding ค้างค่าสุ่มตั้งต้น เหมือนหน่วยความจำที่ไม่ได้จองในโปรแกรม C เรียกใช้ตอนทดสอบจึงเกิดพฤติกรรมที่ไม่นิยาม
  • รูปแบบข้อมูล: JSON กิน token เยอะ YAML ประหยัดกว่า ข้อมูลเดียวกัน 116 vs 99 token ในโลกที่จ่ายตาม token (ทั้งค่าเงินและ context) ควรวัดประสิทธิภาพของรูปแบบต่าง ๆ ใน tiktokenizer เสมอ

16. คำแนะนำสุดท้าย, จุดที่ caption ผิด และการใช้ใน ZVect (~2:10:20–2:12:50)

คำแนะนำของผู้สอน: ขั้นนี้น่าเบื่อแต่อย่าปัดทิ้ง มีกับดัก ขอบคม ปัญหาความปลอดภัย และปัญหา AI safety (เช่นส่ง "หน่วยความจำที่ไม่ได้จอง" เข้าโมเดล) "เกียรติยศนิรันดร์" เป็นของใครก็ตามที่กำจัดขั้นนี้ได้ สำหรับงานตอนนี้:

  1. ถ้าใช้ token และคลังของ GPT-4 ซ้ำได้ ให้พิจารณาก่อน และใช้ tiktoken ซึ่งเร็วสำหรับ inference ผู้สอนชอบ BPE ระดับไบต์แบบของ OpenAI
  2. ถ้าต้องฝึกคลังเอง ใช้ BPE ของ sentencepiece แต่ระวังค่าตั้ง (ผู้สอนไม่ชอบ byte fallback และการทำ BPE บน code point) ลอกค่าของ Meta หรือไล่โค้ดให้แน่ใจ ตั้งผิดอาจตัดประโยคทิ้งโดยไม่รู้ตัว และผู้สอนยังเห็นว่าอัลกอริทึมด้อยกว่าแบบ tiktoken
  3. สิ่งที่อยากได้จริงคือ tiktoken ที่มีโค้ดฝึก ซึ่งยังไม่มี minbpe เป็นตัวต้นแบบแต่ยังเป็น Python (ช้า) อาจมีคลิปขั้นสูงในอนาคต

ใช้ใน ZVect (ผู้จัดทำ): เนื้อหานี้เป็นแหล่งของบท 3.3 Tokenizer ของ GPT (byte-level BPE) ต่อจาก 3.2 BPE ซึ่งเริ่มจากตัวอักษร บทใหม่เปลี่ยนจุดเริ่มเป็นไบต์ UTF-8 (คลัง 256, token ใหม่เริ่มที่ 256) ให้เห็นว่าภาษาไทยกิน 3 ไบต์ต่อตัว เห็นอัตราบีบ, การ decode ด้วย errors="replace" และผลของการแบ่งด้วย regex ก่อนรวม เป็น playground ที่พิมพ์ข้อความแล้วกดเพิ่มรอบได้

Key Takeaways

  1. tokenizer เป็นขั้นแยกจาก LLM มีชุดฝึกของตัวเอง ฝึกครั้งเดียว แล้วแปลงข้อความ ↔ เลข token โมเดลเห็นแต่เลข
  2. GPT ใช้ BPE บนไบต์ UTF-8: เริ่มคลัง 256 ค่า รวมคู่ที่ติดกันบ่อยที่สุดเป็น id 256, 257, … ทุกข้อความแตกเป็นไบต์ได้ จึงไม่มีตัวที่ไม่รู้จัก (ข้อสรุปของผู้จัดทำ)
  3. พารามิเตอร์ของ tokenizer คือ merges (ตามลำดับ) กับ vocab: encode รวมคู่ที่กฎเก่าสุดก่อน decode ต่อไบต์แล้วถอด UTF-8 ด้วย errors="replace"
  4. regex แบ่งข้อความเป็นชิ้น (ตัวอักษร / เลข / เครื่องหมาย / ช่องว่าง) ก่อน BPE เพื่อไม่ให้รวมข้ามประเภท GPT-4 เปลี่ยนให้ 's 't … ไม่สนตัวพิมพ์ เลขไม่เกิน 3 หลัก และรวมช่องว่าง
  5. special token อย่าง <|endoftext|> ไม่ผ่าน BPE และการเพิ่ม token ต้องเพิ่มแถว embedding กับ lm_head
  6. ขนาดคลังเป็นการแลก: ใหญ่ขึ้น = ลำดับสั้น แต่คำนวณแพง token หายากฝึกไม่พอ (หลักหมื่นปลาย ๆ ถึงราว 100k)
  7. ความแปลกของ LLM เช่นสะกดคำ เลขคณิต ภาษาอื่น ช่องว่างท้าย SolidGoldMagikarp และ JSON ที่เปลือง token ล้วนอธิบายได้ด้วย tokenization
