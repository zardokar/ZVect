🧭 สรุปเชิงลึก

แก่นของคลิป: embedding คือชั้นแปลภาษาคนเป็นพิกัดในพื้นที่หลายมิติ ที่ระยะห่างแทนความต่างของความหมาย ถ้าโมเดลวางสองแนวคิดที่ต่างกันไว้ใกล้กัน ความผิดพลาดนั้นติดไปถึงปลายทาง ผู้ดำเนินรายการบอกว่านักพัฒนามักใช้เวลาหลายสัปดาห์ปรับ prompt แต่มองข้ามว่าคอขวดจริงอยู่ที่ตัวแทนข้อมูลใน latent space

RAG และ reranker: RAG พื้นฐานหั่นเอกสาร (เช่น 512 tokens) embed ด้วย bi-encoder ค้นด้วย cosine แล้วส่ง top-k ให้ LLM คลิปอ้างว่าแบบนี้ได้ faithfulness ราว 0.347 และถ้าเพิ่ม chunking ที่ดีกับ reranker จะขึ้นเป็นราว 0.797 เหตุผลคือ bi-encoder อัดทั้งเอกสารเป็นเวกเตอร์เดียวก่อนเห็นคำถาม ส่วน cross-encoder อ่านคำถามกับเอกสารพร้อมกันจึงแม่นกว่าแต่แพงมาก ระบบจริงจึงใช้ bi-encoder คัดผู้สมัครจำนวนมาก (คลิปยกตัวอย่าง 10,000) แล้วให้ cross-encoder จัดอันดับเฉพาะ 10–100 ชิ้นบนสุด และอันดับบน MTEB ซึ่งวัดบนข้อมูลทั่วไป ไม่ได้บอกว่าโมเดลจะรอดในงานเฉพาะทาง

clinical RAG ห้าขั้น (โจทย์ "ดึงทุกโรคของผู้ป่วย"): (1) chunk 500–800 tokens ซ้อน 10–20% และเก็บหัวข้อส่วน เพราะสถานะของโรคผูกกับหัวข้อ (2) ใช้ gemini-embedding-001 ที่มิติสูง เพื่อแยกโรคที่ความหมายใกล้กัน (3) ขยายคำค้นและเน้น recall ดึง 20–40 chunk (4) rerank และกรองคำปฏิเสธ เพราะ embedding มี "affirmative bias" มองข้ามคำว่า "ไม่" (5) สรุปเป็นโครงสร้าง FHIR หรือ JSON พร้อมสถานะและรหัส ICD

จุดบอดเรื่องตัวเลข: งานวิจัยที่ทดสอบ 13 โมเดลบนคำถามการเงินสังเคราะห์ 1,000 ข้อ พบความแม่นเฉลี่ย 54% ใกล้การเดา ทำได้ดีสุดกับทศนิยมหลักเดียว (ราว 62%) และแย่กับจำนวนเต็มสี่หลักหรือเปอร์เซ็นต์ embedder ที่สร้างจาก LLM ดีกว่าราว 5 จุด คลิปจึงแนะนำระบบ hybrid ที่ใช้ตัวคำนวณเชิงสัญลักษณ์หรือ metadata filter คู่กับ dense retrieval เมื่อคำถามเกี่ยวกับตัวเลข

เลือกตามงานและข้อจำกัด: บน Vertex AI มี gemini-embedding-001 (แม่นแต่เวกเตอร์ใหญ่ เปลือง RAM), text-embedding-005 (768 มิติ อังกฤษและโค้ด), text-multilingual-embedding-002 (768 มิติ) รวมถึงโมเดลเปิดจาก Model Garden และ multimodalembedding@001 งาน classification ต้องการเส้นแบ่งระหว่างคลาสที่ชัด (RoBERTa, Qwen3 0.6B), อุปกรณ์เล็กใช้ EmbeddingGemma 300M, MRL ตัดเวกเตอร์ให้สั้นลงได้, งานหลายภาษาดู Qwen3-Embedding-8B และ BGE-M3 ซึ่งให้ dense, sparse และ multi-vector ในรอบเดียว fine-tune ด้วย contrastive learning และ hard negative เฉพาะเมื่อเป็นโดเมนเทคนิคสูงและเสี่ยงสูง เพราะปัญหา false negative และค่าติดป้ายแพง คลิปปิดด้วยทิศทางถัดไปคือ GraphRAG

ตรวจข้อเท็จจริง (เสริมจากผู้จัดทำ): 11 ข้อ ยืนยันได้ 7 ข้อ ยืนยันบางส่วน 4 ข้อ ไม่พบข้อที่ผิดทั้งหมด จุดที่ต้องแก้: gemini-embedding-001 มี 3072 มิติ (caption ได้ยินเป็น "372"), ค่า 0.347 ในงานวิจัยคือ LLM ที่ไม่มีการค้นเลย (RAG พื้นฐานได้ 0.621) และงานนั้นใช้เอกสารนโยบายสาธารณสุข ไม่ใช่ข้อมูลคลินิก, งานวิจัยเรื่องตัวเลขชื่อ EmbedNum-1K, และ EmbeddingGemma มี 308M พารามิเตอร์

1. ทำไม embedding model คือเพดานของระบบ และแหล่งที่คลิปใช้

~0:00–1:54

ผู้ดำเนินรายการสองคนเปิดตอนด้วยคำถามเดียว: จะเลือก embedding model อย่างไร โดยไม่ฟังคำโฆษณา เหตุผลที่เรื่องนี้สำคัญคือ embedding model กำหนดเพดานของความฉลาดและความแม่นของทั้งระบบ ต่อให้ใช้โมเดลให้เหตุผลที่เก่งที่สุด ถ้าชั้นค้นข้อมูลวางข้อความผิดที่ใน "พื้นที่เรขาคณิต" ตั้งแต่ต้น โมเดลภาษาก็ทำงานโดยมองไม่เห็นข้อมูลที่ถูก

คนหนึ่งเรียก embedding ว่าโครงสร้างพื้นฐานที่เงียบ: นักพัฒนาใช้เวลาเป็นสัปดาห์ปรับ prompt และพารามิเตอร์ตอนสร้างคำตอบ แต่มองข้ามว่าคอขวดจริงคือตัวแทนของข้อมูลต้นทางใน latent space ถ้าโมเดลจัดสองแนวคิดที่ต่างกันไว้เป็นกลุ่มเดียวกัน การปรับ prompt ปลายทางก็แยกมันออกจากกันไม่ได้ เพราะความผิดนั้นฝังอยู่ในข้อมูลแล้ว

แหล่งที่คลิปใช้ (~1:15)

  • งานวิจัยเรื่องความสามารถด้านตัวเลขของ embedding (caption ได้ยินเป็น "embedded 1K" ชื่อจริงคือ EmbedNum-1K)
  • survey ทางวิชาการเรื่องใช้ LLM เป็นตัวสร้าง embedding
  • เอกสาร Vertex AI ล่าสุดของ Google Cloud
  • playbook เฉพาะทางสำหรับ clinical RAG ซึ่งผู้ดำเนินรายการบอกว่าเป็นจุดที่เห็นระบบพังได้ชัด

เป้าหมายคือให้ภาพการใช้งานจริง ไม่ว่าจะสร้าง semantic search ระดับองค์กร ระบบแนะนำ หรือ pipeline ข้อมูลของตัวเอง

2. จาก word2vec ถึง transformer และ RAG แบบพื้นฐาน

~1:55–3:13

เริ่มจากสถาปัตยกรรม: โมเดลยุคก่อนอย่าง word2vec (caption: "word tuve") เป็นแบบคงที่และไม่ดูบริบท คำว่า "bank" ได้พิกัดเดียวกันไม่ว่าจะหมายถึงธนาคารหรือริมฝั่งแม่น้ำ ตอนนี้เราอยู่ในยุค transformer ซึ่งได้ตัวแทนที่ขึ้นกับบริบท จากสองทาง: ใช้ encoder โดยเฉพาะอย่าง BERT หรือใช้ decoder เต็มชุดของ LLM สมัยใหม่

ผู้ดำเนินรายการนิยาม embedding ว่าเป็นชั้นแปลจากภาษาคนไปเป็นระบบพิกัดต่อเนื่องหลายมิติ ที่ระยะห่างเท่ากับความคล้ายทางความหมาย และบอกว่าการเข้าใจว่าพื้นที่นี้สร้างอย่างไร เป็นพื้นฐานก่อนจะเข้าใจ RAG

RAG แบบพื้นฐาน (~2:43)

  1. หั่นเอกสารเป็นชิ้น (chunk) ขนาดจัดการได้ เช่น 512 tokens
  2. ส่งแต่ละชิ้นผ่าน bi-encoder หรือ embedding model แล้วเก็บเวกเตอร์ใน vector database
  3. ตอนใช้งาน embed คำถามของผู้ใช้ลงในพื้นที่เดียวกัน วัดด้วยตัวชี้วัดเช่น cosine similarity แล้วดึง top-k ชิ้นที่ใกล้ที่สุด
  4. ส่งชิ้นเหล่านั้นให้ LLM เป็น context

คำอธิบายใต้คลิปยังพูดถึงวิธีนับสถิติยุคแรก (count-based) และ quantization แต่เสียงพูดไม่ได้ลงรายละเอียดสองเรื่องนี้

คลิปบอกว่าวงการขยับเลยแบบนี้ไปแล้ว เพราะปัญหาด้านความซื่อตรงต่อ context (faithfulness)

3. faithfulness: RAG พื้นฐาน เทียบ RAG ขั้นสูงที่มี reranker

~3:14–3:59

ผู้ดำเนินรายการยกตัวเลขความน่าเชื่อถือของคำตอบ: RAG พื้นฐานได้ค่า faithfulness ของ LLM ราว 0.347 และตีความว่าโมเดลแต่งข้อมูลหรืออ่าน context ผิดมากกว่า 60% ของเวลา

ทางแก้คือขยับไปเป็น advanced RAG: ปรับกลยุทธ์ chunking ให้ดี และเพิ่มขั้น re-ranking โดยเฉพาะ เมื่อทำทั้งสองอย่าง คลิปบอกว่าค่า faithfulness ขึ้นเป็น 0.797 ซึ่งเป็นการกระโดดครั้งใหญ่ และเป็นเหตุผลที่ส่วนถัดไปต้องอธิบายว่า reranker ทำงานต่างจากการค้นแบบแรกอย่างไร

เสริมจากผู้จัดทำ งานวิจัยที่มีตัวเลขชุดนี้ (Maharjan และ Yadav, มกราคม 2026) ทดสอบบนเอกสารนโยบายสาธารณสุขของ CDC และรายงานสามค่า: LLM ที่ไม่มีการค้นเลย 0.347, RAG พื้นฐาน 0.621 และ RAG ขั้นสูงที่มี cross-encoder rerank 0.797 คลิปจึงเรียกค่า 0.347 ผิดแบบ และคำว่า "แต่งข้อมูลมากกว่า 60% ของเวลา" เป็นการตีความของผู้ดำเนินรายการ ค่า faithfulness (เช่นใน RAGAS) วัดสัดส่วนข้ออ้างในคำตอบที่หาหลักฐานใน context ได้ ไม่ได้วัดสัดส่วนของ "ครั้ง" ที่ตอบผิด

4. bi-encoder กับ cross-encoder และข้อควรระวังของ MTEB

~4:00–5:59

bi-encoder (~4:04)

ประมวลผลคำถามและเอกสารแยกกันโดยสิ้นเชิง embed คำถาม embed เอกสาร แล้วเทียบสองเวกเตอร์ (คลิปบอกว่าเป็นแค่ dot product) เร็วมากและขยายได้ คัดจากเอกสารหลักล้านชิ้นได้ในระดับมิลลิวินาที

cross-encoder (~4:20)

ป้อนคำถามและเอกสารพร้อมกันเข้ากลไก attention เพื่อดูปฏิสัมพันธ์ระดับ token แต่ต้นทุนคำนวณสูงมาก ผู้ดำเนินรายการเรียกว่าความซับซ้อนแบบ quadratic หรือ O(n²)

เมื่อถูกถามว่าทำไมไม่ฝึก bi-encoder ให้แม่นขึ้นแทน คำตอบคือ bi-encoder ต้องอัดความหมายทั้งเอกสารลงเวกเตอร์ขนาดคงที่ก่อนจะเห็นคำถาม จึงเสียความสัมพันธ์ละเอียดระหว่างคำ ส่วน cross-encoder เห็นทั้งคู่พร้อมกัน เช่นรู้ได้ว่า "apple" ในคำถามโยงกับ "fruit" ในเอกสาร ไม่ใช่บริษัทคอมพิวเตอร์

ด้วยต้นทุนนี้ cross-encoder ใช้ค้นในคลังใหญ่ไม่ได้ pipeline มาตรฐานจึงเป็น: bi-encoder คัดผู้สมัครอย่างเร็ว (คลิปยกตัวอย่าง top 10,000 ชิ้น) แล้ว cross-encoder จัดอันดับอย่างแม่นเฉพาะ 10 ถึง 100 ชิ้นบนสุด

ข้อควรระวังเรื่อง leaderboard (~5:35)

ความต่างนี้ชี้ว่าการดูแค่ leaderboard ทั่วไปอย่าง MTEB (Massive Text Embedding Benchmark, caption: "MTB") ซ่อนความต้องการของงานจริงไว้ อันดับหนึ่งบนชุดข้อมูลภาษาอังกฤษทั่วไป ไม่ได้แปลว่าโมเดลจะใช้ได้ในสภาพแวดล้อมเฉพาะทาง ซึ่งนำไปสู่กรณีศึกษาถัดไป

เสริมจากผู้จัดทำ O(n²) คือต้นทุนของ self-attention ตามความยาวของข้อความที่รวมคำถามกับเอกสาร ปัญหาหลักในการค้นจริงคือ cross-encoder ต้องรันโมเดลเต็มหนึ่งรอบต่อคู่ (คำถาม, เอกสาร) และคำนวณล่วงหน้าไม่ได้ ส่วน bi-encoder คำนวณเวกเตอร์เอกสารเก็บไว้ก่อน ตอนค้นจึง encode แค่คำถาม งาน Sentence-BERT (Reimers และ Gurevych, 2019) แสดงช่องว่างนี้ไว้ชัด

5. clinical RAG ขั้น 1–2: chunking และการเลือกโมเดล

~6:00–8:18

เพื่อพิสูจน์ประเด็น ผู้ดำเนินรายการใช้กรณีเสี่ยงสูง: ระบบ clinical RAG ที่ผู้ใช้สั่งง่าย ๆ ว่าให้ดึงทุกภาวะโรคของผู้ป่วย โมเดลทั่วไปล้มในงานนี้ และความผิดพลาดของการค้นไม่ใช่แค่ผลค้นไม่ตรงแบบร้านค้าออนไลน์ แต่อาจเปลี่ยนแผนการรักษาได้ จึงต้องออกแบบ pipeline ที่แม่นสูงตั้งแต่การจัดการข้อมูลดิบ

ขั้น 1 chunking (~6:26)

สคริปต์สำเร็จรูปที่ตัดตายตัวทุก 512 tokens อาจหั่นความคิดทางการแพทย์ครึ่งกลาง เช่นวลี "ผู้ป่วยไม่ได้ตั้งครรภ์" ถูกแยกคำว่า "ไม่ได้" ออกจาก "ตั้งครรภ์" ไปอยู่คนละ chunk คลิปเรียกว่า semantic leakage ซึ่งทำข้อมูลเสียก่อน embedding model จะได้เห็น playbook ของบันทึกทางคลินิกกำหนด 500–800 tokens และซ้อนกัน 10–20% ที่สำคัญกว่าคือต้องเก็บหัวข้อส่วน เช่น [ASSESSMENT] หรือ [PAST MEDICAL HISTORY] เพราะการวินิจฉัยหนึ่งเป็นโรคที่เป็นอยู่หรือหายไปแล้ว 20 ปี ขึ้นกับหัวข้อที่มันอยู่

ขั้น 2 เลือก embedding model (~7:23)

embedding ทั่วไปล้มเพราะไม่รู้ศัพท์เฉพาะ เช่นไม่รู้ว่า "stat" ในโรงพยาบาลแปลว่า "ทันที" สำหรับ Google Cloud playbook แนะนำ gemini-embedding-001 เหตุผลคือจำนวนมิติ: แนวคิดทางการแพทย์อยู่ใกล้กันมาก เช่น ภาวะหัวใจล้มเหลว (congestive heart failure), cardiomyopathy และโรคหลอดเลือดหัวใจ (coronary artery disease) ผู้ดำเนินรายการบอกว่าโมเดล 768 มิติทั่วไปจะรวมกลุ่มพวกนี้แน่นจนระบบแยกไม่ออก ส่วนมิติที่มากกว่าให้ "ปริมาตร" พอจะแยกแนวคิดที่ใกล้แต่ต่างกันอย่างสำคัญ

เสริมจากผู้จัดทำ caption ได้ยินขนาดเป็น "372 dimensions" แต่ gemini-embedding-001 ให้เวกเตอร์สูงสุด 3072 มิติ (ปรับได้ 128–3072 ด้วย output_dimensionality และ Google แนะนำ 768, 1536 หรือ 3072) ส่วนคำกล่าวว่า 768 มิติ "แยกไม่ออก" เป็นความเห็นของผู้ดำเนินรายการ คุณภาพการแยกขึ้นกับการฝึกของโมเดลด้วย ไม่ใช่แค่จำนวนมิติ

6. clinical RAG ขั้น 3–5: ขยายคำค้น, คำปฏิเสธ และสรุปแบบมีโครงสร้าง

~8:19–10:35

ขั้น 3 retrieval และขยายคำค้น (~8:19)

กับดักคือเอาคำถามดิบ "ดึงทุกภาวะ" ไปค้นตรง ๆ แต่บันทึกทางคลินิกไม่ได้ใช้คำว่า condition เสมอ ระบบต้องขยายคำค้นเบื้องหลัง ไปเป็น patient diagnosis, chronic illnesses, active problems และอื่น ๆ หลักของขั้นนี้คือ recall มาก่อน precision: ดึง 20 ถึง 40 chunk เพื่อไม่ให้โรคใดหลุด เพราะสิ่งรบกวนกรองทีหลังได้ แต่การวินิจฉัยที่หลุดไปแล้วกู้คืนไม่ได้ตอนสร้างคำตอบ

ขั้น 4 reranking และคำปฏิเสธ (~9:02)

ผู้ดำเนินรายการบอกว่านี่อาจนับได้ว่าเป็นปัญหาใหญ่ที่สุดของ AI ทางคลินิก: ตัวแทนของ token ปฏิเสธใน latent space มี affirmative bias คือโมเดลเอนไปทาง "ใช่" เพียงเพราะคำนั้นปรากฏ โดยไม่สนคำว่า "ไม่" ที่อยู่ข้าง ๆ บันทึกที่เขียนว่า "denies diabetes" หรือ "rule out pneumonia" จึงถูก bi-encoder ดึงมา เพราะ token ของโรคมีน้ำหนักในเวกเตอร์มาก แม้ผู้ป่วยไม่ได้เป็น ต้องใช้ cross-encoder reranker หรือ LLM ตัวตรวจโดยเฉพาะ เพื่อตัดการวินิจฉัยที่ถูกปฏิเสธหรือยังไม่ยืนยันออกก่อนถึงผลลัพธ์ และย้ำว่าคอขวดอยู่ที่ตัวแทนของ token ด้านความปลอดภัยและคำปฏิเสธใน latent space

ขั้น 5 สรุปแบบมีโครงสร้าง (~9:55)

ใช้โมเดลสร้างข้อความรับ context ที่ผ่านการตรวจแล้ว ออกผลเป็นมาตรฐานข้อมูลสุขภาพ: FHIR (Fast Healthcare Interoperability Resources, caption: "FHI") ซึ่งเป็นภาษามาตรฐานของเวชระเบียนอิเล็กทรอนิกส์ หรืออย่างน้อยเป็น JSON schema ที่เข้มงวด ระบุสถานะ confirmed, active หรือ resolved พร้อมรหัส ICD สำหรับเบิกจ่าย

ผู้ดำเนินรายการชมว่าเป็น pipeline ที่รัดกุมเมื่อมันทำงาน แต่ทั้งหมดตั้งอยู่บนสมมติฐานว่า embedding model เข้าใจความสัมพันธ์ละเอียดในข้อความ

7. จุดบอดเรื่องตัวเลข (numeracy gap)

~10:36–13:29

คำถามเปลี่ยนผ่าน: ถ้าบันทึกเขียนว่าเนื้องอกโต 2 มิลลิเมตรแทน 20 ล่ะ ผู้ดำเนินรายการบอกว่านี่คือจุดบอดใหญ่ที่คนมองข้าม: embedding อ่านตัวเลขแย่มาก

งานวิจัยตัวเลขบนข้อความการเงิน (~10:50)

  • ทดสอบ embedding model ที่ใช้กันแพร่หลาย 13 ตัว บนคำถามการเงินสังเคราะห์ 1,000 ข้อ
  • ตัวอย่างโจทย์: ประโยค "นักลงทุน Alice ถือหุ้น 20%" กับ "ถือหุ้น 5%" ต่อคำถามที่หาคนถือเกิน 15%
  • ความแม่นเฉลี่ยของ 13 โมเดลคือ 54% แทบไม่ต่างจากโยนเหรียญ
  • รูปแบบตัวเลขมีผลมาก: ดีที่สุดกับทศนิยมหลักเดียวอย่าง 0.8 (ราว 62%) แต่พังกับจำนวนเต็มสี่หลักและเปอร์เซ็นต์
  • ส่วนหนึ่งเป็นความผิดของ tokenizer ที่หั่นตัวเลขจนความหมายของจำนวนหายก่อนถึงชั้น embedding
  • embedder ที่มาจาก LLM อย่าง Mistral และ Qwen (caption: "Quinn") ทำได้ดีกว่าโมเดล encoder แบบเดิมราว 5 จุด ผู้ดำเนินรายการอธิบายว่า LLM ได้ความเข้าใจภาษาจากการ pre-train ขนาดใหญ่ เห็นโครงสร้างตรรกะหลากหลายกว่า encoder แบบ BERT (caption: "Burke") จึงจับความสัมพันธ์ของตัวเลขกับประโยคได้ดีกว่าเล็กน้อย

แปลว่าอะไรสำหรับคนออกแบบระบบ (~12:43)

ถ้าระบบอยู่ในงานการเงิน สุขภาพ หรือวิทยาศาสตร์ การเพิ่มข้อมูลฝึกหรือซื้อโมเดลใหญ่ขึ้นไม่ได้ปิดช่องว่างนี้เอง ต้องจัดการในชั้นแอปพลิเคชัน อย่าคิดว่าระบบค้นเข้าใจว่าความดันลด 2% ต่างจากลด 20% มาก ผู้ดำเนินรายการบอกว่าการพึ่ง dense vector อย่างเดียวกับคำถามเชิงตัวเลขไม่ถูกหลักคณิตศาสตร์ ต้องสร้างระบบ hybrid ที่มี symbolic solver หรือ metadata filter แบบมีโครงสร้างทำงานคู่ขนาน เรื่องนี้สำคัญกับบอตเทรดอัตโนมัติและระบบคัดกรองผู้ป่วย และย้ำว่าการเลือกโมเดลขึ้นกับสภาพแวดล้อมที่ใช้จริง

เสริมจากผู้จัดทำ งานนี้คือ "Revealing the Numeracy Gap: An Empirical Investigation of Text Embedding Models" (Deng, Duan, Tang, Yang, HKUST; Findings of EACL 2026) benchmark ชื่อ EmbedNum-1K ค่าเฉลี่ย 0.54 (โอกาสเดาถูก 0.5), รูปแบบ "0.x" ได้ 0.62 และ LLM-based ได้ราว 0.56 เทียบ encoder-based ราว 0.51 กราฟในสไลด์ (คะแนนตามจำนวนหลักสำคัญ) เป็นภาพประกอบของคลิป ผู้จัดทำไม่ได้ตรวจว่ามาจากตารางในงานวิจัย

ต่อด้วยทางเลือกบน Google Cloud Vertex AI และข้อแลกเชิงวิศวกรรม Google มีโมเดลของตัวเองเป็นชั้น ๆ:

ถ้าจะเอา embedding ไปป้อน classifier ต่อ สิ่งที่ต้องการคือ linear separability: เส้นแบ่งระหว่างคลาสที่นิ่งและชัดทางคณิตศาสตร์ ในงานนี้โมเดล encoder-only เฉพาะทางอย่าง RoBERTa หรือโมเดลเปิดขนาดเล็ก Qwen3 0.6B (caption: "Quinn 30.6b") มักดีกว่าโมเดล multimodal ขนาดใหญ่แบบทั่วไปมาก

edge (~15:22)

ถ้ารัน semantic search บนมือถือที่หน่วยความจำและพลังคำนวณจำกัด มีตัวเลือกอย่าง EmbeddingGemma 300M ใช้ RAM ต่ำกว่า 200 MB และ latency ต่ำกว่า 22 มิลลิวินาที

Matryoshka Representation Learning (~15:42)

สิ่งที่ทำให้บีบโมเดลได้ขนาดนี้คือ MRL (caption: "Matrioska") แทนที่จะให้ทุกมิติสำคัญเท่ากัน MRL ฝึกให้ข้อมูลความหมายที่สำคัญที่สุดอยู่ในมิติแรก ๆ เหมือนตุ๊กตาแม่ลูกดก ถ้าหน่วยความจำไม่พอ ก็ตัดท้ายเวกเตอร์ทิ้งได้เลย เช่นจาก 1024 มิติเหลือ 256 ผู้ดำเนินรายการถามว่าการตัดครึ่งยังรักษาความหมายได้จริงไหม คำตอบคือได้ เพราะ loss function ตอนฝึกออกแบบให้เน้นความแม่นของ 256 มิติแรก จึงเก็บความแม่นของการค้นไว้เกือบทั้งหมด แต่ประหยัดพื้นที่และการคำนวณมาก

เสริมจากผู้จัดทำ EmbeddingGemma มี 308M พารามิเตอร์ (ชื่อเล่น 300M) ใช้ RAM ต่ำกว่า 200 MB เมื่อ quantize และตัดมิติได้ 768 → 512, 256 หรือ 128 หน้า overview ของ Google เขียนว่า "<22 ms on EdgeTPU" ส่วนบล็อกเปิดตัวเขียนว่าต่ำกว่า 15 ms สำหรับ 256 tokens งาน MRL (Kusupati และคณะ, NeurIPS 2022) รวม loss ของหลายความยาวซ้อนกัน (เช่น 8, 16, … ถึงเต็ม) ไม่ได้เน้นเฉพาะ 256 มิติ ตัวอย่าง 1024 → 256 เป็นตัวอย่างประกอบ

10. หลายภาษา, BGE-M3 และการ fine-tune

~16:32–18:43

หลายภาษาและ hybrid search (~16:32)

Qwen3-Embedding-8B (caption: "Quen 3 embedding 8B") ผู้ดำเนินรายการบอกว่ากำลังเป็น state of the art ด้านหลายภาษา แต่ตัวที่เด่นสำหรับ pipeline ซับซ้อนคือ BGE-M3: ในการรันรอบเดียวให้ทั้ง dense vector สำหรับความหมาย, sparse vector สำหรับคำที่ตรงกันเป๊ะ และ multi-vector สำหรับการให้คะแนนแบบ late interaction (caption: "elite interaction") จึงแก้ปัญหา hybrid retrieval ที่ระดับโมเดล แทนที่นักพัฒนาต้องสร้างสาม pipeline แล้วรวมผลเอง

เมื่อโมเดลสำเร็จรูปใช้ไม่ได้: fine-tune (~17:06)

ถ้าทำงานด้านวิศวกรรมอวกาศหรือวัสดุศาสตร์ขั้นสูง โมเดลพื้นฐานจะไม่มีคำศัพท์เหล่านี้ ต้อง fine-tune ซึ่งผู้ดำเนินรายการบอกว่ายากมาก:

  • โดยทั่วไปใช้ contrastive learning ป้อนคู่ข้อความ ดึงแนวคิดที่คล้ายให้ใกล้กันในพื้นที่ และผลักแนวคิดที่ต่างให้ห่างออก
  • hard negative mining คือหัวใจ: hard negative คือเอกสารที่ใช้คำคล้ายคำถามมากแต่ความหมายต่าง ป้อนตัวอย่างยากแบบนี้เพื่อบังคับให้ระบบเรียนศัพท์ของเรา
  • ด่านใหญ่คือ false negative: การป้อน hard negative มักสร้าง false negative ขึ้นมา คือระบบติดป้ายว่าสองสิ่งต่างกัน ทั้งที่ในโดเมนของเรามันหมายถึงสิ่งเดียวกัน
  • แก้ด้วยมนุษย์ติดป้ายซึ่งแพงมาก หรือใช้ LLM ติดป้ายสังเคราะห์ให้เร็วขึ้น แต่เมื่อฝึกหลาย epoch (caption: "epox") reward model มักเลื่อน (drift)

คำแนะนำที่ผู้ดำเนินรายการเรียกว่าฉันทามติ (~18:21): โดเมนทั่วไปให้ใช้โมเดล pre-train สำเร็จรูปเสมอ เพราะต้นทุนและความยุ่งยากของการ fine-tune แทบไม่คุ้มกับผลที่เพิ่มเล็กน้อย แต่ถ้าเป็นโดเมนเทคนิคสูงและเสี่ยงสูง ไม่มีทางเลือก ต้อง fine-tune ด้วย hard negative mining ให้ระบบเรียนขอบเขตของศัพท์เฉพาะ

เสริมจากผู้จัดทำ Qwen3-Embedding มีสามขนาด (0.6B, 4B, 8B) และรุ่น 8B ขึ้นอันดับ 1 ของ MTEB multilingual ด้วยคะแนน 70.58 (ณ 5 มิถุนายน 2025) BGE-M3 รองรับมากกว่า 100 ภาษาและข้อความยาวถึง 8,192 tokens

11. ทบทวนท้ายคลิป และ GraphRAG

~18:44–20:57

ผู้ดำเนินรายการทบทวนเส้นทางทั้งหมด:

  • สถาปัตยกรรมหลัก: การขยับจาก RAG แบบ bi-encoder พื้นฐานไปเป็น cross-encoder rerank เป็นสิ่งที่ต่อรองไม่ได้ ถ้าอยากดัน faithfulness จากราว 0.3 ขึ้นไปเกือบ 0.8
  • clinical RAG: สคริปต์ chunking พื้นฐานทำให้เกิด semantic leakage จึงต้องเก็บหัวข้อส่วน และ affirmative bias ของ latent space ทำให้ต้องมี cross-encoder ตรวจคำปฏิเสธทางการแพทย์
  • numeracy gap: ผู้ดำเนินรายการสรุปว่าแม้โมเดลที่ก้าวหน้าที่สุดก็แม่นแค่ 54% เท่าการโยนเหรียญเมื่อเจอตัวเลข และพังกับเปอร์เซ็นต์และจำนวนเต็มสี่หลัก (54% คือค่าเฉลี่ยของ 13 โมเดลตามที่พูดไว้ที่ ~11:17)
  • Vertex AI: ข้อแลกระหว่างความแม่นของ Gemini มิติสูงกับความคุ้มของโมเดล 768 มิติ และการตัดเวกเตอร์แบบ Matryoshka

แก่นที่ย้ำคือ โมเดลที่ดีที่สุดบน leaderboard สาธารณะ มักไม่ใช่โมเดลที่ดีที่สุดสำหรับงานที่มีข้อจำกัดของเรา

ทิ้งท้าย: GraphRAG (~20:00)

ผู้ดำเนินรายการชี้ว่าทั้งตอนพูดถึงพื้นที่เวกเตอร์ที่แทนความหมายแบบคงที่ แต่งานวิจัยกำลังไปทาง GraphRAG คือรวม embedding model เข้ากับ knowledge graph แบบมีโครงสร้าง และตั้งคำถามว่าถ้าพื้นที่เรขาคณิตในอนาคตเข้ารหัสการให้เหตุผลหลายขั้น (multi-hop) และความสัมพันธ์ของ entity ได้ในตัว หรือถ้า embedding model เข้าใจโครงสร้างของ graph ได้เอง วิธีที่เราใช้ข้อมูลของตัวเองจะเปลี่ยนไปอย่างไร แล้วจบตอนด้วยการย้ำให้ผู้ฟังทดสอบระบบของตัวเอง ไม่เชื่อตัวเลขบน leaderboard โดยไม่ตรวจ และตรวจ latent space ของข้อมูลตัวเองเสมอ

Key Takeaways

  1. embedding model คือเพดานของระบบ ถ้าข้อความถูกวางผิดที่ในพื้นที่เวกเตอร์ การปรับ prompt ปลายทางแก้ไม่ได้
  2. ใช้ pipeline สองขั้น: bi-encoder คัดผู้สมัครจำนวนมาก แล้ว cross-encoder จัดอันดับ 10–100 ชิ้นบนสุด (คลิปพูด 0.347 → 0.797 ส่วนผู้จัดทำตรวจงานวิจัยพบว่า RAG พื้นฐาน 0.621 → 0.797)
  3. งานเฉพาะทางต้องออกแบบทั้ง pipeline: chunk ตามหัวข้อ, ขยายคำค้นเน้น recall, กรองคำปฏิเสธ และสรุปเป็นโครงสร้าง
  4. embedding อ่านตัวเลขแทบไม่ได้ (เฉลี่ย 54% ใน EmbedNum-1K) คำถามเชิงตัวเลขต้องมี filter หรือ solver คู่กัน
  5. มิติสูงแลกกับ RAM และเงิน: 3072 มิติแม่นกว่าแต่แพงกว่า 768 มาก MRL ช่วยตัดเวกเตอร์ให้สั้นลง
  6. เลือกโมเดลตามงาน ไม่ใช่ตาม leaderboard และ fine-tune ด้วย hard negative เฉพาะโดเมนเทคนิคสูง
