บทสรุปย่อ

ผู้สอนวิชา data science ที่พูดภาษาฝรั่งเศส (ช่อง MASTER 2 SISE DATA SCIENCE) ลองใช้ TabFM ของ Google Research จริงเมื่อ 17 กรกฎาคม 2026 โดยติดตั้งจาก GitHub (เวอร์ชัน 1.0.1 ที่ยังไม่อยู่บน PyPI ในวันนั้น) พบว่า backend PyTorch ใช้ไม่ได้บนเครื่องของเขา จึงใช้ JAX แทนและทำงานสำเร็จ งานทดสอบคือจัดประเภทอีเมลสแปม โดยมีข้อมูลฝึกเพียง 100 แถวและข้อมูลทดสอบ 4,501 แถว ได้ F1 ประมาณ 0.886 ใกล้เคียง TabICL ที่เขาเคยใช้ แต่ขั้น predict บน CPU ล้วนใช้เวลาประมาณ 1 ชั่วโมงครึ่ง ซึ่งเขามองว่ายังใช้งานจริงไม่ได้ ณ ตอนนี้ ข้อสังเกตของผู้จัดทำ: นี่เป็นประสบการณ์ผู้ใช้อิสระ ไม่ใช่ผลของ Google และเป็นการทดสอบเครื่องเดียว ชุดข้อมูลเดียว จึงเป็นหลักฐานเรื่อง "ติดตั้งและใช้ได้ไหม ช้าแค่ไหน" มากกว่าเรื่อง "แม่นแค่ไหน"

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แปลจากภาษาฝรั่งเศส แบบวิเคราะห์เชิงลึกพร้อมตรวจข้อเท็จจริง (license มาตรฐานของ YouTube)

สรุปเชิงลึก

ใจความหลัก. ผู้พูดบอกว่าเขาพบ TabFM ระหว่างค้นคว้าเอกสาร (และจะนำเรื่องนี้ไปพูดกับนักศึกษาตอนเปิดเทอมเดือนกันยายน) และต้องการรู้สามอย่าง: ติดตั้งได้ไหม ใช้ได้ไหม และผลเทียบกับเครื่องมือที่เคยทดสอบ (โดยเฉพาะ TabICL ซึ่งเขาเคยทำคลิปมาหลายตอน) เขาอธิบาย TabFM ว่าเป็นการรวมจุดแข็งของสองแนวทาง foundation model สำหรับตาราง คือ TabICL กับ TabPFN โดยอ้างตามบทความของ Google

ติดตั้ง. เขาตั้งใจใช้ PyTorch แต่ใช้เวลาทั้งวันและติดตั้งใหม่ถึงขั้นลง Anaconda ใหม่ก็ยังไม่สำเร็จ จึงเปลี่ยนไปใช้ JAX ซึ่งทำงานได้ เขาติดตั้งจาก GitHub จึงได้ TabFM เวอร์ชัน 1.0.1 ขณะที่ PyPI ยังเป็น 1.0.0 (ตรวจแล้วตรง: changelog ลงวันที่ 1.0.1 เป็น 2026-07-09 และ PyPI ออก 1.0.1 วันที่ 2026-07-21) ส่วนน้ำหนักโมเดลที่โหลดจาก Hugging Face ในภาพจอเป็นรุ่น tabfm-1.0.0-jax

การทดลอง. ชุดข้อมูลคือสแปม ข้อมูลฝึกมีเพียง 100 แถวโดยเจตนา เพราะเขาเห็นว่า foundation model น่าสนใจเมื่อข้อมูลน้อย ส่วนเมื่อข้อมูลฝึกมีมากวิธีคลาสสิกก็ทำได้ดีอยู่แล้ว (เป็นความเห็นของเขา ไม่ได้เทียบกับวิธีคลาสสิกในคลิป) ข้อมูลทดสอบ 4,501 แถว fit ใช้เวลาไม่กี่วินาทีเพราะไม่มีการเทรน ส่วน predict คือที่ที่คำนวณ attention บนแถวและคอลัมน์ บีบข้อมูลและทำนายแบบลำดับ ซึ่งบน CPU ที่ไม่มี GPU ใช้เวลาเกือบ 1 ชั่วโมงครึ่ง

ผลลัพธ์ที่เห็นบนจอ. confusion matrix ของ TabFM คือ [[2643, 78], [303, 1477]] ให้ F1 (คลาสสแปม) 0.8858 และ accuracy 0.9154 (ผู้จัดทำคำนวณจากเมทริกซ์) เทียบกับ TabICL บนชุดทดสอบเดียวกันที่เห็นด้านซ้ายของจอ: [[2635, 86], [289, 1491]] F1 0.8883 ต่างกันเพียง 0.0025 คำบรรยายอัตโนมัติฟังตัวเลข F1 ของ TabICL เพี้ยนเป็น "081 82" แต่หน้าจอแสดง 0.8883 ผู้พูดเตือนเองว่านี่ไม่ใช่หลักฐาน เพราะเป็นชุดข้อมูลเดียว

benchmark ของผู้พัฒนา และ TabFM-Ensemble. ผู้พูดอ่าน benchmark ในบทความต้นทางและบอกว่า TabFM ดูดีกว่าตัวอื่น แต่นั่นเป็นลักษณะของนักวิจัย และเวลาคำนวณไม่ได้ถูกเน้น แผนภูมิ Elo ใน blog (เห็นในคลิป) ให้ TabFM-Ensemble 1815, TabFM 1727, TabPFN-3 1639 และ TabICLv2 1576 สำหรับงานจัดประเภท เขายังบอกว่า TabFM-Ensemble (ที่ปรับข้อมูลหลายแบบ เช่น SVD แล้วส่งเข้า TabFM หลายชุดแล้วรวมผล) ยังเข้าถึงไม่ได้ ณ ตอนนั้น และเวลาคำนวณจะยิ่งสูงขึ้น

ตรวจข้อเท็จจริง. 15 ข้อ: ยืนยัน 10, ยืนยันบางส่วน 2, ไม่พบแหล่งยืนยัน 3 (สองข้อเป็นประสบการณ์บนเครื่องของเขา อีกข้อเป็นความรู้ทั่วไปเรื่อง JAX ที่ตรวจไม่ได้), ขัดแย้ง 0 ข้อที่ผู้จัดทำแก้จากภาพจอ: ตัวเลข F1 ของ TabICL ส่วนจำนวนตัวแปรยังไม่แน่ชัด (คำพูด ราวห้าสิบ, คำอธิบายคลิป 55, UCI Spambase 57)

เอาไปทำอะไร. ใช้เป็นหลักฐานว่าแพ็กเกจรุ่นแรกยังเปลี่ยนเร็ว (PyTorch ใช้ไม่ได้ ณ วันนั้น, ต้องติดตั้งจาก GitHub) และเวลา predict บน CPU เป็นข้อควรระวังหลัก

ผู้พูดบอกว่าคลิปนี้ต่อเนื่องจากชุดที่สำรวจ foundation model สำหรับข้อมูลตาราง วันนี้เขาจะดูเทคโนโลยี TabFM และแพ็กเกจ Python ของมัน เขาชี้ว่าเป็นของ Google Research และเป็นเทคโนโลยีที่ใหม่มาก บทความอ้างอิงที่เปิดให้ดูอยู่คือรุ่นแรก

เขาชี้ว่ารุ่นแรกออกวันที่ 30 (มิถุนายน) และมีการปรับปรุงล่าสุดเมื่อ 9 กรกฎาคม 2026 (วันที่อัดคือ 17 กรกฎาคม) และเวอร์ชัน 1.0.1 ยังไม่อยู่บน PyPI ซึ่งยังเป็น 1.0.0 จึงสรุปว่ามันเปลี่ยนเร็วมาก เขาบอกว่าได้ดูหน้า GitHub โดยละเอียดและอ่านบทความแล้ว ซึ่งน่าสนใจ แต่ยังประเมินไม่ได้ทั้งหมด เพราะเพิ่งเริ่มซึมซับ เหตุผลที่สนใจคือเขาจะพูดถึงเรื่องนี้ตอนเปิดเทอมเดือนกันยายนกับนักศึกษา: จะสอนวิธีคลาสสิกก่อน แล้วค่อยสอนวิธีใหม่ล่าสุด ซึ่งหนึ่งในนั้นคือ foundation model

2. ทำไมเลือก TabFM: TabICL กับ TabPFN (~1:30–4:05)

ผู้พูดบอกว่าเขาเคยสำรวจ TabICL v2 มามาก (ทำคลิปเป็นชุดและมีหน้า GitHub ของมัน) ทำการค้นคว้าเอกสารมาก รวมถึงถาม ChatGPT และเครื่องมืออื่น จนมาเจอ TabFM โดยบังเอิญ และพูดติดตลกว่าถ้าดูเมื่อเดือนพฤษภาคมก็คงไม่เจอ

เขาอ่านรายละเอียดในบทความ ซึ่งบอกว่า TabFM สังเคราะห์จุดแข็งของสองแนวทาง foundation model สำหรับตาราง คือ TabICL (ที่เขาสำรวจมาก) กับ TabPFN เรื่อง TabPFN เขาเคยเตรียมคลิปไว้แล้ว แต่ตอนสร้างแพ็กเกจเพื่อทดลองคำนวณพบว่าต้องสมัครบัญชีออนไลน์เพื่อรับ token ซึ่งเขาตอบว่า "ไม่" เพราะไม่อยากขอให้นักศึกษาทุกคนไปลงทะเบียนด้วยอีเมลส่วนตัว เขาจึงวางแนวคิดนั้นไว้ แม้อ่านละเอียดและลองทดสอบบ้างแล้ว

พอมาเจอ TabFM เขาเห็นว่าเป็นการผสมข้อดีของทั้งสองแบบ และแนะนำให้อ่านบทความอ้างอิงโดยเฉพาะส่วน "how it works" ซึ่งเขาบอกว่าเขียนดี มีแผนภาพ และอธิบายว่าผสมข้อดีของแต่ละแนวทางอย่างไรผ่านกลไกสามอย่าง

ข้อที่ควรเข้าใจให้ตรง

คำบรรยายอัตโนมัติสะกดชื่อเพี้ยนหลายจุด (เช่น "Tabicel", "T Pf", "TF FM", "Taper FN") ผู้จัดทำแปลตามบริบทและชื่อที่ถูกต้อง: TabICL, TabPFN, TabFM บทความที่เขาอ้างตรงกับ blog ของ Google Research ลิงก์ในคำอธิบายคลิป

3. แนวคิด foundation model บนตาราง (~4:05–4:35)

ผู้พูดอธิบายแนวคิดสั้น ๆ ว่า foundation model สร้างชุดข้อมูลสังเคราะห์จำนวนมากที่ครอบคลุมแนวคิดที่เป็นไปได้ทั้งหมดของความสัมพันธ์ระหว่างตัวแปรอธิบาย X กับตัวแปรเป้าหมาย Y เมื่อเรามีชุดข้อมูลของเราก็เป็นรูปแบบหนึ่งของการใส่บริบทให้ (contextualisation)

เขาเปรียบว่าคล้ายกับด้านหนึ่งที่มี LLM แล้วเมื่อมีข้อมูลเฉพาะของเราก็ใช้เทคโนโลยี RAG หรือทำนองนั้น ซึ่งเขาว่าเป็นแนวคิดเดียวกันโดยประมาณ เขาจึงอ่านบทความละเอียดและเข้าไปที่หน้า GitHub ซึ่งเป็นจุดที่ปัญหาเริ่มเกิด

เสริมจากผู้จัดทำ

การเปรียบเทียบกับ LLM + RAG เป็นของผู้พูด ผู้จัดทำขอเสริมว่ามันเทียบได้เฉพาะระดับแนวคิด (ข้อมูลของเราเข้าไปเป็นบริบท ไม่ได้เข้าไปเป็นการเทรน) ใน TabFM แถวฝึกที่มี label ถูกส่งเข้าโมเดลเป็นบริบทโดยตรง ไม่ได้มีขั้นตอนค้นคืนเอกสารมาเติมเหมือน RAG

4. การติดตั้ง: PyTorch ล้มเหลว JAX สำเร็จ (~4:35–6:59)

ผู้พูดบอกว่าโมเดลมีให้ใช้บน Hugging Face ติดตั้งได้ตรง ๆ ตอนแรกเขาอยากใช้ backend PyTorch ที่เขาคุ้นเคย เพื่อให้ได้เวอร์ชันล่าสุด 1.0.1 เขา clone repository จาก GitHub แล้ว pip install ในสภาพแวดล้อม conda ที่สร้างใหม่ แต่ไม่เคยทำงานได้เลย เขาใช้เวลาทั้งวัน ลง Anaconda ใหม่ทั้งหมด (เครื่องของเขาไม่ได้แรง) แล้วทำทุกอย่างใหม่ ก็ยังไม่สำเร็จ

เขาจึงเลิกกับ PyTorch และหันไปใช้ JAX ซึ่งเขาบอกว่าคล้าย NumPy แต่มีข้อได้เปรียบและเก่งเรื่องการคำนวณ gradient ไม่ต้องเขียนฟังก์ชัน gradient เอง มีการคอมไพล์แบบ just-in-time และหน้าตา interface คล้าย NumPy เขาบอกว่าต้องทดสอบเวลาคำนวณต่อไป และยืนยันว่าติดตั้งด้วยวิธีนี้ทำงานได้

ในสภาพแวดล้อมของเขา เมื่อลิสต์แพ็กเกจจะเห็น TabFM ที่ติดตั้งผ่าน GitHub เป็นเวอร์ชันล่าสุด 1.0.1 ซึ่งยังไม่มีบน PyPI ที่ยังอยู่ที่ 1.0.0

เสริมจากผู้จัดทำ

changelog ของ GitHub ระบุว่า 1.0.1 (9 ก.ค.) แก้การโหลด checkpoint ของ PyTorch แต่ผู้พูดติดตั้ง 1.0.1 แล้วก็ยังใช้ไม่ได้ จึงไม่ทราบสาเหตุจริง ตอนท้ายคลิปเขาเองก็บอกว่าอาจใช้ได้ในวันถัดไป

5. ชุดข้อมูลสแปมกับข้อมูลฝึกที่น้อยมาก (~7:01–8:25)

ชุดข้อมูลเป็นชุดเดียวกับในคลิปก่อนหน้าของเขา คือการทำนายสแปม โดยมีข้อมูลฝึกน้อยมากโดยเจตนา ผู้พูดอธิบายเหตุผลว่าถ้าข้อมูลฝึกมีปริมาณมาก การใช้ foundation model ไม่ค่อยมีประโยชน์ เพราะวิธีคลาสสิกทำงานได้ดีอยู่แล้ว แต่เมื่อข้อมูลหายาก foundation model น่าสนใจจริง ๆ และมีช่องว่างจริง เขาเคยทำคลิปแสดงประโยชน์ของ fine-tuning ในกรณีนี้ และเขายังไม่ได้เทียบกับวิธีคลาสสิก แต่คิดว่ายิ่งตัวอย่างฝึกเพิ่มมาก วิธีคลาสสิกยิ่งน่าสนใจ และเมื่อข้อมูลฝึกหายาก foundation model นำสิ่งที่มีคุณค่ามาให้ ซึ่งเป็นแนวคิดของเขาในตอนนี้

ข้อมูลสแปมเป็นที่รู้จักมากในวงการ machine learning ชุดฝึกมีข้อมูลน้อย ส่วนชุดทดสอบมีตัวแปรเป้าหมายสองค่า (0/1) ตัวแปรอธิบายคือคุณลักษณะของข้อความอีเมล และชุดทดสอบมี 4,501 แถว

เสริมจากผู้จัดทำ

ตัวเลข 100 + 4,501 = 4,601 ตรงกับจำนวนแถวของ UCI Spambase ซึ่งมี 57 feature คำอธิบายคลิปเขียน 55 ตัวแปร และผู้พูดพูดว่า "ราว 50" ผู้จัดทำจึงไม่ยืนยันจำนวนตัวแปรที่แน่นอนที่เขาใช้

6. โน้ตบุ๊ก: โหลดโมเดลและ fit (~8:25–11:33)

ผู้พูดเปิดโน้ตบุ๊กตามปกติ โดยใช้ kernel เป็นสภาพแวดล้อมที่ติดตั้ง TabFM นำเข้าข้อมูล (ฝึก 100 แถว ทดสอบ 4,501 แถว) แยก X กับ Y แล้วโหลดโมเดล

เขาตั้งข้อสังเกตว่านี่คือปัญหาของการพึ่งแพ็กเกจที่ใหม่มาก: มีการอัปเดตแทบทุกสัปดาห์ บางอย่างยังไม่ถูกทำ บางอย่างจะเปลี่ยน เมื่อดูโค้ด เขาบอกว่าตอนนี้ในโค้ดยังไม่มี 1.0.1 มีเพียงรุ่น 1 จึงโหลดรุ่น 1.0.0 ของ JAX (ภาพจอที่เห็นที่ ~14:00 แสดงโฟลเดอร์ tabfm-1.0.0-jax)

จากนั้นเขาสร้างโมเดลสำหรับงาน classification (การจัดประเภทแบบมีผู้สอน) ซึ่งใช้เวลาโหลดนานมาก ครั้งแรกเขาต้องเปิด Python ในสภาพแวดล้อมแล้วโหลดด้วยมือ เพราะในโน้ตบุ๊กมีข้อความเด้งขึ้นมามากและช้าอย่างยิ่ง หลังจากนั้นระบบทำสำเนาในเครื่อง (local copy) ครั้งถัดมาในโน้ตบุ๊กจึงโหลดจากสำเนานั้นและเร็วกว่ามาก ภาพจอที่เห็นภายหลังแสดงการดึงไฟล์ 134 ไฟล์จาก Hugging Face

เมื่อโหลดน้ำหนักแล้ว (เขาเรียกว่าน้ำหนักซินแนปส์ของโครงข่ายใน transformer) ก็สร้างตัวจัดประเภท (classifier) ด้วย backend ที่โหลดไว้พร้อมน้ำหนักที่ดึงมาจาก Hugging Face เมื่อโหลดในเครื่องแล้ว "การเทรน" เร็วมากเพราะไม่มีการเทรน มันเป็นการใส่บริบท

ส่วนที่ใช้เวลาคือการจัดประเภท: เมื่อจะสรุปผลกับตัวอย่างเพิ่มเติม ตรงนี้มันคำนวณ attention บนแถวและคอลัมน์ ทำการบีบข้อมูล แล้วได้ embedding เพื่อทำนายในรูปของลำดับ (sequence): ตัวที่ต้องการจัดประเภทถูกวางไว้ในลำดับ แล้วจึงทำนาย เขาจึงสรุปว่านี่คือการยกแนวคิด LLM บนข้อมูลข้อความมาใช้กับข้อมูลตาราง

7. ขั้น predict ช้ามาก (~11:33–13:38)

fit เร็วมาก แต่เมื่อสั่ง predict ก็ใช้เวลาหลายชั่วโมง ผู้พูดบอกว่าเมื่อผ่านไปชั่วโมงครึ่งเขาไม่แน่ใจแล้วว่าความช้าเป็นเพราะตัวเขาหรือเครื่องมือ เขาจึงเลิกรันส่วนที่เหลือของการทดสอบ (โค้ดพร้อมแล้วแต่ไม่ได้สั่งรันเพราะนานเกินไป) แล้วหยุดการทำงาน รีสตาร์ตเครื่อง และแปลงโน้ตบุ๊กเป็นโค้ด Python

ในสคริปต์ Python ทำสิ่งเดียวกับโน้ตบุ๊ก: โหลดข้อมูล เตรียมโครงสร้าง โหลดโมเดล (มีข้อความเริ่ม/จบเพื่อให้เห็นขั้น) สร้างตัวแบบ fit ซึ่งใช้ไม่กี่วินาที แล้ว predict ซึ่งบนเครื่องของเขาใช้หลายชั่วโมงตามคำพูด (ภายหลังเขาระบุว่าใช้เวลาเกือบหนึ่งชั่วโมงครึ่ง) เขาย้ำว่ามีประมาณห้าสิบตัวแปร กับ 4,501 แถว และเครื่องไม่มี GPU ใช้ CPU ล้วน ๆ

เขาสรุปว่า "ยังใช้ไม่ค่อยได้ ณ ตอนนี้": ถ้าทำนายทีละรายก็ยอมรับได้ ไม่รู้สึกว่ามีอะไร แต่ถ้าทำนายไฟล์ข้อมูลใหญ่จะใช้เวลา แต่เขาเตือนว่าเทคโนโลยีใหม่มาก จึงไม่สงสัยเลยว่าด้วยผู้พัฒนาที่อยู่เบื้องหลัง การปรับให้เร็วจะตามมา แต่ตอนนี้ยังไม่สมบูรณ์ ภาพรวมนี้ยังแสดงให้เห็นแนวคิดว่าเอาอะไรออกมาใช้ได้ และเขาจะนำเทคนิคเหล่านี้ไปใส่ในการสอน เพื่อให้นักศึกษามองเห็นภาพเวลาทำงานกับข้อมูลจริง

เสริมจากผู้จัดทำ

ผู้พูดไม่ได้ให้ตัวเลขขนาดตัวแบบหรือหน่วยความจำ และไม่ได้ทดลองบน GPU ตัวเลขเวลา (~1.5 ชม.) จึงใช้ได้เฉพาะการรัน CPU ครั้งนี้ ไม่ควรขยายความเป็นความเร็วของ TabFM โดยทั่วไป

8. ผลลัพธ์: F1 และการเทียบกับ TabICL (~13:39–14:50)

จากนั้นเขาดูค่าทำนายเทียบกับค่าจริง สร้าง confusion matrix และคำนวณ F1 เขาเตรียมภาพจอไว้ (ผู้พูดบอกว่าเริ่มรันเมื่อ 15:53) ซึ่งแสดงว่า predict จบจนได้ผล มีทั้ง confusion matrix และ F1

เพื่อเปรียบเทียบเขาเปิดผลที่เคยได้จาก TabICL บนชุดข้อมูลเดียวกัน ซึ่งได้ F1 ราว 0.88 (คำบรรยายอัตโนมัติเขียนเป็น "081 82" แต่ตัวเลขบนจอคือ 0.8883) เขาย้ำว่าสิ่งนี้ไม่ใช่หลักฐาน เพราะเป็นชุดข้อมูลเดียว เขามีสองคำถาม คือติดตั้งได้ไหม ใช้ได้ไหม และอีกประเด็นที่แสดงภายหลังคือผลเทียบกับเครื่องมืออื่นที่เคยทดสอบได้ใกล้เคียงกันไหม

ข้อที่ควรเข้าใจให้ตรง

เสียงบรรยายอัตโนมัติฟังตัวเลข F1 ของ TabICL เป็น "081 82" ผู้จัดทำใช้ค่า 0.8883 ตามที่เห็นบนจอและตรงกับ confusion matrix (ตรวจด้วยการคำนวณ) ส่วนค่าของ TabFM ผู้พูดไม่ได้อ่านออกเสียง ผู้จัดทำอ่านจากจอ (0.8858)

9. Benchmark ของผู้พัฒนา และ TabFM-Ensemble (~14:48–16:25)

ผู้พูดบอกว่าผู้เขียนแพ็กเกจทดสอบระดับใหญ่และแสดงไว้ในส่วน benchmarking ซึ่งอธิบายวิธีทดสอบด้วยชุดข้อมูลอ้างอิงจำนวนหนึ่งและแสดงผล เขาว่าน่าสนใจ TabFM ดูเหมือนจะดีกว่าตัวอื่น แต่ "นั่นเป็นเรื่องของนักวิจัย" และเรื่องเวลาคำนวณพวกเขาไม่ได้พูดถึงมากนัก ไม่ได้เน้น

จากนั้นมีอีกรุ่นที่ยังเข้าถึงไม่ได้ คือ TabFM ensemble ซึ่งแนวคิดคือชุดข้อมูลถูกแปลงหลายแบบก่อนส่งเข้า TabFM เช่นผ่านการแยกค่าเอกพจน์ (singular value decomposition) เขาไม่พบเอกสารที่เกี่ยวข้องจริง ๆ และบอกว่า ChatGPT อธิบายได้ชัดเจน แต่ความคิดหลักคือมันไม่ใช่วิวัฒนาการของ TabFM เอง แต่เป็นการแปลงชุดข้อมูลเป็นหลายชุดเพื่อเสริมการเรียนรู้ แล้วส่งเข้า TabFM หลายชุดและรวมผล ซึ่งเพิ่มเวลาคำนวณจนเกินจะรับมือได้

เขาบอกว่าผู้พัฒนาระบุว่า ณ ตอนนี้มันเหนือกว่า TabICL v2 และ "tu PF23D" (ผู้พูดบอกว่าเขาก็เชื่ออย่างนั้น) แต่ตัวเขาเองไม่เคยทดสอบ TabPFN เพราะต้องลงทะเบียนและให้อีเมล ซึ่งเขาไม่ต้องการทำ ณ ตอนนี้

เสริมจากผู้จัดทำ

ตามแผนภูมิใน blog TabFM-Ensemble (1815) และ TabFM (1727) นำหน้า TabPFN-3 (1639) และ TabICLv2 (1576) ในงานจัดประเภท ตัวเลขนี้ตรงกับที่ผู้พูดบอก แต่เป็นการวัดของ Google เอง และ TabFM-Ensemble เป็นอีกการตั้งค่าที่ใช้ feature cross + SVD, ensemble 32 ทาง (ตาม blog) ผู้พูดอธิบายสั้นกว่านั้นและแสดงความไม่แน่ใจเรื่องเอกสาร

ข้อที่ควรเข้าใจให้ตรง

เสียงบรรยายอัตโนมัติฟังชื่อรุ่นที่ 16:11 เป็น "tu PF23D" ผู้จัดทำตีความว่าคือ TabPFN-3 (D) ตามแผนภูมิ Elo ใน blog ซึ่งเป็นการตีความ ไม่ใช่คำที่ผู้พูดชัดเจน

10. บทสรุปของผู้พูด (~16:25–18:09)

เขาสรุปว่า foundation model สำหรับข้อมูลตารางมีอะไรให้ขุดอีกมาก เป็นเทคโนโลยีที่ใหม่มาก และมีผู้เล่นสำคัญเข้ามา โดยเฉพาะ Google Research

ในส่วนที่เขาทดสอบ: แพ็กเกจติดตั้งได้ ด้วย backend JAX ไม่ใช่ PyTorch ซึ่งตอนนี้ยังมีบั๊กอยู่ (อาจเป็นวันที่ 17 ก.ค. และบางทีวันที่ 18 อาจใช้ได้ เขาไม่รู้) JAX ทำงานได้ดี เขาใช้ได้ และประสิทธิภาพบนชุดข้อมูลของเขาอยู่ในระดับเดียวกับที่ได้จาก TabICL ที่เขาทดสอบมามาก ผู้พัฒนาทำ benchmark และบอกว่าตัวเองดีกว่า ซึ่งเขาว่าเป็นลักษณะของนักวิจัย

ข้อที่เขามีข้อติจริง ๆ คือเวลาคำนวณ: บนเครื่องที่ไม่แรง ไม่มี GPU มี CPU อย่างเดียว เวลาคำนวณระหว่างสิ่งที่ทดสอบกับ TabICL กับที่ได้จาก TabFM ต่างกันคนละเรื่อง: ตัวหนึ่งนับเป็นไม่กี่นาที อีกตัวหนึ่งนับเป็น 1 ชั่วโมงครึ่ง ซึ่งตอนนี้ทำให้ใช้ในสถานการณ์จริงไม่ได้ แต่เขาไม่สงสัยว่ามันจะพัฒนาไปในทางบวก

Key Takeaways

1.ผู้พูดทดสอบ TabFM 1.0.1 (ติดตั้งจาก GitHub) ด้วย backend JAX เมื่อ 17 ก.ค. 2026 ได้ผลจัดประเภทสแปมใกล้เคียง TabICL (F1 ราว 0.886 เทียบกับ 0.888 บนจอ) จากข้อมูลฝึก 100 แถว
2.ข้อจำกัดที่เขาเจอไม่ใช่ความแม่น แต่เป็นเวลา: fit ไม่กี่วินาที ขณะที่ predict บน CPU ล้วนใช้เกือบ 1 ชั่วโมงครึ่งกับ 4,501 แถว เทียบกับ TabICL ที่นับเป็นไม่กี่นาที
3.แพ็กเกจใหม่มากและเปลี่ยนเร็ว: PyTorch backend ใช้ไม่ได้บนเครื่องเขาในวันนั้น และ 1.0.1 มีเฉพาะบน GitHub (PyPI ออก 1.0.1 ภายหลังวันที่ 21 ก.ค.)
4.ผลชุดเดียวไม่ใช่หลักฐาน ผู้พูดบอกเองว่าไม่ใช่ และ benchmark ที่ชี้ว่า TabFM ดีกว่าเป็นของผู้พัฒนาเอง (แผนภูมิ Elo ใน blog ตรงกับที่เขาเล่า)
5.เขาใช้ foundation model เมื่อข้อมูลฝึกน้อย เพราะเมื่อข้อมูลมากวิธีคลาสสิกก็ดีอยู่แล้ว (เป็นความเห็นของเขา ไม่ได้ทดสอบเทียบในคลิป)
