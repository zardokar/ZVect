📋 บทสรุปย่อ

บทสรุปย่อ: ผู้สอนแยก ColBERT เป็น branch mixed_precision_false แล้วปิดการแปลงเป็น half precision ทุกจุดที่หาเจอ (รวม CUDA kernel โดยให้ Claude และ ChatGPT ช่วยหา) จากนั้นทำ index ชุด ConditionalQA (~70,000 เอกสาร) ทั้งสองแบบแล้วเทียบ: FP32 เต็มเร็วกว่า (70 วินาที เทียบ 180) ใช้ GPU น้อยกว่าเล็กน้อย แต่ CPU มากกว่าเล็กน้อย, recall@10 สูงกว่านิดเดียว (0.1303 เทียบ 0.1299), passage ที่ดึงได้ต่างกัน: ตัวนับสองทิศได้ 388 (ผู้สอนคิดเป็น ~14%), และ centroid ต่างกันมาก แม้ metadata ของ index เหมือนกันทุกค่า ผู้สอนย้ำว่าเป็นการทดลองด้วยความอยากรู้ ชุดข้อมูลเดียว เอกสารสั้น และอาจตกบางจุดที่ต้องแก้

โหมดของเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ (license มาตรฐานของ YouTube, ตรวจ 2026-10-11) ครบทุกประเด็นและตัวเลข ไม่เปลี่ยนความหมาย · คลิปปี 2025 อยู่ในช่วงความรู้ของผู้จัดทำ ไม่ได้ค้นเว็บ ตัวเลขตรวจกับภาพบนจอ

🧭 สรุปเชิงลึก

คำถาม: ColBERT ใช้ half precision (FP16) หลายจุดระหว่างทำ index และค้น ถ้าบังคับเป็น FP32 ทั้งหมด จะต่างอะไรบ้าง ผู้สอนบอกตั้งแต่ต้นว่า ได้ยินมาว่า GPU ทำงานกับ half precision ได้ดีกว่า (ไม่รู้รายละเอียด) และนี่ไม่ใช่ best practice เป็นแค่การสำรวจด้วยความอยากรู้

สิ่งที่แก้ใน branch: ปิด MixedPrecisionManager ใน checkpoint, ไม่แปลง embedding ของเอกสารเป็น half, เก็บ sample embedding / centroid / residual เป็น float, cosine ระหว่าง centroid กับ embedding เป็น float, CUDA kernel ของการคลาย residual จาก half เป็น float, จุด kFloat16 → kFloat32 ที่ทำให้ query ตอนค้นเป็น full precision และตั้งค่าเริ่มต้นใน config (รวมไฟล์ training) เป็น false

วิธีทดลอง: conda สองชุด (ColBERT ปกติ กับ branch FP32) สคริปต์ทำ index พร้อมเธรดวัดหน่วยความจำ CPU/GPU ทุก 5 วินาที และสคริปต์วัด recall ด้วย pytrec_eval ชุดข้อมูล UKPLab DAPR ConditionalQA (~70,000 แถว เอกสารเฉลี่ยราว 15 token — ผู้สอน "คิดว่า")

ผล: เวลา index FP32 70 วินาที / mixed 180 วินาที · GPU สูงสุด 5.5 / 5.78 GB · CPU สูงสุด 0.8235 / 0.814 GB · recall@10 0.130349 / 0.129939 (FP32 สูงกว่าราว 0.3%) · passage ที่ไม่ตรงกัน 388 (นับทั้งสองทิศ; บนจอหาร 388 ด้วย 271×10 = 0.143 — ผู้จัดทำตีความว่า 271 คือจำนวนคำถาม) · ผลรวมคะแนน FP32 80,435 / mixed 80,438 · metadata ของ index เหมือนกันหมด · centroid ต้องใช้ tolerance 1.0 ถึงจะผ่าน allclose · ivf.pid ยาว 963,143 / 975,457 (mixed มากกว่า 12,314) ส่วนจำนวน centroid เท่ากัน 16,384

การคำนวณเพิ่มและข้อสังเกตของผู้จัดทำ: (1) ถ้าทุกคำถามได้ครบ 10 passage ทั้งสองฝั่ง (ผู้สอนพูดว่าคำถามละ 10 ที่ ~10:30 และ dev-0 บนจอมี 10 แต่โน้ตบุ๊กไม่ได้แสดงครบทุกคำถาม) จำนวนที่ต่างในแต่ละทิศจะเท่ากัน 388 จึงเป็น 194 + 194 และสัดส่วน passage ที่เปลี่ยนต่อฝั่งเป็น 194 / 2,710 ≈ 7.2% (หรือ 388 / 5,420) ส่วน 14% บนจอเอาตัวนับสองทิศหารด้วยจำนวน passage ของฝั่งเดียว (2) ตามความรู้ของผู้จัดทำ ColBERT ต้นฉบับตั้ง seed ไว้ (สุ่ม sample และ faiss k-means) ความต่างของ centroid จึงน่าจะมาจาก precision ของ embedding ที่ป้อนเข้า k-means เป็นหลัก แต่คลิปไม่ได้รัน precision เดียวกันซ้ำ จึงยังตัดผลของความไม่ deterministic บน GPU ออกไม่ได้ (ยังไม่ได้ตรวจโค้ดใน fork) (3) ผู้สอนพูดถึงจำนวน centroid สองค่า (~8,000 และ 16,390) ค่าบนจอคือ 16,384

เอาไปใช้กับ ZVect (ผู้จัดทำ): เป็นตัวอย่างหนึ่ง (ชุดข้อมูลเดียว) ว่า precision ของ embedding เปลี่ยน centroid / IVF และ passage ที่ค้นได้ ซึ่งเกี่ยวกับ WIP k-means ที่รอแหล่ง และควรระวังเมื่อลด precision ลงอีก (บท 5.3) แต่คลิปไม่ได้ทดสอบระดับ 1 บิต

1. ตั้งโจทย์และแก้โค้ด ColBERT ให้เป็น FP32 ทุกจุดเท่าที่ผู้สอนหาเจอ (~0:00–3:52)

ผู้สอนอยากรู้ว่า ColBERT ตอนทำ index และตอนค้น ต่างกันอย่างไรระหว่าง FP32 เต็ม กับ mixed precision จึงสร้าง branch ใหม่ใน fork ของ repo ColBERT ชื่อ mixed_precision_false และแก้หลายไฟล์ให้ทุกอย่างเป็น full precision วิธีหาจุดที่ต้องแก้คือส่ง fork/branch ให้ Claude (Opus) ในสองสามบทสนทนา บอกว่าอยากปิดการแปลงเป็น half ทั้งหมด ผู้สอนเจอเองหลายจุด แต่ Claude เจอรายละเอียดเพิ่มอีกมาก เช่นใน CUDA kernel ของการคลาย residual

จุดที่แก้ (ตามลำดับในคลิป): MixedPrecisionManager ใน checkpoint.py ตั้งเป็น false (เป็นที่มาของชื่อ branch) · ในเมธอด doc ของโมเดล ถ้าใช้ GPU จะแปลง embedding จาก BERT เป็น half — comment ออก · ตอน encode passage แปลงเป็น float16 — comment ออก · เซฟ sample embedding เป็น half → เซฟเป็น full · ตอนรวมและแบ่ง sample สร้าง tensor เป็น float16 → float32 · centroid เป็น half → float · คำนวณ residual ตั้ง batch เป็น half → float · cosine ระหว่าง centroid กับ embedding เป็น half → float · เซฟ centroid เป็น full · CUDA kernel (ผู้สอนบอกว่าไม่ค่อยเข้าใจ จึงพึ่ง Claude และ ChatGPT) เปลี่ยน kFloat16 → kFloat32 และหลายจุดจาก half → float · query ตอนค้นเป็น full · ค่าเริ่มต้นใน config เป็น false และเพื่อความครบ ไฟล์ training ก็ตั้งเป็น false แม้ไม่ได้ฝึกอะไร

ผู้สอนบอกว่าเข้าใจว่า GPU เหมาะกับ half precision มากกว่า (ได้ยินและอ่านมา ไม่รู้รายละเอียด) และย้ำว่านี่ไม่ใช่ best practice เป็นการสำรวจด้วยความอยากรู้เท่านั้น

2. ตั้งการทดลอง: สอง environment สองสคริปต์ (~3:53–7:00)

สร้าง conda environment สองชุด: ชุดหนึ่งติดตั้ง ColBERT ปกติ อีกชุดติดตั้ง branch FP32 แล้วรันสองไฟล์ในแต่ละชุด

สคริปต์ที่ 1 (ColBERT MemPlot): ใช้เธรดแยกบันทึกหน่วยความจำทุก 5 วินาทีระหว่างทำ index (CPU เป็น GB และ GPU) ใส่ลง list config ที่ใช้ยกมาจากการทดลองก่อน ไม่ได้ปรับเพื่อการทดลองนี้ เรียก indexer.index กับ passage ของชุด UKPLab DAPR ConditionalQA มี argument เลือก precision เป็น FP32 หรือ AMP (mixed) แล้วเซฟค่าที่อ่านได้และวาดกราฟ รันจาก command line ในแต่ละ environment

สคริปต์ที่ 2 (recall): เตรียม qrels เป็น dictionary ตามรูปแบบที่ pytrec_eval ต้องการ สร้าง evaluator ส่งผลค้นเข้าไปแล้วได้ค่าเฉลี่ย recall ColBERT ต้องการ query เป็น dictionary จุดสำคัญคือ argument ชื่อ index: ใน environment FP32 ส่ง index ที่ทำด้วย FP32 และใน environment mixed ส่ง index ของ mixed ค่าอื่นของ searcher ใช้ค่าที่เคยใช้ เซฟผลค้นไว้วิเคราะห์ต่อ แล้วพิมพ์ recall

3. ผลระหว่างทำ index: เวลาและหน่วยความจำ (~7:01–9:18)

GPU: FP32 ใช้เวลา 70 วินาที สูงสุด 5.5 GB ส่วน mixed ใช้ 180 วินาที สูงสุด 5.78 GB ผู้สอนไม่ได้คาดไว้ คิดว่า FP32 น่าจะใช้หน่วยความจำมากกว่า และไม่รู้ว่าเกิดอะไรขึ้น อาจเพราะชุดข้อมูลเล็กพอ (70,000 แถว) จนความต่างไม่มีนัย

CPU: FP32 สูงสุด 0.8235 GB mixed 0.814 GB คือ FP32 ใช้ CPU มากกว่าเล็กน้อย ผู้สอนย้ำอีกครั้งว่าแปลกใจที่ FP32 ใช้ 70 วินาที แต่ mixed ใช้ 180 และยังไม่ได้ทำ memory profiling เต็มรูปแบบ จึงชี้ไม่ได้ว่าต่างตรงไหน

กราฟ: GPU RAM ของ mixed มีช่วงราบ (plateau) ส่วน FP32 แทบไม่มี ผู้สอนเดาว่า "อาจ" มีความต่างของการประมวลผลตรงนี้ และ "อาจ" เป็นเหตุที่ mixed ช้ากว่าราว 100 วินาที กราฟ CPU: FP32 พุ่งไปราว 0.83 mixed ต่ำกว่า 0.82 เล็กน้อยแล้วคงที่ ความต่างใหญ่สุดคือเวลา และผู้สอนไม่รู้ว่าทำไม mixed ทำ index นานกว่า

4. ผลตอนค้น: recall, passage ที่ได้ และคะแนน (~9:19–12:39)

recall: ต่างกันน้อยมาก FP32 สูงกว่าราว 0.3% ผู้สอนบอกว่าแทบไม่มีความหมาย (บนจอ FP32 0.130349, mixed 0.129939, สัดส่วนต่าง 0.00316) แต่เมื่อรวมกับที่ทำ index เร็วกว่า FP32 ก็ได้ recall ดีกว่าเล็กน้อยในเวลาที่น้อยกว่า

passage ที่ดึงได้: สองแบบไม่ได้ดึง passage ชุดเดียวกัน ผลของแต่ละคำถาม (เช่น dev-0) เป็น dictionary ของ passage id กับคะแนนจากขั้นให้คะแนนของ PLAID คำถามละ 10 passage ผู้สอนไล่ทุก query id ถ้า passage ในผลฝั่ง FP32 ไม่อยู่ในผลฝั่ง mixed นับ 1 และทำกลับทิศด้วย ได้ 388 จากราว 3,000 หรือ "ประมาณ 14%" แปลว่าการเปลี่ยน precision ไม่ได้กระทบแค่การทำ index แต่กระทบ passage ที่ได้จริงด้วย ผู้สอนบอกว่าจะชี้ให้เห็นภายหลังว่าทำไม "หรืออย่างน้อยคำอธิบายหนึ่งที่เป็นไปได้" (ส่วนที่ 5–6)

คะแนน: ผู้สอนเดาว่า FP32 น่าจะได้คะแนนสูงกว่า แต่ผิด ผลรวมคะแนน 10 passage ของทุกคำถาม mixed = 80,438 FP32 = 80,435 คือ FP32 ต่ำกว่าเล็กน้อย

การคำนวณเพิ่มของผู้จัดทำ: บนจอหาร 388 ด้วย 271 × 10 = 2,710 ได้ 0.143 แต่ตัวนับนับทั้งสองทิศ ถ้าทุกคำถามมี 10 passage ทั้งสองฝั่ง (ผู้สอนพูดว่าคำถามละ 10; โน้ตบุ๊กไม่ได้แสดงครบทุกคำถาม) จำนวนที่ต่างในแต่ละทิศจะเท่ากัน (194 + 194) สัดส่วน passage ที่เปลี่ยนต่อฝั่งจึงเป็นราว 7.2% · ผู้สอนพูด "ราว 3,000" แต่ตัวหารบนจอคือ 2,710

5. ไฟล์ index: metadata เหมือนกัน แต่ centroid ต่างกันมาก (~12:40–15:13)

ผู้สอนเทียบไฟล์ index สองชุดที่สร้างในสอง environment ดู metadata เช่น จำนวนบิต รอบของ k-means จำนวน GPU จำนวน chunk จำนวน centroid จำนวน embedding — เหมือนกันทุกค่า

ความต่างเริ่มเห็นที่ centroids.pt ซึ่งคือ centroid ที่ได้จากการจัดกลุ่ม token embedding ของเอกสาร (ผู้สอนพูดว่า "คิดว่าราว 8,000") เทียบด้วย torch.allclose ต้องแปลง precision ให้ตรงกันก่อน: แปลง mixed เป็น full แล้วเทียบด้วย tolerance ปกติ → ไม่ผ่าน กลับทิศแปลง full เป็น half → ไม่ผ่านเหมือนกัน ต้องใช้ tolerance 1.0 ถึงผ่าน ซึ่งใหญ่มากเมื่อค่าเป็นเศษส่วน ผู้สอนสรุปว่า centroid "ต่างกันมาก" (แก้คำตัวเองจาก "ต่างกันทั้งหมด") จำนวนเท่ากันเพราะจำนวน partition เท่ากัน และใช้โมเดล Answer.AI ColBERT 96 มิติเหมือนกัน แผ่ค่า centroid ทุกตัวแล้ววาด scatter เห็นความแปรปรวนชัด

แก้ไขจากผู้จัดทำ: บนจอ centroid แผ่ออกได้ 1,572,864 ค่า = 16,384 × 96 มิติ จำนวน centroid จริงจึงเป็น 16,384 (ตรงกับ ivf.pid[1]) ไม่ใช่ "ราว 8,000"
ข้อสังเกต (ผู้จัดทำ): ตามความรู้ของผู้จัดทำ ColBERT ต้นฉบับตั้ง seed ให้การสุ่ม sample และ k-means ความต่างนี้จึงน่าจะมาจาก precision เป็นหลัก แต่คลิปไม่ได้รัน precision เดียวกันซ้ำ จึงยังแยกผลของความไม่ deterministic บน GPU ไม่ได้

6. Mapping passage–centroid (ivf.pid) และข้อสรุป (~15:14–18:42)

ไฟล์สุดท้ายคือ ivf.pid.pt ซึ่งเก็บ mapping จาก passage id ไปยัง centroid id ส่วนแรกคือลำดับของ passage id เทียบด้วย allclose ไม่ได้เพราะยาวไม่เท่ากัน: FP32 มีราว 963,000 รายการ mixed มีมากกว่าราว 975,000 ต่างกันราว 12,000 (บนจอ 963,143 กับ 975,457 ต่าง 12,314) แปลว่า mixed หา mapping ระหว่าง passage กับ centroid ได้มากกว่า ผู้สอนลังเลที่จะเดาสาเหตุ คำอธิบายหนึ่งที่ "อาจ" เป็นได้คือ token embedding ที่คล้ายกันพอระหว่างสอง passage ถูก mixed precision ลบความต่างออก แล้วเพิ่มจำนวนการจับคู่ — "ผมไม่รู้จริง ๆ" ส่วนที่สองคือจำนวน passage id ต่อ centroid ซึ่งมีจำนวน centroid เท่ากัน (ผู้สอนพูด 16,390; บนจอ 16,384)

สรุปของผู้สอน: mixed ทำ index นานกว่า (ไม่รู้สาเหตุ) ใช้ GPU มากกว่าเล็กน้อย FP32 ใช้ CPU มากกว่าเล็กน้อย (สมเหตุสมผลกว่า) FP32 ได้ recall ดีขึ้นแบบแทบไม่มีนัย ได้ passage ต่างกันพอสมควร คะแนนรวมต่ำกว่า และได้ไฟล์ index ต่างกัน (centroid และ mapping) ข้อแม้: ขนาดตัวอย่างหนึ่ง ชุดข้อมูลเดียวที่ค่อนข้างเล็ก (70,000 เอกสาร ผู้สอน "คิดว่า" เฉลี่ยราว 15 token) วิธีแก้อาจไม่ครบ ผู้สอนลังเลที่จะสรุปอะไรเรื่อง precision กับ ColBERT อยากรู้แค่ว่า "ต่างไหม" และคำตอบคือต่าง โค้ดทั้งหมดจะลงในบล็อก

คำศัพท์ (ความรู้ทั่วไป / ผู้จัดทำเลือก): PLAID = เครื่องค้นของ ColBERTv2 ที่เก็บ token embedding เป็น centroid + residual ที่บีบอัด ivf (inverted file) = รายการว่า centroid ไหนมี passage ใดบ้าง ใช้คัดผู้สมัครก่อนให้คะแนนละเอียด

Key Takeaways

  1. เปลี่ยน precision แล้วผลเปลี่ยนจริง: เวลา (70 s vs 180 s), ไฟล์ index, และ passage ที่ดึงได้
  2. recall@10 แทบไม่ต่าง (FP32 สูงกว่าราว 0.3%) แต่ passage ที่ดึงได้ต่างกัน: ตัวนับสองทิศได้ 388 ซึ่งผู้สอนคิดเป็นราว 14% (ผู้จัดทำคำนวณต่อฝั่งได้ราว 7.2%)
  3. metadata ของ index เหมือนกันหมด แต่ centroid ต่างมาก และ ivf.pid ยาวต่างกัน 12,314
  4. ข้อแม้ของผู้สอน: ขนาดตัวอย่างหนึ่ง ชุดข้อมูลเดียวที่เอกสารสั้น และการแก้โค้ดอาจตกบางจุด · ข้อสังเกตของผู้จัดทำ: คลิปไม่ได้รันซ้ำเพื่อแยกผลของ precision
  5. ผู้สอนใช้ Claude (Opus) และ ChatGPT ช่วยหาจุดแปลง precision รวมถึงใน CUDA kernel โดย Claude เจอหลายจุดที่ผู้สอนไม่เจอ แต่ผู้สอนยอมรับว่าอาจยังตกบางจุด
