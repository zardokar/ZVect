บทสรุปย่อ

นี่คือ workshop ภาคปฏิบัติความยาวราว 90 นาทีของทีมจากบริษัท Neuralk (ปารีส) ที่ PyData London 2026 ว่าด้วย tabular foundation model (TFM) ทั่วไป ได้แก่ TabPFN, TabICL และโมเดลของทีมเอง ไม่ใช่เรื่อง TabFM ของ Google ซึ่งเปิดตัวหลังคลิปนี้ 11 วัน (2026-06-30) ผู้พูดอธิบายว่า TFM คืออะไร ต่างจากต้นไม้ (gradient boosting) อย่างไร ฝึกด้วยข้อมูลสังเคราะห์ทำงานแบบ in-context ตอนใช้ แล้วพาผู้ร่วมงานรันโน้ตบุ๊ก 4 ชุด: ทำนายแรก การเปรียบเทียบที่เป็นธรรม โหมดที่โมเดลล้มเหลว และการตีความด้วย SHAP พร้อมถาม-ตอบยาว ข้อสังเกตของผู้จัดทำ: ผู้พูดเป็นผู้ขายโมเดลของตัวเอง (Seldon) ข้ออ้างเรื่อง win rate และขีดจำกัดของ API จึงเป็นของผู้ขาย ส่วนที่มีค่าที่สุดคือแนวทางเปรียบเทียบโมเดลอย่างระมัดระวัง และรายการข้อจำกัดที่พูดตรง ๆ

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึกพร้อมตรวจข้อเท็จจริง (license มาตรฐานของ YouTube; คำบรรยายเป็น ASR อังกฤษ)

สรุปเชิงลึก

ใจความหลัก. ข้อมูลตารางต่างจากข้อความหรือภาพ เพราะมีหลายชนิดปนกัน (ข้อความ, categorical, ตัวเลข, วันที่) และมักมีค่าที่ขาด ที่ผ่านมาเครือข่ายประสาทแพ้ต้นไม้บนตาราง ผู้พูดอธิบายว่ามาจาก MLP ที่ทำให้การทำนายเรียบเกินไป ขณะที่ต้นไม้แบ่งปริภูมิได้คม แนวคิดใหม่ (เริ่มปี 2022 จากทีมนักวิทยาศาสตร์ชาวเยอรมัน) คือฝึกโมเดลบนชุดข้อมูลทั้งชุดเป็นหนึ่งตัวอย่าง ให้เห็นแถว train พร้อมเฉลยและแถว test ตอนใช้งานจึงส่งข้อมูลทั้งหมดเข้าไปรอบเดียว โมเดลไม่เรียนบนข้อมูลของเรา แต่หาการกระจายจากบริบทแล้วอนุมานแถว test

วิวัฒนาการและเสาหลักสามอย่าง. TabPFN v1 ใช้ attention บนแถวอย่างเดียวและจำกัดจำนวนตัวอย่าง v2 เพิ่ม attention สองทิศทาง (แถวและคอลัมน์) v3 (ผู้พูดบอกว่าออกเมื่อไม่กี่สัปดาห์ก่อน) และ TabICL จากสถาบัน Inria ใช้วิธีบีบข้อมูลก่อนทำ attention บนแถวเพื่อตัดขั้นที่แพงที่สุด ผู้พูดจัดงานวิจัยเป็นสามเสา: prior (ข้อมูลสังเคราะห์ที่ใช้ฝึก สไลด์ระบุว่าส่งผลมากที่สุดและเป็น "ศิลป์ดำ" มากกว่าวิทยาศาสตร์), สถาปัตยกรรม (สไลด์: ถูกจำกัดที่การขยายขนาด) และ context (การเลือกว่าจะใส่แถวไหนเป็นบริบท ซึ่งยังสำรวจน้อยและบางชุดข้อมูลการตัดแถวออกช่วยได้มาก)

จุดแข็งและข้อจำกัดที่พูดตรง ๆ. ดีที่ตารางเล็กถึงกลาง (ถึงราวไม่กี่พันแถว ตามสไลด์) ไม่ต้องค้นหา hyperparameter ได้ baseline แข็งทันที รับชนิดข้อมูลผสมและค่าที่ขาด และความน่าจะเป็นมักจะ calibrate ดีในตัว ข้อจำกัด: ตารางใหญ่ยังแค่ทัดเทียม XGBoost ไม่ได้ชนะขาด ความหน่วงสูงและต้องใช้ GPU (เพราะ attention) ข้อมูลที่ไกลจาก prior มากจะแย่แบบคาดเดาไม่ได้ และตัวโมเดลเสียเวลาที่ขั้น predict ไม่ใช่ขั้น fit เพราะทุกครั้งต้องอ่านบริบททั้งหมด ผู้พูดย้ำว่าไม่ได้อยากแทนที่ต้นไม้ ซึ่งยังเก่งและบางงานยังชนะ

วิธีเปรียบเทียบที่ถูกต้อง (โน้ตบุ๊ก 2). ผลเปลี่ยนมากตามแค่ seed จึงต้องรันหลาย seed/fold ใช้ความเชื่อมั่นแบบ bootstrap และดูส่วนต่างรายคู่ต่อ fold เลี่ยง accuracy บนข้อมูลไม่สมดุล และระวัง preprocessing ที่รั่วข้อมูล test ผลบนสามชุดข้อมูล (heart, shoppers, adult) คือโมเดลเล็กของ Neuralk ดีกว่าต้นไม้บนสองชุดแรก แต่ XGBoost ที่จูนแล้วนำบน adult (ราว 40,000 แถว)

การตีความและการปรับแต่ง. SHAP บนโมเดลของทีมกับ XGBoost ได้ลำดับ feature สำคัญใกล้กัน (ในภาพ ca, cp, thal, slope อยู่ชุดบนทั้งคู่) แต่ขนาดของค่า SHAP ต่างกันมาก ผู้พูดไม่ทราบสาเหตุ ส่วน fine-tuning ทำได้ (ทั้งน้ำหนักทั้งหมดดีกว่า LoRA ตามประสบการณ์ของพวกเขา) และการเพิ่มตัวอย่างด้วย diffusion/CTGAN ก่อน fine-tune ได้ผลน่าประหลาดใจ

ตรวจข้อเท็จจริง (ผู้จัดทำ). 19 ข้อ: ยืนยัน 8, ยืนยันบางส่วน 7, ไม่พบแหล่งยืนยัน 3, ขัดแย้ง 1 ข้อที่ขัดแย้งคือสไลด์เขียนว่าโมเดลโอเพนเวตของ TabPFN และ TabICL ใส่บริบทได้ประมาณ 10,000 แถว ขณะที่ตารางภาพรวมในสไลด์อื่นของเขาเองและแหล่งภายนอกระบุว่า TabICL v2 ไปถึงระดับล้านแถว ส่วน win rate ราว 90% เป็นข้ออ้างของผู้ขาย

เอาไปทำอะไร. ใช้เป็นคู่มือวิธีทดสอบ TFM อย่างซื่อตรง (หลาย seed, ช่วงความเชื่อมั่น, paired delta) และเป็นภาพรวมของ TFM ก่อน TabFM เพื่อเข้าใจว่า TabFM ต่อยอดมาจากอะไร

1. ตาราง ต้นไม้ และกำเนิดของ TFM (~0:03–5:42)

ผู้พูดแนะนำตัวว่ามาจากสตาร์ตอัปในปารีสชื่อ Neuralk (คำบรรยายเขียน "Neural Work") ถามผู้ฟังว่าใครเคยได้ยินหรือใช้ TFM แล้ววางแผนว่าจะอธิบายสั้น ๆ ว่า TFM คืออะไร ต่างจากต้นไม้อย่างไร จากนั้นเข้าสู่โน้ตบุ๊กเพื่อเล่นกับ TFM และดูว่าต่างจาก gradient boosting อย่างไร

ข้อมูลตารางต่างจากข้อความหรือภาพเพราะมีหลายรูปแบบ (ข้อความ categorical ตัวเลข วันที่) ต้องหาวิธีเข้ารหัส และมักมีข้อมูลที่ขาด จึงต้องทำ preprocessing มาก ซึ่ง TFM พยายามเปลี่ยนให้ผ่อนปรนขึ้น ขนาดตารางที่ลูกค้าเจอก็ต่างกันมาก ลูกค้าด้านการแพทย์มีแถวน้อยมาก ส่วนด้านการเงินมีถึงหลักล้านแถว ซึ่งผู้พูดบอกว่ายังเป็นปัญหาสำหรับ TFM ทุกวันนี้

ก่อนมี TFM ไม่มีใครอยากทำ deep learning บนตาราง แม้ใช้ได้แต่ผลมักแย่กว่า งานวิจัยหลายชิ้นชี้ว่าต้นเหตุหลักคือ MLP ที่ทำให้ความไม่ต่อเนื่องของข้อมูลเรียบลงจนการทำนายไม่คม ขณะที่ต้นไม้เก่งเพราะแบ่งปริภูมิได้สะอาด ส่วนการเอาข้อมูลตารางใส่ LLM ผู้พูดว่าไม่ได้ผล การ fine-tune LLM ที่ใหญ่มากเพื่อให้ได้ผลไม่ดีไปกว่า gradient boosting มากนักก็ไม่คุ้ม ทั้งแพงและต้องรอนาน

ในปี 2022 ทีมนักวิทยาศาสตร์ชาวเยอรมันเสนอกระบวนทัศน์ใหม่ (ในคำบรรยายพิมพ์ว่า TFM แต่หมายถึง prior-fitted network): ฝึกโมเดลบนชุดข้อมูลหนึ่งชุดต่อหนึ่งตัวอย่าง ไม่ใช่รายแถว แสดงทั้งแถว train และ test ให้โมเดลหาการกระจายของแถว train แล้วอนุมานบนแถว test เมื่อทำนายก็ส่งข้อมูลทั้งหมดเข้าโมเดลทีเดียว มันจะไม่เรียนบนข้อมูล

ผู้พูดบอกว่า TFM มีมาราวสามปีแล้ว แล้วไล่รุ่น: TabPFN v1 เป็น transformer ใหญ่ที่ทำ attention บนแถว ได้ผลค่อนข้างดีแต่จำกัดมาก ใส่ตัวอย่างได้ไม่กี่แถวไม่เช่นนั้นหน่วยความจำเต็ม TabPFN v2 เพิ่ม attention สองทิศทาง ทั้งบนแถวและคอลัมน์ เพราะข้อมูลความสัมพันธ์ระหว่าง feature ก็สำคัญ และเมื่อไม่กี่สัปดาห์ก่อนมี TabPFN v3 ซึ่งผู้พูดบอกว่าเป็นสถาปัตยกรรมเดียวกับโมเดลโอเพนซอร์สชื่อ TabICL จาก Inria ในปารีส ที่ยังทำ attention บนแถวและ feature แต่บีบชุดข้อมูลก่อนเพื่อตัดขั้น attention ที่แพงบนทุกแถว ทีมของผู้พูดทำงานกับเทคโนโลยีนี้มาปีหนึ่งและมีโมเดลของตัวเองที่ใช้กระบวนทัศน์เดียวกับ TabPFN v3 คือบีบตารางก่อนทำ attention บนแถว

คำบรรยายอัตโนมัติสะกดคำที่เกี่ยวข้องเพี้ยน: "TFM", "TFN", "PFM", "GFM", "TFT" หลายจุดหมายถึง TFM (tabular foundation model) หรือ PFN (prior-fitted network) ตามบริบท; "Neural Work" คือ Neuralk; "cell done" (ที่ 47:34) คือ Seldon; "Tabularina" คือ TabArena ผู้จัดทำแปลตามบริบทและแหล่งที่ตรวจ

2. สามเสาหลักของ TFM: prior, สถาปัตยกรรม, context (~5:42–9:14)

ผู้พูดบอกว่าสิ่งที่ทำให้พวกเขานอนไม่หลับเมื่อพยายามปรับปรุงโมเดลคือสามด้านของงานวิจัย ด้านแรกคือ prior: เทียบกับโมเดลอื่น โมเดลแบบนี้ถูกฝึกด้วยข้อมูลสังเคราะห์ เพราะหาคลังชุดข้อมูลสะอาดขนาดใหญ่บนอินเทอร์เน็ตยาก วิธีที่ง่ายที่สุดคือสร้างตารางปลอมจำนวนมาก โดยสร้างกราฟ ใส่ค่าบนโหนดและการแปลงระหว่างโหนด แล้วสุ่มจากกราฟขนาดใหญ่เหล่านั้นเพื่อแทนข้อมูลตารางที่หลากหลาย สร้างหลายล้านชุดแล้วฝึกโมเดล และบอกว่ามันได้ผล ซึ่งเป็นพื้นที่วิจัยที่ยังเปิดอยู่

สำหรับผู้ใช้ ข้อดีเชิงปฏิบัติคือเมื่อฝึกด้วยข้อมูลสังเคราะห์ล้วน จึงไม่มี leakage: โมเดลไม่เคยเห็นตารางของเรา ไม่มี PFN ตัวไหนเคยเห็นข้อมูลของเรา จึงไม่มีความรู้ล่วงหน้าเกี่ยวกับข้อมูลนั้น แม้เป็นข้อมูลโอเพนซอร์สที่ใช้ทดลองก็ไม่เคยเห็น

ด้านที่สองคือสถาปัตยกรรม ซึ่งผู้พูดว่าเรียบง่าย: attention สองทิศทางบนแถวและคอลัมน์ ซึ่งแพงมาก แต่แนวหน้าล่าสุดคือหาทางบีบข้อมูลเพื่อให้ inference มีประสิทธิภาพ

ด้านที่สามคือ context: ใส่ชุดข้อมูลทั้งชุดเข้าโมเดลเพื่อทำนายได้ แต่บางครั้งไม่ควรใส่ทั้งหมด โมเดลพยายามฟิตการกระจายจากตัวอย่าง train ที่เราให้ หากมันมีสัญญาณรบกวนหรือไม่ตรงงานจริง ผลอาจแย่ลง นี่เป็นพื้นที่ที่ยังสำรวจน้อย ไม่มีสูตรวิเศษ มักมาจากความรู้ของเราเกี่ยวกับข้อมูล แต่เคยเห็นชุดข้อมูลที่การเอาตัวอย่างออกให้การทำนายดีขึ้นมาก

ผู้พูดบอกว่าทีมมี benchmark สำหรับเปรียบเทียบ TFM เพราะไม่ง่ายที่จะรู้ว่าเทคโนโลยีน่าสนใจนี้ใช้ได้จริงหรือไม่ และ benchmark แสดงสมรรถนะของ TFM บนชุดข้อมูลจำนวนมาก (คำบรรยายในช่วงนี้ขาดหาย มีเศษคำเช่น "outshining gradient boosting" เท่านั้น)

เสริมจากผู้จัดทำ

สไลด์ "three pillars" ให้ความเห็นของผู้พูดเองว่า prior คือตัวเลือกที่ส่งผลมากที่สุด สถาปัตยกรรมคือจุดที่ถูกจำกัดเรื่องการขยายขนาดมากที่สุด และ context คือ "วิธีทำงานใหม่กับข้อมูลตาราง" ผู้จัดทำไม่ได้ตรวจเหตุผลเชิงเปรียบเทียบเหล่านี้กับงานวิจัย

3. ใช้ TFM ในงานจริง: ข้อดี ข้อจำกัด และแผนของ workshop (~9:14–13:47)

ใน workshop ผู้เข้าร่วมเลือกได้ว่าจะใช้ API ของ Neuralk (มีคูปองเครดิต) หรือใช้โมเดลโอเพนซอร์ส: TabPFN ซึ่งต้องใช้ key เพื่อดาวน์โหลดน้ำหนักจาก Hugging Face หรือ TabICL ที่รันในเครื่องด้วยการติดตั้งแพ็กเกจ ซึ่งอาจช้า แผนคือทดลองฟิตโมเดลกับข้อมูล เทียบกับ gradient boosting แล้วดูว่าเทียบอย่างจริงจังได้อย่างไรด้วย preprocessing ที่ดีและ cross validation

TFM ถูกห่อให้เข้ากับ scikit-learn มีเมธอด fit แต่ไม่ได้ฟิตอะไรบนข้อมูล เมธอดนี้มีไว้ส่งข้อมูลไปยังเซิร์ฟเวอร์หรือเอามาต่อกับ test ข้อมูลทั้งหมดเข้าโมเดลทีเดียว โมเดลไม่เรียนบนข้อมูล ไม่ทำ gradient descent และไม่มีข้อมูลของเรารั่วเข้าโมเดล มันไม่ได้ฝึกแบบ LLM ในบริบทบางแบบ จึงใช้ง่าย แทนที่วิธี ML คลาสสิกในไปป์ไลน์ได้ ที่ต่างคือสมรรถนะ ความเร็ว และปัญหาที่แก้ได้

ผู้พูดสรุปว่า TFM เป็นความก้าวหน้าใหญ่บนข้อมูลบางประเภท ซึ่งมักเป็นชุดข้อมูลเล็ก เพราะการฝึกด้วยข้อมูลมากทำให้มีความรู้ล่วงหน้าและเข้าใจข้อมูลที่ใส่ได้เร็ว จึงดีบนตารางเล็กถึงกลาง ไม่ต้องค้นหา hyperparameter (ไม่ต้องหาจำนวนต้น ความลึก) และความน่าจะเป็นที่ได้ออกมามัก calibrate ดี จึงไม่ต้องทำ calibration เพิ่ม

ข้อเสียที่ผู้พูดบอก: PFN ยังไม่เก่งบนตารางใหญ่ ยังทัดเทียม XGBoost แต่ไม่มีช่องว่างการปรับปรุงขนาดใหญ่ การขยายสู่ตารางใหญ่มากยังเป็นพื้นที่วิจัย มีปัญหาความหน่วงสำหรับตารางใหญ่มาก ราคาแพง ต้องใช้ GPU เพราะเป็น transformer ที่ทำ attention และหากข้อมูลอยู่ไกลจากข้อมูลสังเคราะห์ที่ใช้ฝึก (แม้ถูกออกแบบให้กว้างและพยายามแทนข้อมูลจริงทั้งหมด) บางครั้งเจอชุดข้อมูลที่อยู่นอกขอบเขตข้อมูลฝึก ผู้พูดย้ำว่า "ไม่ได้อยากแทนที่ต้นไม้ด้วย TFM" มันเป็นเครื่องมือใหม่ ต้นไม้ยังดีมากและหลายงานยังชนะ แต่หวังว่าจะเปลี่ยนในอนาคต

ข้อที่ควรเข้าใจให้ตรง

สไลด์ในภาพเขียนว่าโมเดลโอเพนเวต (TabPFN, TabICL) จำกัดบริบทราว 10,000 แถว ซึ่งขัดกับตารางภาพรวมในสไลด์อีกหน้าของผู้พูดเอง (TabICL v2 "1M-row ICL") และกับแหล่งภายนอก (ดูตารางตรวจข้อเท็จจริง) ผู้จัดทำจึงไม่ใช้ตัวเลข 10,000 เป็นข้อเท็จจริง

4. ถาม-ตอบ: ความเข้าใจพื้นฐาน (~13:47–21:24)

ผู้ฟังถามว่านี่คือ unsupervised learning หรือไม่ เพราะดูเหมือนไม่ได้เรียนอะไรจากข้อมูล ผู้พูดตอบว่าไม่ใช่: เรามี X และ Y เหมือนเดิม จึงทำงานร่วมกับ scikit-learn ได้ง่าย ให้ทั้งสองแก่โมเดลซึ่งพยายามเข้าใจว่าจาก X ไปสู่ Y อย่างไรเหมือนต้นไม้ แต่ไม่ได้ปรับอะไรภายในโมเดล เป็นการแสดงตัวอย่างเหมือน prompt LLM ที่บริบทคือข้อมูล train ส่วน Stanislas เสริมให้ชัดว่าข้อมูล target ถูกเพิ่มเป็น embedding ให้ตัวแทน (representation) ของแถวบริบท ไม่ได้ใช้ target ใน loss ตอนนี้

ผู้ฟังถามว่าเป็น transformer แบบ encoder หรือ decoder ตอบว่า "คล้าย encoder" และคล้ายการใช้ BERT ในการวิเคราะห์ sentiment หรือจัดประเภท intent: เป็นเทคโนโลยีเดียวกัน แต่ใช้กับข้อมูลตาราง จากนั้นผู้พูดชี้ว่าต่างจาก BERT มาก เพราะเป็นสแต็กของ transformer ที่ทำ attention ระหว่างแถว (เวอร์ชันแรก) และระหว่าง feature ด้วย โดยต้อง tokenize feature ด้วย ปัจจุบันมักทำ attention บน feature แล้วใช้ token แบบ CLS ต่อแถว ซึ่งกลายเป็นตัวแทนของแถว แล้วทำ attention บนตัวแทนนั้น ต่างจาก BERT ตรงที่ตัวแทนของ token ผสานกับบริบทและข้อมูลที่แสดงมากกว่า เพราะ attention สองทิศทาง ทุก token มีตัวแทนต่างกันตามคอลัมน์และแถวของมัน

ขนาดโมเดล: ผู้พูดบอกว่าขึ้นกับรุ่น เป็นหลักล้านพารามิเตอร์ เช่น 5 ล้านหรือ 50 ล้าน รันบน CPU ได้ และ TabICL จาก Inria มีโค้ดทำให้รันบนแล็ปท็อปง่ายขึ้น แต่เหมาะตารางเล็ก ตารางใหญ่จะแพงและต้องรอนาน ข้อมูลทั้งชุดเข้าพร้อมกันและเป็น forward pass เดียว ไม่ทีละรายการ

ผู้ฟังถามเรื่อง loss ที่ใช้ฝึก ตอบว่าไม่ใช่ contrastive หรือ unsupervised: เนื่องจากสร้างตารางเอง จึงมีเฉลยของชุด test จึงแค่ถดถอยเป้าหมายจริงแล้วอัปเดตน้ำหนัก ด้วย cross entropy (Stanislas: บางโมเดลใช้ representation loss เช่น masked modeling แต่ตัวหลักคือ loss ของงานคลาสสิก: จัดประเภท ถดถอย หรือทั้งสองอย่างผสม) ส่วน tokenization ในโมเดลส่วนใหญ่เป็นเพียง linear layer ที่ฉายข้อมูล ไม่มีพจนานุกรม ในงานวิจัยและโมเดลโอเพนซอร์สปัจจุบัน feature ตัวเลขกับ categorical ถูก embed แบบเดียวกัน แต่มีการ retokenize ตามเนื้อหาของคอลัมน์ ทำให้ categorical ถูก embed ต่างจากตัวเลขในที่สุด (Stanislas เรียกว่าเป็นการทำลายความสมมาตร ผู้ฟังแย้งว่าโมเดลต้องเรียนรู้เอง)

5. ข้อมูลสังเคราะห์กับข้อมูลจริง การเตรียมงาน และ time series (~21:24–28:07)

ผู้ฟังถามว่าฝึกด้วยข้อมูลสังเคราะห์ล้วนหรือ ผู้พูดตอบว่าโมเดลรุ่นแรก ๆ ฝึกด้วยข้อมูลสังเคราะห์ล้วน ทีมจากแคนาดาฝึกโมเดลด้วยข้อมูลจริงและได้ผลค่อนข้างดี เหตุผลของข้อมูลสังเคราะห์คือสะดวก: ควบคุมขนาดและลักษณะของชุดข้อมูลได้ บางโมเดลฝึกบนข้อมูลสังเคราะห์ก่อน แล้วฝึกต่อด้วยข้อมูลจริงที่คัดมาชุดเล็ก และอาจมีโมเดลที่ฝึกด้วยข้อมูลจริงล้วนในอนาคต แต่ต้องใช้งานมากในการสร้างคลังชุดข้อมูลให้ส่งเข้าโมเดลได้ง่าย

Stanislas อธิบายว่ามีสัญชาตญาณสองข้อสู้กัน: ข้อมูลจริงดีเพราะมีการกระจายและปฏิสัมพันธ์จริง ซึ่งเลียนแบบยาก แต่หายากและมีข้อมูลขยะมาก ข้อมูลสังเคราะห์ให้การควบคุมและความพร้อมใช้ทำงานเฉพาะอุตสาหกรรมหรือโดเมนได้ ข้อจำกัดเดียวคือต้องทำให้ตรงกับข้อมูลจริง ซึ่งยากมาก และเป็นสิ่งที่พวกเขาต่อสู้กับมันเมื่อทำงานกับ prior คือให้ตรงกับการกระจายและปฏิสัมพันธ์ระหว่าง feature จริง

เรื่องการเตรียมงาน: ผู้เข้าร่วมใช้โมเดลของทีมหรือโอเพนซอร์สก็ได้ ตารางเล็กรันในเครื่องได้ แต่ตารางใหญ่ต้องรอนาน ต้องสร้างบัญชีและกรอกคูปองเพื่อรับเครดิต ถ้าเลือกโอเพนซอร์สให้เปลี่ยนตัวเลือก TFM ในโน้ตบุ๊กระหว่าง TabPFN กับ TabICL ซึ่ง TabICL ติดตั้งด้วย pip ใช้ได้เลยแต่อาจช้ากว่า

ผู้ฟังถามเรื่อง time series ผู้พูดเล่าว่าเมื่อราวหนึ่งปีก่อน ตอนที่ทีม PFN ปล่อยโมเดลรุ่นแรก ๆ มีผู้ลองใช้ patch encoding กับอนุกรมเวลา โดยตรงกับโมเดลที่ไม่เคยฝึกกับอนุกรมเวลาเลย และได้ผลดีมากทันทีอย่างน่าแปลกใจ แต่ตอนนี้โมเดลอนุกรมเวลาดีขึ้นเรื่อย ๆ จึงไม่แข่งขันได้อีกแล้ว พวกเขากำลังใส่กลไกที่เลียนแบบอนุกรมเวลาจริงลงใน prior เพื่อฝึกกับรูปแบบเหล่านั้น แต่ใช้สถาปัตยกรรมเดียวกันได้

6. โน้ตบุ๊ก 1: ทำนายโรคหัวใจ, preprocessing และ feature engineering (~28:07–35:19)

โน้ตบุ๊กแรกเน้นการทำนายครั้งแรกด้วย TFM และตรวจว่าทุกอย่างทำงาน ใช้ชุดข้อมูลเล็กมากเพื่อทำนายโรคหัวใจ ซึ่งเป็นชุดที่ข้อมูลมีน้อยจนต้นไม้ลู่เข้ายาก ต้องหา hyperparameter ที่ดี แต่ TFM ไม่มี hyperparameter จึงใช้ได้เลย และเพราะถูกฝึกด้วยชุดข้อมูลจำนวนมากจึงมีความรู้ล่วงหน้าเกี่ยวกับปัญหา ผู้พูดบอกว่าปัจจุบันงานวิจัยด้านการแพทย์จำนวนมากใช้ PFN ทำนาย เพราะใช้ง่าย ผู้ที่ทำงานในโรงพยาบาลอาจไม่ใช่นักวิทยาศาสตร์ข้อมูล ไม่รู้ว่าจะฟิตต้นไม้อย่างไร และใช้ได้แม้มีผู้ป่วยไม่กี่ราย

ข้อมูลเป็น categorical และตัวเลขเป็นหลัก ทำเพียงแบ่ง train/test ธรรมดาก่อน แล้วค่อยดูภายหลังว่าต้องทำ cross validation จึงจะเห็นความต่างจริง ผู้พูดบอกว่าตอนนี้ส่วนใหญ่จะเจอสัญญาณรบกวนของการทำนาย ซึ่งขึ้นกับ fold และ seed ที่ใช้แบ่งข้อมูล

ผู้พูดบอกว่ายังต้องทำ preprocessing บ้าง แต่น้อยกว่าวิธีอื่น ไม่ต้องใช้เวลาหลายชั่วโมงหา preprocessing ที่สมบูรณ์แบบ สำหรับ TFM การเปลี่ยน preprocessing ไม่ทำให้สมรรถนะเปลี่ยนมาก เทียบกับ MLP ที่ไวต่อการเข้ารหัสตัวเลขบางแบบ (เช่น งานของ RTDL) และต้นไม้ที่มีงานเรื่อง preprocessing ด้วย เมื่อเปลี่ยน preprocessing ของแต่ละชนิดข้อมูลในตาราง ค่าทำนายของ TFM ดูไม่เปลี่ยนมาก ผู้พูดบอกว่าไม่ทราบเหตุผลมากนัก แต่ Stanislas เสริมว่ามาจากคลังข้อมูลสังเคราะห์มหึมาที่มีการเปลี่ยนแปลงมากมาย โมเดลจึงเคยเห็น preprocessing ทุกแบบในช่วง pre-training

ผู้ฟังถามว่ายังต้องเน้น preprocessing หรือไม่ (เช่นเมื่อมีคอลัมน์มาก) ตอบว่ายังต้องทำ feature engineering: ถ้ามีความรู้เรื่องข้อมูลแล้วสร้างการรวมคอลัมน์ที่เพิ่มสัญญาณ ก็ใส่ข้อมูลเพิ่มเข้า และได้ผลกับ TFM สมรรถนะจะดีขึ้นเมื่อรู้จักสร้างข้อมูล แต่โมเดลไวต่อชนิดการ scale หรือการเข้ารหัส categorical น้อยกว่า

ผู้ฟังอีกคนถามว่า ถ้าชุดข้อมูลใหญ่มาก (เช่น 10 ล้านแถว) จะ fit บนตัวอย่างหนึ่งแล้วทำนายส่วนที่เหลือทีละก้อนได้ไหม ผู้พูดตอบว่าการแบ่งก้อนแถว test ได้อย่างอิสระ เพราะแถว test ไม่ attend ซึ่งกันและกัน จะทีละแถวหรือทีละก้อนก็ได้ แต่การแบ่งบริบท (train) ขึ้นกับว่าก้อนเล็กแทนการกระจายของทั้งชุดได้ไหม ต้องหาตัวแทนที่เล็กกว่าด้วยการสุ่มแถวที่แทนความยากของงาน Stanislas เสริมว่า ณ ตอนนี้ TFM มี learning curve แบบเดียวกับโมเดลคลาสสิก: ใส่ข้อมูลเป็นบริบทมากยิ่งดี บางครั้งมีสัญญาณรบกวนมากจนข้อมูลเพิ่มเป็นผลเสีย แต่ส่วนใหญ่ดีขึ้น ผู้พูดบอกว่าใส่เกิน 10,000 แถวได้ API ปัจจุบันส่งได้ 1 ล้านแถว และจะมีรุ่นใหม่ในสัปดาห์หน้าที่ถึงราว 4–5 ล้านแถว ซึ่งเป็นสิ่งที่โมเดลของพวกเขาทำได้ แต่ API ของเจ้าอื่นไม่ทำ (ข้ออ้างของผู้ขาย)

7. โน้ตบุ๊ก 1: ผลทำนาย การสลับ feature และ calibration (~35:19–38:51)

ในเซลล์ก่อนหน้าทดสอบ logistic regression และสำหรับ TFM ก็ทำเหมือนกัน คือ fit แล้ว predict โดย fit แค่ต่อข้อมูล train เข้ากับ test แล้วส่งเข้าโมเดล (หรือส่งไปยัง API) งานจริงทั้งหมดอยู่ที่ predict ผลที่ได้เทียบเคียงกันพอสมควร logistic regression ทำงานได้ดีมากบนชุดข้อมูลนี้ ผู้พูดเตือนว่าอย่าดู accuracy เพราะข้อมูลไม่สมดุลมาก ตัวเลขจึง "โกหก" เมื่อเทียบสองโมเดลตรง ๆ ในแง่ ROC ใกล้เคียงกัน และใช้โมเดลรุ่นเล็กของพวกเขา

เรื่องที่ยังไม่ได้พูด: TFM มี hyperparameter หนึ่งตัวคือจำนวนครั้งที่สลับ feature ของชุดข้อมูล TFM ไม่ขึ้นกับลำดับของแถว แต่ปัจจุบัน (และผู้พูดบอกว่าจะเปลี่ยนในอนาคต) ยังไม่เป็นอิสระจากลำดับของ feature เหมือน LLM ที่ใส่ positional encoding บอกว่า token นี้อยู่ก่อนนั้น TFM ก็มีเช่นกันสำหรับ feature ตอนฝึก transformer มี positional encoding บอกว่า feature นี้อยู่ก่อน ตัวนี้อยู่หลัง ดังนั้นหากเปลี่ยนลำดับ feature ผลทำนายจะเปลี่ยน TFM จึงมีกลไกที่ทำ forward pass หลายรอบ โดยแต่ละรอบสลับลำดับ feature เพื่อพยายามกู้ความเท่าเทียมของลำดับ

ความน่าจะเป็นที่ทำนายครอบคลุมช่วงทั้งหมด มีตัวอย่างที่โมเดลค่อนข้างมั่นใจและตัวอย่างที่ลังเล ผู้พูดบอกว่าไม่ได้น่าตื่นเต้นอะไร: มันทำงานเหมือนต้นไม้ตัดสินใจที่ใช้อยู่ ไม่ต้องเปลี่ยนอะไร ข้อต่างคือไม่ต้องหา hyperparameter ซึ่งจะเห็นชัดขึ้นกับโมเดลอื่น โน้ตบุ๊กนี้แค่แสดงผล ยังไม่ได้ตรวจว่าโมเดลแม่นแค่ไหนและเปลี่ยนไปเท่าไรเมื่อสุ่มข้อมูลต่างกัน

8. โน้ตบุ๊ก 2: เปรียบเทียบอย่างเข้มงวด (~38:51–45:30)

ผู้พูดสาธิตปัญหาที่เจอได้ถ้าไม่ระวัง preprocessing: ตัวอย่างแรกใช้ preprocessing แบบสุ่มโดยมีคอลัมน์หนึ่งเข้าถึง test ทำให้ทำนายง่าย และสาธิตว่าแค่เปลี่ยน seed (ซึ่งกำหนดว่าแถวไหนเป็น train/test) ความแม่นก็ผันแปรมาก นอกจากนี้ยังดูตัวชี้วัดผิดได้: เมื่อปัญหาไม่สมดุลมาก ตัวทำนายสุ่มก็ได้ accuracy สูง มี benchmark จำนวนมากที่เทียบ TFM กับต้นไม้ และบางครั้งก็ทำได้ไม่ดีนัก

วิธีที่ถูกต้องคือดูหลาย seed หลาย fold แล้วดูว่าช่วงความเชื่อมั่นซ้อนกันหรือไม่ ผู้พูดรัน benchmark เล็กบนสามชุดข้อมูลด้วยสามโมเดล: random forest, XGBoost และ TFM โดยไม่จูน XGBoost (เชิญให้ผู้เข้าร่วมลองจูนเอง) จุดเด่นของ TFM คือไม่ต้องหาจำนวนต้นหรือความลึก Stanislas เสริมว่า benchmark ที่มีอยู่แสดงว่า TFM ดีกว่าต้นไม้เล็กน้อยเมื่อต้นไม้ถูกจูน ซึ่งใช้เวลามากและบางครั้งใช้ใน production ไม่ได้ แต่เมื่อใช้ต้นไม้ค่าเริ่มต้น TFM แบบใช้ทันทีดีกว่า "มากกว่ามาก" และช่วยให้ทดลอง feature engineering ได้ทันทีโดยไม่ต้องหา hyperparameter ใหม่ รวมถึงงาน time series ที่อยากลองหลายหน้าต่างเวลา

ผลที่เห็น: TFM โดดเด่นบนข้อมูลเล็ก (heart และ shoppers เล็กมากเมื่อเทียบกับ adult ซึ่งมีราว 40,000 แถว) ที่นี่ใช้โมเดลรุ่นเล็ก จึงลำบากบนชุดขนาดนี้ แต่ผู้พูดบอกว่าถ้าใช้รุ่นใหญ่กว่าจะดีกว่าต้นไม้ และบนชุดเหล่านี้เขาจูนพารามิเตอร์ของต้นไม้แล้ว ปัญหาของกราฟแรกคือเปรียบเทียบโดยไม่แยกปัญหา: ถ้าเทียบ fold ต่างกันรวมกันก็ไม่ได้เทียบปัญหาเดียวกันของแต่ละโมเดล จึงดูส่วนต่างของสมรรถนะภายใน fold เดียวกันระหว่างโมเดล เพื่อดูว่ามีกำไรจริงไหม ผลคือมีช่องว่างจริงบนข้อมูลเล็ก ส่วนบนข้อมูลใหญ่ XGBoost นำ TFM รุ่นเล็กจริง

ผู้ฟังถามถึง AutoGluon ซึ่งก็มีการ ensemble พวกเขาตอบว่ารู้จักดี และมันอยู่ในทุก benchmark ปัจจุบัน และ TFM ยังดีกว่า AutoGluon บน Tabularina (คือ TabArena ตามที่ตรวจ ผู้พูดบอกว่าเป็น benchmark เยอรมัน) ที่มี AutoGluon โหมดสุดขีดให้รัน 4–5 ชั่วโมงกับชุดข้อมูลของเรา ผู้พูดบอกว่าเท่าที่จำได้ TFM ก็ยังดีกว่าด้วยการ inference ครั้งเดียว ผู้ฟังบอกว่าเคยรัน AutoGluon 15 นาทีและได้ผลดี ผู้พูดบอกว่าเป็นแพ็กเกจที่ดีมาก และใช้ TFM เป็นสมาชิกหนึ่งใน ensemble ของ AutoGluon ได้

9. Embedding จากโมเดล, การเปลี่ยนขนาดโมเดล และเรื่องเครดิต (~45:30–49:41)

ผู้ฟังถามว่าได้ embedding จากโมเดลไหม ผู้พูดตอบว่าได้: เพราะกู้ embedding ของทุกแถวได้ จึงทำ pooling ของ embedding ทุกแถวเป็น embedding เดียวสำหรับชุดข้อมูลได้ มีงานวิจัยในรอบ 6 เดือนที่ศึกษาว่า embedding เช่นนี้แทนชุดข้อมูลได้ดีแค่ไหน (ชุดนี้คล้ายชุดนั้นไหม) ใช้ embedding ของโมเดล หรือสร้างจาก meta-feature สถิติของชุดข้อมูล และ Stanislas เสริมว่ามีรายงานจากการแข่งขันแนว Kaggle ว่าแนวโน้มใหม่อย่างหนึ่งคือเอา embedding จาก TFM ไปใส่ใน ensemble ของโมเดลอื่น เพราะ decoder ที่ pre-train มากับ TFM เป็นแค่ MLP แบบง่าย จึงทำได้ดีกว่าด้วยตัวแทนนี้ (ผู้จัดทำไม่ได้ตรวจรายงานนี้)

จากนั้นผู้พูดชวนให้ลองเปลี่ยนขนาดโมเดลในเซลล์ที่ตั้งค่า TFM ค่าเริ่มต้นเป็นรุ่นเล็ก ลองรุ่นใหญ่ซึ่งช้ากว่าบ้าง (ชื่อโมเดลที่ผู้พูดอ่านในช่วงนี้ คำบรรยายเขียนว่า "cell done" คือ Seldon) ผู้ฟังบางคนใช้เครดิตหมดจนทำงานต่อไม่ได้ ผู้พูดตอบว่าให้กรอกคูปองที่กล่าวไว้ในการนำเสนอ (รายละเอียดวิธีรับเครดิตถูกตัดออกจากรายงานนี้)

10. โน้ตบุ๊ก 3: โหมดล้มเหลว ความหน่วง และ scaling (~49:41–60:45)

ผู้พูดรันการทดลองที่เทียบสมรรถนะ คราวนี้ใช้ random forest และลดช่องว่างกับ XGBoost บนชุดข้อมูลใหญ่มาก ซึ่งเป็นชุดที่รู้ว่า TFM ไม่ใช่ที่สุด จงใจไม่โกงด้วยการบอกว่า TFM ดีที่สุดเสมอ เป็นสาขาที่เพิ่งเกิด จะมีงานวิจัยอีก 2–3 ปีและยังมีคนทำน้อย ทีมชอบงานนี้เพราะทุกอย่างยังรอการค้นพบ Stanislas บอกว่าเขาคิดว่า win rate ของ TFM บน benchmark คลาสสิกอยู่ราว 90% (ข้ออ้างของผู้ขาย ผู้จัดทำตรวจไม่ได้) แต่ยังมีชุดข้อมูลที่พวกเขาสู้ไม่ได้ ยากที่จะเข้าใจเหตุผล และพวกเขามีเบาะแสบ้างว่าทำไม ขณะที่บางชุดดีมากเมื่อเทียบกับโมเดลคลาสสิก

เรื่องความเร็ว: มีความพยายามมากที่จะทำให้โมเดลเร็วขึ้น บนชุดเล็กเวลาส่วนใหญ่เสียไปกับ RAM และการเดินทางอัปโหลดข้อมูล พวกเขาพยายามลดเวลาทำนายให้แข่งกับ gradient boosting ได้ แต่เป็นโมเดลคนละแบบ flops ที่ต้องใช้มากกว่ามาก จึงต้องใช้ GPU รันบน CPU ในเครื่องได้เฉพาะงานเล็ก และอาจ distill โมเดลได้ แต่ต้องเทียบกับเวลา fit + predict ของโมเดลคลาสสิกใน production ที่บริบทเปลี่ยนตลอดเวลา

ผู้ฟังถามว่า ถ้าพารามิเตอร์ไม่กี่สิบล้านก็น่าจะรันในเครื่องได้ ใช่ไหม ผู้พูดตอบว่าทำได้ แต่ไม่รู้ว่าคนทำหรือเปล่า และตัวเขาไม่ทำเพราะไม่อยากรอ ทำได้กับตารางเล็กมาก เพราะแม้พารามิเตอร์ไม่มาก ข้อมูลที่ใส่ใหญ่มากเหมือนมี LLM ตัวเล็กที่ความยาวลำดับเป็นล้านโทเค็น หน่วยของโทเค็นคือหนึ่งเซลล์ ดังนั้นบริบทฝึก 100,000 หรือ 1 ล้านแถวเทียบเท่าบริบทใหญ่มากของ LLM และจ่ายต้นทุนที่ขั้น predict ไม่ใช่ fit (ผู้ถามสรุป) ผู้พูดเสริมว่ามีกลไกอย่างการ cache อย่างหนัก: เมื่อทำ forward pass แรกบนบริบทฝึกก็เก็บข้อมูลส่วนมากไว้ ทำให้ลดการคำนวณตอนทำนาย test ได้มาก

ผู้ฟังชี้ว่าบนข้อมูลเล็กมาก TFM ควรเทียบกับโมเดล Bayesian คลาสสิก ผู้พูดยอมรับว่า PFN เก่งบนข้อมูลเล็ก แต่ไม่ทราบว่าเทียบกับโมเดล Bayesian อย่างไร และเห็นด้วยว่าแนวคิดคล้ายกัน

ผู้ฟังถามว่ามี scaling law หรือไม่ ผู้พูดอ้างงานหนึ่งของทีมแคนาดาเมื่อสองปีก่อนที่ทดลอง scaling law เล็กน้อย พบว่าไม่มีเมื่อฝึกด้วยข้อมูลสังเคราะห์: ถึงจุดหนึ่งโมเดลใหญ่ขึ้นก็ไม่ได้ข้อมูลใหม่ และอิ่มตัวเร็วบนข้อมูลที่สร้าง แต่อาจกลับมามี scaling law เมื่อฝึกด้วยข้อมูลจริง จึงยังมีช่องว่างระหว่างข้อมูลจริงกับสังเคราะห์ ทีมกำลังทำเรื่องนี้และจะเผยแพร่ในเดือนข้างหน้า Stanislas เสริมว่าโมเดลมักฝึกบนขนาดตารางคงที่ค่อนข้างเล็ก (ไม่กี่พันตัวอย่าง) และยังไม่มี scaling law ที่เผยแพร่เรื่องขนาดตารางตอนฝึก และสัญชาตญาณคือต้องขยายทั้งสถาปัตยกรรมและกระบวนการสร้างข้อมูลสังเคราะห์ ซึ่งยากเพราะ "ความน่าสนใจ" ของข้อมูลไม่ขยายตามจำนวนตาราง

เรื่อง time series อีกครั้ง: ผู้พูดบอกว่ามีผู้ทดลองใส่ lag แล้วทำนาย ถ้าข้อมูลสม่ำเสมอมีรูปแบบชัดก็มักได้ผล ไม่เช่นนั้นก็ไม่ใช่โมเดล time series ทำนายราคาหุ้นพรุ่งนี้ไม่ได้ แต่แม้ออกนอกกรอบก็ดีเมื่อเทียบกับ time series foundation model ที่ฝึกกับอนุกรมเวลาโดยตรง และแข่งขันได้กับ Chronos รุ่นแรก ๆ (ผู้พูดบอกว่าไม่คิดว่ามีบทความ อย่างน้อยทีมเขาไม่มี ผู้ร่วมพูดบอกว่ามีงานชื่อ time series PFN) ช่วงท้ายเรื่องเครดิต: คูปองให้ 1,000 เครดิต เท่ากับประมาณ 1 ล้านแถวทำนาย

11. โน้ตบุ๊ก 4: SHAP การตีความ และจำนวนคลาส (~60:45–74:06)

โน้ตบุ๊กนี้ตอบคำถามที่ถูกถามมากว่าโมเดลตัดสินใจจากอะไร: ใช้การประมาณ Shapley อย่างง่ายดูว่า TFM ตัดสินใจจาก feature เดียวกับโมเดลแบบต้นไม้หรือไม่ บนชุดข้อมูลโรคหัวใจเล็ก ๆ เหมือนโน้ตบุ๊กแรก ช้ากว่าปกติเพราะมีการเดินทางไปกลับของ API มาก

ผู้ฟังถามว่าสถานการณ์ที่ข้อมูลฝึกน้อย (ต่ำกว่า 10,000 จุด) แต่ใน production มีข้อมูลระดับหลายแสนจุดเข้ากับ TFM ได้หรือไม่ ผู้พูดตอบว่าจะได้ความแม่นของโมเดลที่ฝึกด้วย 10,000 จุด ขึ้นกับการกระจายที่พยายามจำลอง เหมือนโมเดลคลาสสิก ยิ่งข้อมูลฝึกมากยิ่งดี และจำนวนแถว inference ไม่สำคัญตราบใดที่จำลองการกระจายได้

ผู้พูดบอกว่า SHAP ใช้ได้กับโมเดลประเภทนี้ ซึ่งบริษัทลูกค้ามักขอ เพราะอยากรู้ว่าโมเดลทำนายอย่างไร โมเดลทั้งสองเห็นพ้องกันค่อนข้างมากเรื่อง feature สำคัญสูงสุด สำหรับงานตารางต่างจาก LLM ที่ไม่ค่อยพยายามเข้าใจ ถ้าทำงานด้านการฉ้อโกงเครดิตหรือการแพทย์ก็อยากรู้ว่าทำไมได้ผลนี้ วิธีสถิติแบบ Shapley ใช้ได้หากอยากได้หลักฐานทางคณิตศาสตร์ และมีบทความที่กำลังจะเผยแพร่ว่า TFM ให้ดูภายในโมเดลได้ว่าตัดสินใจอย่างไร ไม่ใช่เชิงสถิติล้วน: จากกลไก attention ดูว่าแถวฝึกใดมีผลชี้ขาดต่อการทำนายหนึ่งตัวอย่างทดสอบ (เช่นผู้ป่วยรายนี้จะเป็นโรคหัวใจ มันมองผู้ป่วยรายใด) ขึ้นกับเกณฑ์ที่ตั้งว่าอะไรถือว่าตีความได้ Stanislas เสริมว่า TFM เป็นมากกว่าโมเดลแบบ retrieval ข้อมูลในโมเดลมีมากกว่าการดู attention ระหว่างแถว ซึ่งเป็นสิ่งที่พยายามทำในวิธีที่ผู้พูดเรียกว่า "sample shop" (คำบรรยายฟังเป็น sample shop ผู้จัดทำไม่แน่ใจชื่อ [ฟังไม่ชัด])

ผู้ฟังสังเกตว่าโมเดลมาตรฐานมีการจับกลุ่ม ผู้พูดอธิบายทฤษฎีสั้น ๆ ว่าขึ้นกับการตัดสินใจเรื่อง feature และ TFM รุ่นล่าสุดมักบีบมิติของ feature เป็นหนึ่งโทเค็น จากชุดข้อมูลนี้โมเดลอาจตัดสินว่า feature ด้านบนสำคัญที่สุดและให้น้ำหนักมากกว่า ส่วนที่เหลือไม่ได้หายไปแต่ถูกทิ้งไป ผู้ฟังถามต่อว่าทำไมขนาดค่า Shapley ต่างกัน ผู้พูดตอบว่าไม่รู้จริง ๆ ตัวเขาไม่ใช่ผู้เชี่ยวชาญ SHAP

ผู้ฟังอีกคนถามว่าเหตุผลที่เทียบกับโมเดลที่ยอมรับแล้วคือเพื่อชี้ว่าแนวทาง TFM สมเหตุสมผลใช่ไหม ผู้พูดว่าใช่: การทำนายไม่ใช่การสุ่ม ถ้าเชื่อ gradient boosting ก็จะเห็นว่า TFM ตัดสินจากข้อมูลเดียวกัน ไม่ได้มาจากความว่างเปล่า คนที่ใช้ gradient boosting มา 10 ปีย่อมเชื่อถือมัน เมื่อมีเทคโนโลยีใหม่แบบ transformer ซึ่งทำให้นึกถึง LLM ที่ไม่ไว้ใจ จึงต้องแสดงบางอย่างเพื่อพิสูจน์ว่าการตัดสินใจสมเหตุสมผล

ผู้พูดตอบคำถามเรื่องจำนวนคลาสว่าไม่มีปัญหา: โมเดลถูกฝึกด้วยจำนวนคลาสจำกัดแต่ทำนายได้ถึงราว 1,000 คลาส (ข้ออ้างของผู้ขาย) และมีโมเดล regression บน API ด้วย แม้ไม่ได้นำเสนอวันนี้ Stanislas เสริมว่าด้วยวิธีแบบลำดับชั้นขยายถึงหลายคลาสได้ หรือใช้ตัวแทน (representation) ไปฝึก head/decoder ใหม่ หรือใช้ในงานแบบ retrieval ซึ่งก็ได้ผลดี

12. ถาม-ตอบ: ขนาดของ SHAP และ fine-tuning (~74:06–79:40)

ผู้ฟังย้ำว่าในชุดนี้ค่า SHAP ของ TFM เล็กกว่าของ XGBoost มาก ถามว่าเป็นทั่วไปหรือเฉพาะชุดนี้ ผู้พูดตอบว่าเป็นทั่วไป ไม่มีคำอธิบาย (มีเพื่อนร่วมงานที่ทำเรื่องนี้โดยเฉพาะ) ผู้พูดอีกคนเสริมว่าเห็นผลคล้ายกันเมื่อคำนวณ permutation importance ความเข้าใจคือเกี่ยวกับปฏิสัมพันธ์ระหว่าง feature มากกว่าข้อมูลของ feature เดี่ยว ๆ แต่ไม่มีคำตอบวิเศษ ผู้ฟังบอกว่าน่าจะเป็นบทความที่น่าสนใจ และผู้พูดตอบว่ากำลังทำอยู่

เรื่อง fine-tuning: ทำได้ ผู้พูดเทียบกับโมเดล encoder ทั่วไป: fine-tune น้ำหนักทั้งหมดได้ ส่วน LoRA ผู้พูดไม่คิดว่าได้ผลดีเท่าในประสบการณ์ที่ทดลองมา การ fine-tune แบบคลาสสิกดีกว่า บทความ fine-tuning สำหรับ TFM มักแสดงว่าต้อง fine-tune น้ำหนักทั้งหมด และใน repository ของ Tabular มีสูตรการ fine-tune บนงานเฉพาะ ซึ่งเป็นแบบคลาสสิก ได้ผลบ้างและบางครั้งไม่ได้ผล

เมื่อมีตัวอย่างน้อยมาก (few-shot) มีงานศึกษาเรื่องนี้: สิ่งที่ได้ผลเล็กน้อยคือใช้โมเดล diffusion สำหรับตารางสร้างตัวอย่างเพิ่มแล้ว fine-tune ซึ่งได้ผลดีน่าแปลกใจเพราะเป็นการขยายข้อมูลที่มีในตัวอย่างน้อยนิดให้มากขึ้นเล็กน้อย ใช้ CTGAN แบบคลาสสิกหรือ diffusion รุ่น CTGAN ได้ ผู้ฟังถามต่อว่าจะปรับการกระจายของ prior ให้เข้ากับโดเมนของเราอย่างไร ผู้พูดบอกว่าสิ่งที่ทำได้ง่ายและพอได้ผลคือหาอาการของข้อมูลเฉพาะที่ต่างจากข้อมูลวิชาการทั่วไป: ปัญหาไม่สมดุลมากไหม การกระจายเป็นชนิดเฉพาะไหม เช่นข้อมูลการเงินที่ target ไม่ได้มีการกระจายแบบ Student's t (คำบรรยายเขียนว่า student-like) ใช้ EDA คลาสสิกเข้าใจชนิดข้อมูลแล้ว pre-train บนข้อมูลชนิดนั้น แต่ต้องเคารพความหลากหลาย เพราะมี trade-off ของการ generalize: อยากให้โมเดลเรียนจากชุดข้อมูลหลากหลาย

13. Benchmark ของ Neuralk บริบทขนาดใหญ่ และความหน่วง (~79:40–88:19)

ผู้พูดชี้ไปที่ benchmark ที่ทีมเผยแพร่เมื่อไม่กี่วันก่อน เทียบ TFM ชั้นนำกับอัลกอริทึม ML ดั้งเดิม แยกตามประเภทงาน (สุขภาพ พฤติกรรม การเงิน เกม ฯลฯ) คัดชุดข้อมูลสาธารณะมากที่สุดเท่าที่ทำได้ โดยระวังไม่ให้ซ้ำกัน เพื่อให้ผู้ใช้สำรวจว่าได้สมรรถนะแบบไหนจาก TFM Stanislas ว่า win rate ของ TFM เทียบกับ baseline คลาสสิกดีมาก และ baseline ทั้งหมดถูกจูนและ ensemble แล้ว ปัจจุบันมีเฉพาะงานจัดประเภท งาน regression จะตามมาในไม่กี่เดือน

ผู้พูดถามผู้ฟังว่าตอนนี้เชื่อเรื่อง TFM แล้วหรือยัง ผู้ฟังคนหนึ่งตอบว่าเป็นก้าวที่ถูกทาง แต่ควรเข้าใจว่าทำไมสเกลของค่า SHAP ต่างกัน เพราะการตีความโมเดลแบบ transformer สำคัญ ผู้ฟังถามว่าความท้าทายของชุดข้อมูลใหญ่เป็นแค่เรื่องคอมพิวต์หรือไม่ ผู้พูดว่าไม่ใช่: ไม่ง่ายขนาดนั้น เมื่อบริบทยาวมาก attention และความน่าจะเป็นในการหาบริบทที่เกี่ยวข้องเจือจาง ต้องหาวิธีไม่ให้โมเดลหลงในบริบทและยังทำนายสิ่งที่น่าสนใจได้ จึงเป็นปัญหาเชิงทฤษฎีว่าจะปรับ attention อย่างไร เช่นเดียวกับที่ LLM ต้องจัดการ positional encoding สำหรับบริบทยาว

ในเรื่องขนาดบริบท: ผู้พูดว่า TFM โดดเด่นเหนือ XGBoost และ deep learning คลาสสิกในช่วงราวหลักร้อยถึงหลักพันแถว เพราะ baseline เหล่านั้นไม่ดีนัก และขยายถึงราว 100,000 แถวก็ยังมีแต้มต่อ แต่เมื่อถึงระดับล้านหรือสิบล้านแถว วิธีคลาสสิกมักเด่นกว่า ทั้งนี้ขึ้นกับปัญหา มีชุดข้อมูลล้านแถวที่ TFM ดีกว่า และชุดไม่กี่พันแถวที่ gradient boosting ดีกว่า Stanislas เสริมว่ามันเคลื่อนเร็ว: เมื่อสองปีก่อน TabPFN ออกมา ระดับสมรรถนะอยู่ที่ราว 100 แถว ตอนนี้ขยายเป็นหลักพันถึงหลักแสนแถว

ผู้ฟังเทียบกับโมเดล autoregressive (ChatGPT) ที่ใส่บริบท 128,000 โทเค็นก็พอ แต่ TFM ต้องให้ข้อมูลทั้งชุด ผู้พูดว่าใช่ ในที่สุดจะเป็นปัญหาที่ยังต้องให้ข้อมูลฝึกทั้งหมด ถ้าอยากขยายถึง 1 พันล้าน อาจไม่มี GPU พอ จึงต้องหาวิธี ทิศทางวิจัยที่น่าสนใจคือบริบทที่แต่ละจุดต้องการ: ไม่จำเป็นต้องใช้ข้อมูลพันล้านสำหรับทุกจุด ต้องใช้เพื่อเข้าใจการกระจายทั้งหมด แต่ไม่จำเป็นสำหรับแต่ละจุด แต่ในการจัดการปัจจุบันยังต้องใส่ตารางฝึกทั้งหมด

ผู้ฟังถามคำถามหนึ่ง (คำบรรยายเขียนว่า TabPFN แต่จากคำตอบน่าจะเป็นเรื่องความหน่วง) ผู้พูดว่า benchmark ไม่แสดงเวลาหน่วงเพราะต้องการเทียบโมเดลที่รันบน CPU หรือ GPU ชุดเดียวกัน และด้วยขนาดของงานจูนโมเดลที่ต้องรันบนเครื่องต่างกัน ข้อมูลเรื่องความหน่วงจึงไม่มี TFM จะช้ากว่า gradient boosting เพราะรันบน GPU ถ้าไม่ต้องจูน XGBoost แต่ต้องมองไปป์ไลน์ทั้งหมด การจูน gradient boosting ใช้เวลา ขณะที่ TFM แค่ใส่ข้อมูลก็จบ "คุณอาจเสียเวลา 10 วินาทีที่นี่ แต่อาจประหยัดได้อีกหลายชั่วโมงก่อนหน้านั้น" ผู้ฟังบอกว่าเวลาทำนาย (prediction latency) ยังช้ากว่าเสมอเพราะเป็นโครงข่ายประสาทใหญ่เทียบกับต้นไม้หลายร้อยต้น ผู้พูดเห็นด้วย: ทำให้เร็วขึ้นได้ด้วยเทคนิควิศวกรรมหรือไม่ก็ต้องเปลี่ยนตัวโมเดล

เสริมจากผู้จัดทำ

ในคลิปนี้ ตัวชี้วัดความหน่วงไม่ถูกเทียบใน benchmark และจุดที่ผู้ฟังตั้งคำถามซ้ำ ๆ (ความหน่วงตอน predict, ต้องใช้ GPU, บริบทที่โตไม่หยุด) ตรงกับสิ่งที่คลิปที่ 2 ของชุดนี้วัดจริงกับ TabFM บน CPU (ราว 1.5 ชั่วโมงสำหรับ 4,501 แถว) ซึ่งเป็นตัวอย่างเชิงตัวเลขของข้อจำกัดเดียวกัน

Key Takeaways

1.TFM ทำนายโดยส่งแถว train พร้อมเฉลยและแถว test เข้าโมเดลที่ pre-train บนข้อมูลสังเคราะห์ใน forward pass เดียว fit ใน API ของ scikit-learn ไม่ได้ฝึกอะไร
2.เสาหลักสามข้อ (prior, สถาปัตยกรรม, context) คือกรอบที่ผู้พูดใช้มองงานวิจัย; prior สังเคราะห์คือการเลือกที่ส่งผลมากสุด และบางชุดข้อมูลการเลือกแถวบริบทให้ดีขึ้นช่วยได้มาก
3.จุดแข็งอยู่ที่ตารางเล็กถึงกลางและไม่ต้องจูน ส่วนตารางใหญ่ยังแค่ทัดเทียมต้นไม้ ความหน่วงสูง ต้องใช้ GPU และข้อมูลไกลจาก prior อาจแย่ ผู้พูดบอกว่าไม่ได้อยากแทนที่ต้นไม้
4.เปรียบเทียบให้เป็นธรรม: หลาย seed/fold, ช่วงความเชื่อมั่น, paired delta รายคู่ต่อ fold และไม่ใช้ accuracy กับข้อมูลไม่สมดุล
5.ข้ออ้างของผู้ขาย (win rate ราว 90%, API 1 ล้านแถว, 1,000 คลาส) ตรวจเองไม่ได้ และสไลด์ที่ว่าโมเดลโอเพนเวตจำกัดบริบท ~10,000 แถวขัดกับแหล่งอื่นรวมถึงสไลด์อีกหน้าของผู้พูด
6.คลิปนี้ไม่ใช่เรื่อง TabFM (เผยแพร่ก่อน TabFM 11 วัน) แต่เป็นพื้นหลังที่ดีว่า TabFM ต่อยอดจากอะไร
