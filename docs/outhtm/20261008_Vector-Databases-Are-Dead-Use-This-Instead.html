Vector Databases Are Dead. Use This Instead — Devsplainers

✍️ Devsplainers📅 เผยแพร่ 2026-10-08⏱ 8:29🎞 caption อังกฤษอัตโนมัติ (ASR)📝 แปลแบบตีความ ครบทุกรายละเอียด🔎 ตรวจข้อเท็จจริง 18 ข้อ 🔗 คลิปต้นฉบับ (YouTube)

📋 บทสรุปย่อ

บทสรุปย่อ: turbopuffer บริษัทที่ขาย vector database เอง (และทำ search ให้ Cursor, Notion, Anthropic) เขียนบล็อก "RIP, vector database" เมื่อ 30 กันยายน คลิปจึงถามว่าถ้าแชตบอต RAG ของเราใช้ vector DB อยู่ ต้องรื้อไหม แล้วเทียบ "ผู้ท้าชิง" สามทางด้วยตัวเลขจาก benchmark และต้นทุนต่อคำตอบ: (1) agentic search ที่ให้โมเดลค้นวนเป็นลูป ชนะ pipeline แบบเดิมในคำถามยากแต่แพงกว่าราว 3 เท่า และในลูปนั้น BM25 (ค้นด้วยคำ) มักชนะ vector search บนข้อมูลบริษัท (2) MCP connector ที่ถามแอปโดยตรงโดยไม่ทำ index และ (3) โฟลเดอร์ความรู้ที่คอมไพล์ไว้ (จากคลิป OKF ของช่องเอง) ซึ่งงานวิจัยพบว่าแพงต่อคำถามกว่าที่ผู้เล่าเคยบอก ข้อสรุปของคลิป: vector database ไม่ได้ตาย แต่ "ถูกลดตำแหน่ง" จากศูนย์กลางเป็นเครื่องมือหนึ่งในหลายตัว

โหมดของเนื้อหา: แปลแบบตีความ ครบทุกรายละเอียด (license มาตรฐานของ YouTube, ตรวจ 2026-10-10) ทุกประเด็นและตัวเลขอยู่ครบตามลำดับ เรียบเรียงด้วยคำของผู้จัดทำโดยไม่เปลี่ยนความหมาย คลิปนี้ใหม่กว่าความรู้ของผู้จัดทำ ผู้จัดทำจึงตรวจข้อเท็จจริงทั้ง 18 ข้อด้วยการค้นเว็บ (ส่วนที่ 8) ส่วนที่ผู้จัดทำเพิ่มเองอยู่ในส่วนที่ 8 และ 9

🧭 สรุปเชิงลึก

จุดเริ่ม: vector database เก็บข้อความเป็น embedding (รายการตัวเลขยาวที่จับความหมาย) แล้วคืนชิ้นข้อความที่ใกล้คำถามที่สุด turbopuffer เคยสร้างทั้งเอนจินรอบสิ่งนี้ โดยเก็บเอกสารไว้ที่ "ที่อยู่" ของเวกเตอร์ ทำให้ vector search เร็วแต่เรื่องอื่นลำบาก ในเวอร์ชัน 3 เอกสารได้ ID ธรรมดา และ vector index กลายเป็น index หนึ่งข้าง ๆ keyword search และ filter ผู้เล่าบอกว่า v3 ยังไม่ขึ้น production จึงยังเป็นการตลาดระดับหัวข้อข่าว แต่นี่คือบริษัทที่ดูแล search ของเอกสาร Notion 10 พันล้านชิ้น และกำลังบอกว่า vector index ไม่ได้อยู่ตรงกลางอีกแล้ว

ผู้ท้าชิง 1 agentic search: pipeline RAG แบบเดิมได้โอกาสเดียว (หยิบ chunk ที่ใกล้สุดใส่ prompt) แม้มี reranker ก็ไม่ตัดสินว่าทุก chunk ใช้ไม่ได้แล้วค้นใหม่ แต่ agent ทำได้ บน FRAMES ของ Google (824 คำถาม บทความ Wikipedia 12,000 บทความ) PipesHub รายงานว่า agent ตอบถูก 92.7% pipeline ที่ดีที่สุดจาก 18 แบบได้ 78.9 และเมื่อให้บทความที่ถูกพอดีได้ 93 คำถามที่ต้องใช้ 5 บทความขึ้นไป pipeline 62% agent 90% แต่ agent แพงกว่าราว 3 เท่าต่อคำถาม คำตอบที่ช้าที่สุดใน 20 ใช้ 134 วินาที (pipeline 54) และ 7% ของคำถามกินงบ 37% งานจาก LREC ปีนี้พบแบบเดียวกัน: input tokens มากกว่า 3 เท่า เวลามากกว่า 50% และ reranker ธรรมดาจัดอันดับได้ดีกว่า agent

BM25 กับเวกเตอร์: ใน EnterpriseRAG-Bench (เอกสารบริษัทครึ่งล้านจาก Slack, Gmail, Jira, Confluence, GitHub) BM25 ตอบถูก 68.8% vector 51.4 และเวกเตอร์แพ้แม้แต่ในคำถามที่เขียนมาให้เข้าทางเวกเตอร์ เพราะ embedding model ที่ฝึกจากข้อความสาธารณะไม่รู้จักชื่อรหัสภายใน (code name) ตัวย่อ และเลข ticket ขององค์กร (benchmark นี้มาจาก Onyx ซึ่งขาย enterprise search) แต่เวกเตอร์ยังมีที่ทาง: BrowseComp-Plus ที่ GPT-5 ได้ 70.1% กับ embedding retriever เทียบ 55.9 กับ BM25 และ Cursor บอกว่า agent แม่นขึ้น 12.5% เมื่อเพิ่ม semantic search บน grep ตัวเวกเตอร์ถูกมาก (embedding เล็กของ OpenAI 2 เซนต์ต่อล้าน tokens) ที่แพงคือลูปที่เรียกมัน

ผู้ท้าชิง 2 และ 3: MCP connector ให้ AI ถามแอปตรง ๆ เช่น federated Copilot connectors ของ Microsoft ที่ดึงข้อมูลสดด้วยสิทธิ์ของผู้ใช้โดยไม่ทำ index, Claude Marketplace เปิด 23 กันยายนพร้อม connector และ plugin กว่า 2,000 ตัว, ChatGPT ให้เฉพาะ admin sync แอปเข้า index ได้ และ Slack ห้าม bulk export ทาง API ตั้งแต่ 2025 แต่ query แบบ federated ช้าเท่าแอปที่ช้าที่สุด Glean (ซึ่งขาย index) วัด Claude Cowork บน live connector ได้ $2.98 ต่อ task เทียบ $0.58 ของ Glean ส่วนโฟลเดอร์ความรู้ งานวิจัยที่ทดสอบคำกล่าวของผู้เล่าเรื่อง wiki ที่คอมไพล์ พบว่าใช้ tokens สร้างมากกว่า RAG ราว 100 เท่า (ผู้เขียนคาดไว้) และต่อคำถามมากกว่าราว 21 เท่า จึงไม่มีจุดคุ้มทุน แม้จะอ้างอิงได้ดีกว่ามาก (40% เทียบ 19%) แต่เป็นงานของผู้เขียนคนเดียว 13 คำถาม ผู้เล่าจึงให้มองเป็นไฟเตือน และ repo ของ OKF ก็เงียบลง

คำตัดสิน: vector database ถูกลดตำแหน่งเป็นเครื่องมือหนึ่ง ค่าเริ่มต้นของงานใหม่ส่วนใหญ่คือ agent ที่มีเครื่องมือค้นราคาถูก: keyword ก่อน, เวกเตอร์สำหรับความหมายคลุมเครือ, live connector สำหรับแอปที่ไม่ได้เป็นเจ้าของ pipeline แบบครั้งเดียวยังชนะเรื่องราคาและความเร็วสำหรับคำถามง่ายจำนวนมาก, coding agent หรือเอกสารชุดเล็กใช้ grep กับไฟล์โน้ตก็พอ, ต่ำกว่า 10 ล้านเวกเตอร์ใช้ Postgres + pgvector (อัปเดตเป็น 0.8.7), ข้อมูลบริษัทหลายแอปเริ่มจาก live connector แล้วเพิ่ม index เฉพาะจุดที่ latency หรือการจัดอันดับเป็นปัญหา และคอมไพล์ความรู้เฉพาะเมื่อมันนิ่งและมีค่า คำถามที่ตัดสินคือ คำถามทั่วไปต้องกระโดดกี่ hop และผู้ใช้รอ 2 นาทีได้ไหม

ตรวจข้อเท็จจริง (เสริมจากผู้จัดทำ): จาก 18 ข้อ ยืนยันได้ 11 ข้อ ยืนยันได้บางส่วน 7 ข้อ (ในนั้นมีสองประเด็นย่อยที่หาไม่เจอ) และไม่พบข้อที่ขัดกับแหล่งตรง ๆ จุดที่ควรรู้: Notion คือ "10B+ vectors" ไม่ใช่เอกสาร, ตัวเลข pgvector 10 ล้านมาจากเอกสารของ turbopuffer ไม่ใช่คำพูดของ CTO ที่ค้นเจอ, 12.5% ของ Cursor เป็นค่าเฉลี่ยแบบสัมพัทธ์บน benchmark ภายใน และต้นทุนสร้าง wiki "100 เท่า" เป็นค่าหลังถ่วงด้วย prompt caching (ค่าดิบ 645 เท่า)

1. บริษัทขาย vector DB เขียนว่า "RIP" และ v3 เปลี่ยนอะไร

~0:00–1:22

บริษัทที่ขาย vector database เองกลับ "ฝัง" vector database ไว้ในบล็อกโพสต์ บริษัทนั้นชื่อ turbopuffer ซึ่งดูแลระบบค้นหาให้ Cursor, Notion และ Anthropic ผู้เล่าบอกว่า ถ้าคุณสร้างแชตบอต AI บนเอกสารของตัวเอง มีโอกาสสูงว่ามันรันบน vector DB แล้วต้องรื้อออกไหม บริษัท AI ใหญ่ ๆ ลองอีกสามวิธีให้ AI หาข้อมูลของคุณกันอยู่แล้ว และยังถกกันอยู่ว่าวิธีไหนชนะ จบคลิปนี้คุณจะรู้ว่าควรเลือกวิธีไหน และเมื่อไรที่ vector database แบบเดิมยังเป็นคำตอบที่ถูก

vector database ทำอะไร และ turbopuffer เปลี่ยนอะไร (~0:33)

vector database เก็บข้อความของคุณเป็น embedding คือรายการตัวเลขยาว ๆ ที่จับความหมาย แล้วคืนชิ้นข้อความ (chunk) ที่ใกล้คำถามที่สุด turbopuffer สร้างทั้งเอนจินรอบสิ่งนี้: ทุกเอกสารอยู่ที่ "ที่อยู่" ของเวกเตอร์ของมัน เหมือนห้องสมุดที่จัดหนังสือขึ้นชั้นตามหัวข้อ ทำให้ vector search เร็ว แต่เรื่องอื่นทั้งหมดลำบาก

ในเวอร์ชัน 3 ทุกเอกสารได้ ID ธรรมดา และ vector index กลายเป็นแค่ index อีกตัวหนึ่ง ข้าง ๆ keyword search และ filter ผู้เล่าบอกว่า v3 ยังไม่ขึ้น production ทั้งหมดนี้จึงยังเป็นการตลาดระดับหัวข้อข่าว แต่นี่คือบริษัทที่ดูแลการค้นหาเอกสาร Notion 10 พันล้านชิ้น และกำลังบอกว่า vector index ไม่ได้อยู่ตรงกลางอีกแล้ว แล้วอะไรจะมาอยู่ตรงกลางแทน มีคำตอบสามข้อบนโต๊ะ ผู้เล่าจะไล่ทีละข้อ

2. ผู้ท้าชิง 1: agentic search, FRAMES และราคาของลูป

~1:23–3:03

pipeline RAG แบบคลาสสิก ที่พวกเราส่วนใหญ่สร้างกัน จะหั่นเอกสารเป็น chunk แล้ว embed ไว้ ตอนถามก็หยิบ chunk ที่ใกล้ที่สุดไม่กี่ชิ้นมาแปะใน prompt มันได้โอกาสเดียว CTO ของ turbopuffer ชี้ว่า แม้แต่ reranker ที่จัดลำดับ chunk เหล่านี้ ก็ไม่ได้ตัดสินว่า "ไม่มีชิ้นไหนดีเลย" แล้วค้นใหม่ แต่ agent ทำได้

ผู้ท้าชิงรายแรกคือ agentic search: โมเดลถือเครื่องมือค้นหาและวนเป็นลูป ค้น อ่าน คิดว่ายังขาดอะไร แล้วค้นอีก

FRAMES: agent ตัวเดียว เทียบ pipeline 18 แบบ (~1:57)

PipesHub ทดสอบเรื่องนี้บน benchmark FRAMES ของ Google: 824 คำถาม บนบทความ Wikipedia 12,000 บทความ

  • agent ตอบถูก 92.7% ส่วน pipeline ที่ดีที่สุดจาก 18 แบบที่ตายตัวได้ 78.9
  • เมื่อ PipesHub ส่งบทความที่ถูกพอดีให้โมเดล (perfect retrieval) ได้ 93 agent จึงต่ำกว่าการค้นที่สมบูรณ์แบบอยู่หนึ่งในสามของจุด
  • คำถามที่ต้องใช้ห้าบทความขึ้นไป: pipeline ได้ 62% agent ได้ 90

ผู้เล่าบอกว่า PipesHub ขายระบบแบบนี้ แต่ก็เผยแพร่โค้ดและต้นทุนไว้ด้วย

ลูปของ agent มีราคา (~2:29)

  • agent แพงกว่าราวสามเท่าต่อคำถาม
  • คำตอบที่ช้าที่สุดใน 20 ใช้ 134 วินาที เทียบ 54 วินาทีของ pipeline
  • 7% ของคำถามกินงบไป 37%

งานวิจัยอิสระจากการประชุม LREC ปีนี้พบรูปแบบเดียวกัน: ใช้ input tokens มากกว่าสามเท่า ใช้เวลามากกว่า 50% และ reranker ธรรมดาจัดอันดับได้ดีกว่า agent สรุปคือ ลูปชนะคำถามยาก แต่ต้องจ่ายทุกรอบที่วน

3. BM25 เทียบ vector search บนข้อมูลบริษัท

~3:04–3:51

ในลูปนั้น keyword search แบบเก่ามักจะชนะเวกเตอร์ BM25 คือสูตรจัดอันดับที่ search engine ใช้มาตั้งแต่ก่อนยุค AI ให้คะแนนเอกสารตามคำที่ตรงกับคำค้นแบบเป๊ะ ๆ

EnterpriseRAG-Bench โยนเอกสารบริษัทครึ่งล้านชิ้นจาก Slack, Gmail, Jira, Confluence และ GitHub ให้ทั้งสองแบบ: BM25 ตอบถูก 68.8% ส่วน vector search ได้ 51.4

เวกเตอร์แพ้แม้แต่ในคำถามที่เขียนมาให้เข้าทางเวกเตอร์ เพราะ embedding model ที่ฝึกจากข้อความสาธารณะไม่รู้จักชื่อรหัสภายใน (code name) ตัวย่อ และเลข ticket ของคุณ นักพัฒนาคนหนึ่งบน Reddit เขียนว่า "Customer IDs need equality, not a soulmate." (เลขลูกค้าต้องการความตรงกันเป๊ะ ไม่ใช่คู่แท้) ผู้เล่าบอกว่า benchmark นี้มาจาก Onyx ซึ่งขาย enterprise search

4. ที่ที่เวกเตอร์ยังชนะ

~3:52–4:29

เวกเตอร์ยังมีที่ในกล่องเครื่องมือ:

  • บน benchmark งานค้นคว้า BrowseComp-Plus GPT-5 ในฐานะ search agent ได้ 70.1% เมื่อใช้ embedding retriever และ 55.9 เมื่อใช้ BM25 และต้องค้นน้อยครั้งกว่า (ผู้เล่าบอกว่ามีผู้ขาย BM25 รายหนึ่งแย้งว่า BM25 ในการทดสอบนั้นตั้งค่าไม่ดี)
  • Cursor รายงานว่า agent ของตัวเองแม่นขึ้น 12.5% เมื่อเพิ่ม semantic search ไว้บน grep

ตัวเวกเตอร์เองถูกมาก: embedding model ขนาดเล็กของ OpenAI ราคา 2 เซนต์ต่อล้าน tokens ส่วนที่แพงคือลูปที่เรียกใช้มัน

5. ผู้ท้าชิง 2: MCP connector และราคาของการเข้าถึงสด

~4:30–5:45

ผู้ท้าชิงรายที่สองข้าม index ไปเลย: MCP connector คือปลั๊กมาตรฐานที่ให้ AI ถามแอปอย่าง Notion หรือ Salesforce ได้โดยตรง

  • federated Copilot connectors ของ Microsoft ทำงานแบบนั้น ดึงข้อมูลสดผ่าน MCP ด้วยการล็อกอินและสิทธิ์ของผู้ใช้เอง และ Microsoft ไม่ทำ index อะไรเลย
  • Claude Marketplace ของ Anthropic เปิดเมื่อ 23 กันยายน พร้อม connector และ plugin กว่า 2,000 ตัว
  • OpenAI ไปไกลที่สุด: ผู้ใช้รายบุคคล sync แอปเข้า index ของ ChatGPT ไม่ได้อีกแล้ว มีแต่ admin ที่ทำได้
  • เงื่อนไข API ของ Slack ห้าม bulk export มาตั้งแต่ปี 2025

แอปที่ถือข้อมูลของคุณเป็นคนตัดสินว่าคุณคัดลอกได้แค่ไหน และผู้เล่าบอกว่าไม่คาดว่าแอปจะใจกว้างขึ้น

การเข้าถึงสดก็มีราคา (~5:18)

query แบบ federated เร็วได้เท่ากับแอปที่ช้าที่สุดที่ถูกถาม และแต่ละแอปจัดอันดับผลลัพธ์ของตัวเอง Glean ซึ่งขาย index วัด Claude Cowork บน live connector ได้ $2.98 ต่อ task เทียบ $0.58 ของ Glean และใช้ tokens มากกว่าสามเท่า เมื่อ 22 กันยายน Glean เพิ่ม template ของ live MCP server 182 ตัวในผลิตภัณฑ์ของตัวเอง

6. ผู้ท้าชิง 3: โฟลเดอร์ความรู้ที่คอมไพล์ (OKF) ย้อนดูอีกครั้ง

~5:46–7:08

ผู้ท้าชิงรายที่สามเป็นสิ่งที่ผู้เล่าผลักดันเอง: ในเดือนมิถุนายน ช่องทำคลิปเรื่อง open knowledge format (OKF) ของ Google ที่ AI คอมไพล์ความรู้ของคุณเป็นโฟลเดอร์ไฟล์ markdown ผู้เล่าเคยพูดว่าโฟลเดอร์ "คิดครั้งเดียวล่วงหน้า แล้วคุณก็แค่อ่านคำตอบ" คอมเมนต์ที่มีคนกดไลก์มากที่สุดเขียนว่า ให้เอาไฟล์ MD ใหม่พวกนั้นไปหั่นเป็น chunk แล้ว embed ลง vector DB เพื่อให้ค้นได้ดีและเร็วขึ้น สี่เดือนต่อมา หลักฐานเข้าข้างคอมเมนต์นั้นมากกว่าผู้เล่า

wiki เทียบ RAG: บิลค่า tokens (~6:15)

งานวิจัยจากเดือนสิงหาคมทดสอบคำกล่าวของผู้เล่าตรง ๆ:

  • wiki ที่คอมไพล์ใช้ tokens ในการสร้างมากกว่า RAG index ราวร้อยเท่า ซึ่งผู้เขียนงานวิจัยคาดไว้อยู่แล้ว
  • สิ่งที่หวังคือจะคืนทุนในทุกคำถาม แต่ตามคำในงานวิจัย wiki ใช้ tokens ต่อคำถามมากกว่าราว 21 เท่า จึงไม่มีจุดคุ้มทุน
  • wiki ยังอ้างอิงได้ดีกว่ามาก: ข้ออ้างที่อ้างแหล่งไว้ถูกต้อง 40% เทียบ 19% ของ RAG
  • เป็นงานของผู้เขียนคนเดียว 13 คำถาม ผู้เล่าบอกให้มองเป็น "ไฟเตือน"

ตัวฟอร์แมตเองก็เงียบลง: commit ล่าสุดของ repo OKF เข้ามาเมื่อ 21 สิงหาคม จากผู้ร่วมพัฒนาคนเดียวของมัน และนับจากนั้นมี issue comment 88 รายการที่ไม่ได้รับคำตอบจาก maintainer เลย แต่ไอเดียยังอยู่ในผลิตภัณฑ์อย่าง Open Wiki ของ LangChain และ Nexus ของ Pinecone ซึ่งคอมไพล์ข้อมูลบริษัทไว้ล่วงหน้า

7. คำตัดสิน และควรเลือกแบบไหน

~7:09–8:13

vector database ตายแล้วไหม ผู้เล่าตอบว่ามันถูกลดตำแหน่งจากศูนย์กลางของ stack เป็นเครื่องมือหนึ่งในหลาย ๆ ตัว

เลือกแบบไหน (~7:31)

  • งานใหม่ส่วนใหญ่: ค่าเริ่มต้นคือ agent ที่มีเครื่องมือค้นราคาถูก: keyword search ก่อน, เวกเตอร์สำหรับความหมายคลุมเครือ และ live connector สำหรับแอปที่คุณไม่ได้เป็นเจ้าของ
  • pipeline แบบครั้งเดียว ยังชนะเรื่องราคาและความเร็ว สำหรับคำถามง่าย ๆ ปริมาณมาก
  • coding agent หรือเอกสารชุดเล็ก: grep กับไฟล์โน้ตก็พอ
  • ต่ำกว่า 10 ล้านเวกเตอร์: CTO ของ turbopuffer เองบอกว่า Postgres กับ pgvector ถูกกว่า แค่อัปเดตเป็น 0.8.7 ซึ่งแก้ช่องโหว่ด้านความปลอดภัย
  • ข้อมูลบริษัทกระจายหลายแอป: เริ่มจาก live connector แล้วเพิ่ม index เฉพาะจุดที่ latency หรือการจัดอันดับเป็นปัญหา
  • คอมไพล์ความรู้เฉพาะเมื่อความรู้นั้นนิ่งและมีค่า

คำถามที่ใช้ตัดสินคือ คำถามทั่วไปของคุณต้องกระโดดกี่ hop และผู้ใช้รอ 2 นาทีสำหรับคำถามที่ช้าได้ไหม ผู้เล่าปิดว่า ก่อนจ่ายเงินซื้อ vector index อีกตัว ให้ agent มีเครื่องมือ keyword search ก่อน

8. ตรวจข้อเท็จจริงและข้อมูลเสริม (จากผู้จัดทำ)

เสริมจากผู้จัดทำ ทั้งส่วนนี้ไม่ได้อยู่ในคลิป

ตรวจข้อเท็จจริง 18 ข้อ (ค้นเว็บ 2026-10-10)

คลิปเผยแพร่หลังความรู้ของผู้จัดทำ จึงตรวจทุกข้อด้วยการค้นเว็บ หน้าเว็บต้นทางหลายหน้าเปิดอ่านตรงไม่ได้ในงานนี้ จึงใช้สำเนาหรือแหล่งรองแทน (ระบุในคอลัมน์ "อ่านจาก") ผลคือ ยืนยันได้ 11 ข้อ, ยืนยันได้บางส่วน 7 ข้อ (ในนั้นมีสองประเด็นย่อยที่หาไม่เจอ: คำพูดเรื่อง reranker ในข้อ 3 และตัวเลข 88 comment ในข้อ 16) และไม่พบข้อที่ขัดกับแหล่งตรง ๆ

Key Takeaways

  1. vector DB ไม่ได้ตาย แต่ถูกลดตำแหน่ง จากศูนย์กลางเป็นเครื่องมือหนึ่งของ agent
  2. agentic search ชนะคำถามยาก (FRAMES 92.7% เทียบ 78.9%) แต่แพงกว่าราว 3 เท่า และคำตอบที่ช้าที่สุดราว 1 ใน 20 ใช้ราว 2 นาที
  3. บนข้อมูลบริษัท BM25 มักชนะเวกเตอร์ (68.8% เทียบ 51.4%) เพราะ embedding ไม่รู้จักชื่อและรหัสภายใน แต่เวกเตอร์ยังช่วยในงานค้นคว้าและบนโค้ด
  4. MCP connector ถามแอปสดโดยไม่ทำ index แต่ช้าเท่าแอปที่ช้าสุด และในการทดสอบของ Glean แพงกว่า index
  5. โฟลเดอร์ความรู้ที่คอมไพล์แพงต่อคำถามกว่าที่คิด (ราว 21 เท่าในงานวิจัยชิ้นเล็ก) ใช้เฉพาะความรู้ที่นิ่งและมีค่า
  6. ตัวตัดสินคือจำนวน hop และเวลาที่ผู้ใช้รอได้ ก่อนจ่ายเงินซื้อ vector index อีกตัว ให้ agent มีเครื่องมือ keyword search ก่อน
