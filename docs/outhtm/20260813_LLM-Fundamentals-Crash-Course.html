บทสรุปย่อ

คลิปนี้เป็นคอร์สพื้นฐานสำหรับคนที่จะเริ่มทำงานกับ LLM โดยไม่ผ่าน framework: อธิบายว่าข้อความถูกตัดเป็น token แล้วโมเดลทำนาย token ถัดไปทีละตัวอย่างไร, ควบคุมพฤติกรรมด้วย system prompt, temperature และ max tokens, เทคนิค zero-shot / few-shot / chain of thought, เรียก API ของ OpenAI ด้วยโค้ดจริง, บังคับให้ตอบเป็น JSON ด้วย Pydantic และจบด้วย tool call ซึ่งผู้พูดบอกว่าเป็นรากของ AI agent ทุกตัว ระดับความลึกคือ "ใช้งานได้" ไม่ใช่ "รู้ภายใน" — ผู้พูดข้ามกลไกภายในของโมเดล (เช่น วิธีตัด token หรือสถาปัตยกรรม) โดยตั้งใจ

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึก ครบทุกบทของคลิป (license มาตรฐานของ YouTube; คำบรรยายเป็น ASR อัตโนมัติ)

สรุปเชิงลึก

ข้อโต้แย้งหลักของผู้พูด: คนที่กระโดดไปใช้ LangChain, LangGraph หรือ RAG เลยโดยไม่เข้าใจชั้นล่าง จะ debug ไม่ได้เมื่อระบบพัง จึงควรเรียนพื้นฐานด้วย raw API ก่อน คลิปนี้ต่อหลายตอนเข้าด้วยกัน (คำอธิบายคลิปแบ่งเป็นแปดบท) และหลายตอนจบด้วย "เจอกันตอนหน้า"

กลไกของ LLM. โมเดลเป็นแบบจำลองทางคณิตศาสตร์ที่รับได้แต่ตัวเลข ข้อความจึงถูก tokenizer ตัดเป็นชิ้น (token) แล้วแปลงเป็นรหัสตัวเลข กฎคร่าว ๆ ที่ผู้พูดให้คือ 1 token ≈ 0.75 คำอังกฤษ (1,000 token ≈ 750 คำ) ส่วนโค้ด JSON และภาษาที่ไม่ใช่อังกฤษใช้ token เปลือง ทุกอย่างวัดเป็น token: ค่าใช้จ่าย ความเร็ว และ context window (สไลด์ในคลิปแสดง Claude Opus 4.7 = 1,000,000, GPT-5.5 = 1,050,000, Gemini 3.1 Pro = 1,000,000 token) โมเดล "ไม่มีความจำ" — แอปแชตส่งประวัติทั้งก้อนซ้ำทุกครั้ง และเมื่อเกินหน้าต่าง ข้อความเก่าจะถูกมองข้าม จากนั้นโมเดลทำนาย token ถัดไปวนซ้ำ ซึ่งเป็นเหตุผลที่ response เลื่อนออกมาทีละคำ (streaming)

การควบคุม. ทุก call มีสี่ตัวเลือก: system prompt (ผู้สร้างแอปเป็นคนเขียน ซ่อนจากผู้ใช้), user prompt, temperature (ตัวคุมการสุ่มจากการแจกแจงความน่าจะเป็น: 0 = เลือกตัวที่น่าจะเป็นที่สุดเสมอ, 1 = สุ่มตามการแจกแจง, มากกว่า 1 = แบนลงจนไม่ปะติดปะต่อ) และ max tokens (เพดานแข็งของความยาวคำตอบ ตั้งต่ำไปจะขาดกลางประโยค สูงไปจะจ่ายเกินจำเป็น)

เทคนิค prompt. zero-shot ต้อง "เจาะจง" ไม่ใช่ "ขี้เกียจ"; few-shot (ผู้พูดว่า 3–5 ตัวอย่างคือจุดที่ดีจากประสบการณ์ของเขา) บังคับ pattern ด้วยตัวอย่างจริง แลกกับ token ที่เพิ่ม; chain of thought ให้โมเดลเขียนเหตุผลออกมาก่อน เพราะ token เหตุผลกลายเป็น context ของ token ถัดไป ใช้กับโจทย์หลายขั้น ไม่ต้องใช้กับ Q&A ง่าย ๆ หรืองานสร้างสรรค์

การเขียนโค้ด. ด้วย OpenAI SDK (client.responses.create) ผู้พูดสาธิต input แบบรายการข้อความหลายตา, instructions เป็น system prompt, ค่า usage (input / output / total token), max_output_tokens ที่ตัดคำตอบกลางประโยคจริง และ stream=True ที่คืน generator

Structured output. ขอ JSON ใน prompt ยังเป็นแค่ข้อเสนอแนะ (ได้ string และอาจมีรั้ว markdown) ส่วน responses.parse กับคลาส Pydantic ผ่าน text_format ส่ง JSON Schema ไปให้เซิร์ฟเวอร์ ผู้พูดบอกว่าเป็น "การรับประกัน" ที่บังคับก่อนถึงมือเรา (ตรวจแล้ว: เอกสาร OpenAI ยืนยันการรับประกันตาม schema)

Tool call — หัวใจของคลิป. โมเดลไม่ได้เรียกฟังก์ชันเอง: เราส่งชื่อ คำอธิบาย และพารามิเตอร์ของฟังก์ชัน (ไม่ส่งตัวโค้ด), โมเดลตอบเป็น function_call พร้อมอาร์กิวเมนต์ JSON และ call_id, โค้ดของเรารันฟังก์ชัน แล้วส่งผลกลับเป็น function_call_output ที่ผูกด้วย call_id เดียวกัน โมเดลจึงสรุปคำตอบ ผู้พูดสรุปว่าโมเดลเป็นผู้ประสานงาน โค้ดเป็นผู้ลงมือ และ agent ทุกตัวคือวงนี้ที่ซ้ำพร้อมเครื่องมือมากขึ้น

ข้อควรระวังที่เราตรวจเพิ่ม (ผู้จัดทำ). (1) ตัวอย่างการตัด token ที่ผู้พูดยกไม่ตรงกับ tokenizer ของ OpenAI (เช่น "unhappiness" เป็น 3 token ใน cl100k_base และ o200k_base ไม่ใช่ 2) (2) "โมเดลไม่เคยวางแผนล่วงหน้า" เป็นการเล่าแบบง่าย งานวิจัย interpretability ของ Anthropic พบหลักฐานว่า Claude เลือกคำสัมผัสไว้ก่อนเขียนบรรทัดกลอน (3) temperature = 0 ไม่ได้การันตีผลซ้ำเป๊ะในทางปฏิบัติ และโมเดลตระกูล GPT-5 บางรุ่นไม่รับ temperature เมื่อเปิด reasoning (4) หัวข้อคลิประบุ OpenAI, Anthropic และ Gemini แต่เนื้อหาจริงสาธิตเฉพาะ OpenAI ผลการตรวจข้อเท็จจริง 17 ข้อ: ยืนยัน 7, ยืนยันบางส่วน 6, ไม่ตรงกับของจริงหรือกับต้นฉบับ 3, ไม่พบในเอกสารที่เปิดอ่านได้ 1

1. บทนำและแผนการเรียน (~0:00–2:08)

ผู้พูดเริ่มด้วยข้อสังเกตว่ามือใหม่สาย AI engineering มักกระโดดไป framework อย่าง LangChain, LangGraph และ RAG โดยไม่เข้าใจสิ่งที่เกิดข้างใต้ พอระบบพังก็ debug ไม่ได้ และมักไม่มั่นใจตอนสัมภาษณ์งาน จึงต้องเริ่มที่พื้นฐานของ LLM ก่อน

เป้าหมายที่ประกาศไว้มีสามอย่าง: เข้าใจว่าเกิดอะไรขึ้นข้างใต้เมื่อคุยกับ LLM, เข้าใจเทคนิค prompt พร้อมสัญชาตญาณว่าทำไมได้ผล และเข้าใจ tool call ซึ่งผู้พูดเรียกว่า "รากฐานของ AI agent ทุกตัว" ทั้งหมดนี้ทำโดยไม่ใช้ framework ใด ๆ คั่นกลาง แผนการเรียนมีหกหัวข้อ: (1) LLM ทำงานอย่างไร (token, context window, การสร้างคำตอบ) (2) พื้นฐาน prompt (system/user prompt, temperature, max tokens) (3) เทคนิค prompt (zero-shot, few-shot, chain of thought) (4) เรียก API ตรง ๆ พร้อม streaming และการจัดการค่าใช้จ่าย (5) structured output (6) tool call ในเหตุผลของ structured output ผู้พูดชี้ว่าซอฟต์แวร์จริงทำงานบนข้อมูลที่มีโครงสร้าง ไม่ใช่ข้อความภาษาอังกฤษ

2. Token และ tokenizer (~2:08–8:43)

ผู้พูดตั้งต้นว่า LLM เป็นแบบจำลองทางคณิตศาสตร์ ไม่เข้าใจภาษาอังกฤษหรือภาษาใดเลย มันรับได้แค่ตัวเลข ดังนั้นข้อความของผู้ใช้ เช่น "Hey, how are you?" ต้องถูกแปลงเป็นตัวเลขก่อน ตัวทำงานนี้คือ tokenizer ซึ่งเป็น "สะพาน" ระหว่างภาษามนุษย์กับคณิตศาสตร์

token คืออะไร. คือชิ้นของข้อความ อาจเป็นทั้งคำ ส่วนของคำ หรือแม้แต่เครื่องหมายวรรคตอน tokenizer คือตัวตัด ตัวอย่างที่ผู้พูดและสไลด์แสดง: hello = 1 token; Hello (H ใหญ่) = 1 token แต่เป็นคนละ token กับตัวเล็ก; unhappiness = 2 token (un + happiness); สตริงหน้าตาเหมือน JSON {"key": "value"} = 9 token ผู้พูดไม่อธิบายว่าทำไมตัดแบบนั้น โดยบอกว่ามีคณิตศาสตร์ซับซ้อนอยู่และจะค่อย ๆ ไปถึงภายหลัง

กฎประมาณ. 1 token ≈ 0.75 คำอังกฤษ ดังนั้น 1,000 token ≈ 750 คำ แต่โค้ด JSON และภาษาที่ไม่ใช่อังกฤษจะ "เผา" token เร็วกว่า

แล้ว token คือตัวเลขอย่างไร. tokenizer ยังจับคู่ token แต่ละตัวกับรหัสเฉพาะ ผู้พูดยกตัวอย่างว่า token "hello" อาจเป็น 9906 และ "unhappiness" อาจเป็นรายการรหัสสองตัว (เขาพูดตัวเลข 167 กับ 1327 แบบประกอบ) โมเดลจึง "ไม่เคยเห็นตัวอักษร เห็นแต่ลำดับตัวเลข" ภาพรวมคือ ข้อความ → token → ตัวเลข แล้วโมเดลทำงานในโลกตัวเลขล้วน

ทำไมวิศวกรต้องสน. เพราะทุกอย่างวัดเป็น token: ค่าใช้จ่าย (จ่ายตาม token ขาเข้าและขาออก) ความเร็ว (ยิ่งส่ง token เข้าไปมาก คำตอบยิ่งช้า) และขีดจำกัดของ context window

ผู้จัดทำทดลองนับด้วย tiktoken เทียบกับตัวอย่างที่ผู้พูดและสไลด์แสดง (ผู้พูดไม่ได้ระบุว่าใช้ tokenizer ตัวใด): "Hello" (H ใหญ่) คือ id 9906 ใน cl100k_base ส่วน "hello" ตัวเล็กคือ 15339; "unhappiness" ถูกตัดเป็น 3 token (un, h, appiness) ทั้ง cl100k_base และ o200k_base และ สตริงบนสไลด์ {"key": "value"} ได้ 6 token (ถ้าไม่มีช่องว่างหลังเครื่องหมาย : ได้ 5) ไม่ใช่ 9 ในทั้งสองตัวเข้ารหัส ประเด็นหลักของผู้พูด (ข้อความถูกตัดเป็นชิ้นแล้วเป็นตัวเลข โค้ด/JSON เปลือง token) ยังถูกต้อง แต่ไม่ควรนำตัวเลข token บนสไลด์ไปใช้นับจริงกับ tokenizer ของ OpenAI

3. Context window และการที่โมเดลไม่มีความจำ (~8:43–11:15)

ผู้พูดให้ยึดข้อเท็จจริงข้อหนึ่งให้มั่น: LLM ไม่มีความจำ ทุก API call เริ่มจากศูนย์ ไม่รู้ว่าเมื่อ 5 นาทีก่อนหรือใน session ก่อนหน้าคุยอะไรมา แล้วทำไม ChatGPT หรือ Claude ถึงดูเหมือนจำได้ คำตอบคือทุกอย่างถูกยัดลงใน "text buffer" ก้อนเดียวและส่งให้โมเดลใหม่ทุกครั้ง

ภาพบัฟเฟอร์ที่เขาใช้เรียงจากบนลงล่างคือ system prompt, ข้อความแรกของผู้ใช้, คำตอบแรกของโมเดล, ข้อความที่สองของผู้ใช้, คำตอบที่สอง และข้อความปัจจุบัน "ก้อนนี้ทั้งก้อนคือความจำทั้งหมด" ต่อกันเป็นข้อความเดียวแล้วส่งใหม่ทุกครั้ง

นิยาม. context window คือจำนวน token สูงสุดที่ LLM ประมวลผลได้ในครั้งเดียว ผู้พูดเปรียบกับความจำระยะสั้นของคน ณ เวลาที่อัดคลิป รุ่นล่าสุดของ Anthropic คือ Opus 4.7 ซึ่งมองได้ 1 ล้าน token; GPT-5.5 และ Gemini 3.1 ก็ใกล้ 1 ล้าน (ผู้พูดบอก "closer to 1 million"; สไลด์แสดง 1,000,000 / 1,050,000 / 1,000,000) เพื่อเทียบ 128,000 token ราว 300 หน้า ส่วน 1 ล้านเทียบเท่า codebase ทั้งก้อน เมื่อเกินขีดจำกัด ข้อความเก่าจะถูกโมเดลมองข้าม ซึ่งวิศวกรจะชนเพดานนี้เร็วกว่าที่คิด

ผู้พูดบอกว่าจะสอนวิธีรับมือ เช่น chunking และ RAG ในส่วนถัดไปของคอร์ส (ซึ่งไม่อยู่ในคลิปนี้)

4. โมเดลคือเครื่องทำนาย token ถัดไป และ streaming (~11:15–15:32)

ผู้พูดบอกว่าจะไม่ลงลึกสถาปัตยกรรมภายใน เพราะนี่เป็นคอร์ส applied AI แต่ต้องมี mental model พื้นฐาน: โมเดลรับรายการตัวเลข ทำนายว่า token ไหนควรมาต่อ แล้วต่อไปอีกทีละ token จนคำตอบจบ "นั่นคือทั้งหมดที่ LLM เป็น — เครื่องทำนาย token ถัดไป"

ตัวอย่างคือคำถาม "What is gravity?" รอบแรกโมเดลเห็นทั้งประโยคนี้แล้วทำนาย "Gravity" รอบสองเห็นประโยคเดิมบวกคำที่เพิ่งได้แล้วทำนาย "is" รอบสามได้ "a" รอบสี่ได้ "universal" รอบห้าได้ "force" เมื่อต่อกันเป็น "gravity is a universal force" ผู้พูดเรียกว่า prediction loop

ผู้พูดสรุปว่าโมเดลไม่มองไปข้างหน้าและไม่วางแผนทั้งประโยค มันถามคำถามข้อเดียวเสมอ: จากทุกอย่างที่เห็นมาทั้งหมด (อินพุตผู้ใช้และเอาต์พุตของมันเอง) token ไหนมาต่อ นี่คือเหตุผลที่ streaming ทำได้: โมเดลไม่ต้องรอคำตอบเสร็จ ส่งแต่ละ token ไปที่จอทันทีที่ทำนายได้ จึงเห็น ChatGPT หรือ Claude พิมพ์ทีละคำ เขาแก้ความเข้าใจผิดที่ว่าโมเดลคิดคำตอบทั้งหมดไว้ก่อนแล้วจึงพิมพ์ออกมา และแนะนำคลิปของ Andrej Karpathy เรื่อง Deep Dive into LLMs like ChatGPT สำหรับคนที่อยากรู้กลไกภายในลึกขึ้น

ข้อที่ควรเข้าใจให้ตรง

"โมเดลไม่เคยวางแผนล่วงหน้า" เป็นการเล่าแบบง่ายของผู้พูด ในเชิงการฝึก โมเดลถูกฝึกให้ทำนายทีละ token จริง แต่งานวิจัย interpretability ของ Anthropic ("Tracing the thoughts of a large language model") รายงานว่า Claude พิจารณาคำสัมผัสไว้ก่อนเขียนบรรทัดที่สองของกลอน แล้วเขียนไปหาคำนั้น ผู้จัดทำจึงแนะนำให้อ่านประโยคของผู้พูดเป็น "กลไกการสร้างคือทีละ token" ไม่ใช่ "ภายในไม่มีการเตรียมล่วงหน้าเลย"

5. พื้นฐาน prompt: บทบาทและ system prompt (~15:32–18:57)

คำถามที่ตามมาคือจะควบคุมสิ่งที่โมเดลทำนายอย่างไร ให้ทำตัวเป็นฝ่ายซัพพอร์ตลูกค้า ผู้ช่วยเขียนโค้ด หรือนักวิเคราะห์ข้อมูล นั่นคือ prompting ซึ่งมีโครงสร้างมากกว่าที่คนส่วนใหญ่คิด ใต้กล่องข้อความทุก call ประกอบด้วยข้อความที่มี role

มีสาม role: system (คำสั่งถึงโมเดล กำหนดพฤติกรรม persona และกฎ), user (อินพุตของผู้ใช้) และ assistant (คำตอบของโมเดล) payload จริงเป็น JSON ที่มีรายการ messages โดยแต่ละอ็อบเจ็กต์มี role กับ content

system prompt คือที่ที่ "วิศวกรพูดกับโมเดล". ผู้ใช้ปลายทางไม่ได้เขียนหรือเห็นมัน (ส่วนใหญ่ถูกซ่อน) วิศวกรเขียนตอน build: user prompt คือสิ่งที่คนถาม ส่วน system prompt คือบริบทและกฎที่โมเดลใช้ตอบ แม้ผู้ใช้พิมพ์ "hey, how are you" เป็นข้อความแรกใน Claude ก็ยังมี system message ถูกส่งไปพร้อมกันเสมอ

ตัวอย่างของเขา: ผู้ใช้พิมพ์ "can you help me with this?" ถ้า system prompt บอกว่าเป็นเจ้าหน้าที่ซัพพอร์ตของบริษัทซอฟต์แวร์ โมเดลจะถามว่ามีปัญหาซอฟต์แวร์อะไร แต่ถ้า system prompt เป็นเรื่องฟิตเนส โมเดลจะถามเป้าหมายการออกกำลังกายหรืออาหาร ผู้ใช้พิมพ์ห้าหกคำเท่าเดิมแต่ได้คำตอบคนละแบบ ผู้พูดบอกว่าแอปเกือบทุกตัวมี system prompt ที่เขียนอย่างตั้งใจ ซึ่งกำหนด persona, เรื่องที่พูดหรือไม่พูด, รูปแบบคำตอบ และกฎข้อจำกัด และสรุปว่า "system prompt ที่อ่อนให้โมเดลทั่วไป system prompt ที่แข็งแรงให้ผลิตภัณฑ์"

6. temperature และ max tokens (~18:57–23:08)

temperature = ควบคุมความสุ่ม. ตามที่ผู้พูดอธิบาย ในแต่ละก้าวโมเดลไม่ได้เลือก token เดียวทันที แต่คำนวณการแจกแจงความน่าจะเป็นของ token ถัดไปทั้งหมด ตัวอย่างสมมติ: ให้ประโยค "objects fall due to" โมเดลอาจให้ "gravity" 40%, "force" 20% และ token อีกตัว 15% (ชื่อ token นั้นฟังไม่ชัดในเสียง) และอื่น ๆ temperature คือพารามิเตอร์ที่ผู้พูดบอกว่าส่งได้ใน API ของ LLM ส่วนใหญ่ และกำหนดว่าจะ "สุ่มจากการแจกแจงนี้อย่างไร" ว่าจะกล้าหรือระวัง

  • temperature = 0: เลือก token ที่น่าจะเป็นที่สุดเสมอ ผลจึง deterministic ถามคำถามเดิมสองครั้งได้คำตอบเดิม
  • temperature = 1: สุ่มจากการแจกแจง ผู้พูดว่าบางครั้งจะเลือก token ที่น่าจะเป็นต่ำกว่า คำตอบหลากหลาย สร้างสรรค์ และน่าประหลาดใจมากขึ้น
  • มากกว่า 1: การแจกแจงแบนลงไปอีก คำตอบคาดเดาไม่ได้ยิ่งขึ้น และสุดท้ายอาจไม่ปะติดปะต่อ
เสริมจากผู้จัดทำ

ผู้พูดอธิบาย temperature เป็นคำพูดและไม่ได้เขียนสูตร ผู้จัดทำเพิ่มสมการ softmax ที่หารคะแนนด้วย temperature ซึ่งเป็นรูปแบบมาตรฐานที่ใช้อธิบายแนวคิดนี้ เพื่อให้เห็นว่า 0, 1 และมากกว่า 1 ต่างกันอย่างไร

max tokens. คือจำนวน token สูงสุดที่โมเดลมีสิทธิ์สร้าง สำคัญเพราะ (1) ค่าใช้จ่าย จ่ายทุก token ขาออก ถ้าต้องการคำตอบบรรทัดเดียวก็ไม่อยากให้เขียนสามย่อหน้า (2) ความปลอดภัยเชิงการใช้งาน เป็น "hard cap" บังคับให้สั้น ข้อควรระวังมีสองข้อ: ตั้งต่ำไปโมเดลตัดกลางประโยค ได้คำตอบไม่จบ; ตั้งสูงไปอาจจ่ายค่า padding และความยืดเยื้อโดยไม่จำเป็น ค่าที่เหมาะขึ้นกับงาน: งานจำแนกอาจพอที่ 10–20 token ส่วนคำอธิบายเชิงเทคนิคอาจต้อง 500 ขึ้นไป (ตัวเลขช่วงบนไม่ชัดในเสียง)

รวมสี่ตัวเลือก. ทุก call ที่ทำ วิศวกรตัดสินใจสี่เรื่อง: system prompt, user prompt, temperature, max tokens ถ้าตั้งถูกจะควบคุมพฤติกรรมได้แน่น ถ้าตั้งผิดจะได้คำตอบไม่คงที่ แพง หรือนอกประเด็น

7. zero-shot และ few-shot prompting (~23:08–29:50)

ผู้พูดบอกว่าจะสอนสี่เทคนิค (zero-shot, few-shot, chain of thought, role prompting) ซึ่งออกในการสัมภาษณ์งานบ่อย และการรู้ว่าเมื่อไรใช้อะไรส่งผลต่อทั้งคุณภาพและต้นทุน

zero-shot คือสั่งงานโดยไม่ให้ตัวอย่าง ให้โมเดลเดาจากคำสั่งล้วน ๆ เป็นสิ่งที่ทุกคนทำเมื่อพิมพ์ "สรุปบทความนี้" "แปลเป็นฝรั่งเศส" หรือ "รีวิวนี้บวกหรือลบ" ผู้พูดเตือนว่าหลายคนเข้าใจผิดว่า zero-shot คือ prompt ขี้เกียจ ซึ่ง "ไม่ใช่ นั่นแค่ prompt ที่แย่" zero-shot ที่ดียังต้องเจาะจง: "summarize this" เฉย ๆ โมเดลอาจตอบเป็น bullet ย่อหน้า ยาวหรือสั้นก็ได้ แต่ "สรุปเป็น 3 bullet ไม่เกิน 15 คำต่อข้อ สำหรับผู้อ่านที่ไม่ใช่สายเทคนิค" ให้ข้อจำกัดชัด เทคนิคเดียวกัน ผลต่างกัน zero-shot เหมาะกับจำแนก แปล สรุป ถามตอบง่าย แต่จะเริ่มสะดุดเมื่อโจทย์ซับซ้อนหรือต้องการรูปแบบเฉพาะมาก

few-shot. ผู้พูดบอกว่าน่าจะเป็นเทคนิคที่ใช้งานได้จริงที่สุดในคลิป และเป็นแบบที่เขาเองใช้บ่อย แนวคิดคือนอกจากคำสั่งแล้ว ให้ตัวอย่างว่าคำตอบที่ดีหน้าตาอย่างไร ตัวอย่างหนึ่งอัน = one-shot สองอันขึ้นไป = few-shot และในวงการสองคำนี้ถูกใช้ปนกัน

ทำไมได้ผล: เพราะโมเดลคือเครื่องทำนาย token ถัดไป เมื่อใส่ตัวอย่างไว้ใน prompt เท่ากับ "ชี้นำการแจกแจงความน่าจะเป็น" โมเดลเห็นแบบแผนจากตัวอย่างแล้วอยากต่อให้เหมือน ผู้พูดว่าไม่ใช่เวทมนตร์ แค่ prediction loop ที่ทำงานตามปกติ

ตัวอย่างคือตัวจำแนก ticket ซัพพอร์ตเป็น billing, technical หรือ general เวอร์ชัน zero-shot ใส่คำสั่งจำแนกกับ ticket "I can't log into my account" ซึ่งเป็น prompt ที่ดีอยู่แล้ว แต่ถ้าใช้ในระบบอัตโนมัติที่ความแม่นยำสำคัญ เขาสมมติว่าอาจถูกเก้าจากสิบครั้งและพลาดหนึ่งครั้ง จึงเพิ่มตัวอย่างหลายแถว (ticket พร้อมหมวด) ไว้ก่อน ticket สุดท้าย เพื่อหวังความแม่นยำราว 99.9% (ตัวเลขเป็นการสมมติของผู้พูด ไม่ใช่ผลวัด) โมเดลจึงเห็นแล้วว่าอินพุตเป็นอย่างไร เอาต์พุตเป็นอย่างไร และรูปแบบที่ต้องการ

แนวปฏิบัติ. (1) ควรให้กี่ตัวอย่าง: ผู้พูดว่า 3–5 คือจุดที่ดีจากประสบการณ์ของเขา มากกว่านั้นเปลือง token โดยได้ประโยชน์เพิ่มน้อย (2) ตัวอย่างที่ดี: ต้องครอบคลุม edge case และรูปแบบที่แตกต่าง ไม่ใช่แค่กรณีง่ายชัดเจน (3) เมื่อไรไม่คุ้ม: งานที่นิยามชัดและ zero-shot ให้ผลสะอาดอยู่แล้ว เพราะทุกตัวอย่างที่เพิ่มคือ token ใน context window ซึ่งเป็นการแลกระหว่างคุณภาพกับต้นทุน ผลลัพธ์ที่มีความเสี่ยงสูงและเน้นรูปแบบ/ความแม่นยำ few-shot คุ้ม งานง่ายใช้ zero-shot ก็พอ

8. chain of thought และ role prompting (~29:50–34:48)

ผู้พูดเรียกว่ามี "ข้อมูลเชิงลึกที่น่าประหลาดใจ": ถามโมเดลโจทย์หลายขั้น (คณิต ปริศนาตรรกะ หรือการตัดสินใจทางธุรกิจ) แล้วตอบผิด แต่เติมสี่คำ "think step by step" ก็ตอบถูกได้

เหตุผลย้อนกลับไปที่ prediction loop: โมเดลทำนายทีละ token และทุก token ที่สร้างจะกลายเป็น context ของการทำนายถัดไป เมื่อบังคับให้เขียนเหตุผลก่อนคำตอบสุดท้าย token เหตุผลเหล่านั้นก็เป็นบริบทที่โมเดลใช้ต่อ "มันกำลังคิดออกเสียง และการคิดนั้นทำให้สิ่งที่ตามมาดีขึ้น" ถ้าไม่มี chain of thought โมเดลกระโดดไปที่ token คำตอบเลย ซึ่งกดดันให้ต้องถูกด้วย token เดียว แต่ถ้ามี มันสร้างสายเหตุผลก่อน แล้วสายนั้นนำไปสู่คำตอบที่ดีกว่า

ตัวอย่างโจทย์: ร้านขายแอปเปิลลูกละ $1.5; Maya ซื้อ 4 ลูกและจ่ายด้วยธนบัตร $10 จากนั้นซื้ออีก 2 ลูก เหลือเงินเท่าไร ถ้าไม่ใช้ chain of thought โมเดลอาจตอบตัวเลขตรง ๆ เช่น $4 หรือ $2 และคำนวณพลาด แต่เมื่อเติม "think step by step" มันแตกเป็นขั้น: ขั้น 1 สี่ลูกลูกละ $1.5 = $6; ขั้น 2 จ่าย $10 ได้เงินทอน $4; ขั้น 3 ซื้ออีกสองลูก $3 แล้วต่อด้วยขั้นสุดท้ายที่ให้คำตอบ (ตัวเลขสุดท้ายไม่ปรากฏใน transcript; ผู้จัดทำคำนวณเองได้ $4 − $3 = $1) โมเดลและพารามิเตอร์เดิมทุกอย่าง แค่ผลักให้คิดออกเสียง

1เงินที่เหลือ (ผู้จัดทำคำนวณ)

คู่มือเลือกใช้ของผู้พูด: โจทย์คณิตหรือตรรกะหลายขั้น ใช้เสมอ; การจำแนกซับซ้อนที่มี edge case ใช้แน่นอน; Q&A ข้อเท็จจริงง่าย ๆ ไม่ควรใช้เพราะเปลือง token; งานเขียนสร้างสรรค์ไม่ต้อง เพราะขั้นเหตุผลไม่ช่วย

สรุปชุดเครื่องมือ. zero-shot เมื่องานตรงไปตรงมาและเขียนคำสั่งเจาะจงได้; few-shot เมื่อต้องการรูปแบบเฉพาะหรือ zero-shot ไม่นิ่ง; chain of thought เมื่อต้องคิดหลายขั้นและความแม่นยำสำคัญ; role prompting เมื่อต้องให้โมเดลสวม persona หรือความเชี่ยวชาญ ซึ่งผู้พูดบอกว่าผู้ชมรู้แล้วจากตอน system prompt (ไม่ได้สอนแยก) ตอนถัดไปจะลงมือเรียก API จริง

เสริมจากผู้จัดทำ

ผู้พูดอธิบาย chain of thought จากมุมที่ผู้ใช้เติมคำสั่งลงใน prompt ส่วนใน API ปัจจุบันบางค่ายแยกการคิดเป็นพารามิเตอร์ของตัวเอง เช่น reasoning.effort ของ GPT-5.5 (none/low/medium/high/xhigh ตามหน้าโมเดลของ OpenAI) และ budget_tokens ของ extended thinking ใน Claude ซึ่งคลิปไม่ได้พูดถึง ผู้จัดทำไม่ได้ทดสอบว่าการเติม "think step by step" ยังช่วยอยู่เท่าไรกับโมเดลรุ่นที่คิดภายในได้

9. เรียก API ของ OpenAI ครั้งแรกและ streaming (~34:48–47:04)

ตอนนี้ผู้พูดสาธิตสิ่งที่เรียนมา (system prompt, temperature, max tokens) ผ่านโค้ดจริง

เตรียมสภาพแวดล้อม. สร้างโฟลเดอร์ชื่อ LLM fundamentals เปิดใน VS Code (หรือ Cursor), สร้าง Python virtual environment (Mac ใช้ python3 -m venv, Windows ใช้ python) แล้ว activate, ติดตั้งสองแพ็กเกจ openai กับ python-dotenv, สร้างไฟล์ .env ใส่ OpenAI API key ซึ่งสร้างได้จาก platform.openai.com → Settings → API keys → Create new secret key, และสร้าง .gitignore ให้ ignore ทั้ง .env และโฟลเดอร์ venv เพื่อไม่ push ขึ้น GitHub ผู้พูดบอกว่า repo ของโค้ดมีลิงก์ในคำอธิบายคลิป ถ้าเจอ error insufficient balance ต้องไป "Add to credit balance" ขั้นต่ำ $5

ไฟล์ LLM basics (ผู้พูดนับได้เจ็ดส่วน). เริ่มต้น: import SDK, โหลดตัวแปรสภาพแวดล้อม, สร้าง client call แรก: client.responses.create ที่ง่ายที่สุด ระบุโมเดล (ในคลิปใช้ GPT-4o; ใช้ GPT-5, 5.5 หรือ 4o mini ก็ได้) กับอินพุตของผู้ใช้ แล้วพิมพ์ผลลัพธ์ ซึ่งเป็น Python object ที่ SDK แปลงมาจาก JSON ที่เซิร์ฟเวอร์ตอบ มีฟิลด์ที่ไม่ต้องใช้เยอะ (id, created at, metadata, instructions, model, output ฯลฯ) และคำตอบ "ฝังลึก" ใน content จึงใช้ property output_text เพื่อดึงเฉพาะข้อความ (ผลคือ "square root of 49 is 7")

หลายรอบ (multi-turn). ส่งประวัติสนทนาเป็นรายการ input ซึ่งแต่ละตัวมี role กับ content เช่น user: "my name is Harish", assistant: "nice to meet you Harish", แล้วถามต่อ "what is my name?" โมเดลตอบชื่อได้เพราะเราส่งประวัติทั้งหมดไปด้วย ซึ่งสอดคล้องกับเรื่อง "ไม่มีความจำ"

system prompt, max tokens และ usage. พารามิเตอร์ instructions คือ system message (ผู้พูดบอกว่าจะใส่เป็น role system ในรายการ input แทนก็ได้) ตัวอย่างสั่งให้เป็นผู้ช่วยที่ตลก ถามรากที่สองของ 49 ผลคือตอบ 7 พร้อมมุกเล่นคำ เมื่อพิมพ์ usage จะเห็น input tokens (ผลรวม token ของทุกประโยคที่ส่ง), output tokens (ราว 30 token ในตัวอย่าง) และ total tokens ส่วน max_output_tokens: ตอนตั้งเป็น 10 API ปฏิเสธเพราะต่ำกว่าค่าต่ำสุด ผู้พูดจึงตั้ง 20 แล้วคำตอบ ("why was the math sad because...") ถูกตัดที่ token ที่ 20 สมกับเป็น hard cap แล้วตั้งกลับเป็น 100

streaming. ตั้ง stream=True แล้วแทนที่จะได้ response object ทั้งก้อน เราได้ Python generator (ตัวสร้างค่าทีละตัวตามที่ได้รับ) วนด้วย for ... in แล้วพิมพ์ทุก event จะเห็นว่าทุก token ถูกส่งมาทีละตัวแทนที่จะมาทั้งหมดในคราวเดียว

ข้อที่ควรเข้าใจให้ตรง

ผู้จัดทำตั้งข้อสังเกต: หัวข้อบทในคำอธิบายคลิประบุ "OpenAI, Anthropic, Gemini" และผู้พูดเองก็บอกไว้ก่อนเริ่มบท (~34:26) ว่าจะเรียกทั้ง OpenAI และ Anthropic ในโค้ดจริง แต่ตลอดบทที่สาธิตมีเฉพาะ OpenAI (Responses API) ไม่มีตัวอย่างเรียก Anthropic หรือ Gemini เลย ผู้อ่านที่ต้องการของสองเจ้านั้นต้องหาจากที่อื่น อีกข้อ: ข้อความ error ที่ผู้พูดอ่านออกเสียงบอกว่าค่าต้อง "greater than 16" และต่ำกว่าค่าต่ำสุด ผู้จัดทำอ่านว่าค่าต่ำสุดคือ 16 (ไม่พบตัวเลขนี้ในเอกสารที่เปิดอ่านได้)

10. Structured output: ให้ LLM คืน JSON อย่างเชื่อถือได้ (~47:04–52:59)

เป้าหมายคือให้ได้อ็อบเจ็กต์ที่มี name, age, city เพื่อเรียก result.name ได้ ไม่ใช่ข้อความภาษาอังกฤษ ผู้พูดลองสามระดับ

ระดับ 1 — ขอตรง ๆ. ถามว่า "ให้ชื่อ อายุ เมือง ของคนสมมติ" ผลเป็นข้อความทำนอง "Sure, here's a fictional person ..." ที่ parse ยากในระบบซอฟต์แวร์ เมื่อรันจริงได้ name, age, city แต่ยังเป็น string ก้อนเดียว (ตรวจด้วย type() ได้ str)

ระดับ 2 — วิธี "naive": เขียนใน prompt ว่าตอบเป็น JSON. บางครั้งก็ได้ผล แต่โมเดลอาจห่อด้วยบล็อก JSON ของ markdown เปลี่ยนชื่อ key หรือเพิ่มฟิลด์ที่ไม่ได้ขอ ในการรันจริง ยังเป็น string และมีรั้ว markdown ติดมา ต้องเขียนตรรกะเองเพื่อตัดออก ผู้พูดสรุปว่าไม่ใช่วิธีที่เชื่อถือได้

ระดับ 3 — Pydantic (วิธีที่ดีที่สุดตามผู้พูด). Pydantic ให้นิยามรูปร่างของข้อมูลที่คาดหวัง แต่ละฟิลด์มีชื่อและชนิด (string, int, float, bool, list ฯลฯ) ตัวอย่างคือคลาส Person สืบจาก BaseModel ที่มี name: str, age: int, city: str เมื่อส่ง text_format=Person ให้ client.responses.parse ตัว SDK แปลงคลาสเป็น JSON Schema ส่งไปยังเซิร์ฟเวอร์ OpenAI ผู้พูดอธิบายว่าโมเดลถูกจำกัด "ที่ระดับเซิร์ฟเวอร์" ให้คืนเฉพาะข้อมูลที่ตรง schema ความต่างคือ การบอกในพรอมต์ว่า "ตอบเป็น JSON" เป็นเพียงข้อเสนอแนะที่โมเดลเมินได้ ส่วน text format เป็นการรับประกันที่บังคับก่อนถึงมือเรา ไม่ต้องเขียนคำว่า JSON ใน instructions อีก ผลคือได้ Python object ใช้ .name .age .city แยกกันได้ และผู้พูดบอกว่าจะใช้ Pydantic แบบนี้ตลอดคอร์ส

เสริมจากผู้จัดทำ

จากเอกสาร OpenAI (ไม่ได้อยู่ในคลิป): ใน Python Responses API อ่านผลที่ parse แล้วได้จาก response.output_parsed; JSON mode การันตีเพียงว่าเป็น JSON ที่ถูกต้อง ส่วน Structured Outputs การันตีว่าตรง schema; และการปฏิเสธเพื่อความปลอดภัย (refusal) แยกจากการตรง schema ตรวจพบได้ด้วยโค้ด ผู้จัดทำไม่พบในหน้าเอกสารที่เปิดอ่านได้ว่ากลไกภายในเป็น constrained decoding ตามคำอธิบายของผู้พูดหรือไม่

11. โครงสร้าง response payload ของ OpenAI (~52:59–58:44)

ตอนนี้เป็นการเตรียมตัวก่อนเรียนเรื่อง tool call: ต้องเข้าใจโครงสร้างเต็มของสิ่งที่ OpenAI ส่งกลับ ผู้พูดเปิดบรรทัดโค้ดที่แสดง JSON ดิบแทนอ็อบเจ็กต์ที่ SDK ขัดเกลาแล้ว

ส่วนบนสุด. มีฟิลด์เมตาดาตา เช่น id, created at, model (รุ่นที่ใช้) และสถานะว่าทำงานเสร็จหรือไม่ ผู้พูดว่าในงานประจำวันแทบไม่ต้องใช้ส่วนใหญ่ usage คือ input tokens, output tokens, total tokens ซึ่งเขาเรียกว่า "มิเตอร์ค่าใช้จ่าย" และมีค่าพารามิเตอร์ เช่น temperature ที่ OpenAI สะท้อน (echo) กลับตามที่เราส่ง

ส่วนที่น่าสนใจคือ output. เป็นรายการ (list) ที่แต่ละ item มี id, content, role, status, type คำตอบอยู่ที่นี่ ทำไมเป็นรายการ ไม่ใช่อ็อบเจ็กต์เดียว: เพราะคำตอบของ LLM ไม่ได้เป็นข้อความเสมอไป อาจมี tool call ที่โมเดลตัดสินใจเรียกฟังก์ชันแทนการตอบข้อความ ซึ่งจะเห็นในตอนถัดไป และบางครั้งอาจมีทั้ง tool call และข้อความ (type message) รวมกัน โครงสร้างจึงรองรับกรณีซับซ้อนไว้แล้ว ในกรณีง่าย ๆ ตอนนี้มี item เดียวเป็นข้อความ

ภายใน item ชนิด message มี content ซึ่งก็เป็นรายการอีกชั้น ที่เก็บข้อความ "square root of 49 is 7" ทำไมเป็นรายการ: เพราะบางครั้งโมเดลอาจตอบทั้งภาพและข้อความ หรือภาพล้วน (คำของผู้พูด: "you get the idea") ทำให้ขยายได้ การเดินไป item แรก content แรกเพื่อเอาข้อความนั้นยุ่งยาก OpenAI จึงเตรียม output_text เป็นทางลัด ผู้พูดแนะนำให้ไปอ่านเอกสาร OpenAI SDK ส่วน text generation และลิงก์ structured outputs

ข้อที่ควรเข้าใจให้ตรง

ผู้จัดทำเทียบกับเอกสารที่ผู้พูดเปิดขึ้นจอ: ผู้พูดอธิบาย output_text ว่าไปหยิบ item แรกและ content แรก (~57:26) แต่เอกสารที่เขาอ่านขึ้นจอท้ายบทเดียวกัน (~58:12) บอกว่า property นี้รวมข้อความทุกชิ้นจากผลลัพธ์ของโมเดลเป็น string เดียว ซึ่งต่างกันเมื่อ output มีหลาย item ที่เป็นข้อความ ผู้จัดทำจึงแนะนำให้ยึดคำอธิบายในเอกสาร

12. Tool call: โมเดลเรียกฟังก์ชันภายนอกอย่างไร (~58:44–73:42)

ปัญหา. ตอนก่อนหน้าเราได้ JSON ที่เชื่อถือได้ แต่โมเดลยังติดอยู่ในกล่อง (ผู้พูดว่าโมเดลติดอยู่ในกล่องของมัน): ทำงานได้เฉพาะสิ่งที่เราส่งให้ ไม่รู้ว่าสภาพอากาศตอนนี้เป็นอย่างไร เช็กฐานข้อมูลไม่ได้ ส่งอีเมลไม่ได้ ดูราคาหุ้นไม่ได้ มันเป็นตัวทำนายข้อความที่มี knowledge cutoff (ถูกฝึกด้วยข้อมูลถึงช่วงหนึ่ง เช่น 2024 ตามตัวอย่างของผู้พูด) ผู้พูดบอกตรง ๆ ว่า tool call เป็นแนวคิดที่สำคัญที่สุดเพียงข้อเดียวของโมดูลนี้ เพราะเมื่อเข้าใจก็จะเข้าใจ AI agent

เมื่อรันโค้ดถาม "what is the current weather in Bangalore" โดยยังไม่ให้เครื่องมือ โมเดลตอบว่าให้ข้อมูลสภาพอากาศเรียลไทม์ไม่ได้ ซึ่งสมเหตุสมผลเพราะไม่มีอินเทอร์เน็ตและรู้เฉพาะข้อมูลที่ใช้ฝึก

tool คืออะไร. คือฟังก์ชัน Python ในโค้ดเบสของเราที่เปิดเผยให้โมเดลรู้ โดยบอกว่ามีเครื่องมืออะไร แต่ละตัวทำอะไร และรับอินพุตอะไร (อาร์กิวเมนต์ของฟังก์ชัน) สิ่งที่ส่งไปคือชื่อ คำอธิบายว่าทำอะไร และอาร์กิวเมนต์ ผู้พูดย้ำว่า ไม่ส่งตัวโค้ดของฟังก์ชัน ส่งแค่คำอธิบาย และ function calling กับ tool calling คือสิ่งเดียวกัน

mental model สำคัญ. คนส่วนใหญ่เข้าใจว่าเมื่อให้เครื่องมือ โมเดลจะออกไปเรียกฟังก์ชันเอง เช่น วิ่งไปที่ weather API แล้วกลับมา ผู้พูดบอกว่าไม่ใช่ สิ่งที่เกิดจริงมีห้าขั้น:

  1. เราถามโมเดล (เช่น อากาศที่ Bangalore) พร้อมยื่นรายการเครื่องมือที่โมเดลขอให้เราใช้ได้
  2. โมเดลดูคำถามกับเครื่องมือที่มี แล้วตอบทำนองว่า "ให้เรียกเครื่องมือ get_weather โดย city = Bangalore" โมเดลไม่ได้เรียกเอง แค่ส่งคำสั่งมาให้
  3. โค้ดของเราเอาคำสั่งนั้นไปรันฟังก์ชันในโค้ดของเราเองและเก็บผลลัพธ์
  4. เรากลับไปหาโมเดลพร้อมทุกอย่าง: คำถามเดิม คำสั่งที่โมเดลให้มา และผลลัพธ์ของเครื่องมือ
  5. โมเดลมีข้อมูลครบแล้ว ตอบสุดท้าย เช่น "อากาศที่ Bangalore ตอนนี้ค่อนข้างดี 28° แดดจัด"

ผู้พูดสรุปว่า "โมเดลเป็นผู้ประสานงาน โค้ดของเราเป็นผู้ลงมือ"

โค้ดและ tool definition. ฟังก์ชัน get_weather(city) ในคลิปเป็นฟังก์ชัน Python ธรรมดาที่แสร้งคืนค่า (ของจริงจะเรียก weather API) ได้ JSON ที่มี city, temperature, unit, condition จากนั้นต้องอธิบายฟังก์ชันให้โมเดลด้วยโครงสร้างที่เรียกว่า tool definition ผู้พูดเน้นว่าต้องเข้าใจโครงสร้างนี้ให้ดี: tools เป็นรายการ (ใส่ได้หลายตัว) แต่ละตัวมี type: "function" (มาตรฐาน), name (get_weather), description ("get the current weather for a given city" สำคัญมากเพราะโมเดลอ่านแล้วตัดสินใจ) และ parameters ที่เป็น type: object (มาตรฐาน) กับ properties ที่ระบุชื่ออาร์กิวเมนต์ ชนิด และคำอธิบาย (ที่นี่คือ city ชนิด string) และ required ซึ่งเป็นรายการพารามิเตอร์ที่จำเป็น โมเดลจะไม่พยายามเรียกโดยไม่มี city ถ้าฟังก์ชันมีอาร์กิวเมนต์เพิ่มก็เพิ่มใน properties ได้ เช่นปี

เรียกโมเดล. ส่งข้อความผู้ใช้ "what is the current weather in Bangalore" พร้อมรายการ tools ให้ Responses API เมื่อดู JSON ดิบ item ใน output ไม่ใช่ข้อความภาษาอังกฤษ แต่มี type เป็น function call บอกให้เรียก get_weather พร้อมอาร์กิวเมนต์เป็น JSON (city = Bangalore) และมี function call ID ซึ่งผู้พูดย้ำว่าสำคัญ

ทำตามคำสั่ง. โค้ดดึงชื่อฟังก์ชันและอาร์กิวเมนต์จาก item แรกของ output ใช้ json.loads แปลงเป็นอ็อบเจ็กต์ Python แล้วรัน get_weather ด้วยตนเอง จากนั้นสร้างประวัติสนทนาเต็มเพื่อส่งกลับ ประกอบด้วย (1) ข้อความผู้ใช้เดิม (2) อ็อบเจ็กต์ tool call ที่โมเดลส่งมา (3) ผลลัพธ์ของ tool ซึ่งมี type เป็น function call output (คำสงวนมาตรฐานของ SDK) และฟิลด์ output ผู้พูดเน้นว่าต้องแปลงผลลัพธ์เป็น string ด้วย JSON ก่อนส่ง เพราะ LLM มองอ็อบเจ็กต์ Python ไม่ได้ และต้องส่ง function call ID เดิมกลับไปด้วย เพื่อให้โมเดลจับคู่ได้ว่าผลลัพธ์ไหนตอบ tool call ไหน เพราะในอนาคตอาจมี tool call 5, 10, 15, 20 ตัว สุดท้ายส่งรายการอินพุตทั้งหมดให้โมเดลเพื่อคำตอบสุดท้าย

ผลที่รัน: โมเดลแนะนำเรียก get_weather ด้วย Bangalore ได้ผลดิบแล้วตอบ "current weather in Bangalore is 28°" เมื่อเปลี่ยนเป็น Delhi ก็ได้ว่า Delhi แดดจัด 28° (ค่า 28° เป็นข้อมูลปลอมที่ฟังก์ชันในคลิปคืนเสมอ)

ข้อสรุป. โมเดลไม่เคยแตะฟังก์ชันสภาพอากาศ ไม่เคยเรียก API แค่อ่านคำถามกับคำอธิบายเครื่องมือแล้วบอกว่าให้เรียกอะไรด้วยอาร์กิวเมนต์ใด โค้ดของเราทำงานจริงแล้วส่งผลกลับให้โมเดลใช้ตอบ นี่คือ tool call ทั้งหมด และ AI agent ทุกตัว ไม่ว่าจะท่องเว็บ query ฐานข้อมูล ส่งอีเมล หรือรันโค้ด คือแนวคิดเดียวกันที่ทำซ้ำกับเครื่องมือมากขึ้น: โมเดลตัดสินใจว่าจะทำอะไร โค้ดลงมือ ผลกลับไปหาโมเดล เมื่อเข้าใจวงนี้ agent จะเลิกดูเป็นเวทมนตร์และกลายเป็นงานวิศวกรรม ท้ายคลิปผู้พูดชวนไปเรียน LangChain, LangGraph, RAG ต่อ หรือซื้อคอร์ส production AI ของเขา (ตัดส่วนโฆษณาออกจากรายงาน)

เสริมจากผู้จัดทำ

จากเอกสาร OpenAI function calling (ไม่ได้อยู่ในคลิป): tool definition มีฟิลด์ strict เพิ่มได้ ผลที่โมเดลคืนคือ arguments เป็นสตริง JSON ซึ่งตรงกับที่ผู้พูดใช้ json.loads ถอด และสำหรับโมเดล reasoning ต้องส่ง reasoning item ที่ได้พร้อม tool call กลับไปพร้อมผลของ tool ด้วย ส่วนห้าขั้นตอนในเอกสารตรงกับห้าขั้นที่ผู้พูดสอน

Key Takeaways

1.LLM ทำงานในโลกตัวเลข: ข้อความ → token → รหัส แล้ววนทำนาย token ถัดไป ทุกอย่าง (ราคา ความเร็ว ขีดจำกัด) วัดเป็น token
2.โมเดลไม่มีความจำ: ประวัติบทสนทนาทั้งก้อนถูกส่งซ้ำทุก call และถูกจำกัดด้วย context window
3.คุณคุมพฤติกรรมด้วย system prompt, temperature, max tokens และเทคนิค prompt: zero-shot ต้องเจาะจง few-shot (3–5 ตัวอย่างตามประสบการณ์ผู้พูด) ชี้นำรูปแบบ chain of thought ให้เหตุผลก่อนคำตอบ
4.ถ้าโค้ดต้องอ่านผลต่อ อย่าฝากไว้กับคำสั่ง "ตอบเป็น JSON" ใช้ Pydantic กับ text_format ที่ส่ง schema ให้เซิร์ฟเวอร์
5.tool call คือโมเดลสั่ง โค้ดของเราลงมือ แล้วส่งผลกลับพร้อม call ID — agent คือวงนี้ที่ทำซ้ำ
6.ข้อควรระวังที่คลิปไม่พูด: ตัวอย่างการตัด token ในคลิปไม่ตรงกับ tokenizer ของ OpenAI, temperature 0 ไม่การันตีผลซ้ำเป๊ะ, บางรุ่นไม่รับ temperature, และเนื้อหาจริงมีเฉพาะ OpenAI
