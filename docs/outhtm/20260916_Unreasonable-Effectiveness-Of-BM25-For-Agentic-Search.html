บทสรุปย่อ

Jo Kristian Bergum (CEO ของ Hornet.dev) เสนอว่า BM25 ฟังก์ชันให้คะแนนแบบ lexical อายุราว 30 ปี "ไม่ได้กลายเป็นเวทมนตร์" แต่ ผู้ใช้เปลี่ยน: LLM ที่ทำงานเป็น agent มีความรู้ทั่วไปในตัว เขียน query ยาวและเจาะจง (ใช้ site:, ปี, ชื่อเฉพาะ, วลีในเครื่องหมายคำพูด) และยิงซ้ำได้หลายสิบรอบ เครื่องมือเรียบง่ายอย่าง BM25 กับ grep จึงทรงพลังขึ้นมาก หลักฐานหลักมาจากเกณฑ์วัด BrowseComp-Plus และงาน Pi-Serini ที่แสดงว่า "BM25 ตัวไหน" สำคัญมาก: ค่า k1 = 0.9, b = 0.4 ได้ 64.0% ขณะที่ k1 = 25, b = 1 ได้ 82.0% (สไลด์)

ผู้พูด ไม่ได้เขียนหรืออ่านสูตร BM25 เลย สไลด์มีเพียงสัญกรณ์ score(query, document), ค่า k1/b และชื่อตัววัด nDCG@10 ฉบับนี้จึงแสดงสมการที่สไลด์อ้างถึงทั้งหมดเป็นสมการจริง (BM25 แบบตำรา, แบบ Lucene, IDF สองแบบ, NDCG) โดยติดป้ายชัดว่ามาจากสไลด์หรือจากผู้จัดทำ และแทนค่าด้วยตัวเลขของคลิปให้ดูทีละขั้น

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึก (license มาตรฐานของ YouTube) ข้อความบนสไลด์ ตัวเลข และสตริง query ถอดตรงตามภาพ สมการที่ไม่มีในคลิปติดป้าย "ผู้จัดทำ"

สรุปเชิงลึก

ข้อโต้แย้งหลัก ผู้พูดนิยาม agentic search ว่าเป็น "การค้นหาที่อยู่ในวงจรของ agent" ซึ่งต้องมีสามส่วน: โมเดลที่เก่งพอจะเรียกเครื่องมือและตั้ง query, harness ที่เปิดเครื่องมือค้นหาให้โมเดล (tool calling หรือ code mode) และ retrieval engine ที่ค้นได้เร็วแม้คลังจะใหญ่ระดับพันล้านเอกสาร BM25 คือฟังก์ชันให้คะแนนที่รวม "ความหายากของคำ ความถี่ของคำ และการปรับตามความยาวเอกสาร" เป็นตัวเลขเดียว (สไลด์ 04) ส่วนการดึง top-k ให้เร็วเป็นอีกเรื่องหนึ่ง (inverted index, WAND) ตัวฟังก์ชันไม่เปลี่ยน สิ่งที่เปลี่ยนคือผู้ใช้: query ของมนุษย์ใน AOL log มัธยฐาน 2 คำ แต่ GPT-5 มัธยฐาน 10 คำ และ query แรกเฉลี่ย 19 คำ (สไลด์ 10)

หลักฐาน BrowseComp-Plus มีคำถามแนวปริศนา 830 ข้อบนคลังเว็บ 100,195 หน้า (สไลด์ 06) ถ้าใส่หลักฐานที่ถูกต้องให้โมเดลโดยตรง ความแม่นยำถึง 93% แต่ใน agent loop เดียวกัน retriever A ได้ 55.9% และ B ได้ 70.1% (สไลด์ 08) ผู้พูดสรุปว่าการให้เหตุผลไม่ใช่คอขวด คุณภาพการค้นคืนต่างหาก เขาเทียบ context window กับแผ่นฟลอปปี้ (ราว 1.4 MB) และเห็นว่าโมเดลเริ่มด้อยลงที่ราว 350,000 token; สไลด์ 07 ระบุ 1.44 MB ≈ 350K–370K token ที่ราว 4 ไบต์ต่อ token และ ≈ 0.05% ของคลัง 736 ล้าน token (ผู้จัดทำคำนวณ 1.44 MB ÷ 4 ≈ 360,000 และ 0.048–0.050%)

BM25 ตัวไหน BM25 มีไฮเปอร์พารามิเตอร์สองตัว (k1 คุมการอิ่มตัวของความถี่คำ, b คุมการปรับตามความยาว) baseline BM25 ใน BrowseComp-Plus "แย่มาก" ในคำของผู้พูด เพราะค่าไม่เหมาะกับเอกสารยาว Pi-Serini จูนแล้วได้ +18.0 จุด (64.0% → 82.0%) และ recall ของหลักฐานเพิ่ม +11.1 จุด (84.6% → 95.7%) เราแทนค่าในสูตร Lucene (สมการ 9) ให้เห็นกลไก: ที่ k1 = 25, b = 1 เทอมความถี่แทบเป็นเส้นตรงจน tf ราว 25 เท่าของค่าปรับความยาว และเอกสารยาวสองเท่าถูกหารด้วยความยาวเต็ม ๆ ส่วน k1 = 0.9 อิ่มตัวเกือบทันที ตัวอย่างคู่เอกสารของเราแสดงว่าลำดับพลิกได้จริงเมื่อเปลี่ยนค่า (สั้นแต่คำน้อย ชนะ เมื่อใช้ค่าที่จูน)

ทำไมเหมาะกับ agent สามข้อบนสไลด์ 12: EXACT (ชื่อ วันที่ ID วลี), CHEAP (ไม่ต้องรัน embedding ซึ่งบางตัวมี 8 พันล้านพารามิเตอร์), EXPLAIN (คำที่ตรงกันกลายเป็นการขยับครั้งต่อไปของ agent) งาน DR-DCI ใช้ BM25 นำผู้สมัครเข้า workspace แบบไฟล์แล้วให้ agent ใช้ rg/grep/read ต่อ สไลด์ให้ 61% เทียบ Qwen3 retrieval agent 45% และ 73.3% เมื่อมี reset การประเมินแบบ IR ดั้งเดิม (query เดียว ลิสต์เดียว nDCG@10) ผู้พูดว่า "แทบตายแล้ว" สำหรับ agent ให้วัดความสำเร็จของงานแทน (สไลด์ 14: success, recall, calls, latency, cost)

สิ่งที่ผู้จัดทำตรวจ ตรวจข้อเท็จจริง 16 รายการ: ยืนยัน 11, ยืนยันบางส่วน 3, ไม่พบ 2 (ตัวเลข 61%/45% ของ DR-DCI และความยาว query 2/10/19 คำ) ผู้พูดเป็น CEO ของบริษัทที่ขาย BM25 engine แผนภูมิ latency (สไลด์ 15) เป็นข้อมูลของบริษัทเองกับ engine ที่ไม่เปิดชื่อ ข้อควรนำไปใช้: เวลาพูดว่า "BM25" ให้ระบุสูตร IDF รูปแบบ TF (มีหรือไม่มี k1 + 1) และค่า k1, b เสมอ และจูนบนชุดคำถามของตัวเอง

2. Agentic search คือการค้นหาที่อยู่ในวงจรของ agent (~1:05–2:15)

นิยามของผู้พูด: agentic search คือการค้นหาภายใน agent loop agent พยายามทำงานบางอย่าง (เขียนโค้ด ทำ deep research หรืองานอื่น) และระหว่างทางมี "ความต้องการข้อมูล" ที่ต้องเติมให้ได้ งานจึงจะสำเร็จ

ระบบที่ดีต้องมีสามอย่าง:

  1. โมเดลที่เก่งพอ ใช้เครื่องมือเป็นและตั้ง query ได้ (สไลด์: เลือกว่าจะค้นเมื่อไรและตั้ง query เอง)
  2. harness รอบโมเดล ซึ่งกำหนดว่าจะเปิดฟังก์ชันค้นหาให้โมเดลแบบไหน ผู้พูดยกสองแบบคือ tool calling และ code mode (ผู้บรรยายคนก่อนหน้าสาธิตแบบหลัง) สไลด์ระบุว่า harness กำหนด tool contract เช่น search(query) และคุมงบ (context, calls, cost)
  3. retrieval engine ที่ค้นได้อย่างมีประสิทธิภาพ "อาจถึงระดับพันล้านเอกสาร" (สไลด์: จัดอันดับผู้สมัครอย่างถูก แสดงผล และรองรับการค้นซ้ำ)
เสริมจากผู้จัดทำ: ทำไมนิยามนี้สำคัญกับบทเรียน

นิยามนี้แยก "สูตรให้คะแนน" (ส่วนที่ 3 ของระบบ) ออกจาก "ใครเป็นคนตั้ง query" (ส่วนที่ 1) ข้อโต้แย้งทั้งการบรรยายอยู่บนการแยกนี้: สูตรเท่าเดิม แต่คนตั้ง query เปลี่ยน

3. BM25 คือฟังก์ชันให้คะแนน: สัญกรณ์บนสไลด์และสูตรเต็ม (~2:15–3:32)

ผู้พูดเล่าว่า BM25 ย่อมาจาก best match 25 นักวิจัยทดลองหลายแบบและ "การทดลองที่ 25" ดีที่สุด จึงได้ชื่อนี้ (เรื่องเลข 25 ยืนยันได้เพียงบางส่วน ดูตรวจข้อเท็จจริง) แก่นของมันคือ ฟังก์ชันให้คะแนน: รับ query กับเอกสาร คำนวณคะแนนจากปฏิสัมพันธ์ระหว่างคำใน query กับคำในเอกสาร และ "หวังว่า" คะแนนนั้นจะเป็นตัวแทนที่ดีของความเกี่ยวข้อง

วิธีตรงที่สุดคือให้คะแนนทุกเอกสารแล้วเลือก top-K (ผู้พูดพลั้งเรียก "BM35" ตรงนี้ครั้งหนึ่ง) แต่มีงานวิจัย 30–40 ปีเรื่องการเร่งการดึง top-K ซึ่ง Hornet ก็ลงทุนด้านนี้ สไลด์สรุปเป็นสายงาน posting lists → upper bounds → skip candidates → top-k heap (อัลกอริทึมแบบ WAND) ผู้พูดย้ำว่า BM25 เป็นฟังก์ชันให้คะแนน และการเร่ง top-K เป็นอีกเรื่องหนึ่ง และ ฟังก์ชันนี้ไม่ได้เปลี่ยน

ในอดีต BM25 เป็น baseline: งานวิจัย IR ทุกชิ้นใส่ BM25 ไว้ แล้วเอาวิธี neural ที่ซับซ้อนมาเทียบให้ชนะ ผู้พูดชี้ว่าการประเมินแบบเดิมคือดู "ลิงก์สีน้ำเงิน 10 อัน" แล้วคำนวณตัววัด และสิ่งเหล่านี้กำลังหายไป เพราะ agent พิมพ์ query ได้มากกว่ามนุษย์มาก การประเมินด้วย query เดียวจึง "มีความหมายน้อยลง"

6. Context window เท่ากับแผ่นฟลอปปี้หนึ่งแผ่น (~6:01–6:40)

ทำไมยังต้องมี retrieval: ผู้พูดชอบเทียบ context window กับ แผ่นฟลอปปี้ (สมัยยุค 80 ที่ลงเกมด้วยฟลอปปี้) แผ่นหนึ่งจุ "ราว 1.4 เมกะไบต์" และ ในความเห็นของเขา โมเดลปัจจุบันเริ่มด้อยคุณภาพที่ราว 350,000 token ซึ่ง "ก็คือฟลอปปี้หนึ่งแผ่น" retrieval จึงจำเป็นเพื่อดึงเฉพาะข้อมูลที่ต้องใช้จริงเข้า context

สไลด์ 07 ให้ตัวเลขครบกว่าที่พูด: คลัง BrowseComp-Plus มี 736M tokens, ฟลอปปี้ 1.44 MB ≈ context ที่ใช้ได้จริง ≈ 350K–370K token โดยถือว่าภาษาอังกฤษราว 4 ไบต์ต่อ token และสิ่งที่เข้าได้ก่อน context rot เป็นเพียง ~0.05% ของคลัง

7. คุณภาพการค้นคืนเปลี่ยนความแม่นยำของคำตอบ (~6:40–8:14)

BrowseComp-Plus แสดงให้เห็นว่าคุณภาพ retrieval ส่งผลต่อความแม่นยำปลายทาง ถ้า "ยัด" เอกสารหลักฐานที่ต้องใช้เข้า context ของโมเดลโดยตรง ความแม่นยำสูงมาก การให้เหตุผลจึงไม่ใช่คอขวด ผู้พูดบอกว่าแม้ "GPT4" ก็ตอบได้แม่นเมื่อได้หลักฐานล่วงหน้า แต่เมื่อให้โมเดลใช้ harness ที่มีเครื่องมือ retrieval ความแม่นยำตก เพราะตอนนี้ขึ้นกับ harness, ความสามารถของโมเดลในการตั้ง query และคุณภาพของ retriever

เขาให้น้ำหนักเรื่องนี้มาก: ต่อให้มีโมเดลที่สมบูรณ์แบบระดับ AGI ที่ไม่ต้องสั่งว่า "อย่าทำผิด" ก็ยังติดอยู่กับ context window ขนาดราวฟลอปปี้หนึ่งแผ่น จึงต้องตัดสินว่าอะไรควรเข้า context และ retrieval ยังสำคัญมาก

9. GPT-5 เป็นผู้ใช้ระดับ power user: เทียบกับบันทึก AOL (~8:44–9:44)

ทีมของผู้พูดใช้เวลาสำรวจ trajectory เหล่านี้ว่า GPT-5 ตั้ง query อย่างไร และเขียนเป็นบล็อกบน hornet.dev แล้วเทียบกับ บันทึก query ของ AOL ซึ่ง AOL เคยปล่อยตัวอย่างการค้นหาจำนวนมากออกมา "โดยไม่ตั้งใจ" query ของคนในนั้นสั้น และผู้พูดบอกว่า log รุ่นใหม่ที่เขาเคยเห็นก็ยังเป็นแบบเดิม: มนุษย์ยังค้นด้วยคำไม่กี่คำ

GPT-5 ต่างออกไป: มีความรู้ทั่วไปและ "เขียน query ยาวมากออกมาได้ทันที" ใช้ operator ไวยากรณ์ที่เรียนรู้จากเว็บ เช่น site: และวลี ผู้พูดเรียกสิ่งนี้ว่า workload แบบใหม่

10. "คุณหมายถึง BM25 ตัวไหน?": k1, b และสูตรแต่ละรุ่น (~9:44–10:50)

ผู้พูดบอกว่า BM25 มี ไฮเปอร์พารามิเตอร์สองตัว ที่คุมหลายด้านของฟังก์ชันให้คะแนน (เขาไม่ได้เอ่ยชื่อ สไลด์เขียนว่า k1 และ b) BrowseComp-Plus มี baseline เป็น BM25 แต่ "baseline นั้นแย่มาก" ถ้าดูรายงานต้นฉบับ วิธีที่ซับซ้อนกว่าอย่าง embedding model ดูเป็นกระบวนทัศน์ที่ดีกว่า BM25 มาก แต่ งานวิจัยใหม่กว่าแสดงว่าพารามิเตอร์ที่ใช้ในรายงานนั้นไม่เหมาะกับเอกสารยาว เขาจึงชอบถามว่า "คุณหมายถึง BM25 ตัวไหน" เพราะในเกณฑ์วัดนี้มันมีผลต่อความแม่นยำรวม "ค่อนข้างมาก"

11. ทำไม BM25 ทรงพลังขึ้นกับผู้ใช้แบบใหม่: EXACT, CHEAP, EXPLAIN (~10:50–12:03)

ผู้พูดให้สามเหตุผลว่าทำไม BM25 ทรงพลังขึ้นเมื่อผู้ใช้คือ agent:

  1. EXACT — การจับคำตรงตัวยังสำคัญ ผู้ใช้แบบใหม่มีความรู้ทั่วไป พิมพ์เร็วกว่าและเจาะจงกว่า โมเดลรู้จักชื่อ บุคคล/หน่วยงาน รหัสไปรษณีย์ SKU ฯลฯ ซึ่งผู้พูดว่า "ไม่ง่าย" ที่จะแทนด้วย embedding model ที่เข้ารหัส token ทั้งหมดผ่านคำศัพท์ที่ตายตัว
  2. CHEAP — ค่อนข้างถูก โดยเฉพาะเมื่อเทียบกับต้นทุน inference ของ embedding บางรุ่นมี "ราว 8 พันล้านพารามิเตอร์" ต้องตั้งโครงสร้างพื้นฐานเพิ่ม BM25 เรียบง่าย และเครื่องมือในระบบนิเวศดีและหาได้ทั่วไป
  3. EXPLAIN — โมเดลตรวจผลได้ง่าย เข้าใจได้ว่าทำไม query แบบนั้นจึงได้ผลแบบนี้ เพราะเป็นการจับคำและวลีตามตัวอักษร ซึ่งช่วยให้มันปรับ query รอบถัดไป (สไลด์: "คำที่ตรงกันกลายเป็นการขยับครั้งต่อไป")

12. BM25 + grep is all you need: งาน DR-DCI และ workspace แบบไฟล์ (~12:03–14:53)

ผู้พูดเข้าสู่ "หัวข้อร้อน" ว่าอะไรคือ "all you need" โดยยกงานใหม่จากกลุ่มของ Jimmy Lin ที่ Waterloo ซึ่งเขาชมว่าทำงานด้าน IR และ agentic search ได้ดี งานชื่อ "scaling direct corpus interaction via dynamic workspace expansion" (DR-DCI)

ฉากที่เขาให้นึกภาพ: ตั้งโครงสร้าง web search สำหรับ agent (หลายบริษัททำอยู่ และ Hornet ช่วยบางรายสร้าง) มีเอกสารนับพันล้าน ใส่ context ไม่ได้ จึงต้องมี retrieval และ BM25 เป็น baseline ที่ดี ผลลัพธ์เปรียบได้กับ หน้าผลการค้นหา (SERP) สำหรับ agent โดยวางเอกสารที่ดึงได้ไว้ใน workspace

ถ้าจัด workspace เป็น file system ก็ใช้แนวคิดเดียวกับ skills ได้ คือ progressive disclosure: ให้โมเดลเห็นชื่อเรื่องและ snippet สั้น ๆ ก่อน แล้วโมเดลตัดสินเองว่าต้องอ่านเอกสารไหนต่อ เมื่ออ่าน มันใช้เครื่องมือพื้นฐานที่เก่งอยู่แล้วจาก coding agent: grep, ripgrep, sed เพื่อจัดการ context สไลด์ระบุชุดเครื่องมือเป็น rg / grep, read lines, cat / sed, count / verify

ผู้พูดมองว่านี่ได้ "ประโยชน์ทั้งสองโลก" รวม sandbox, retrieval, VFS และ bash เข้าด้วยกัน และยอมรับว่าเป็น "แฮ็ก" แบบหนึ่ง เพราะใช้สิ่งที่โมเดลเก่งตอนนี้: บริษัท LLM ชั้นนำปรับโมเดลให้เก่งการเขียนโค้ด bash และการใช้เครื่องมือ งานที่วางบนเส้นทางนั้นจะดีขึ้นตามโมเดลใหม่ทุกรุ่น "อาจจะ" เมื่อมี AGI โมเดลจะใช้เบราว์เซอร์เองได้ "เดี๋ยวก็รู้" แต่ตอนนี้วิธีนี้ทรงพลังมาก

13. การประเมิน: จาก nDCG@10 ของ query เดียว สู่การวัดทั้ง trajectory (~14:53–15:23)

  1. ผู้ใช้แบบใหม่ ทรงพลังกว่า พิมพ์และอ่านเร็วกว่า ปรับ query ได้ และมีความรู้ทั่วไปมาก ทำให้เครื่องมือง่าย ๆ อย่าง grep และ BM25 ทรงพลังขึ้น (สไลด์: GPT-5 ค้นด้วย operator ปี วลี และการลองซ้ำ)
  2. BM25 ตัวไหน มีความต่างทั้ง implementation ประสิทธิภาพ และพารามิเตอร์ "ให้คิดถึงเรื่องนี้" (สไลด์แจกแจงกว่าที่พูด: parser / chunks / fields / k1 / b / top-k)
  3. ทำไมได้ผลกับ agentic search "ง่าย ๆ เพราะโมเดลอธิบายผลได้" และใช้ร่วมกับ grep ได้ เพราะทั้งคู่เป็นการจับตามตัวอักษร (สไลด์: exact, cheap, inspectable, steerable in the loop)
