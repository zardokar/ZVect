Google's GPT-3 Moment for Databases & Spreadsheets (TabFM) — Prompt Engineering

✍️ Prompt Engineering (YouTube)📅 เผยแพร่ 2026-10-11⏱ 10:57🧩 โหมด iwd 🔗 คลิปต้นฉบับ (YouTube)

บทสรุปย่อ

คลิปนี้แนะนำ TabFM ซึ่งเป็น foundation model สำหรับข้อมูลแบบตาราง (tabular data) จาก Google Research: เราส่งแถวที่รู้คำตอบ (label) แล้วต่อด้วยแถวที่ยังไม่รู้เข้าไปพร้อมกัน โมเดลทำนายแถวหลังในรอบเดียว (single pass) โดยไม่ต้องเทรนบนข้อมูลของเรา ผู้พูดอธิบายว่าโมเดลเรียนจากตารางสังเคราะห์ ทำไมมันจึงมองไม่เห็นชื่อคอลัมน์ และ TabFM-Auto ที่เอา LLM agent มาครอบแก้จุดอ่อนนี้ จากนั้นสาธิตทำนาย churn ของลูกค้า SaaS สมมติบน Postgres (Neon) พร้อมบทเรียนเรื่อง data leakage

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึก (license มาตรฐานของ YouTube; transcript เป็น ASR ภาษาอังกฤษ)

สรุปเชิงลึก

ข้อโต้แย้งหลักของคลิป งานจริงของธุรกิจส่วนใหญ่อยู่บนตาราง (ธุรกรรม churn ของลูกค้า log จากเซนเซอร์ การเคลมที่เป็นการฉ้อโกง สินค้าคงคลัง) ไม่ใช่ข้อความ และเวลาจะทำนายอะไรจากตาราง คนส่วนใหญ่ยังใช้ machine learning แบบคลาสสิก โดยเฉพาะ gradient boosted trees ซึ่งต้องล้างข้อมูล ทำ feature engineering ด้วยมือ เทรน ปรับ hyperparameter แล้วทำซ้ำทั้งหมดกับชุดข้อมูลถัดไป ผู้พูดเทียบว่าข้อความเคยเจ็บปวดแบบเดียวกัน (โมเดลแยกสำหรับ sentiment, spam, แปลภาษา) จน GPT-3 ทำให้แค่ใส่ตัวอย่างไม่กี่ตัวใน prompt ก็พอ และตารางเพิ่งมีช่วงเวลาแบบนั้นด้วย TabFM

TabFM ทำงานอย่างไรตามที่ผู้พูดเล่า ส่งแถวที่มี label รวมกับแถวที่ต้องการให้ทำนาย ชุดข้อมูลจึงกลายเป็น prompt ตัวโมเดลถูกฝึกจาก "สายธารตารางสังเคราะห์" ไม่รู้จบ: สุ่ม causal graph แล้วสร้างแถวจากกราฟนั้น แล้วบังคับให้ทำนายเซลล์ที่ซ่อนไว้ ผลคือมันจำชุดข้อมูลใดชุดหนึ่งไม่ได้ และเรียนรู้ "meta algorithm" ของการเรียนรู้จากตารางแทน ข้อควรระวังที่ผู้พูดย้ำ: weights ตอนนี้ใช้ได้เฉพาะงานวิจัยที่ไม่ใช่เชิงพาณิชย์ จึงควรมองเป็นแนวทางสถาปัตยกรรม ไม่ใช่โค้ดที่หยิบไปใช้ใน production ได้ทันที

สาธิต ข้อมูล SaaS สังเคราะห์ (customer, usage, invoice, ticket) ดึงจาก Neon Postgres ป้อน label ย้อนหลังให้ TabFM แล้วให้คะแนน churn ของลูกค้าที่เหลือ เขียนผลกลับตาราง ผู้พูดบอกว่าโดยไม่ทำ feature engineering เลยและใช้ตารางเดียว ก็ชนะ tree-based model ที่ปรับจูนแล้วของเขา ตัวเลขบนสไลด์คือ AUC เดือนพฤศจิกายน 0.60 เทียบ 0.52 ของ tuned tree และ 0.50 ของการเดาสุ่ม ผู้พูดเองบอกว่า 0.60 "ไม่ดีนัก" และใช้ตัวเลขนี้เป็นทางเข้าสู่จุดอ่อน

จุดอ่อนและทางแก้ เพราะ TabFM ฝึกจากกราฟสังเคราะห์ล้วน มันไม่เคยเห็นชื่อคอลัมน์ จึงมองทุกอย่างเป็นตัวเลข ไม่รู้ว่าคอลัมน์ไหนคือยอดใช้จ่าย ไหนคืออุณหภูมิ หรือว่า 0 หมายถึงยังไม่ได้วัด ผู้วิจัยจึงจับคู่กับ LLM เป็น TabFM-Auto: ตรึง (frozen) TabFM เป็นเครื่องอนุมาน แล้วให้ agent ที่ขับด้วย LLM ดูชื่อคอลัมน์ เขียนโค้ดแปลงข้อมูล เลือกแถว context และปรับเทียบ (calibrate) ผลทำนาย ซึ่งผู้วิจัยรายงานว่าติดอันดับหนึ่งใน TabArena โค้ดของ TabFM-Auto ยังไม่เปิดสาธารณะตามที่ผู้พูดบอก เขาจึงให้ Opus 5.5 สร้างเวอร์ชันของตนเองโดยใช้ Gemini เป็นตัวควบคุม (orchestrator)

บทเรียนด้านฐานข้อมูลที่ผู้พูดเน้น (1) semantic grounding: เก็บ data dictionary เป็น column comment ใน Postgres (2) sandbox: ให้ agent ทดลองบน branch แบบ copy-on-write ที่สร้างได้ในราวหนึ่งวินาที พังก็ลบ production ไม่กระทบ (3) กัน data leakage: คอลัมน์ที่ถูกเติมหลังลูกค้าขอยกเลิกดูเป็น "กระสุนเงิน" แต่สะท้อนผลลัพธ์ที่เกิดขึ้นแล้ว (ผู้พูดใช้คำว่า past outcome; ผู้จัดทำ: คือข้อมูลที่รั่วมาจากหลังจุดทำนาย) ในการทดสอบครึ่งหนึ่ง agent เห็นความสัมพันธ์แล้วเอาไปใช้ทั้งที่เสี่ยงด้านเวลา วิธีแก้คือให้เทรนบน branch ที่ย้อนกลับไปยังเวลาก่อนช่วงทำนาย โมเดลที่ดูสมบูรณ์แบบกลับแย่ที่สุดเมื่อเทียบกับสิ่งที่เกิดขึ้นจริงเดือนถัดไป ส่วนโมเดลที่ไม่มีคอลัมน์รั่วทำได้ดี สุดท้ายผู้พูดทำเป็น pipeline รายคืน และรายการลูกค้าเสี่ยงอันดับบนส่วนใหญ่ขอยกเลิกจริง

ผลจากการตรวจของเรา (ดูตารางตรวจข้อเท็จจริง 13 ข้อ: ยืนยัน 8 · ยืนยันบางส่วน 2 · ยังไม่พบ 2 · ไม่ได้ตรวจ 1) TabFM และ TabFM-Auto มีอยู่จริงตาม blog ของ Google (2026-06-30) และ paper 2 ฉบับบน arXiv (ส่ง 2026-09-29) โมเดลมีขนาดราว 400M พารามิเตอร์ตาม paper (รุ่น 1.0.x ที่ปล่อยก่อนหน้ามีราว 1.64 พันล้าน) ฝึกจากตารางสังเคราะห์ล้วน ส่วนที่คลิปไม่ได้พูดแต่ควรรู้: เกณฑ์ default ของไลบรารีคือ 500 feature และ 100 แถว context, แยก class ได้ไม่เกิน 10 คลาสในงาน classification, และตัวเลข AUC 0.60 มาจากข้อมูลสังเคราะห์ของผู้พูดเอง จึงเป็นตัวอย่างประกอบ ไม่ใช่ผล benchmark

ควรเอาไปทำอะไรต่อ (ข้อเสนอของผู้จัดทำ) อ่านเป็นแบบแผนของระบบ: โมเดลตาราง (ไม่ต้องเทรน) + LLM ที่อ่านความหมายของคอลัมน์ + ฐานข้อมูลที่ให้ branch และย้อนเวลาได้ แต่ต้องตรวจสิทธิ์ใช้งาน weights ก่อนแตะงานเชิงพาณิชย์

1. ปัญหา: ธุรกิจรันอยู่บนตาราง แต่ LLM ใช้ตรง ๆ ไม่ได้ (~0:00–1:50)

ผู้พูดเปิดด้วยการชี้ว่าทุกคนกำลังหมกมุ่นกับ LLM และเสียงส่วนใหญ่เป็นเรื่อง coding agent กับ chatbot ซึ่ง LLM เก่งจริง แต่สิ่งที่ธุรกิจจริงใช้งานไม่ใช่ข้อความ แต่เป็นตาราง เช่น ธุรกรรม churn ของลูกค้า log ของเซนเซอร์ การเคลมที่เป็นการฉ้อโกง และอาจรวมถึงข้อมูลสินค้าคงคลัง เมื่อต้องทำนายอะไรจากตาราง เขาบอกว่าใช้ LLM ตรง ๆ ไม่ได้ คนยังหันไปใช้วิธี machine learning แบบคลาสสิก ซึ่งมีข้อเสียว่าทุกปัญหาใหม่ต้องเทรนโมเดลใหม่ตั้งแต่ต้น ผู้พูดบอกว่าวันนี้จะแสดงโมเดลที่อาจทำให้กระบวนการเดิมหายไปเลย และจะแสดงวิธีเอามันไปครอบ agent วิทยาศาสตร์ข้อมูลอัตโนมัติบน back end ที่ใช้งานจริง

ผู้พูดบอกว่าเขาสร้างโมเดลทำนายบนข้อมูลตารางและอนุกรมเวลามาหลายปี สูตรปกติคือล้างข้อมูล ใช้เวลาทำ feature engineering ด้วยมือมาก เทรนโมเดลคลาสสิก โดยเฉพาะตระกูล gradient boosted trees ปรับ hyperparameter แล้วเริ่มงานพื้นฐานเดิมซ้ำกับชุดข้อมูลถัดไป เขาเทียบกับงานข้อความในอดีต ที่ต้องมีโมเดลหนึ่งตัวสำหรับ sentiment อีกตัวสำหรับจำแนก spam และอีกตัวสำหรับแปลภาษา จนเมื่อ GPT-3 ออก ก็ไม่ต้องเทรนแยกอีก แค่ให้ foundation model ดูตัวอย่างไม่กี่ตัวใน prompt มันก็เข้าใจเองได้ ส่วนตารางไม่เคยมีช่วงเวลานั้นจนกระทั่งตอนนี้

2. TabFM คืออะไร และฝึกอย่างไร (~1:50–3:17)

Google Research เพิ่งปล่อย TabFM ซึ่งเป็น foundation model ที่สร้างมาเพื่อข้อมูลตารางโดยเฉพาะ ส่วนที่ผู้พูดว่าบ้าที่สุดคือไม่ต้องเทรนโมเดลบนชุดข้อมูลของเราเอง ไอเดียคือส่งแถวที่รู้ label แล้วแนบแถวที่ยังไม่มี label ซึ่งอยากให้ทำนาย โมเดลใช้ข้อมูลที่มี label อนุมานคำตอบของแถวที่ไม่มี label ในรอบเดียว ชุดข้อมูลของเราจึง "เป็น prompt" ไปเลย ผลคือเป็น foundation model ทั่วไปสำหรับข้อมูลตาราง

Google ทำอย่างไร ทีมวิจัยฝึกมันทั้งหมดจากกระแสข้อมูลสังเคราะห์ที่ไม่มีวันหมด ซึ่งก็คือตารางสังเคราะห์ ในแต่ละตารางจะสุ่ม causal graph หนึ่งอัน สร้างแถวจากมัน แล้วบังคับให้โมเดลทำนายเซลล์ที่ซ่อนไว้ (held-out) ผู้พูดว่าความงามของวิธีนี้คือโมเดลไม่สามารถจำชุดข้อมูลเฉพาะชุดไหนได้ มันเรียนรู้ meta algorithm ว่าจะเรียนรู้จากตารางอย่างไร ข้อมูลตารางเป็นส่วนสำคัญของทุกองค์กร ผู้พูดบอกว่านี่คือเหตุผลที่อยากทำวิดีโอนี้

เขาเตือนไว้ล่วงหน้าว่า weights ของ TabFM ตอนนี้ใช้ได้เฉพาะงานวิจัยที่ไม่ใช่เชิงพาณิชย์ จึงให้มองเป็นแบบแผนทางสถาปัตยกรรม (architectural blueprint) มากกว่าโค้ดพร้อมใช้ที่หยิบไปใส่ production ได้

เสริมจากผู้จัดทำ

ข้อมูลเสริมจาก blog ของ Google (ไม่ได้พูดในคลิป): สถาปัตยกรรมผสมแนวคิดของ TabPFN กับ TabICL คือสลับ attention ระหว่างแถวกับคอลัมน์เพื่อสร้าง representation, บีบแต่ละแถวให้เป็นเวกเตอร์หนาแน่นหนึ่งอัน (row compression), แล้วใช้ Transformer ทำ in-context learning บนเวกเตอร์ของแถวเหล่านั้น paper ระบุว่าขนาดโมเดลราว 400M พารามิเตอร์ (รุ่น 1.0.x ราว 1.64 พันล้าน) ส่วนในคลิปคำว่า "single pass" ตรงกับคำของ blog ที่ว่า "single forward pass"

3. สถาปัตยกรรมที่ผู้พูดใช้: ข้อมูลใน Postgres, โมเดลรันที่เครื่อง (~3:17–3:57)

ผู้พูดบอกว่า foundation model เป็นเพียงครึ่งหนึ่งของเรื่อง อีกครึ่งคือที่ที่ข้อมูลสดอยู่ และเราต้องให้ agent มีสภาพแวดล้อมที่ทำงานกับข้อมูลได้จริง จุดนี้เป็นช่วงของสปอนเซอร์ Neon (ผู้จัดทำตัดข้อความโฆษณาออก) สิ่งที่เป็นสาระคือรูปแบบการวางระบบของเขา: ข้อมูลอยู่ใน Postgres บน Neon, TabFM รันในเครื่องบน DGX Spark ของเขาเอง, และ agent ถูกให้ไปรันงานบน database engine โดยตรง

เสริมจากผู้จัดทำ

ส่วนนี้ผู้จัดทำตั้งใจย่อ เพราะประโยคส่วนใหญ่เป็นการแนะนำสินค้าของสปอนเซอร์ ที่เกี่ยวกับสถาปัตยกรรมจริง ๆ มีเพียงสามจุดที่สรุปไว้ข้างต้น รายละเอียดว่า branch และการย้อนเวลาช่วยอย่างไรอยู่ในหัวข้อ 7

4. ตัวอย่าง: ทำนาย churn โดยไม่ต้องเทรน (~3:57–4:58)

ข้อมูลที่ใช้เป็น SaaS สังเคราะห์ซึ่งผู้พูดสร้างเอง มีโปรไฟล์ลูกค้า การใช้ผลิตภัณฑ์ ใบแจ้งหนี้ และ ticket สนับสนุน เป้าหมายคือทำนายว่าลูกค้ารายไหนจะ churn ขั้นตอนคือดึงตารางลูกค้าดิบจาก Neon ป้อนประวัติ label ให้ TabFM (ผู้พูดบอกว่าจะแสดงวิธีทำภายหลังในคลิป) แล้วขอให้ให้คะแนนผู้ใช้ที่เหลือ ไม่มีการเทรนเลย โมเดลให้คะแนน churn ที่อนุมานได้ของลูกค้าทุกราย แล้วเขียนกลับตาราง Postgres

ส่วนที่ผู้พูดเรียกว่า "ดีที่สุด" คือเมื่อไม่ทำ feature engineering เลยและใช้ตารางเดียว มันก็ชนะ tree-based model ที่ปรับจูนแล้วซึ่งเขาเทรนไว้

แล้วผู้พูดก็บอกว่าคะแนนคือ 0.60 ซึ่ง "ไม่ดีนัก" และตัวเลขนี้เผยหนึ่งในปัญหาใหญ่ที่สุดของ TabFM ซึ่งเป็นหัวข้อถัดไป

เสริมจากผู้จัดทำ

ข้อควรตีความ: AUC 0.60 ห่างจากการเดาสุ่มเพียง 0.10 และข้อมูลเป็นของสังเคราะห์ที่ผู้พูดสร้างเอง จึงบอกได้แค่ว่าในตัวอย่างนี้ TabFM ดีกว่า tree ที่เขาจูนไว้ ไม่ได้บอกว่าทั่วไปจะดีกว่า paper ของ Google ซึ่งทดสอบบน 51 ชุดข้อมูลของ TabArena เป็นหลักฐานที่ใหญ่กว่าบนหัวข้อนั้น

5. จุดบอด: TabFM ไม่เข้าใจความหมายของคอลัมน์ (~4:58–6:00)

ผู้พูดอธิบายว่า TabFM ฝึกจาก causal graph ที่สร้างขึ้นเองล้วน ๆ นั่นแปลว่ามันไม่เคยเห็นหัวคอลัมน์หรือชื่อ label เลยในระหว่างการฝึก มันจึงแยกไม่ออกด้วยซ้ำว่าคอลัมน์หนึ่งคือยอดใช้จ่ายรายเดือน ส่วนอีกคอลัมน์เป็นอุณหภูมิ มันมองทุกอย่างเป็นตัวเลข

แต่ตารางจริงมีความหมายซ่อนอยู่ เช่น คอลัมน์ที่ใช้เลข 1 2 3 เป็นรหัสของเหตุการณ์ต่าง ๆ หรือ 0 อาจแปลว่า "ไม่ได้วัด" และค่าที่ขาดอาจถูกแทนด้วยรหัสพิเศษ TabFM นำช่องว่างทางความหมายเหล่านี้มาพิจารณาไม่ได้ ผู้พูดจึงสรุปว่านี่คือจุดที่ LLM เข้ามาอยู่ใน loop เพราะการเข้าใจบริบทเชิงความหมายเป็นสิ่งที่ LLM ทำได้ดีที่สุด

เสริมจากผู้จัดทำ

ผู้จัดทำสังเกตว่าข้อสรุป "ไม่เห็นชื่อคอลัมน์" เป็นคำอธิบายของผู้พูด ผลตรวจของเราสอดคล้องกับภาพรวมใน paper แต่ไม่ได้ยืนยันประโยคนี้ทีละบรรทัด (ดูตารางตรวจข้อเท็จจริง)

6. TabFM-Auto: LLM agent ครอบโมเดลที่ตรึงไว้ (~6:00–6:58)

นักวิจัยจับคู่โมเดลภาษาขนาดใหญ่เข้ากับสถาปัตยกรรมใหม่ที่ผู้พูดอ่านว่า "TabFusion Auto" (ในที่นี้ผู้จัดทำแปลว่า TabFM-Auto เพราะ ASR ฟังเพี้ยน และ paper ใช้ชื่อนี้) แนวคิดคือตรึง (frozen) TabFM ไว้เป็นเครื่องอนุมาน แล้วให้โมเดลภาษาที่ขับ agent ดูแลทั้ง pipeline: agent ตรวจชื่อคอลัมน์ เขียนตรรกะแปลงข้อมูล อาจเลือกแถว context และปรับเทียบ (calibrate) ผลทำนาย ผู้วิจัยแสดงว่าชุดนี้ขึ้นอันดับสูงสุดใน TabArena ได้

โค้ดของ TabFM-Auto ยังไม่เปิดสาธารณะ ผู้พูดจึงใช้ Opus 5.5 สร้างการ implement ของเขาเอง โดยใช้ Gemini เป็น orchestrator

เสริมจากผู้จัดทำ

จาก paper: TabFM-Auto วนปรับ pipeline ด้วย LLM agent ที่ใช้ metadata ของ dataset และผลตรวจกับ validation ห้าการตั้งค่าของมันได้ห้าอันดับแรกบน TabArena (51 ชุดข้อมูล) Elo ที่ดีที่สุดเพิ่มจาก 1785 เป็น 2013 และบน 8 การแข่งขันตารางใน MLE-Bench มันได้อันดับหนึ่งในกลุ่ม MLE agent ตัวเลขเหล่านี้เป็นข้อมูลเสริม ไม่ได้อยู่ในคลิป

7. ฐานข้อมูลที่ agent ต้องการ: ความหมาย, sandbox, และกัน leakage (~6:58–8:52)

ผู้พูดมองว่าถ้าจะใช้แบบนี้ ต้องเข้าใจก่อนว่าต้องมีสถาปัตยกรรมฐานข้อมูลที่แข็งแรงรองรับโมเดลอย่าง TabFM-Auto โดยมีสามข้อ

ข้อแรก semantic grounding agent ต้องรู้ความหมายของข้อมูล ใน Postgres เก็บ data dictionary เป็น comment ของคอลัมน์ได้ agent จึงใช้ schema ร่วมกับ comment ที่ฝังไว้เพื่อตัดสินใจว่าจะเขียนโค้ดแบบไหน

ข้อสอง sandbox ปล่อยให้ LLM อัตโนมัติแก้ข้อมูล production ไม่ได้ ทุกการทดลอง agent จึงเปิด branch ของ Neon ที่แยกต่างหาก ซึ่งเป็นสำเนาฐานข้อมูลแบบ copy-on-write ที่พร้อมใช้ในราวหนึ่งวินาที ภายในนั้น agent สร้างตาราง feature ทดสอบ join ทิ้งคอลัมน์ และเก็บผลของรอบนั้น ถ้าพังก็ลบ branch ทิ้ง และ production ก็ไม่ถูกแตะต้องเลย

ข้อสาม ป้องกัน data leakage ซึ่งผู้พูดว่าสำคัญที่สุด ในชุดข้อมูลของเขามีคอลัมน์ที่เกี่ยวกับ retention ซึ่งจะถูกเติมเฉพาะหลังลูกค้าเริ่มขอยกเลิก คอลัมน์นี้ดูเหมือน "กระสุนเงิน" สำหรับ agent ใด ๆ ที่มองสแนปช็อตของฐานข้อมูลวันนี้ แต่มันไม่ใช่ feature ที่มีให้ใช้ได้จริง เพราะมันแสดงผลลัพธ์ในอดีต agent จึงไม่ควรใช้ ในความเป็นจริง ในครึ่งหนึ่งของรอบทดสอบ agent เห็นความสัมพันธ์ แล้วเพิกเฉยความเสี่ยงด้านเวลาโดยสิ้นเชิง และฝังมันไว้ใน pipeline

วิธีแก้ของผู้พูดคือให้ agent เทรนบน branch ที่แยกไว้และคืนค่าไปยังเวลาก่อนช่วงทำนายพอดี ในการทดสอบ เมื่อเทียบทั้งสองโมเดลกับสิ่งที่ลูกค้า churn จริงในเดือนถัดไป โมเดลที่ดูสมบูรณ์แบบกลับเป็นโมเดลที่แย่ที่สุด เพราะใช้คอลัมน์ที่รั่ว ส่วนโมเดลที่ไม่มีคอลัมน์รั่วทำได้ดี

เสริมจากผู้จัดทำ

ผู้จัดทำเสริมว่า ชื่อคอลัมน์ในรูปคือ retention_offer_sent ส่วนสไลด์ "honest data" (ผลลัพธ์ที่ได้จากการย้อนเวลา) บอกเพียงว่า agent ฝึกจาก branch snap-sep30 ตัวเลขวันที่บนเส้นเวลาคือ 30 ก.ย. และ 31 ต.ค. ซึ่งเป็นตัวอย่างของผู้พูด ไม่ใช่ข้อกำหนด

8. ขึ้น production: pipeline รายคืน (~8:52–9:49)

ผู้พูดบอกว่าระบบจริงไม่ใช่การทำนายครั้งเดียว ตัวอย่างเช่นถ้าเปิดธุรกิจจริงและอยากรู้ว่าลูกค้ากลุ่มไหนอาจ churn ก็บันทึก pipeline ที่ agent สร้างไว้ในฐานข้อมูล แล้วให้ Neon function รันตามตาราง ในกรณีของเขาทุกคืนมันสร้าง feature จาก Postgres โดยตรง เข้าคิวงานที่ DGX Spark มารับ เขียนคะแนนของลูกค้าทุกรายกลับฐานข้อมูล แล้วรายการลูกค้าเสี่ยงไปอยู่ใน object storage ข้าง ๆ

เพื่อทดลอง เขาเลื่อนนาฬิกาไปข้างหน้าหนึ่งเดือน โหลดสิ่งที่เกิดขึ้นจริง แล้วสร้างรายการ ลูกค้าส่วนใหญ่ที่อยู่อันดับบนของรายการ ขอยกเลิกจริง ซึ่งผู้พูดว่าแสดงพลังของ TabFM โดยเฉพาะเมื่อห่อมันไว้ใน agentic loop

เสริมจากผู้จัดทำ

"ส่วนใหญ่" เป็นคำของผู้พูด ไม่มีตัวเลขสัดส่วนในคลิป (ฉากนี้บนสไลด์คือเลื่อนนาฬิกาในโปรแกรมจำลอง ผู้พูดไม่ได้บอก recall หรือ precision)

9. ข้อสรุปของผู้พูด และข้อควรระวัง (~9:49–10:57)

ผู้พูดสรุปสามข้อ ข้อแรก สำหรับการทำนายบนตาราง โมเดลไม่ต้องเทรนบนข้อมูลของเราอีกต่อไป ข้อมูลของเราเป็น prompt ได้เลย ข้อสอง LLM ยังมีประโยชน์มากในที่นี้ แต่ไม่ใช่แค่ในฐานะตัวทำนาย มันมีประโยชน์อย่างยิ่งกับส่วนที่อ่านชื่อคอลัมน์และนำความรู้เฉพาะโดเมนเข้ามา ข้อสาม ถ้าจะให้ agent ทำ data science ต้องมี back end จริงให้มันทำงาน โดยเฉพาะ branch ของตัวเองต่อการทดลองทุกครั้ง ความหมายของทุกคอลัมน์ไว้ข้างข้อมูล และวิธีมองข้อมูลตามที่มันเป็นในช่วงเวลาที่การทำนายจะเกิดขึ้น เขาใช้ Neon เป็น back end ของทั้งหมด (ส่วนโฆษณาที่เหลือถูกตัดออก) และจะใส่ลิงก์ paper กับ GitHub ไว้ ผู้พูดย้ำอีกครั้งว่าสิทธิ์ใช้งานเป็นแบบไม่ใช่เชิงพาณิชย์ แต่ให้มองเป็นแบบแผนที่นำไปต่อยอดได้

ข้อที่ควรเข้าใจให้ตรง

ข้อที่ควรเข้าใจให้ตรง: ชื่อ "TabFusion" ที่ได้ยินในเสียงบรรยายเป็นการฟังเพี้ยนของ ASR ชื่อจริงคือ TabFM และ TabFM-Auto, "causal tag" ในช่วง 2:38 คือ causal graph และ "customers had treated" ในช่วง 8:37 น่าจะเป็น "customers had churned" ตามบริบท (การซ่อมคำ ASR โดยผู้จัดทำ ไม่ได้แก้ไฟล์ transcript)

Key Takeaways

1.TabFM ใช้ชุดข้อมูลของเราเป็น prompt ได้: ป้อนแถวที่มี label กับแถวที่ต้องการทำนาย แล้วได้ผลในรอบเดียว ไม่ต้องเทรนบนข้อมูลของเรา
2.มันฝึกจากตารางสังเคราะห์ล้วน จึงเรียนรู้วิธีเรียนรู้จากตาราง แต่ไม่เคยเห็นชื่อคอลัมน์ และต้องมี LLM ช่วยอ่านความหมาย (TabFM-Auto)
3.ตัวอย่าง AUC 0.60 ของผู้พูดมาจากข้อมูลสังเคราะห์ของเขาเอง ใช้เป็นภาพประกอบ ไม่ใช่หลักฐานว่าดีกว่า tree เสมอ
4.ถ้าให้ agent ทำ data science ต้องมี sandbox (branch) ความหมายคอลัมน์ข้างข้อมูล และข้อมูลย้อนเวลา เพื่อกัน data leakage ที่ทำให้โมเดลดูดีเกินจริง
5.weights อยู่ภายใต้ license ที่ไม่ใช่เชิงพาณิชย์ ต้องตรวจก่อนนำไปใช้ในงานจริง
