บทสรุปย่อ

คลิปแนะนำ TabFM โมเดลพื้นฐาน (foundation model) สำหรับข้อมูลตารางจาก Google Research เริ่มจากทำไมข้อมูลตารางทำงานด้วยยาก (ชนิดข้อมูลผสม ต้อง preprocess ต้องจูน hyperparameter ข้อมูลไม่สมดุล) แล้วเปิดดูโครงสร้างโมเดลทีละส่วน อธิบาย in-context learning (ICL) และทดลองกับชุดข้อมูล Adult Income โดยใช้ตัวอย่างฝึกเพียง 50 ถึง 500 แถว ผู้พูดชอบผลที่ได้แต่ติงเรื่องเวลาที่ใช้ ผู้จัดทำตรวจแล้วพบว่าคลิปคลาดเคลื่อนสองข้อ (แหล่งข้อมูลฝึก และความหมายของ context) ส่วนตัวเลข 1.64 พันล้านพารามิเตอร์ถูกต้องสำหรับ weights รุ่น 1.0.x แต่รุ่น 1.1.0 ปัจจุบันและ paper เป็น 400M ดูตารางตรวจข้อเท็จจริง

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึก (license มาตรฐานของ YouTube; transcript เป็น ASR ภาษาอังกฤษ)

สรุปเชิงลึก

ข้อโต้แย้งของคลิป foundation model ส่วนใหญ่ถูกสร้างสำหรับข้อมูลไร้โครงสร้าง (ภาพ ข้อความ เสียง วิดีโอ) เพราะเก็บข้อมูลที่ไม่มี label ปริมาณมหาศาลมา pre-train ได้ง่าย ส่วนข้อมูลตาราง (แถวคือตัวอย่าง คอลัมน์คือ feature) ทำงานด้วยลำบาก: ชนิดข้อมูลปนกัน เช่น ตัวเลขกับหมวดหมู่ (ในชุด Adult Income คอลัมน์ occupation กับ marital status ไม่ใช่ตัวเลข) ต้องตัดสินใจเรื่อง encoding และ scaling ต้องตั้ง hyperparameter ของโมเดลที่เลือก และยังมีความไม่สมดุลของ class (ราว 76% ต่ำกว่า 50,000 ดอลลาร์ และราว 24% สูงกว่า) TabFM ช่วยให้ "ใส่ตารางตรง ๆ แล้วได้คำทำนาย"

โครงสร้างตามที่ผู้พูดอ่านจากโมเดลที่พิมพ์ออกมา (1) cell embedder แปลงทุกค่าในตาราง ทั้งตัวเลข หมวดหมู่ และ label ให้เป็นเวกเตอร์ 256 มิติ (2) column embedder ใช้ attention เพราะสลับลำดับคอลัมน์แล้วปัญหาต้องไม่เปลี่ยน ผู้พูดเข้าใจว่ามันพยายามหาว่าเวกเตอร์ของแต่ละเซลล์ "หมายถึงอะไร" (3) มี RMSNorm ตามแบบ Transformer ทั่วไป (4) ส่วนท้ายคือ MLP ที่กำหนดจำนวน class ตายตัวไว้ที่ 10 จึงแก้ปัญหา classification ได้สูงสุด 10 class ผู้พูดมองว่านี่เป็นข้อจำกัดใหญ่ แผนภาพจาก blog ของ Google สรุปไว้ว่า สลับ attention ระหว่างแถวกับคอลัมน์ บีบแต่ละแถวเป็น row embedding แล้วทำนาย label ที่หายไปของแถวทดสอบ

ICL แทนที่จะปรับพารามิเตอร์ด้วย loss function แบบเดิม TabFM ปล่อยพารามิเตอร์ไว้เฉย ๆ และใช้ข้อมูลที่มี label เป็น "context หรือตัวอย่างสาธิต" เพื่อทำนายแถวใหม่ ผู้พูดอธิบายว่ามีประโยชน์เมื่อมีตัวอย่างน้อย และเมื่อโมเดลมีพารามิเตอร์มหาศาลซึ่งปรับยาก

การทดลอง ใช้ Adult Income (ผู้พูดว่าราว 50,000 แถว ตั้งใจใช้ตัวอย่างฝึกเพียง 50, 100, 200, 500 แถวเพื่อ "stress test") วัด accuracy, precision, recall, F1 เพราะข้อมูลไม่สมดุล ตัวเลขบนสไลด์ของ 500 ตัวอย่างคือ accuracy 0.837, precision 0.686, recall 0.593, F1 0.636 ส่วน 50 ตัวอย่างได้ accuracy 0.780 และ F1 0.413 ผู้พูดบอกว่าไม่ต้องทำ feature processing, scaling หรือ hyperparameter tuning เลย ข้อเสียที่เขาเห็นคือความซับซ้อนในการคำนวณ บน GPU A100 ใช้เวลา 293.65 วินาทีกับ 50 ตัวอย่าง และ 681.63 วินาทีกับ 500 ตัวอย่าง

สิ่งที่คลิปคลาดเคลื่อนหรือไม่ได้บอก (ผลตรวจของเรา) (1) ตัวเลข "1.64 พันล้านพารามิเตอร์" ในคลิปไม่ผิด ถ้าอ้างถึง weights รุ่น 1.0.x (ไฟล์ classification ใน Hugging Face ขนาด 6.56 GB ซึ่งที่ 4 ไบต์ต่อค่าเท่ากับราว 1.64 พันล้านค่า) แต่ paper ของ Google (กันยายน 2026) และรุ่น 1.1.0 ปัจจุบัน (ไฟล์ 821 MB) เป็น 400M จึงต้องระบุรุ่นทุกครั้งที่อ้างตัวเลข (2) คลิปว่า Google ยังไม่เปิดเผยวิธีสร้างข้อมูลฝึกที่มี label แต่ blog บอกว่าใช้ชุดข้อมูลสังเคราะห์จาก structural causal model (3) context ของ ICL คือแถวที่ผู้ใช้ป้อนเข้าไป ไม่ใช่ข้อมูล pre-training ทั้งหมด (4) ตัวเลข 293 ถึง 682 วินาทีเป็นเวลา fit และทำนาย ไม่มีการเทรนแบบปรับพารามิเตอร์ และคลิปไม่บอกจำนวนแถวทดสอบ (5) ความแม่นยำ "สูงกว่า 80%" ต้องดูบริบทเพราะ class ใหญ่คิดเป็นราว 76% ของข้อมูล การเดาว่าทุกแถวเป็น class ใหญ่ก็ได้ประมาณนั้นแล้ว

ใช้คลิปนี้อย่างไร (ข้อเสนอของผู้จัดทำ) เหมาะเป็นบทนำแนวคิดของ tabular foundation model และการอ่านชั้นของโมเดล แต่ตัวเลขขนาดโมเดลต้องระบุรุ่นของ weights และแหล่งข้อมูลฝึกต้องใช้ตามแหล่งทางการ

เสริมจากผู้จัดทำ

ตารางนี้ผู้จัดทำจัดจากเนื้อหาในคลิปเพื่อให้เห็นภาพเทียบ ผู้พูดไม่ได้วัดโมเดลแบบเดิมเทียบกับ TabFM ในคลิปนี้ จึงไม่มีตัวเลขเปรียบเทียบคะแนน

ข้อสรุปตามสถานการณ์ (ผู้จัดทำ) ถ้าต้องการลองใช้กับตารางที่มีตัวอย่างน้อยโดยไม่อยากเตรียมข้อมูลมาก TabFM น่าลอง (เกณฑ์: จำนวนแถว จำนวน class ต้องไม่เกิน 10 และเวลาที่ยอมรับได้) ถ้ามี class มากกว่า 10 หรือเวลาเป็นเรื่องสำคัญ ยังต้องใช้วิธีเดิม

  6. 6. In-context learning เทียบกับ supervised learning แบบเดิม (~9:59–12:16)
  7. 7. ทดลองกับ Adult Income ด้วยตัวอย่างฝึกน้อยมาก (~12:16–14:05)
  8. 8. ข้อเสีย: ค่าคำนวณ (~14:05–15:37)

1. TabFM คืออะไร และทำไมโมเดลพื้นฐานส่วนใหญ่ยังเป็นเรื่องข้อมูลไร้โครงสร้าง (~0:00–1:04)

ผู้พูดเริ่มด้วยความตื่นเต้นกับโมเดลพื้นฐานใหม่ที่ Google Research เพิ่งปล่อยในชื่อ TabFM ซึ่งย่อมาจาก tabular foundation model เขาชี้ว่าโมเดลพื้นฐานจนถึงตอนนี้ส่วนใหญ่ทำมาสำหรับข้อมูลไร้โครงสร้าง ได้แก่ ภาพ ข้อความ เสียง และวิดีโอ เหตุผลหลักคือเก็บข้อมูลที่ไม่มี label ปริมาณมหาศาลได้ค่อนข้างง่าย แล้วนำมา pre-train โมเดลขนาดใหญ่

จากนั้นเขาเปลี่ยนเข้าหัวข้อของคลิป คือโมเดลพื้นฐานสำหรับข้อมูลตาราง ซึ่งเขาให้นิยามว่าเป็นตารางสองมิติหรือเมทริกซ์ที่มีแถวและคอลัมน์ แถวคือตัวอย่าง (sample, example หรือ observation) ส่วนคอลัมน์คือ feature หรือ attribute

2. ทำไมข้อมูลตารางจึงยาก (~1:04–3:59)

ผู้พูดบอกว่าปัญหาแรกคือต้องจัดการกับข้อมูลหลายชนิดปนกัน (heterogeneous) ทั้งตัวแปรต่อเนื่องและหมวดหมู่ ดังที่เห็นในชุดข้อมูลจริง Adult Income ที่เป้าหมายคือทำนายว่ารายได้ต่อปีของคนหนึ่งเกิน 50,000 ดอลลาร์หรือไม่ เป็นปัญหา binary classification แบบง่าย แต่ใช้งานยาก เพราะบางคอลัมน์เช่น occupation หรือ marital status ไม่ใช่ตัวเลข จึงใส่ตรง ๆ ให้ decision tree หรือ neural network ไม่ได้ ต้อง preprocess และ scale ก่อน และต้องตัดสินใจหลายอย่าง เช่น จะใช้คอลัมน์ occupation หรือไม่ จะ encode แบบ one-hot หรือแบบอื่น

ปัญหาที่สองมาหลังเลือกโมเดล ต้องตั้ง hyperparameter ถ้าใช้ decision tree ก็ต้องตั้ง max depth ถ้าใช้ random forest ก็ต้องตัดสินจำนวนต้นไม้ ถ้าใช้ neural network ก็ต้องเลือก learning rate และ batch size สรุปคือการทำงานกับตารางลำบากเพราะต้องเตรียมข้อมูลและจูน hyperparameter อย่างหนัก

ปัญหาที่สามคือ class imbalance ในชุดนี้ราว 76% ของกรณีต่ำกว่า 50,000 ดอลลาร์ และมีเพียงราว 24% ที่สูงกว่า จึงต้องเลือกวิธีจัดการ ผู้พูดว่านี่คือเหตุผลที่ TabFM มีประโยชน์ เพราะให้เราใส่ตารางที่เห็นเข้าไปตรง ๆ แล้วได้คำทำนาย

เสริมจากผู้จัดทำ

ผู้จัดทำเพิ่มว่า UCI ระบุว่าชุด Adult มี 48,842 แถวและ 14 feature (ผู้พูดบอกว่า "ราว 50,000" ในภายหลัง) ส่วนสัดส่วน 76% กับ 24% เป็นตัวเลขที่ผู้พูดบอก หน้า UCI ไม่ได้ให้ตัวเลขนี้

3. ขนาดโมเดลและข้อมูลฝึก ตามที่ผู้พูดสืบค้น (~3:59–5:40)

ผู้พูดบอกว่าเขาค้นคว้าเกี่ยวกับโมเดลนี้เพื่อให้ข้อมูลที่ใช้เริ่มต้นได้ ข้อแรกคือโมเดลมีราว 1.64 พันล้านพารามิเตอร์ ซึ่งเขาว่าเป็นสิ่งที่คาดอยู่แล้ว เพราะโมเดลพื้นฐานถูกฝึกจากข้อมูลที่ไม่มี label ปริมาณมหาศาล จึงต้องมีพารามิเตอร์มาก และเป็นเรื่องปกติที่จะมีหลายล้านถึงหลายพันล้านพารามิเตอร์

ข้อที่สองคือโมเดลต้องแก้ปัญหา supervised learning (ในที่นี้คือ classification) ผู้พูดบอกว่า "ดูเหมือน" ว่าคนที่ Google Research สร้างข้อมูลที่มี label ปริมาณมหาศาลขึ้นมา ซึ่งต่างจากการ pre-train LLM ทั่วไปเพราะต้องมี label และเขาบอกว่าวิธีที่ทำให้ข้อมูลที่ไม่มี label มี label ยังไม่ถูกเปิดเผย ณ ตอนนั้น

เสริมจากผู้จัดทำ

ผลตรวจของเรา (ไม่ใช่คำของผู้พูด): ตัวเลข 1.64 พันล้านตรงกับ weights รุ่น 1.0.x ซึ่งไฟล์ classification ใน Hugging Face มีขนาด 6.56 GB (4 ไบต์ต่อค่า) ส่วน paper (กันยายน 2026) และรุ่น 1.1.0 ปัจจุบัน (ไฟล์ 821 MB) เป็น 400M จึงควรระบุรุ่นทุกครั้ง

ข้อที่ควรเข้าใจให้ตรง

ข้อที่ควรเข้าใจให้ตรง: เรื่องที่ผู้พูดว่ายังไม่เปิดเผยแหล่งข้อมูลฝึกที่มี label blog ของ Google (30 มิถุนายน 2026 ก่อนคลิป) ระบุว่าฝึกด้วยชุดข้อมูลสังเคราะห์จาก structural causal model ไม่ใช่ข้อมูลจริงที่ติด label ทีหลัง

4. โครงสร้างโมเดลทีละส่วน (~5:40–8:55)

ผู้พูดแสดงโครงสร้างของ TabFM classifier (บอกว่ามี regressor ด้วย แต่เมื่อเข้าใจตัวหนึ่งอีกตัวจะง่ายขึ้น) โดยชี้ว่ามีกลเม็ดหลายอย่าง อย่างแรกคือ cell embedder ซึ่งมีสองส่วน ส่วนหนึ่งสำหรับค่าตัวเลข อีกส่วนสำหรับค่าหมวดหมู่ และน่าสนใจที่มี embedding ของ label ด้วย ทุกอย่างถูกแปลงเป็นเวกเตอร์ 256 มิติ ทำให้รองรับตารางได้ทุกแบบไม่ว่ามี feature ตัวเลขหรือหมวดหมู่

อย่างที่สองคือ column embedder เหตุผลง่าย ๆ คือถ้าสลับลำดับคอลัมน์ของตาราง ปัญหาต้องไม่เปลี่ยน จึงต้องใช้ attention ใน Transformer ที่เข้าใจความสัมพันธ์ระหว่างคอลัมน์และระหว่างแถว ผู้พูดบอกว่า "ความเข้าใจของผม" คือส่วนนี้พยายามหาว่าเวกเตอร์ 256 มิติของแต่ละเซลล์แทนอะไรและหมายถึงอะไร เช่น บางคอลัมน์คืออาชีพ บางคอลัมน์คือจำนวนปีการศึกษา หรืออาจเป็นจำนวนบัตรเครดิต จึงสำคัญที่ต้องเข้าใจบริบทของแต่ละคอลัมน์

ถัดไปมีชั้น normalization คือ RMSNorm ซึ่งพบได้บ่อยใน Transformer อีกส่วนที่ผู้พูดว่าน่าสนใจมากคือปลายโมเดล ปกติเราใช้ multi-layer perceptron (MLP) เพื่อหา logit แล้วเลือก class ที่ความน่าจะเป็นสูงสุด แต่ที่นี่จำนวน class ถูกกำหนดตายตัวไว้ในโค้ด ผู้พูดอธิบายว่าหลังส่วน Transformer ได้การแทนค่าขนาดหนึ่ง แล้วขยายเป็นสองเท่า แล้วลงเหลือ 10 (ในสไลด์คือ 2048 เป็น 4096 เป็น 10) เลข 10 คือจำนวน class สูงสุด ถ้ามีสอง class ไม่มีปัญหา แต่มากกว่า 10 ไม่ได้ ผู้พูดมองว่านี่เป็นข้อจำกัดใหญ่ในตอนนี้ เพราะค่านี้ถูก hardcode ไว้ในโค้ด

ข้อที่ควรเข้าใจให้ตรง

ASR ได้ยินตัวเลขเพี้ยน ("48 ... 496") ผู้จัดทำแปลตามตัวเลขที่เห็นบนสไลด์ (2048 เป็น 4096 เป็น 10) ตามที่ผู้พูดอธิบายเรื่อง "สองเท่า"

5. ภาพรวมจาก blog: แถว คอลัมน์ และ row compression (~8:55–9:59)

ผู้พูดบอกว่าครอบคลุมส่วนสำคัญของสถาปัตยกรรมแล้ว และ blog ที่ Google Research ปล่อยก็มีภาพอธิบายที่ดี ด้านซ้ายคือตารางต้นฉบับซึ่งง่ายกว่าชุด Adult Income ที่เขาแสดง จากนั้นหลังทำ cell embedding เป้าหมายคือหาปฏิสัมพันธ์ระหว่างแถวกับคอลัมน์ โดยสลับกันไปมา เพื่อให้แน่ใจว่ารองรับความจริงที่ว่าสิ่งเหล่านี้สลับลำดับได้ (permutable) และเมื่อได้ row compression แล้ว จะทำนาย label ของข้อมูลทดสอบหรือชุด held-out

เสริมจากผู้จัดทำ

ผู้จัดทำเสริมจาก blog: row compression คือบีบแต่ละแถวให้เป็นเวกเตอร์หนาแน่นหนึ่งอัน แล้ว Transformer ทำ in-context learning บนเวกเตอร์ของแถวเหล่านี้ (ผู้จัดทำคาดว่าช่วยลดต้นทุนเมื่อมี feature มาก แต่ blog ไม่ได้ระบุเรื่องนี้ และคำอธิบายทั้งกล่องไม่ได้อยู่ในคำพูดของผู้พูด)

6. In-context learning เทียบกับ supervised learning แบบเดิม (~9:59–12:16)

ผู้พูดอธิบายส่วนสุดท้ายของ TabFM ว่าแทนที่จะใช้ supervised learning แบบดั้งเดิม มันใช้ in-context learning (ICL) แบบเดิมคือเรามีโมเดล pre-train และมีข้อมูลใหม่ (x ตัวเข้า, y ผลลัพธ์ที่สัมพันธ์กัน) เรากำหนด loss function วัดความต่างระหว่างคำทำนายกับผลลัพธ์จริง แล้วปรับพารามิเตอร์ให้เข้ากับข้อมูลที่มี label นี้ ส่วนแนวคิด in-context learning ใช้ได้ดีเมื่อมีตัวอย่างจำกัด ซึ่งเป็นกรณีของปัญหาจริงหลายอย่างที่ไม่มีข้อมูลมากสำหรับงานปลายทาง โดยอาศัยว่าตอน pre-train โมเดลได้เห็นงานที่เกี่ยวข้องมาแล้วและต้องการปรับมาใช้กับงานใหม่

ส่วน ICL คือเราไม่ปรับพารามิเตอร์ ปล่อยไว้เฉย ๆ ซึ่งช่วยมาก เพราะโมเดลมีราว 1.64 พันล้านพารามิเตอร์ (รุ่น 1.0.x ดูตารางตรวจข้อเท็จจริง) ซึ่งปรับทั้งหมดยากถ้ามีข้อมูลเพียงหลักสิบหรือหลักร้อยแถวสำหรับงานของเรา แทนที่จะปรับ เราใช้สิ่งที่เรียกว่า context ข้อมูลฝึกที่เรามีจึงไม่ใช่เพื่อฝึกแบบเดิม แต่เป็นตัวอย่างสาธิตให้โมเดลเห็นว่านี่คือกรณีของงานใหม่ แล้วให้หาผลลัพธ์ที่ดีที่สุดสำหรับจุดข้อมูลทดสอบ ในภาษาความน่าจะเป็น คือการแก้ปัญหาความน่าจะเป็นแบบมีเงื่อนไข โดยเงื่อนไขคือ context ซึ่งเป็นข้อมูลที่มี label ของงานใหม่

ข้อที่ควรเข้าใจให้ตรง

ข้อที่ควรเข้าใจให้ตรง (ผลตรวจของเรา): ประโยคท้ายของคลิป (หัวข้อ 8) ที่ว่า Transformer ต้องเทียบตัวอย่างสาธิตกับข้อมูล pre-training ทั้งหมด ไม่ตรงกับวิธีทำงาน: context ของ ICL คือแถวที่เราป้อนเข้าไปเท่านั้น

7. ทดลองกับ Adult Income ด้วยตัวอย่างฝึกน้อยมาก (~12:16–14:05)

ผู้พูดนำ TabFM ไปใช้กับชุด Adult Income โดยป้อนตัวอย่างฝึกจำนวนน้อยเท่านั้น (ย้ำว่าเป็นการให้ ICL ไม่ใช่การฝึกเพื่อปรับพารามิเตอร์) แม้ชุดข้อมูลมี "ราว 50,000 แถว" เขาตั้งใจใช้ตัวอย่างน้อยมาก และเพิ่มจาก 50 เป็น 500 เพื่อดูว่าประสิทธิภาพเปลี่ยนอย่างไรเมื่อมีตัวอย่างมากขึ้น เพราะเป็นปัญหา class imbalance เขาจึงดู accuracy, precision, recall และ F1 เพราะต้องสนใจ true positive, true negative, false positive และ false negative เพื่อให้มั่นใจว่าโมเดลคำนึงถึงทั้ง class ที่มีมากและมีน้อย

ข้อที่ควรเข้าใจให้ตรง

ข้อที่ควรเข้าใจให้ตรง: ในคลิปผู้พูดพูดว่า F1 "มากกว่า 60% accuracy" ซึ่งเป็นการพูดพลาด (หมายถึง F1) และตัวเลขทั้งสองข้อ (accuracy เกิน 80% และ F1 เกิน 60%) เป็นจริงพร้อมกันเฉพาะที่ 500 แถว ที่ 50 แถวได้ accuracy 0.780 และ F1 0.413

เสริมจากผู้จัดทำ

ข้อควรตีความ (ผู้จัดทำ): ในชุดนี้ class ใหญ่ราว 76% (ตามที่ผู้พูดบอก) การเดา class ใหญ่ทุกแถวจึงได้ accuracy ราว 0.76 อยู่แล้ว ค่า 0.780 ที่ 50 แถวจึงใกล้เส้นฐานนั้นมาก และเป็นเหตุผลที่ F1 กับ recall บอกเรื่องราวได้มากกว่า recall ที่ 50 แถวคือ 0.322 คือโมเดลพลาด class เล็กมากกว่าครึ่ง ข้อสังเกตนี้ไม่ได้มาจากผู้พูด และคลิปไม่ได้เทียบกับโมเดลเดิม (เช่น tree) ด้วยจำนวนตัวอย่างเท่ากัน

8. ข้อเสีย: ค่าคำนวณ (~14:05–15:37)

ผู้พูดมองว่าข้อเสียหรือข้อจำกัดใหญ่เพียงข้อเดียวคือความซับซ้อนในการคำนวณ เพราะอาศัย Transformer ซึ่ง "รู้กันว่า" แพง ต้องพิจารณา context ขนาดใหญ่เพื่อเทียบตัวอย่างสาธิตกับข้อมูล pre-training ทั้งหมดที่มี เขาเสริมว่าไม่ทราบขนาดและสเกลของข้อมูล pre-training แน่ชัด (ซึ่ง ณ ตอนนี้เป็นความลับ ตามที่เขาว่า) และแม้ใช้ GPU คุณภาพดีอย่าง A100 กรณีมีตัวอย่างฝึก 50 ตัวอย่างใช้เวลาราว 300 วินาทีหรือ 5 นาที และที่ 500 ตัวอย่างราว 680 วินาที ซึ่งเกิน 10 นาที

เขายอมรับว่ามีผู้โต้แย้งได้ว่าไม่เป็นไร เพราะไม่ต้องใช้เวลากับ hyperparameter tuning และ preprocessing อย่างหนัก ซึ่งเขาเห็นว่ามีเหตุผล แต่โดยรวมอยากเห็นการลดความซับซ้อนของ TabFM เพื่อให้ใช้งานได้กว้างขึ้นสำหรับนักวิทยาการข้อมูลและคนที่ทำงาน AI เชิงประยุกต์ ปิดท้ายเขาบอกว่ายินดีทำวิดีโอเดินโค้ดทีละขั้นถ้ามีคนสนใจ

ข้อที่ควรเข้าใจให้ตรง

ข้อที่ควรเข้าใจให้ตรง: ในคลิปใช้คำว่า "เทรน" แต่ TabFM ไม่ปรับพารามิเตอร์ ตัวเลขนี้จึงเป็นเวลา fit กับทำนาย ผู้พูดไม่ได้บอกว่าทำนายกี่แถว ส่วนที่ว่า "ต้องเทียบกับข้อมูล pre-training ทั้งหมด" ไม่ตรงกับวิธีทำงานของ ICL (ดูหัวข้อ 6) แต่ข้อสังเกตว่าค่าคำนวณโตตามจำนวนแถว context สอดคล้องกับหน้า Hugging Face ที่เตือนว่าหน่วยความจำเพิ่มตามจำนวนแถว

Key Takeaways

1.TabFM แก้ความเจ็บปวดของข้อมูลตาราง (encoding, scaling, hyperparameter, imbalance) ด้วยการใส่ตารางตรง ๆ และใช้ ICL แทนการปรับพารามิเตอร์
2.โครงสร้างหลัก: cell embedder (เวกเตอร์ 256 มิติ) กับ attention ระหว่างแถวและคอลัมน์ แล้วบีบแถวเป็น row embedding ปลายทางเป็น MLP ที่รองรับสูงสุด 10 class
3.ผลทดลองบน Adult Income ที่ 50 ถึง 500 แถว: accuracy 0.780 ถึง 0.837, F1 0.413 ถึง 0.636 ผู้พูดไม่ได้เทียบกับโมเดลอื่น
4.ข้อเสียที่ผู้พูดเห็นคือเวลา (293.65 ถึง 681.63 วินาทีบน A100) ข้อจำกัดคือไม่เกิน 10 class
5.คลิปคลาดเคลื่อนสองข้อ: แหล่งข้อมูลฝึก (blog: synthetic SCM) และความหมายของ context ใน ICL ส่วนคำว่า "เทรน" ควรเข้าใจเป็นเวลา fit กับทำนาย และจำนวนพารามิเตอร์ 1.64 พันล้านถูกต้องสำหรับ weights รุ่น 1.0.x (รุ่น 1.1.0 และ paper คือ 400M) ควรระบุรุ่นเสมอ
