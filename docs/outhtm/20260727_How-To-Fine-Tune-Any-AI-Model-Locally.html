บทสรุปย่อ

Tim (Tech With Tim) สอน fine-tune LLM บนเครื่องตัวเองด้วย Unsloth Studio ซึ่งเป็นหน้าเว็บที่ครอบไลบรารี Unsloth ไว้ ช่วงแรกราว 9 นาทีเป็นทฤษฎีสั้น ๆ ได้แก่ fine-tuning คืออะไร, LoRA, QLoRA, ต่างจาก RAG อย่างไร และต้องใช้ฮาร์ดแวร์แค่ไหน ส่วนที่เหลือเป็น demo ครบวงจร: ติดตั้ง, เลือก Llama 3.1 8B Instruct แบบ 4-bit, ทำชุดข้อมูลครูสอนภาษาอินโดนีเซียที่ใช้แต่คำที่ Tim รู้ (ให้ Claude สร้าง และสร้างด้วย Recipe ในตัว Studio), ฝึกแบบ QLoRA, เทียบคำตอบกับ model ตั้งต้น แล้ว export รายงานนี้เพิ่มผลตรวจของผู้จัดทำ: บางตัวเลขในคลิปไม่ตรงกับเอกสาร Unsloth และคำตอบหนึ่งของ model ที่ฝึกแล้วผิด

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ ครบทุกประเด็นและตัวเลข พร้อมตรวจข้อเท็จจริงกับเอกสาร Unsloth และงานวิจัย (license มาตรฐานของ YouTube · ใช้คำบรรยายภาษาอังกฤษที่ทำด้วยคน en-CA)

สรุปเชิงลึก

แนวคิด: แทนที่จะสร้าง LLM เองตั้งแต่ศูนย์ ให้เอา model ที่เก่งภาษาอยู่แล้วมาฝึกต่อด้วยตัวอย่างของเราเอง จนได้ model เฉพาะทาง ส่วนที่ทำให้ทำได้บนการ์ดจอเกมคือ LoRA (สไลด์) ซึ่งแช่แข็ง weight เดิมไว้ทั้งหมด แล้วฝึกแค่ adapter เล็ก ๆ ที่ผู้พูดบอกว่าเล็กกว่า 1% ของ model และ QLoRA ซึ่งเก็บ model เดิมแบบ 4-bit ทำให้ model 8B ราว 16 GB เหลือราว 5–7 GB (สไลด์: VRAM ราว 20 GB เหลือราว 10 GB) ผู้พูดแนะนำ QLoRA เพราะคนส่วนใหญ่ไม่มี GPU ร้อยตัว Fine-tuning กับ RAG: ผู้พูดบอกว่าความเชื่อว่า fine-tuning สอนความรู้ใหม่ไม่ได้เป็นความเข้าใจผิดที่พบบ่อย RAG ดึงข้อมูลสด ๆ ใส่ใน prompt ส่วน fine-tuning เปลี่ยน weight จน model ตอบต่างไปโดยไม่ต้องแก้ prompt ขั้นตอนใน Studio: ติดตั้งด้วยคำสั่งเดียว เปิด localhost:8888 → ไปที่ Hub กรอง "fine-tune ready" แล้วโหลด unsloth/llama-3.1-8b-instruct-unsloth-bnb-4bit (ราว 6 GB) ห้ามใช้ GGUF → เตรียมข้อมูลคอลัมน์ instruction / input (ไม่บังคับ) / output: 300–1,000 แถวเปลี่ยนน้ำเสียงและรูปแบบได้ 5,000 แถวขึ้นไปสอนทักษะจริงได้ → ชุดข้อมูลของ Tim มี 3,000 แถว ให้ Claude สร้างจากคำศัพท์ราว 300 คำที่เขารู้ และ Recipe ในตัว Studio ก็สร้างได้ (seed CSV → สุ่มประเภทงานตามน้ำหนัก → prompt ครู → AI สร้าง input / output) แต่ช้ามากถ้าใช้ model ในเครื่อง → แท็บ Train เลือก QLoRA, จับคู่คอลัมน์ (instruction = system, input = user, output = assistant), เริ่มที่ 1 epoch (มาตรฐานคือ 3 ถ้าข้อมูลเยอะ) และมือใหม่อย่าเพิ่งแตะค่าอื่น → ดู loss ลด ผู้พูดบอกว่าต่ำกว่า 1 มักแปลว่าใช้ได้ อย่างน้อยตามที่ประเมินตัวเองระหว่างฝึก → Compare chat กับ model ตั้งต้น → export เป็น GGUF (Ollama), 16-bit เต็ม หรือ LoRA อย่างเดียว ผลตรวจ (ผู้จัดทำ): ตรวจ 15 ข้อ: ยืนยัน 4 · บางส่วน 9 · ไม่พบ 0 · ขัดแย้ง 2 — ประเด็นที่ควรรู้:

  • Unsloth ไม่ได้สร้างโดยวิศวกร NVIDIA (ผู้พูดบอกว่า "เข้าใจว่า") ผู้สร้างคือพี่น้อง Han แต่ Data Recipes ใช้ NeMo Data Designer ของ NVIDIA
  • ตาราง VRAM ขั้นต่ำของ Unsloth สำหรับ QLoRA ต่ำกว่าในคลิปราว 1.7–2.4 เท่า (8B แบบ QLoRA 6 GB เทียบกับราว 10 GB บนสไลด์) ส่วน LoRA 16-bit กลับสูงกว่าเล็กน้อย (22 GB เทียบกับราว 20 GB)
  • Unsloth เองบอกว่า loss ใกล้ 0 หรือต่ำกว่า 0.2 อาจเป็น overfitting แต่ checkpoint ที่เลือกไว้บนหน้า Export มี loss 0.0582
  • model ที่ฝึกแล้วแปล "alone" เป็น "sama" ซึ่งผิด (ที่ถูกคือ sendiri / sendirian) ส่วนคำตอบของ model ตั้งต้นมี "sendirian" ซึ่งถูก
  • งานวิจัยอิสระพบว่า RAG ใส่ความรู้ใหม่ได้ดีกว่า fine-tuning แบบไม่มีผู้สอน (unsupervised) และการยัดข้อเท็จจริงใหม่ผ่าน fine-tuning เพิ่มการแต่งเรื่อง ซึ่งเอกสาร Unsloth เองก็ใช้คำว่า "mostly" ไม่ใช่ "ทั้งหมด"

เอาไปใช้: เป็นคู่มือเริ่มต้นที่ดีมาก ใช้ได้จริงทั้ง workflow โดยเฉพาะส่วนเตรียมข้อมูลและ Recipe แต่ควรเพิ่มชุดข้อมูลแยกไว้วัดผล (ช่อง Eval Loss บนจอยังว่าง) หยุดก่อน loss ลงไปใกล้ 0 และใช้ fine-tuning เพื่อเปลี่ยนพฤติกรรม รูปแบบ และน้ำเสียง ส่วนข้อเท็จจริงที่เปลี่ยนบ่อยหรือต้องอ้างแหล่งให้ใช้ RAG (ผู้จัดทำ)

1. Fine-tuning คืออะไร และ Unsloth Studio (~0:00–2:36)

Tim สัญญาว่าจะสอนครบ: เลือก LLM ให้ถูก, fine-tune ด้วยข้อมูลของเราเอง แล้วเอาไปเทียบกับ model ตั้งต้นว่าได้ผลจริงไหม แนวคิด: การสร้าง LLM เองตั้งแต่ศูนย์ยากมากและต้องใช้ฮาร์ดแวร์มหาศาล fine-tuning จึงเอา model ที่เก่งภาษาอยู่แล้ว (สร้างประโยคได้แล้ว) มาฝึกต่อด้วยตัวอย่างของเรา จนได้ model ที่เข้ากับงานของเรา เช่น "Tim Llama" ที่พูดเหมือนเขา ซึ่งเขาบอกว่าทำง่ายมาก Unsloth Studio เป็นเครื่องมือใหม่ของ Unsloth ผู้พูดบอกว่า "เข้าใจว่า" สร้างและดูแลโดยวิศวกร NVIDIA (ดูกล่องแก้ด้านล่าง) เดิม Unsloth มักใช้ผ่านบรรทัดคำสั่งซึ่งค่อนข้างยาก ตอนนี้มีหน้าเว็บสำหรับ fine-tune ฟรี open source ไม่ต้องมีบัญชี ไม่ต้องต่ออินเทอร์เน็ต รันในเครื่องทั้งหมด และโหลด model open source มา fine-tune ได้แทบทุกตัว ผู้พูดบอกว่ารันเร็วมากเพราะเบื้องหลังเป็นซอฟต์แวร์ที่ปรับแต่งมาดี ใช้ GPU, CPU และ RAM ได้เร็วกว่าเขียนเองมาก ทำได้สามอย่าง: fine-tune, สร้างชุดข้อมูล (ซึ่งเขาว่าอาจสำคัญกว่า) และ export หรือแพ็ก model ไปแบ่งให้คนอื่น บนสไลด์มีบรรทัด "Mental model": prompting = สั่งใหม่ทุกครั้ง · RAG = ยื่นเอกสารอ้างอิงให้ · fine-tuning = ฝึกตัว model เอง ~0:00–2:36

Unsloth ไม่ได้สร้างโดยวิศวกร NVIDIA บริษัท Unsloth AI ก่อตั้งโดยพี่น้อง Daniel กับ Michael Han (Y Combinator S24) ความเกี่ยวข้องกับ NVIDIA ที่มีจริงคือ Daniel เคยทำงานที่ NVIDIA ช่วง 2018–2020, Data Recipes ใน Studio ใช้ NVIDIA NeMo Data Designer และประกาศเปิดตัวขอบคุณ NVIDIA ในฐานะพาร์ตเนอร์ Studio เปิดตัวแบบ Beta เมื่อ 17 มีนาคม 2026

2. LoRA: แช่แข็ง model แล้วฝึกแค่ adapter (~2:36–4:08)

หลักการคือเก็บ base model ไว้ เพิ่มตัวอย่างของเราในรูปชุดข้อมูล แล้วฝึก LoRA adapter ที่อยู่ "บน หรือข้าง ๆ" base model (ผู้พูดเลือกคำไม่ถูกเอง) รวมกันเป็น model เฉพาะทาง base ไม่ถูกแตะเลย: ถ้าเลือก Llama 8B weight เดิมยังเหมือนเดิมทุกตัว สิ่งที่ฝึกคือชั้น adapter ซึ่งผู้พูดบอกว่า เล็กกว่า 1% ของขนาด base และไม่ต้องกังวลรายละเอียดมาก ชั้นเหล่านี้ช่วย "จูน ปรับ หรือดัน" คำตอบของ model ให้ใกล้ตัวอย่างและผลที่เราต้องการ ผู้พูดย้ำว่าอธิบายแบบภาพกว้างมาก ๆ วิธีนี้ทำให้ฝึกได้เร็วและ model ยังเล็ก โดยไม่ต้องฝึก weight จำนวนมาก สไลด์อธิบายเพิ่ม: ทุกคำตอบ = ผลของ model ที่แช่แข็ง บวก การแก้ของ adapter, A ย่อลง B ขยายกลับ, การฝึกขยับแค่กล่องเล็กสีเขียว จึงทำ base 8B พังไม่ได้ และ GPU เก็บ gradient แค่ราว 1% ของ weight ~2:36–4:08

เสริมจากผู้จัดทำ

คำนวณเอง: Llama 3.1 8B มี 32 ชั้น ถ้าใส่ LoRA rank 16 ให้ทุกชั้น linear (q, k, v, o, gate, up, down) จะได้ 1,310,720 พารามิเตอร์ต่อชั้น รวม ≈ 41.9 ล้าน หรือ ≈ 0.52% ของ 8.03 พันล้าน เก็บแบบ 16-bit ได้ราว 84 MB ใกล้กับ "~100 MB" ที่หน้า Export บอก ตัวเลข "เล็กกว่า 1%" จึงถูกสำหรับ rank 16 (ถ้าใช้ rank 32 จะราว 1.04%)

3. QLoRA: adapter เหมือนเดิม แต่บีบ base เหลือ 4-bit (~4:08–5:40)

fine-tune ได้หลายวิธี เช่น LoRA และ QLoRA ตัวที่ใช้ใน demo และผู้พูดแนะนำคือ QLoRA ซึ่ง "แทบเหมือน" LoRA ทุกอย่าง ต่างแค่ใช้ base แบบบีบอัด model ปกติเก็บ weight แบบ 16-bit (16 บิตต่อ weight) จึงใหญ่ เช่น base 16 GB ที่กิน video memory มาก ถ้า quantize เหลือ 4-bit จะเล็กลงมาก จากราว 16 GB เหลือ "5, 6, 7 GB" แล้วใส่ทั้ง model และการฝึก adapter ลงหน่วยความจำได้ RAM ที่ต้องใช้รวมจึงน้อยกว่าเดิมมาก ข้อแลก: ความแม่นยำลดลงจาก model เดิมเล็กน้อย แต่ผู้พูดบอกว่าได้พื้นที่มากขึ้นมาก และ "จริง ๆ แล้วจะได้ผลดีกว่า" เพราะมีที่เหลือไว้ฝึก adapter เขาไม่อยากลงคณิตศาสตร์ และสรุปว่าคนเกือบทุกคนต้องใช้วิธีนี้เพราะไม่มี GPU ร้อยตัวกับพื้นที่ไม่จำกัด สไลด์: "Q" เป็นแค่เรื่องการเก็บ base บีบเป็น 4-bit จึงใช้หน่วยความจำหนึ่งในสี่ ส่วน adapter ที่ฝึกยังแม่นเต็มที่ ทำให้ fine-tune 8B ลงการ์ดเกม 12 GB ได้ และเป็นค่าเริ่มต้นของ Studio ~4:08–5:40

ทำไม 4-bit ไม่ได้เหลือ 4 GB พอดี: 8.03 พันล้าน × 2 ไบต์ ≈ 16.1 GB ถ้าเป็น 4-bit ทั้งหมดจะเหลือราว 4 GB แต่ชั้น embedding กับชั้น output (คลังคำ 128,256 × 4,096 อย่างละราว 1.05 GB) มักเก็บแบบ 16-bit ไว้ คำนวณคร่าว ๆ ได้ราว 5.6 GB ไฟล์ของ Unsloth จริง 5.98 GB เพราะ dynamic 4-bit เก็บบางชั้นแม่นขึ้นอีก VRAM บนจอสูงกว่าที่สไลด์บอก: ระหว่างฝึก demo ใช้ 16.77 จาก 23.99 GiB ในคลิปไม่ได้บอกว่าทำไม (อาจเป็นความยาว context, batch หรือหน่วยความจำที่จองไว้) ถ้าจะใช้การ์ด 12 GB ให้ทดลองกับข้อมูลชุดเล็กก่อน

ตัวเลขเทียบเอกสาร: บทความ QLoRA (Dettmers et al. 2023) อ้างว่าใช้ NF4 แล้วรักษาผลของการฝึก 16-bit ไว้ได้ ตรงกับ "same quality" บนสไลด์ ส่วนผู้พูดบอกว่าความแม่นยำลดลงเล็กน้อย ตาราง VRAM ของ Unsloth สำหรับ 8B คือ QLoRA 6 GB และ LoRA 16-bit 22 GB ไม่ใช่ราว 10 กับ 20 GB ตามสไลด์

4. Fine-tuning กับ RAG (~7:03–7:51)

(ช่วง ~5:40–7:03 เป็นโฆษณาผู้สนับสนุน ตัดออก) ผู้พูดบอกว่าหลายคนเชื่อว่า fine-tuning สอนข้อมูลใหม่ให้ LLM ไม่ได้ ต้องใช้ RAG เสมอ และงานที่ต้องเชี่ยวชาญเฉพาะทางต้องใช้ RAG เขาบอกว่า ไม่จริง เป็นความเข้าใจผิดที่พบบ่อย ความต่าง: RAG ดึงข้อมูลจริงที่ทันสมัยมาใส่ใน prompt คือฉีดข้อเท็จจริงหรือข้อมูลใหม่เข้าไปให้ model คิดต่อ ส่วน fine-tuning ปรับ weight จริง (ผ่าน adapter LoRA) model จึงตอบต่างไปเองโดยไม่ต้องทำอะไรกับ prompt บนสไลด์ (ไม่ได้พูดทั้งหมด):

  • myth สามข้อ: "fine-tuning สอนความรู้ใหม่ไม่ได้" (เอกสาร Unsloth บอกว่าผิดชัดเจน), "RAG ดีกว่า fine-tuning" (ผิดถ้าใช้เป็นกฎตายตัว เพราะ RAG เปลี่ยน weight ไม่ได้) และ "ต้องใช้ RAG กับความเชี่ยวชาญเฉพาะทาง" (ชุดข้อมูลที่คัดมาดีใส่ความรู้ลง model ได้)
  • ฝั่ง reality: fine-tuning ใส่ความรู้ลง weight พร้อมน้ำเสียง สไตล์ และโครงสร้าง · RAG ไม่เปลี่ยน model แค่เพิ่มบริบทตอนตอบ · อ้าง Unsloth ว่า fine-tuning "ทำได้ทุกอย่างที่ RAG ทำ" แต่กลับกันไม่ได้
  • แถบล่าง: RAG ยังเหมาะกับข้อมูลที่เปลี่ยนรายชั่วโมง (ข่าว สต็อก ticket) และคำตอบที่ต้องอ้างแหล่ง ระบบจริงจังใช้ทั้งสองอย่าง (ปรับพฤติกรรมและความรู้ที่นิ่งด้วย fine-tuning) ~7:03–7:51
ข้อที่ควรเข้าใจให้ตรง

เอกสาร Unsloth ใช้คำว่า "mostly": "Fine-tuning can do mostly everything RAG can - but not the other way around" ไม่ใช่ "ทั้งหมด" ตามสไลด์ งานวิจัยอิสระระมัดระวังกว่านี้:

  • Ovadia et al. (2023): RAG ดีกว่า fine-tuning แบบไม่มีผู้สอน (unsupervised) อย่างสม่ำเสมอ ทั้งกับความรู้เดิมและความรู้ใหม่ทั้งหมด
  • Gekhman et al. (2024): model เรียนข้อเท็จจริงใหม่ผ่าน fine-tuning ได้ยากและช้ากว่า และเมื่อเรียนได้ก็มีแนวโน้มแต่งเรื่อง (hallucinate) มากขึ้นตามสัดส่วน

fine-tuning จึงเหมาะกับการเปลี่ยนพฤติกรรม รูปแบบ และน้ำเสียงมากกว่าการยัดข้อเท็จจริงใหม่

  4. ต้องเปิด terminal ทิ้งไว้ ย่อหน้าต่างได้แต่ห้ามปิด ไม่งั้น Studio จะหยุด ครั้งต่อไปให้รันคำสั่ง launch เดิม หรือรันคำสั่งติดตั้งซ้ำแล้วตอบ yes ~9:10–10:48

คำสั่งตามเอกสาร Unsloth (ผลตรวจของผู้จัดทำ): Mac / Linux / WSL curl -fsSL https://unsloth.ai/install.sh | sh · Windows PowerShell irm https://unsloth.ai/install.ps1 | iex แล้วเปิด http://127.0.0.1:8888

7. เลือก model ที่จะ fine-tune (~10:48–14:57)

ขั้นแรกคือโหลด model ที่จะ fine-tune จากตัวเลือก model ด้านบนหรือแท็บ Hub ส่วนหน้า Chat จะแสดง model ที่โหลดไว้แล้ว ข้อห้าม: model แบบ GGUF ใช้ fine-tune ไม่ได้ ต้องเป็นรูปแบบ safetensors (ผู้พูดเอ่ยอีกรูปแบบที่ caption เขียนว่า "MLK" ผู้จัดทำคิดว่าน่าจะเป็น MLX) model GGUF ที่โหลดไว้ในโปรแกรมอย่าง LM Studio จึงใช้ไม่ได้ เพราะ GGUF ออกแบบมาสำหรับรัน model ขนาด model ตาม VRAM หรือ unified memory (ผู้พูด):

  • 6 GB → น่าจะได้ 3–4B
  • 10 GB → 7–8B ซึ่งเขาเรียกว่า จุดที่ลงตัว
  • 16–20 GB → 12–14B
  • มากกว่านั้น → 27, 35, 70B แต่ใหญ่มาก และเขาว่าส่วนใหญ่ไม่จำเป็นต้อง fine-tune หรือได้ประโยชน์น้อยกว่า

เขาพบว่า 8B ให้ผลดีมาก ถ้าไม่ไหวก็ลดขนาดลง และแนะนำให้ถาม Claude หรือ ChatGPT ว่าตอนนี้ model ไหนดีที่สุดสำหรับเครื่องเรา เพราะคงเปลี่ยนหลังคลิปออก model ที่ใช้: ใน Hub เปลี่ยนตัวกรองเป็น fine-tune ready (ย้ำว่าสำคัญมาก) ค้น llama 3.1 แล้วเลือก unsloth/llama-3.1-8b-instruct-unsloth-bnb-4bit ขนาดราว 6 GB เป็น Llama 3.1 8B Instruct ที่ quantize แล้ว จึงโหลดเร็วกว่า (ให้ Studio บีบอัตโนมัติก็ได้ แต่โหลดตัวนี้ตรง ๆ ดีกว่า) ตัวนี้ค่อนข้างปลอดภัยสำหรับเครื่องระดับกลาง จะใช้ model อื่นก็ได้ ขอแค่อยู่ในกลุ่ม fine-tune ready และขนาดพอดีกับ VRAM หรือ unified memory ของเครื่อง คำแนะนำในการเลือก:

  • เลือก Instruct ไม่ใช่ base เพราะฝึกให้ทำตามคำสั่งมาแล้ว จะได้ผลดีกว่ามาก
  • ถ้ามีรุ่น bnb 4-bit ให้เลือก เพราะบีบไว้พร้อมสำหรับ QLoRA ถ้าไม่มีก็ให้บีบอัตโนมัติ โดยเอา safetensors ไม่ใช่ GGUF

ทดสอบก่อนฝึก: ไปที่ Chat เลือก model รอโหลด พิมพ์ "hello world" แล้วได้คำตอบ ควรเช็กว่า model ใช้ได้ก่อนเสียเวลาฝึก ~10:48–14:57

ข้อที่ควรเข้าใจให้ตรง

Instruct หรือ base ขึ้นกับจำนวนข้อมูล: เอกสาร Unsloth แนะนำว่าต่ำกว่า 300 แถวมักใช้ instruct, 300–1,000 แถวได้ทั้งคู่ และเกิน 1,000 แถวมักฝึกจาก base ดีกว่า ชุดของ Tim มี 3,000 แถว ตาราง VRAM ขั้นต่ำของ Unsloth สำหรับ QLoRA ต่ำกว่าในคลิปราว 1.7–2.4 เท่า (3B 3.5 GB, 7B 5 GB, 8B 6 GB, 14B 8.5 GB) ตัวเลขในคลิปจึงเป็นค่าที่เผื่อไว้ ไฟล์ model ของ demo หนัก 5.98 GB

8. ข้อมูลฝึกควรหน้าตาแบบไหน (~14:57–17:34)

fine-tune ที่แท็บ Train แต่ก่อนอื่นต้องมีชุดข้อมูล ที่ต้องการคือสามคอลัมน์: instruction, input และ output ซึ่งพอให้ model เริ่มเรียนรูปแบบในข้อมูลและฝึก adapter ให้เข้ากับงานของเรา หลักคือป้อนตัวอย่างจำนวนหนึ่งให้ model เรียนว่า input แบบนี้ควรตอบแบบไหน แต่ model ยืดหยุ่นพอรับสถานการณ์ใหม่ได้ จึง ไม่ต้องใช้หลายหมื่นตัวอย่าง แค่หลักร้อยถึงหลักพันก็พอ:

  • 300–1,000 แถว: เปลี่ยนน้ำเสียงและรูปแบบ
  • 5,000, 10,000, 15,000 แถว: สอนทักษะจริงจังที่ model จะทำได้ดีขึ้น
  • ตรงนี้ผู้พูดบอกว่า "คิดว่าจะใช้ 1,100 แถว" (ผู้จัดทำ: ชุดที่ใช้จริงในส่วนถัดไปมี 3,000 แถว)

input ไม่บังคับ: แค่ instruction กับ output ก็พอ แต่ใส่ input ตัวอย่างแล้วจะได้ผลดีกว่า สรุปคือเป็นตัวอย่างบทสนทนา ชุดข้อมูลแบบอื่นมีอีกมาก แต่แบบนี้ง่ายที่สุดและให้ AI สร้างให้ได้ ตัวอย่างบนจอ (ชุดงานบริการลูกค้า): จัดการคำขอคืนเงิน, ตอบเรื่องส่วนลด ("มีราคานักศึกษาไหม" → "มี") และแก้ปัญหารายงานแครช แต่ละแถวมี input กับ output เป้าหมายคือให้ข้อมูลใหม่นี้ "ฝังลง weight" ~14:57–17:34

ข้อที่ควรเข้าใจให้ตรง

เอกสาร Unsloth ให้ขั้นต่ำ 100 แถว และบอกว่าเกิน 1,000 แถวจะดีกว่า ไม่พบการแบ่งขั้น 300–1k / 5k–10k แบบในคลิป รูปแบบสามคอลัมน์นี้คือรูปแบบ Alpaca และ Studio รองรับ ShareGPT / ChatML ด้วย

9. ชุดข้อมูลครูภาษาอินโดนีเซียของ Tim (~17:34–18:38)

ชุดที่ใช้จริง: instruction เหมือนกันทุกแถว ส่วน input กับ output เปลี่ยนไปตามที่เขาอยากให้ model ทำงาน โจทย์: Tim กำลังเรียนภาษาอินโดนีเซีย รู้แค่ไม่กี่ร้อยคำ ("ผู้พูดระดับพื้นฐาน") เขาอยากได้ LLM ที่คุยกับเขาเป็นภาษาอินโดนีเซีย โดยใช้แต่คำที่เขารู้ และในรูปแบบที่เขาเคยฝึก จะได้พัฒนาโดยไม่ท่วมหัว ทั้ง input และ output จึงเป็นคำที่เขารู้ วิธีสร้าง: เขาบอก Claude ว่านี่คือคำที่รู้ แล้ววางคำศัพท์ราว 300 คำจากแอปคำศัพท์ ขอให้สร้างชุดข้อมูลหน้าตาแบบนี้ Claude สร้างให้เป็น JSONL 3,000 แถว ที่มี instruction / input / output ส่งให้ Studio ได้เลย ผู้พูดเรียกว่าวิธีที่ง่ายที่สุด: บอก Claude ว่ากำลังฝึก model ใน Studio แล้วขอชุดข้อมูลตามเงื่อนไขของเรา ซึ่ง ครั้งนี้ได้ผลดีมาก ส่วนถัดไปเป็นอีกทางคือสร้างใน Studio ด้วย Recipe ซึ่งเขายอมรับว่า "สับสนอยู่บ้าง" ~17:34–18:38

เสริมจากผู้จัดทำ

เมื่อใช้ LLM อีกตัวสร้างข้อมูลฝึก ข้อผิดของ model ที่สร้าง (เช่น คำแปลผิด หรือใช้คำนอกรายการ) จะถูกฝังลง weight ไปด้วย ในคลิปไม่ได้บอกว่าตรวจ 3,000 แถวนี้อย่างไร ถ้าทำเองควรสุ่มตรวจด้วยคนที่รู้ภาษา หรือเขียนสคริปต์เช็กว่าทุกคำอยู่ในรายการคำศัพท์

10. สร้างชุดข้อมูลด้วย Recipe (~18:38–28:58)

แท็บ Recipes สร้าง recipe ใหม่ได้ เริ่มจาก learning recipe ที่มีให้ หรือเริ่มเปล่า ผู้พูดว่าแบบที่มีให้ตัวเขาดูแล้วงง จึงทำเองแบบที่เขาคิดว่าเข้าใจง่ายกว่ามาก จะใช้ชุดข้อมูลที่มีอยู่บน Hugging Face ก็เลือกได้ แต่ส่วนใหญ่ไม่ตรงงานเรา เขาจึงสอนทำเอง ซึ่งเขาคิดว่ามีค่ากว่า โหนดที่ใช้ (ใน "Indo Recipe"):

  1. ข้อมูลตั้งต้น (seed): มาจาก GitHub repo, ไฟล์ CSV / JSON, ชุดข้อมูล Hugging Face หรือเอกสาร PDF ที่แยกเป็นแถวได้ (เช่น นโยบายคืนเงินหรือ Q&A ของบริษัท) เขาใช้ vocab_seed.csv ซึ่งเป็นรายการคำอินโดนีเซียที่รู้ 276 แถว 5 คอลัมน์ (Indonesian, English, category, example, example English) ตอนแรกบอกว่าให้ Claude สร้าง แล้วบอกว่าได้มาจากแพลตฟอร์มที่ใช้ฝึกภาษา ข้อมูลนี้ยังไม่อยู่ในรูปแบบที่ fine-tune ได้ ซึ่งต้องมี instruction + output หรือ instruction + input + output เขาลบบางคอลัมน์ได้แต่เลือกเก็บไว้ทั้งหมด
  2. task_type (Category · Generated field): ประเภทงานที่อยากได้ ได้แก่ แปลอังกฤษเป็นอินโดนีเซีย, คุยทั่วไป, ความหมายของคำ, quiz, คำใหม่, แก้คำผิด, ฝึกประจำวัน แต่ละแบบมีน้ำหนัก เช่น 27% เป็นแบบหนึ่ง 23% เป็น chat 5% เป็น correction ระบบจะสุ่มประเภทตามสัดส่วนนี้ เพิ่ม subcategory ได้ (ในเมนู Generated fields ยังมีตัวสร้างแบบอื่น เช่น สุ่มตัวเลข หรือค่า yes / no)
  3. instruction (Formula): นิพจน์ที่รวมตัวแปรกับข้อความ เขาวาง prompt "You are Kartu, Tim's personal Indonesian tutor…" ให้พูดอินโดนีเซียง่าย ๆ ด้วยคำที่ Tim รู้แล้วเท่านั้น ชนิด string และเก็บไว้ในชุดข้อมูลสุดท้าย (ถ้าจะใช้เป็นแค่ค่ากลาง ให้ติ๊กช่องที่กันคอลัมน์นี้ออกจากชุดข้อมูลสุดท้าย)
  4. Model provider: ใช้ local model (model ที่โหลดอยู่ในเครื่อง) หรือใส่ endpoint กับ API key ของ OpenAI หรือ Anthropic เพื่อใช้ model ปิดซึ่งสร้างข้อมูลได้เร็วกว่า
  5. Model config: เลือก model (บนจอคือ llama 3.1 8b) และ temperature คือความสุ่ม (บนจอ 0.7)
  6. AI Structured Data (make_row): ตัวที่ผู้พูดแนะนำ (มี AI score, AI code, AI text ด้วย) ใช้ preset model_1 ที่สร้างไว้ด้านบนซึ่งต่อให้อัตโนมัติ ใส่ prompt ยาวว่ากำลังสร้างตัวอย่างฝึกหนึ่งตัวสำหรับครูสอนภาษาของ Tim ที่เป็นมือใหม่

กฎใน prompt ของ make_row:

  • คำอินโดนีเซียทุกคำต้องมาจากรายการคำที่รู้ ภาษาอังกฤษไม่จำกัด
  • ข้อยกเว้นเดียว: ถ้าประเภทคือ new word ให้ใช้คำจาก pool คำใหม่ หนึ่งคำพอดี เพื่อค่อย ๆ เพิ่มคำใหม่
  • แทรกตัวแปร: task type, การ์ดคำศัพท์ (Indonesian = English), ตัวอย่างประโยค
  • คำสั่งแยกตามประเภท (chat, translate, quiz, new word …) · กฎสไตล์ "สั้นและเป็นมิตร" · รายการคำที่รู้ทั้งหมด

ช่อง output format ใส่ JSON schema ให้มี input และ output เป็น string ที่บังคับ แนวคิดคือวนผ่าน seed ทุกแถว สุ่มประเภท ใส่ instruction แล้วให้ AI สร้าง input / output ใหม่ นี่เป็นตัวอย่างพื้นฐาน ยังทำได้อีกมาก และมีตัวอย่างอื่นให้ดู ผู้พูดย้ำว่าถ้าไม่อยากทำแบบนี้ ขอ AI สร้างให้ตรง ๆ ก็ได้ ไม่ต้องเยอะ ไม่กี่พันแถวก็ fine-tune ได้ดีมาก ที่สำคัญคือมี instruction, input, output ~18:38–28:58

11. ทดสอบและรัน Recipe (~28:58–32:06)

Check ตรวจว่า workflow ถูกต้อง จากนั้น test run 2 แถว แถบความคืบหน้าจะขึ้น แล้วเปิดดูข้อมูลดิบว่าสมเหตุสมผลไหม ผลทดสอบมีคอลัมน์จาก seed (Indonesian, English, category, example, example English) ตามด้วย instruction และ make_row ที่มี input / output เช่น input ถามว่า "brush teeth" ภาษาอินโดนีเซียพูดว่าอะไร แล้ว output ตอบ ซึ่งผู้พูดบอกว่าเป็นคำที่เขารู้ทั้งหมด full run: บันทึกผล กลับไปหน้า editor แล้วกด Run แบบ full run ตั้งชื่อชุดข้อมูล (Indo words) และจำนวนแถว (1,000, 10,000 หรือเท่าไรก็ได้) เปิด batching, throughput, retries ได้ เขาลองสร้าง 50 แถว ก่อนหน้านี้เคยสร้าง 3,000 แถว แต่ไม่รอให้จบในคลิปเพราะใช้เวลาพอสมควรบนเครื่องเขา ความเร็ว: หน้าจอแสดงอัตราแถวต่อวินาที ในกรณีของเขา "ช้ามาก" เพราะใช้ model ในเครื่อง ประมาณเวลาไว้ 332 วินาที (ราว 5 นาที) ความคืบหน้าไม่ใช่แบบสด แต่อัปเดตเป็นช่วง (ครั้งนี้ทุก 5 แถว) ถ้าไม่แน่ใจให้เปิด overview หรือดูใน terminal อย่าคิดว่าค้าง อยากเร็วขึ้นให้เปลี่ยน provider เป็นเจ้าภายนอกอย่าง OpenAI ซึ่งเสียเงินเล็กน้อย ผู้พูดบอกว่าจากที่เขาลอง ได้ผลดีกว่าเมื่อทำผ่าน Claude ตรง ๆ รอบนี้ใช้เวลานานจนเครื่องหน่วง แล้วได้ 50 แถวพร้อมคอลัมน์ make_row ~28:58–32:06

13. ตั้งค่าและฝึก (~34:39–38:10)

Parameters:

  • ตั้งชื่อโปรเจกต์ (เขาใช้ indo_training_2)
  • จำนวน step หรือ epoch: แนะนำ เริ่มที่ 1 epoch โดยเฉพาะข้อมูลง่าย แล้วดูผล ส่วน "มาตรฐาน" คือ 3 ถ้าข้อมูลเยอะ (ข้อมูลยิ่งมาก epoch ยิ่งมาก) โดยทั่วไป งานง่าย ๆ ถ้าเกิน 1 epoch loss จะลดเร็วมาก
  • ค่าอื่น (rank, alpha, dropout, adapter, hyperparameter) มือใหม่ ปล่อยไว้ตามเดิม ปรับแค่ epoch ซึ่งกำหนดเวลาฝึกโดยตรง

ค่าบนจอ (~35:40): context 2048 · learning rate 0.0002 (คำแนะนำในช่อง: 2e-4 สำหรับ LoRA, 5e-5 สำหรับ CPT, 2e-5 สำหรับ full fine-tune) · rank 16 · alpha 16 · dropout 0.00 เวลาฝึก ขึ้นกับจำนวนแถว ขนาด base และจำนวน step / epoch ดูประวัติได้ในแท็บ history และดูใน terminal ว่าทำงานอยู่ ระหว่างฝึก: เห็น VRAM, อุณหภูมิ, กำลังไฟ และกราฟ training loss, gradient norm, learning rate

  • learning rate จะค่อย ๆ ลดลง เพราะยิ่งฝึกนาน ยิ่งอยากให้เรียนของใหม่น้อยลง ปรับทีละนิด
  • training loss คือกราฟหลัก ควรลดลง loss บอกว่า model ทาย token ถัดไปได้ใกล้ตัวอย่างแค่ไหน ข้อมูลของเขาง่าย (ภาษา, model รู้รูปแบบอยู่แล้ว, เป็นแม่แบบ) จึงลดฮวบ loss เริ่มสูงมาก พอถึง step 10 ก็ต่ำกว่าค่าที่เขาชี้บนกราฟแล้ว ซึ่งเขาว่าแปลว่าทำงานได้ดีมากแล้ว และหวังว่าจะลดต่อไป เห็นการลดชันแบบนี้ก็รู้ว่าฝึกได้ถูกทาง และน่าจะทำงานได้ค่อนข้างดี
  • gradient norm ไม่ต้องกังวล ถามให้ AI อธิบายได้
  • ระหว่างรอจะเห็น ETA, step, token และแถวข้อมูลที่ผ่านไป ปรับการแสดงผลหรือหยุดการฝึกได้

ผู้พูดบอกว่าถ้า loss ต่ำกว่า 1 มักแปลว่าทำงานได้ค่อนข้างดี "อย่างน้อยตามที่มันประเมินตัวเองระหว่างฝึก" จากนั้นเขาหยุดการฝึกรอบนี้ เพราะฝึกไว้แล้วก่อนอัดคลิป ~34:39–38:10

ข้อที่ควรเข้าใจให้ตรง

loss ต่ำมากไม่ได้แปลว่าดีเสมอ: เอกสาร Unsloth บอกว่า loss ราว 0.5–1.0 เป็นสัญญาณดี ถ้าลงใกล้ 0 อาจ overfitting และคู่มือ hyperparameter บอกว่าต่ำกว่า 0.2 น่าจะ overfitting แล้ว checkpoint ที่เลือกไว้บนหน้า Export (run indo_training) มี loss 0.0582 และหน้าจอระหว่างฝึกก็ 0.1468 ค่าเริ่มต้นในเอกสาร Studio คือ alpha 32, dropout 0.05 ต่างจากบนจอ (16 / 0.00 อาจเป็นคนละเวอร์ชัน) คำแนะนำ LR 2e-4 กับ 1–3 epoch ตรงกับเอกสาร

เสริมจากผู้จัดทำ

อ่านกราฟเพิ่ม: กราฟ learning rate บนจอขึ้นจากเกือบ 0 ถึงราว 2e-4 ใน 5–6 step แรก (warm-up) แล้วจึงค่อย ๆ ลด ไม่ได้ลดตั้งแต่ต้น ช่อง Eval Loss ยังว่าง ("Evaluation not configured") คือไม่ได้แบ่งข้อมูลไว้วัดผล loss ที่เห็นจึงเป็นของข้อมูลฝึกอย่างเดียว ถ้าแบ่งราว 5–10% ไว้เป็น eval จะรู้ได้ว่า model จำหรือเข้าใจ

14. เทียบกับ model ตั้งต้น (~38:10–40:22)

ไปที่ On device ค้น model ที่ฝึกแล้ว (เขาฝึกไว้ก่อนอัดคลิป) โหลดแล้วคุยได้เลย เพื่อเช็กว่า model ทำงานถูกต้อง ถ้ากด + → More → Compare chat จะส่งข้อความเดียวกันให้ base กับตัวที่ fine-tune แล้ว และปรับ temperature, top P, system prompt ได้ สามคำถามที่ลอง:

คำถามfine-tuned (ตามที่ผู้พูดอ่าน)base
"Hello, apa kabar" (สวัสดี สบายดีไหม)ใช้แต่คำที่ Tim รู้ แปลได้ทุกคำใช้คำที่อาจยังง่ายแต่เกินที่ Tim เข้าใจ ทำให้คุยต่อยากมาก
คำว่า alone แปลว่าอะไร"alone = sama … (He goes alone)" แล้วอธิบายตอบเป็นภาษาอินโดนีเซียยาวที่ Tim อ่านไม่ออกทั้งหมด
"I want to go work out today" พูดอย่างไรให้คำแปลตรง ๆ ซึ่ง "ตรงกับที่ต้องการ" เป็นวิธีพูดที่ง่ายมากตอบเป็นภาษาอินโดนีเซียล้วน ไม่มีภาษาอังกฤษเลย ซับซ้อนกว่ามากและเขาไม่เข้าใจ

ผู้พูดสรุปว่าเพราะ fine-tuning เขาได้ "ครู" ที่เข้าใจว่าเขาเป็นมือใหม่และใช้คำพื้นฐาน ทำให้คุยได้ดีขึ้นมาก ~38:10–40:22

ข้อที่ควรเข้าใจให้ตรง

คำตอบเรื่อง "alone" ผิด: ภาษาอินโดนีเซีย "sama" แปลว่า "กับ" หรือ "เหมือนกัน" ไม่ได้แปลว่า "คนเดียว" คำที่ถูกคือ sendiri / sendirian ("Dia pergi sendirian" = เขาไปคนเดียว) model ตั้งต้นทางซ้ายตอบ "sendirian" ซึ่งถูก (แต่มี "sendiriri" ที่สะกดผิด และ "tersendiri" ที่หมายถึง "แยกต่างหาก" ปนมาด้วย) ผู้พูดรับคำตอบนี้ไปโดยไม่ได้ทักว่าผิด (เขาเป็นผู้เรียนระดับพื้นฐาน) "Aku mau olahraga hari ini" ใช้ได้แบบกันเอง (แบบทางการคือ berolahraga)

เสริมจากผู้จัดทำ

ทำไมพลาดแบบนี้ (ผู้จัดทำวิเคราะห์): ชุดข้อมูลบังคับให้ใช้แต่คำที่รู้ ถ้า sendiri ไม่อยู่ในรายการ model ก็เรียนว่าต้องหาคำในรายการมาตอบแม้ไม่ตรง สไตล์เปลี่ยนสำเร็จ แต่ความถูกต้องเสีย การเทียบด้วย 3 คำถามที่ temperature 1.5 (บนจอ) จึงยังไม่ใช่การวัดผล ควรมีชุดคำถามที่รู้คำตอบแน่ และให้คนที่รู้ภาษาตรวจ คำตอบของ "apa kabar" บนจอก็เป็นคำถามกลับหลายข้อแทนการตอบว่าสบายดี

15. Export model (~40:22–41:06)

ถ้าพอใจกับผลก็ export ได้ เลือก model แล้วเลือกปลายทาง:

  • GGUF: ใช้กับโปรแกรมอย่าง Ollama
  • 16-bit เต็ม: สำหรับ inference
  • LoRA อย่างเดียว

ใช้ในเครื่องมือแทบทุกตัว แบ่งให้คนอื่น หรืออัปโหลดขึ้น Hugging Face ก็ได้ บนจอ (~40:45): training run ของ Llama 3.1 8B Instruct มี 39 checkpoints, checkpoint ที่เลือกมี loss 0.0582, method LoRA / QLoRA rank 16

  • Merged Model: model 16-bit เต็มพร้อม inference
  • LoRA Only: ไฟล์ adapter เบา ราว 100 MB ต้องใช้คู่กับ base
  • GGUF / Llama.cpp: หลายระดับ quantization เช่น Q4_K_M ราว 4.6 GB (แนะนำ), Q8_0 ราว 8.2 GB, BF16 / F16 ราว 15 GB และมีตัวเลือก importance matrix (imatrix)

ผู้พูดปิดว่าเป็นคอร์สเต็มของ Unsloth Studio ที่ยาวเพราะมีเรื่องต้องอธิบายเยอะ ~40:22–41:06

Key Takeaways

1.fine-tuning ไม่ต้องสร้าง model ใหม่: แช่แข็ง base แล้วฝึก adapter LoRA เล็ก ๆ (เล็กกว่า 1%) ส่วน QLoRA เก็บ base แบบ 4-bit ทำให้ 8B ลงการ์ดเกมได้
2.Unsloth Studio ทำครบในหน้าเว็บเดียวบนเครื่องเรา: Hub → Recipes → Train → Compare → Export ใช้ model แบบ safetensors ที่ "fine-tune ready" เพราะ GGUF ใช้ fine-tune ไม่ได้
3.ข้อมูลคือหัวใจ: instruction / input / output หลักร้อยถึงหลักพันแถว ให้ Claude สร้างหรือใช้ Recipe ผู้พูดตรวจผล test run ว่าสมเหตุสมผล · ชุดที่ AI สร้างควรสุ่มตรวจคุณภาพ (ผู้จัดทำ)
4.เริ่มที่ 1 epoch และมือใหม่ปล่อยค่าอื่นตามเดิม (ผู้พูด) · loss ใกล้ 0 (เช่น 0.0582) อาจเป็น overfitting ตามเอกสาร Unsloth ควรแบ่งชุด eval แยก (ผลตรวจของผู้จัดทำ)
5.ผู้พูด (และสไลด์) บอกว่า fine-tuning ใส่ความรู้ลง weight ได้ พร้อมปรับน้ำเสียงและรูปแบบ ส่วนข้อมูลที่เปลี่ยนรายชั่วโมงหรือคำตอบที่ต้องอ้างแหล่งยังเหมาะกับ RAG (สไลด์) · งานวิจัยพบว่าการเพิ่มความรู้ใหม่ RAG มักได้ผลดีกว่า (ผลตรวจของผู้จัดทำ)
