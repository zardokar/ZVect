📋 บทสรุปย่อ

บทสรุปย่อ: ผู้สอนชี้ว่า dense embedding ที่ใช้กันใน RAG มีจุดอ่อน: ทั้ง chunk ถูกอัดเป็นเวกเตอร์เดียว ยิ่ง chunk ยาว ข้อมูลยิ่งหาย ทางออกที่เสนอคือ ColBERTv2 ซึ่งใช้ late interaction: ตัดเอกสารและคำถามเป็น token ทำเวกเตอร์ให้ทุก token แล้วให้แต่ละ token ของคำถามเทียบกับทุก token ของเอกสาร ก่อนรวมเป็นคะแนนของเอกสาร จากนั้นสาธิตด้วย library RAGatouille บนเปเปอร์ Orca (chunk 256 แล้ว 512 tokens) และเทียบกับ embedding ของ OpenAI และ BGE small ในตัวอย่างนี้ ColBERT ดึง chunk ที่ตรงคำถามได้ดีกว่า ส่วน dense embedding ดึงหน้าสารบัญมาปนบ้าง

โหมดของเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ (license มาตรฐานของ YouTube, ตรวจ 2026-10-11) ทุกประเด็นและตัวเลขอยู่ครบตามลำดับคลิป โดยไม่เปลี่ยนความหมาย แต่ไม่ได้ถอดคำพูดทีละประโยค ตัวเลขบางตัว (34,104 embeddings, MaxSim ในรูปของเปเปอร์) อ่านจากภาพบนจอ ไม่ได้มาจากเสียงพูด และกำกับไว้ทุกจุด

🧭 สรุปเชิงลึก

ปัญหา: RAG ทั่วไปคำนวณ embedding ให้แต่ละ chunk เป็นเวกเตอร์เดียว แล้วหา chunk ที่ใกล้เวกเตอร์ของคำถามที่สุด โมเดลแต่ละตัวมีขนาดมิติต่างกัน ผู้สอนยกตัวอย่างว่า BGE small ที่ใช้กันมากมีแค่ 384 มิติ ถ้า chunk เป็นหลายย่อหน้า ทุกอย่างถูกบีบลงเวกเตอร์เดียว และเวกเตอร์นั้นอาจแทนทุกเรื่องใน chunk ไม่ได้ การบีบคือการเสียข้อมูล

ทางออก (ColBERTv2): ColBERT ย่อจาก contextualized late interaction ขั้นตอนแบบย่อ: (1) ตัดทั้งเอกสารและคำถามเป็น token (2) ทำเวกเตอร์ให้ทุก token และเวกเตอร์นี้ขึ้นกับบริบทของประโยค (3) ทุก token ของคำถามคำนวณความคล้ายกับทุก token ของเอกสาร (4) รวมคะแนนย่อยเป็นคะแนนเดียวของเอกสาร รูปในเปเปอร์ที่แสดงบนจอเขียนขั้นที่ 4 เป็น MaxSim ต่อ token แล้วรวมด้วย Σ ผู้สอนย้ำว่านี่เป็นคำอธิบายแบบง่ายมากและข้ามรายละเอียดทางเทคนิค

ลองจริง: ใช้ RAGatouille (สร้างบน ColBERT) กับเปเปอร์ Orca: index ชื่อ orca, max_document_length 256, แบ่งเอกสาร ได้ 219 passages (บนจอขึ้นว่าประมาณ 34,104 embeddings คือหนึ่งเวกเตอร์ต่อ token) ถาม "what is instruction tuning" ได้ 3 chunk ที่พูดเรื่องนี้ทั้งหมด ส่วน OpenAI embedding + FAISS (chunk 256 ด้วย tokenizer ของ GPT-4) ได้ chunk แรกเหมือน ColBERT แต่ chunk ที่สามเป็นหน้าสารบัญ และ BGE small ได้สารบัญเป็นอันดับแรก

chunk 512 กับคำถามสองส่วน ("system message คืออะไร และมีอะไรบ้างในเปเปอร์"): ColBERT ได้นิยามก่อน แล้วได้รายการ 12 ข้อครึ่งจาก 16 ข้อ ตามด้วยตาราง และรายการส่วนที่เหลือ OpenAI ได้รายการบางส่วน สารบัญ นิยาม และบทบาทของ system instruction ส่วน BGE small มีปัญหามากสุด ผู้สอนสรุปว่าในตัวอย่างนี้ ColBERT "อาจ" ให้ context ที่ดีกว่า และความแม่นของ dense ขึ้นกับขนาดโมเดลด้วย (เช่น SFR-Embedding-Mistral และ OpenAI ที่ผู้สอนคิดว่าเป็นรุ่น small 1,536 มิติ)

ข้อควรรู้ (ผู้จัดทำ): ผลเทียบเป็นคำถามสองข้อบนเอกสารเดียว ไม่ใช่การวัดผลแบบมีชุดทดสอบ และคลิปไม่ได้พูดถึงต้นทุน: เก็บหนึ่งเวกเตอร์ต่อ token ใช้ที่มากกว่าหนึ่งเวกเตอร์ต่อ chunk หลายเท่า (บนจอ: 219 passages → ราว 34,104 เวกเตอร์ ส่วน dense กับชุดเดียวกันจะเป็น 219)

เอาไปใช้: ZVect เพิ่มหัวข้อ 6.2 Late interaction ระหว่าง Bi-Encoder กับ Cross-Encoder (ส่วนที่ 8)

1. ปัญหาของ dense embedding ใน RAG

~0:00–1:52 (Problem with Dense Embeddings in RAG)

ผู้สอนเปิดว่า dense embedding ที่เราใช้ใน RAG pipeline มีข้อบกพร่องสำคัญที่น่าจะทำให้การค้น (retrieval) แม่นน้อยลง (caption ได้ยิน RAG เป็น "rack")

ตัวอย่างบนกระดาน: มีเอกสาร 3 ชิ้น ชิ้นละหนึ่งประโยค และคำถามหนึ่งข้อ เราคำนวณ embedding ของแต่ละเอกสารหรือ chunk ได้หนึ่งเวกเตอร์ต่อ chunk (ขนาดขึ้นกับโมเดลที่เลือก) คำถามก็ได้หนึ่งเวกเตอร์ แล้วทำ similarity search: เทียบเวกเตอร์ของคำถามกับของแต่ละเอกสาร หาตัวที่ใกล้ที่สุด แล้วส่งเป็นผลของขั้น retrieval

โมเดล embedding แต่ละตัวมีจำนวนมิติต่างกัน ผู้สอนชี้ไปที่ตาราง leaderboard ว่าโมเดลโอเพนซอร์สที่ใช้กันมากที่สุดตัวหนึ่งคือ BGE small ซึ่งมีแค่ 384 มิติ และช่วงหลังเริ่มเห็นโมเดลโอเพนซอร์สที่มีมิติใหญ่ขึ้นมาก

ปัญหาคือ ถ้า chunk ไม่ใช่ประโยคเดียว แต่มีหลายย่อหน้าเพราะตั้ง chunk size ใหญ่ การคำนวณ embedding จะบีบข้อมูลทั้งหมดลงเวกเตอร์เดียว ซึ่งอาจแทนทุกอย่างใน chunk ไม่ได้ ผู้สอนเรียกการบีบนี้ว่าการเสียข้อมูลไปมาก

2. ColBERTv2 และ late interaction

~1:52–4:55 (ColBERT v2 for Efficient Retrieval)

ทางออกที่เป็นไปได้อยู่ในเปเปอร์ ColBERTv2: Effective and Efficient Retrieval via Lightweight Late Interaction ผู้สอนบอกว่าเปเปอร์อ่านยาก จึงอธิบายด้วยตัวอย่างง่าย ๆ และจะมีโค้ดตัวอย่างทีหลัง (caption ได้ยิน ColBERT เป็น "coal bur / coal bear")

dense embedding ใช้เวกเตอร์เดียวแทนทั้ง chunk แต่ ColBERT ใช้วิธีอื่น: COL ย่อจาก contextualized late interaction

  1. ตัดเป็น token ทั้งเอกสาร (chunk) และคำถาม ตาม tokenizer ที่ใช้ ในตัวอย่าง เอกสารแรกมี 5 token เอกสารที่สองมี 5 token เอกสารที่สามมี 6 token และคำถามก็ถูกตัดเป็น token เช่นกัน
  2. ทำ embedding ให้ทุก token: ทุก token ได้เวกเตอร์ของตัวเอง เอกสารหนึ่งชิ้นจึงมีเวกเตอร์หลายตัว ตามจำนวน token
  3. เทียบทีละ token ของคำถาม: token แรกของคำถามคำนวณความคล้ายกับทุก token ในเอกสารที่ 1 แล้วทำซ้ำกับเอกสารที่ 2 และ 3 และทำแบบนี้กับทุก token ของคำถาม
  4. รวมเป็นคะแนนของเอกสาร จากคะแนนย่อยเหล่านี้ เรียกว่า late interaction

ผู้สอนย้ำว่านี่เป็นคำอธิบายที่ ง่ายมาก และข้ามรายละเอียดทางเทคนิคไปเยอะ จุดสำคัญคือ ทุก token มีส่วนในคะแนน แทนที่ทุกอย่างจะถูกบีบลงเวกเตอร์เดียว และเวกเตอร์ของแต่ละ token ขึ้นกับบริบท (contextualized): บริบทรอบ token ถูกนำมาคิดตอนคำนวณ embedding ผู้สอนแนะนำให้อ่านเปเปอร์เพิ่ม

เสริมจากผู้จัดทำ: เสียงพูดบอกแค่ว่า "รวมคะแนนย่อยเป็นคะแนนเดียว" ส่วนวิธีรวมอ่านจากรูปบนจอ: ต่อ token ของคำถามเอาค่าที่สูงที่สุด (MaxSim) แล้วบวกทุก token เข้าด้วยกัน (Σ) เขียนเป็นสูตรได้ว่า score(q, d) = Σi maxj (qi · dj)

3. RAGatouille

~4:55–5:32 (RAGatouille to the rescue)

ต่อไปเป็นตัวอย่างใช้งานจริงว่าค้นแบบ semantic search ด้วย ColBERT แทน dense embedding อย่างไร ColBERTv2 มี GitHub repo ของตัวเอง แต่ผู้สอนเลือกใช้อีก package ชื่อ RAGatouille (caption ได้ยินเป็น "regatoui") ซึ่งสร้างบน ColBERT

หน้า repo ของ RAGatouille แสดงวิธี train และ fine-tune โมเดล ColBERT, ใช้ทำ embedding และ index เอกสาร และมีตัวอย่างการดึงเอกสาร ผู้สอนแนะนำให้ลองดู และทำ Google Colab ไว้ให้ (ลิงก์ในคำอธิบายคลิป)

เสริมจากผู้จัดทำ: library นี้ซ่อนรายละเอียดของ ColBERT ผู้ใช้ส่งรายการข้อความ แล้วเรียก index กับ search คล้าย vector database ทั่วไป (ผู้สอนไม่ได้บอกเหตุผลที่เลือก RAGatouille แทน repo ต้นฉบับ)

4. ลองค้นด้วย ColBERTv2 บนเปเปอร์ Orca

~5:32–9:33 (Semantic Search in Action)

ขั้นตอนใน Colab:

  1. ติดตั้ง package ที่ต้องใช้
  2. ใช้ เปเปอร์ Orca เป็นเอกสาร (ผู้สอนอัปโหลดไฟล์เข้า Colab เอง) โหลด PDF ด้วย PDF reader ของ LlamaIndex
  3. ดึงข้อความออกจาก document object ของ LlamaIndex ให้เป็นรายการข้อความธรรมดา ซึ่งใช้กับ RAGatouille ได้ง่ายกว่า
  4. โหลดโมเดลที่ฝึกไว้แล้ว: ColBERT มีหลายเวอร์ชัน ใช้เวอร์ชันที่ 2 ได้เป็น RAG pipeline ของ RAGatouille (มีคำเตือนเรื่อง token ของ Hugging Face แต่ไม่จำเป็นต้องใช้)
  5. สร้าง index คล้ายการสร้าง vector DB: ส่งรายการข้อความ ตั้งชื่อ index ว่า orca, max_document_length = 256 (ให้คิดเหมือน chunk size) และ split_documents = True เพื่อแบ่งเอกสารตามความยาวนั้น
  6. vector store ค่าเริ่มต้นคือ PLAID แต่บังคับให้ใช้ FAISS ได้ (caption ได้ยินเป็น "plate" และ "fires")

ผลคือข้อความถูกแบ่งเป็น 219 passages และคำนวณ embedding ให้ทุก token

การค้นใช้ฟังก์ชัน search บน index: ใส่คำถาม จำนวนเอกสารที่ต้องการ และชื่อ index (มีหลาย index ได้ ตัวอย่างนี้มีตัวเดียว) ผลต่างจาก vector store ทั่วไปเล็กน้อย: ได้ตัวเอกสารหรือ chunk, score, rank และข้อมูลเฉพาะเอกสาร เช่น passage id และ document id ที่ใช้ภายใน ผู้สอนบอกว่า rank สำคัญมากเพราะเรียงเอกสารตามความคล้ายกับคำถาม

คำถาม "what is instruction tuning" ได้ 3 chunk: chunk แรกมีหัวข้อย่อย instruction tuning และพูดเรื่องนี้ตรง ๆ chunk ที่สองพูดถึง instruction tuning สำหรับงาน multimodal chunk ที่สามพูดถึง instruction tuning ด้วยคำตอบจาก GPT-4 ถ้าทำ RAG ก็ส่งทั้งสามชิ้นนี้เป็น context ให้ LLM พร้อมคำถาม

เสริมจากผู้จัดทำ: 34,104 embeddings อ่านจาก log บนจอ (ผู้สอนไม่ได้พูด) ถ้าใช้ dense กับ 219 passages ชุดเดียวกันจะเก็บแค่ 219 เวกเตอร์ (ผู้จัดทำคำนวณเอง ในคลิป dense แบ่ง chunk ด้วย tokenizer อื่นและไม่ได้แสดงจำนวน) log ยังบอกความยาวเฉลี่ยราว 155.7 token ต่อ passage ซึ่งสอดคล้องกัน (219 × 155.7 ≈ 34,100)

5. เทียบกับ OpenAI embedding และ BGE small

~9:33–12:54 (Comparing Retrieval Performance)

เทียบกับ dense embedding ผ่าน LangChain: ใช้ embedding ของ OpenAI (ต้องใส่ API key) และโมเดลโอเพนซอร์สอีกตัว โหลดเปเปอร์ใหม่ รวมเป็นข้อความเดียว แล้วแบ่ง chunk ด้วย tokenizer ของ GPT-4 ขนาด 256 ให้ใกล้กับฝั่ง ColBERT แต่ผู้สอนเตือนว่า chunk จะไม่เหมือนกันทุกตัว เพราะ tokenizer ต่างกัน ใช้ FAISS เป็น vector store และถามคำถามเดิม

  • OpenAI (4 chunk): chunk แรกเหมือนของ ColBERT ทุกตัวอักษร chunk ที่สองก็พูดถึง instruction tuning แต่ chunk ที่สามคือหน้าสารบัญ (มีคำว่า instruction tuning แต่ไม่มีเนื้อหา) chunk สุดท้ายพูดถึง instruction tuning ผู้สอนบอกว่าทั้งหมดจะเข้า LLM และชิ้นที่ค่อนข้างไม่เกี่ยวอาจก่อปัญหา
  • BGE small English: chunk size 256 token ตาม tokenizer ของ BGE small chunk แรกกลับเป็นสารบัญ ซึ่งไม่ช่วยอะไรเลย chunk ที่ 2, 3 และ 4 มีข้อมูลเรื่อง instruction tuning

ผู้สอนสรุปว่าในตัวอย่างนี้ ColBERT ดึง context ได้ดีกว่ามาก "ผมคิดว่า" (เขาใช้คำนี้เอง)

6. chunk 512 กับคำถามสองส่วน และสรุปของผู้สอน

~12:54–17:44 (Enhancing Retrieval with Increased Chunk Size)

ย้อนไปที่ปัญหาตอนต้น: ขึ้นกับขนาดของโมเดล dense embedding น่าจะเริ่มมีปัญหามากขึ้นเมื่อ chunk ใหญ่ขึ้น จึงเพิ่ม max_document_length ของ ColBERTv2 เป็น 512 และใช้คำถามที่ซับซ้อนกว่า: "what is a system message and list all the system messages in the paper" ซึ่งจริง ๆ เป็นสองคำถามในข้อเดียว

  • ColBERT: chunk แรกตอบว่า system message คืออะไร (system instruction กำหนดน้ำเสียง รูปแบบงาน และข้อจำกัดของคำตอบได้ และช่วยให้คำตอบปลอดภัยขึ้น) chunk ที่สองเป็นรายการ system message ที่เปเปอร์เสนอ ซึ่งมีทั้งหมด 16 ข้อ แต่ chunk ยาว 512 จึงได้แค่ราว 12 ข้อครึ่ง chunk ที่สามเป็นตารางผลลัพธ์แยกตาม system message และ chunk สุดท้ายมีรายการที่เหลือ ผู้สอนบอกว่าควรปรับวิธีแบ่ง chunk ให้ดีขึ้น และ RAGatouille ต่อกับ LangChain ได้ (เขาถามผู้ชมว่าอยากให้ทำคลิปวิธีใช้กับ LangChain ไหม) โดยรวมผล "ไม่แย่เลย" เพราะสองชิ้นแรกมีข้อมูลตรงกับที่ถาม
  • OpenAI: chunk แรกมีรายการ system message บางส่วน chunk ที่สอง "ด้วยเหตุผลบางอย่าง" ได้สารบัญอีก chunk ที่สามคือนิยามของ system message (ดี) และ chunk สุดท้ายพูดถึงบทบาทของ system instruction
  • BGE small: มีปัญหามากที่สุด chunk แรกเป็นรายการบางส่วน chunk ที่สองเป็นคำบรรยายรูปกับตาราง chunk ที่สามมีนิยามบางส่วนแล้วไปพูดเรื่องอื่น chunk ที่สี่ไม่เกี่ยวเลย แค่มีคำว่า system message

สรุปของผู้สอน: ColBERT อาจให้ context ที่ดีกว่า ซึ่งช่วยให้ LLM ตอบได้ดีขึ้น เขาแนะนำให้ลองใช้ และคิดว่ายังไม่ค่อยมีคนใช้ แต่มีศักยภาพสูงมาก ก่อนจบเขาเสริมว่า ความแม่นของการค้นขึ้นกับขนาดของโมเดล embedding ด้วย เช่น SFR-Embedding-Mistral น่าจะดีกว่าเพราะ embedding ใหญ่กว่า (caption: "SFR embedding mist") ผู้สอนคิดว่าเป็นเหตุผลที่ OpenAI ได้ผลใกล้ ColBERT เพราะโมเดลใหญ่ และคิดว่าที่ใช้คือโมเดล small ของ OpenAI ซึ่งมี 1,536 มิติ แล้วย้ำอีกครั้งว่า RAGatouille มีศักยภาพมาก และถามว่าอยากให้ทำคลิปต่อยอดเป็น RAG pipeline แบบครบวงจรไหม

ช่วงท้ายเป็นการชวนสมัครคอร์ส RAG ซึ่งตัดออกตามกติกาของรายงาน

7. ข้อที่ควรเข้าใจให้ตรง (จากผู้จัดทำ)

เสริมจากผู้จัดทำ

ข้อที่ควรเข้าใจให้ตรง

  • ผลเทียบเป็นตัวอย่าง ไม่ใช่การวัดผล: คำถามสองข้อบนเอกสารเดียว chunk ของแต่ละฝั่งไม่เหมือนกัน (tokenizer ต่างกัน) และจำนวนผลต่างกัน (ColBERT 3, OpenAI 4) ผู้สอนเองใช้คำว่า "น่าจะ", "ผมคิดว่า", "อาจ" ตลอด
  • ต้นทุนที่คลิปไม่ได้พูด: late interaction เก็บหนึ่งเวกเตอร์ต่อ token log บนจอบอกราว 34,104 embeddings สำหรับ 219 passages ถ้าเป็น dense กับ passages ชุดเดียวกันจะเก็บ 219 เวกเตอร์ (ผู้จัดทำคำนวณ) ColBERTv2 จึงมีวิธีบีบเวกเตอร์ให้เล็กลง (คำว่า "lightweight" ในชื่อเปเปอร์) และ PLAID ช่วยค้นให้เร็ว (ความรู้ทั่วไป)
  • วิธีรวมคะแนน: เสียงพูดไม่ได้บอก รูปบนจอบอก MaxSim + Σ (ส่วนที่ 2)

8. เชื่อมกับบทเรียนใน ZVect

ทำแล้วใน ZVect (2026-10-11 ตามที่เจ้าของโปรเจกต์ขอ)

ZVect เพิ่มหัวข้อ 6.2 Late interaction (ColBERT) ในบท 6 การผสานทฤษฎี ระหว่าง 6.1 Bi-Encoder กับ Cross-Encoder (เลื่อนเป็น 6.3) เพราะเรียงจากถูกไปแพงได้พอดี:

  • 6.1 Bi-Encoder: หนึ่งเวกเตอร์ต่อประโยค เทียบ cosine ครั้งเดียว
  • 6.2 Late interaction: หนึ่งเวกเตอร์ต่อ token ใช้ MaxSim + Σ (ตัดคำจากบท 3.1, dot จากบท 2.2)
  • 6.3 Cross-Encoder: อ่านคำถามกับเอกสารพร้อมกัน

หัวข้อนี้ใช้ภาษาเดียวกับ 6.1 (EN / TH / 中文 / 日本語) เวกเตอร์ของ token เป็นของเล่นชุดเดียวกับ 6.1 จึงยังไม่ "ขึ้นกับบริบท" แบบ ColBERT จริง ซึ่งเขียนกำกับไว้ในบท

Key Takeaways

  1. dense embedding บีบทั้ง chunk เป็นเวกเตอร์เดียว chunk ยิ่งยาว รายละเอียดยิ่งหาย
  2. ColBERT ให้เวกเตอร์ทุก token และเวกเตอร์ขึ้นกับบริบท ทุก token มีส่วนในคะแนน
  3. คะแนน = แต่ละ token ของคำถามหาค่าที่ใกล้ที่สุดในเอกสาร แล้วรวมกัน (MaxSim + Σ ตามรูปในเปเปอร์)
  4. RAGatouille ใช้ง่ายเหมือน vector DB: index (ชื่อ, ความยาวเอกสาร, แบ่งหรือไม่) แล้ว search (คำถาม, k, ชื่อ index)
  5. ในตัวอย่างของคลิป ColBERT ไม่ดึงสารบัญมาปน ส่วน dense ดึงมา แต่ผลนี้เป็นตัวอย่างเดียว และ dense ตัวใหญ่ได้ผลใกล้เคียง (ผู้จัดทำ: late interaction เก็บเวกเตอร์มากกว่าหลายเท่า)
