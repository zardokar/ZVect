บทสรุปย่อ

คลิปเขียนโค้ดสด 32 นาทีนี้สร้าง TF-IDF ด้วย JavaScript (p5.js) เพื่อหา "คำสำคัญ" ของบทความหนึ่งเทียบกับบทความอื่น ผู้พูดอธิบายสูตรบนกระดานเป็นสี่ขั้น: score = TF × 1/df (100 × 1/10 = 10 กับ 100 × 1/1 = 100) → เปลี่ยน 1 เป็นจำนวนเอกสารทั้งหมด N = 50 (500 กับ 5,000) → ใส่ log เพื่อลดอิทธิพลของจำนวนเอกสาร แล้วเขียนโค้ดจริง: TF = จำนวนนับดิบ, df เริ่มที่ 1, คะแนน = tf × log(files.length ÷ df) ซึ่ง log ของ p5.js คือ ln ผลกับ 4 ไฟล์ได้ arc และ rainbow สูงสุด 6.931471805599453 = 5 × ln 4 รายงานฉบับนี้แสดงทุกขั้นของกระดานเป็นสมการจริง ถอดโค้ดสำคัญจากจอตรงตามภาพ (รวมบั๊กที่ผู้พูดแก้ระหว่างทาง) และคำนวณตัวเลขบนจอซ้ำทุกตัว ที่มาของเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ (license มาตรฐานของ YouTube) สมการ โค้ด และตัวเลขถอดตามภาพ

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึก (license มาตรฐานของ YouTube) สมการบนกระดาน โค้ดบนจอ และตัวเลขผลลัพธ์ถอดตรงตามภาพ ผู้จัดทำคำนวณซ้ำทุกตัวด้วย python (recompute.py)

สรุปเชิงลึก

โจทย์ (0:00–2:16): word counter จากตอนก่อนนับคำของบทความ Wikipedia ฉบับย่อเรื่องรุ้งได้ the 16, a 8, of 7 นี่คือ term frequency (TF) ถ้าเอาคำที่ถี่ที่สุดเป็น keyword จะได้ the, a, of, in, and ซึ่งไม่มีความหมายสำหรับงานนี้ (ผู้พูดหมายเหตุว่าคำพวกนี้มีความหมายในงานวิเคราะห์แบบอื่น อ้างงานของ James Pennebaker) ส่วน rainbow มีความหมาย และน่าจะไม่ค่อยพบในบทความเรื่องอื่น คำที่ถี่ในเอกสารหนึ่งแต่ไม่ถี่ในเอกสารอื่นจึงน่าจะสำคัญกับเอกสารนั้น

สูตรบนกระดาน (2:16–4:42): score = TF × IDF ขั้นแรกใช้ 1/df: คำที่ปรากฏ 100 ครั้งและอยู่ใน 10 เอกสารได้ 100 × 1/10 = 10 อยู่เอกสารเดียวได้ 100 × 1/1 = 100 ขั้นที่สองตาม "นิยามทางเทคนิค" เปลี่ยน 1 เป็นจำนวนเอกสารทั้งหมด (corpus 50 เอกสาร) ได้ 100 × 50/10 = 500 และ 100 × 50/1 = 5,000 ผู้พูดบอกว่าเทียบกันแล้ว "เกือบเท่าเดิม" (อัตราส่วนยังเป็น 10 เท่า) ภาพกระดานที่ ~3:20 ยังเขียนผล = 10 และ = 100 ค้างจากขั้นแรก แต่ที่ ~3:42 แก้เป็น = 500 และ =5000 แล้ว (ผู้จัดทำตรวจจากเฟรม: ไม่ใช่การพูดกับเขียนขัดกัน) ขั้นที่สามใส่ log หน้า N/df เพราะแบบเดิม "ถ่วงแรงเกินไป" log ช่วยลดผลของจำนวนเอกสารที่อาจท่วมคะแนน ผู้พูดไม่ได้บอกฐานของ log

โค้ด (4:58–29:45): ใช้ 4 ไฟล์ (eclipse, fish, rainbow, sports) และยอมรับว่าข้อมูลเล็กเกินจะให้ผลดี เก็บข้อมูลต่อคำเป็น object { tf, df } ลำดับงาน: โหลดไฟล์ → นับ tf ของไฟล์แรก (lowercase) → df เริ่มที่ 1 แล้วไล่ไฟล์อื่น → refactor ให้สร้างเซตคำของแต่ละไฟล์ครั้งเดียว (othercounts) → wordobj.tf * log(files.length / wordobj.df) → เรียงตามคะแนน ระหว่างทางมีบั๊กที่ผู้พูดแก้บนจอ: j = allwords.length (ลูปไม่รู้จบ), ใช้ i แทน j และ k, เก็บ true แต่เทียบ === 1, ตัวแปร word ชนกัน และวงเล็บเกิน หลังแก้ คำว่า "a" ได้ df 4, tf 8

ผล (29:45–30:14): rainbow.txt: arc และ rainbow 6.931471805599453, light และ caused 5.545177444479562, water/droplets/rainbows 4.1588830833596715 และอีกหกคำ 2.772588722239781 ส่วน sports.txt: or 24.95329850015803, conduct 15.249237972318797, unsportsmanlike 9.704060527839234 ผู้พูดบอกว่า or ผิดปกติเพราะข้อมูลเล็ก ผู้จัดทำคำนวณซ้ำแล้วทุกค่าเท่ากับ k × ln 4 พอดี (k = 5, 4, 3, 2 และ 18, 11, 7, 6, 5, 4) แปลว่าทุกคำที่ติดอันดับมี df = 1 และลำดับเท่ากับลำดับของ tf ในกลุ่มคำที่ไม่อยู่ไฟล์อื่น ตัวอย่างลากไฟล์บนเว็บ A2Z ให้ค่าระดับ 0.04 ซึ่งผู้พูดบอกว่าใช้สูตรต่างออกไป (ผู้จัดทำเปิดดูโค้ดหน้านั้นไม่ได้)

ตรวจสอบ: ข้อเท็จจริง 8 ข้อ: ยืนยัน 5 ยืนยันบางส่วน 2 ไม่พบ 1 (ลิงก์ Khan Academy และลิงก์หนังสือที่บอกว่าอยู่ในคำอธิบาย ไม่พบในคำอธิบายที่อ่าน)

ใช้ต่ออย่างไร (ผู้จัดทำ): โค้ดนี้คือ TF นับดิบ × ln(N ÷ df) ไม่มี smoothing และไม่ normalise คนละสูตรกับรายงานคู่ (Stanford: log10 ทั้งสองพจน์) ขั้น refactor คือเมล็ดของ inverted index (คำ → ชุดเอกสาร) ซึ่งเป็นฐานของการค้นแบบ BM25 ถ้าใช้กับภาษาไทยต้องตัดคำก่อน เพราะ split(/\W+/) ใช้ไม่ได้กับข้อความที่ไม่มีช่องว่าง

2. ทำไมคำที่ถี่ที่สุดไม่ใช่ keyword (~1:03–2:16)

ผู้พูดตั้งโจทย์ว่าอยากให้อัลกอริทึม สกัด keyword ของบทความโดยอัตโนมัติ วิธีแรกที่คิดได้คือคำที่ถี่ที่สุดน่าจะสำคัญ แต่ผลคือ the, a, of, in, and, by ซึ่ง "ไม่มีความหมาย" สำหรับงานนี้

เขาออกตัวว่าคำพวกนี้มีความหมายมากในงานวิเคราะห์ข้อความแบบอื่น โดยอ้างงานวิจัยของ James Pennebaker (บทถอดเสียงสะกด "Penn Baker") และหนังสือ The Secret Life of Pronouns แล้วบอกว่าจะกลับมาเรื่องนี้อีกครั้ง แต่สำหรับการสกัด keyword คำเหล่านี้ไม่ช่วย

ตรงข้าม rainbow เป็นคำที่มีความหมาย ถ้าเปิดหน้า Wikipedia ของมะม่วงหรือบลูเบอร์รีก็คงไม่ค่อยเจอคำว่า rainbow แต่จะเจอ the, a, of, in เสมอ จึงได้หลักว่า: คำที่ถี่ในเอกสารหนึ่งแต่ไม่ถี่ใน corpus ของเอกสารอื่น อาจเป็นคำเฉพาะหรือสำคัญของเอกสารนั้น และนั่นคือที่มาของ IDF

เสริมจากผู้จัดทำ: stop word ไม่ได้ไร้ค่าเสมอ

ประเด็น Pennebaker ที่ผู้พูดแตะไว้เป็นเหตุผลว่าทำไมไม่ควรลบ stop word ทิ้งตายตัว: ในงานสกัด keyword มันเป็นสัญญาณรบกวน แต่ในงานวิเคราะห์ผู้เขียนหรืออารมณ์ มันอาจเป็นสัญญาณหลัก IDF แก้ปัญหานี้โดยไม่ต้องมีรายการ stop word เพราะคำที่อยู่ทุกเอกสารจะถูกกดเป็น 0 เอง (ผู้จัดทำวิเคราะห์)

3. กระดานขั้น 1: IDF แบบ 1 ÷ df (~2:16–3:04)

for (var j = 1; j < allwords.length; j++) {          // word set of every other file, once
  var tempcounts = {};
  var tokens = allwords[j].split(/\W+/);
  for (var k = 0; k < tokens.length; k++) {
    tempcounts[tokens[k].toLowerCase()] = true;
  }
  othercounts.push(tempcounts);
}
for (var i = 0; i < keys.length; i++) {
  var word = keys[i];
  for (var j = 0; j < othercounts.length; j++) {
    if (othercounts[j][word]) counts[word].df++;
  }
  var wordobj = counts[word];
  wordobj.tfidf = wordobj.tf * log(files.length / wordobj.df);   // p5.js log() = ln
}
keys.sort(function (a, b) { return counts[b].tfidf - counts[a].tfidf; });

ข้อควรระวังสำหรับภาษาไทย: split(/\W+/) แยกด้วยอักขระที่ไม่ใช่ตัวอักษรละติน ใช้กับข้อความไทยที่ไม่มีช่องว่างไม่ได้ ต้องตัดคำก่อน (ผูกกับบทเรียนเรื่อง token ของ ZVect)

Key Takeaways

1.กระดานสร้าง IDF เป็นขั้น: 1/df → N/df (คูณ N ไม่เปลี่ยนอัตราส่วน 10 เท่า) → log(N/df) ซึ่งหดช่องว่างเหลือ 2.43 เท่า
2.ภาพกระดาน "= 10 / = 100" ที่ ~3:20 เป็นผลค้างจากขั้น 1/df ภายหลังแก้เป็น 500 และ 5000 ตรงกับที่พูด
3.โค้ดใช้ TF นับดิบ × log(files.length ÷ df) โดย log ของ p5.js คือ ln และ df เริ่มที่ 1 จึงไม่หารศูนย์
4.บั๊กที่แก้บนจอเป็นบทเรียน: = แทน < ในเงื่อนไขลูป, ใช้ index ผิดตัว, เก็บ true แต่เทียบ === 1, ตัวแปร var ชื่อซ้ำ
5.สร้างเซตคำของเอกสารอื่นครั้งเดียว (othercounts) แทนทำใหม่ทุกคำ คือแนวคิดเดียวกับ inverted index
6.ผลบนจอทุกค่าเท่ากับ tf × ln 4: corpus 4 ไฟล์เล็กเกินไป คำบนสุดจึงเป็นคำที่ไม่อยู่ไฟล์อื่นเรียงตาม tf (เช่น or)
