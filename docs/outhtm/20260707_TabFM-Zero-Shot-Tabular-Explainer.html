TabFM: Google's Zero-Shot Tabular AI (no training, no tuning!) — Omar Kamal

✍️ Omar Kamal (YouTube)📅 เผยแพร่ 2026-07-07⏱ 7:57🏷 TabFM · tabular foundation model · in-context learning🧩 โหมด iwd 🔗 คลิปต้นฉบับ (YouTube)

บทสรุปย่อ

คลิปสั้นนี้อธิบายว่า TabFM คือโมเดลสำเร็จรูปสำหรับข้อมูลตาราง (tabular foundation model) จาก Google Research ที่ทำนายผลได้ทันทีโดยไม่ต้องเทรนบนตารางของเรา ไม่ต้องจูนค่า และไม่ต้องทำ feature engineering เอง เพราะมันอ่านแถวที่มีเฉลย (label) เป็นบริบท แล้วอนุมานคำตอบของแถวที่ยังไม่มีเฉลยในการคำนวณรอบเดียว (in-context learning) ผู้ทำคลิปไล่ตั้งแต่แนวคิด สถาปัตยกรรม 3 ขั้น ข้อมูลที่ใช้ pre-train โค้ดแบบ scikit-learn ไปจนถึงผลทดสอบ Titanic และ Bike Sharing และปิดด้วยข้อจำกัดที่ควรรู้ก่อนใช้งาน ข้อสังเกตของผู้จัดทำ: ผลทดสอบสองชุดในคลิปเป็นการรันเองครั้งเดียว ส่วนข้ออ้างเรื่องเหนือกว่าอัลกอริทึมที่จูนมาอย่างหนักมาจาก benchmark ของ Google เอง (ตรวจแล้วตรงกับ blog ต้นทาง)

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึกพร้อมตรวจข้อเท็จจริง (license มาตรฐานของ YouTube; คำบรรยายเป็น ASR อังกฤษ)

สรุปเชิงลึก

ใจความหลัก. งาน ML บนตารางแบบเดิมต้องเลือกโมเดล ออกแบบ feature จูน hyperparameter แล้วเทรนกับตรวจสอบซ้ำทุกครั้งที่ได้ตารางใหม่ ซึ่งได้ผลแต่ช้าและเป็นงานมือ TabFM ใช้แนวคิดเดียวกับ language model คือเทรนครั้งเดียว (pre-train) แล้วใช้ซ้ำกับตารางหลากหลาย โดยเอาแถวที่มี label เป็น "บริบท" วางคู่กับแถวทดสอบที่ยังไม่มี label ให้โมเดลดูรูปแบบแล้วตอบ ไม่มีการอัปเดตน้ำหนักบนตารางของผู้ใช้ การเรียนรู้เกิดใน forward pass ไม่ใช่ training loop

สถาปัตยกรรม. เป็น transformer ผสม 3 ขั้น ขั้นแรกสลับ attention ระหว่างคอลัมน์ (ให้ feature ปะทะกัน เทียบกับความสัมพันธ์ที่ปกติต้องออกแบบเอง) กับระหว่างแถว (ให้ตัวอย่างเทียบกัน) ขั้นสองบีบแต่ละแถวจากตารางของเซลล์ให้เหลือเวกเตอร์หนาแน่นหนึ่งเส้น ซึ่งผู้พูดบอกว่าเป็นกุญแจให้เร็วแม้ตารางใหญ่ขึ้น ขั้นสามเป็น transformer แบบ in-context learning ที่ทำ attention บนเวกเตอร์แถวที่บีบแล้ว (ไม่ใช่ตารางดิบ) จำนวน 24 บล็อก แล้วอ่านผลทำนายออกมา ผู้พูดบอกว่าแนวคิดนี้ต่อยอดจาก TabPFN และ TabICL โดยฝึกในขนาดที่ใหญ่กว่ามาก

ข้อมูลฝึก. ใช้ข้อมูลสังเคราะห์หลายร้อยล้านชุดที่สร้างจาก structural causal model พร้อมฟังก์ชันสุ่ม ผู้พูดบอกว่าวิธีนี้เลี่ยงปัญหาข้อมูลขาดแคลนและเรื่องความเป็นส่วนตัวไปทั้งหมด

วิธีใช้งานและความแม่น. ตอน inference โมเดลต่อแถว train กับแถว test เป็น prompt ก้อนเดียวแล้วรัน forward pass ครั้งเดียว ไม่มีการแบ่ง fold ไม่มี tuning loop ผู้พูดบอกว่าขั้นเตรียมข้อมูลตรวจชนิดคอลัมน์ ทำ encoding และ scaling เติมค่าที่ขาด และตัดค่าโด่ง (ยืนยันจาก README ได้เพียงบางส่วน) เพื่อเพิ่มความแม่นมันสร้างมุมมองของตารางหลายแบบ (สลับลำดับ feature เลื่อนป้ายคลาส เปลี่ยนวิธี normalize) แล้วเฉลี่ยผล ส่วน TabFM ensemble ตัวเต็มเพิ่ม feature cross และ SVD ใช้ ensemble 32 ทางถ่วงน้ำหนักด้วย non-negative least squares และ Platt scaling ปรับความน่าจะเป็น โค้ดหน้าตาเหมือน scikit-learn (โหลดโมเดล หุ้มด้วย TabFMClassifier หรือ TabFMRegressor แล้ว fit กับ predict) โดย fit ไม่ทำ gradient training

ตัวเลขสำคัญ. Titanic: accuracy 80.3% และ AUC 0.852 สูงกว่า gradient boosting กับ logistic regression (สไลด์: accuracy 0.803 / 0.789 / 0.776 และ AUC 0.852 / 0.802 / 0.842) Bike Sharing: RMSE ประมาณ 562 การเช่าต่อวัน และ R² 0.92 (สไลด์ 0.918) ดีกว่า gradient boosting ที่ 667 และ ridge ที่ 814 benchmark ที่ Google รายงาน: 38 ชุดจัดประเภท กับ 13 ชุดถดถอย ขนาด 700 ถึง 150,000 แถว ผู้พูดอ้างว่า Google รายงานว่า TabFM ชนะอัลกอริทึมมาตรฐานที่จูนหนักอย่างสม่ำเสมอเมื่อวัดด้วยคะแนน Elo

ถูก ผิด ขาด (จากการตรวจของผู้จัดทำ). ตรวจข้อเท็จจริง 17 ข้อ: ยืนยัน 11, ยืนยันบางส่วน 2, ไม่พบแหล่งยืนยัน 4, ขัดแย้ง 0 ข้อที่ควรระวังคือคำอธิบายคลิปเขียนว่า TabFM เป็น Apache-2.0 ซึ่งจริงเฉพาะ code ส่วน weights ตั้งต้นใช้ license ไม่อนุญาตเชิงพาณิชย์ และผลทดสอบสองชุดเป็นการรันเองครั้งเดียว (AUC ต่างจาก logistic regression เพียง 0.010) จึงใช้เป็นภาพประกอบ ไม่ใช่หลักฐาน นอกจากนี้ผู้พูดบอกว่าบน GPU ทำนายใช้เวลาไม่กี่วินาที แต่คลิปที่ 2 ในชุดเดียวกัน (ซีพียูล้วน) รายงานว่ากว่า 1 ชั่วโมงครึ่ง

เอาไปทำอะไร. ใช้เป็น baseline เร็ว ๆ และงานต้นแบบกับตารางขนาดเล็กถึงกลาง โดยรู้ขอบเขตก่อน: รุ่นที่ปล่อยรองรับไม่เกิน 10 คลาส จำกัดจำนวน feature และแถวที่อ่าน (ตารางใหญ่ถูกสุ่มย่อย) และพฤติกรรมสะท้อน prior สังเคราะห์ที่เรียนมา

  4. 4. สถาปัตยกรรม 3 ขั้นของ TabFM (~2:05–3:39)

1. ปัญหาของ ML บนตารางแบบเดิมและคำถามตั้งต้น (~0:00–0:40)

ผู้พูดเริ่มด้วยภาพของงาน machine learning บนสเปรดชีตที่ยังเป็นแบบเดิมอยู่ คือทุกครั้งที่ได้ตารางใหม่ต้องเลือกโมเดล ออกแบบ feature ด้วยมือ จูน hyperparameter เป็นกองใหญ่ แล้วเทรนและตรวจสอบซ้ำแล้วซ้ำอีก ได้ผลก็จริงแต่ช้าและเป็นงานมือ

จากนั้นตั้งคำถามว่า ถ้าโมเดลอ่านตารางของเราได้เหมือนที่ language model อ่านย่อหน้า แล้วให้ผลทำนายออกมาตรง ๆ ได้จะเป็นอย่างไร โดยไม่ต้องเทรนบนข้อมูลของเรา ไม่ต้องจูน ได้คำตอบในรอบเดียว นี่คือโจทย์ที่ TabFM ตอบ

2. Foundation model สำหรับตาราง และกลไก in-context learning (~0:40–1:30)

language model ถูกเทรนครั้งเดียวแล้วเอาไปใช้ซ้ำกับงานนับไม่ถ้วน TabFM เอาแนวคิด foundation model เดียวกันมาใช้กับข้อมูลตาราง คือโมเดลเดียวที่ pre-train ครั้งเดียวแล้วใช้ได้ทันทีกับตารางหลายแบบ

เคล็ดลับคือ in-context learning แทนที่จะอัปเดตน้ำหนัก TabFM ถือแถว train ที่มี label เป็นบริบท อ่านแถว test ที่ยังไม่มี label ที่วางอยู่ข้างกัน แล้วอนุมานคำตอบจากรูปแบบที่เห็น การเรียนรู้เกิดใน forward pass ไม่ใช่ใน training loop

ผู้พูดสรุปเป็นประโยคเดียวว่า TabFM คือโมเดลที่เข้ากับ scikit-learn ทำ classification และ regression แบบ zero-shot บนตารางชนิดคอลัมน์ผสม รวมถึงค่าที่ขาด โดยไม่เคยเทรนบนชุดข้อมูลของเรา

เสริมจากผู้จัดทำ

คำว่า zero-shot ในที่นี้หมายถึงไม่เทรนหรือปรับน้ำหนักบนชุดข้อมูลของผู้ใช้ ไม่ได้แปลว่าโมเดลไม่ต้องเห็นข้อมูลของผู้ใช้เลย เพราะแถว train ที่มี label ยังต้องส่งเข้าไปเป็นบริบททุกครั้ง

3. ที่มาของแนวคิดและข้อมูลสังเคราะห์ที่ใช้ pre-train (~1:30–2:05)

ผู้พูดบอกว่า TabFM ไม่ได้โผล่ขึ้นมาจากความว่างเปล่า มันต่อยอดจาก TabPFN (prior-data fitted network ที่ตีพิมพ์ใน Nature) และจากการทำ in-context learning อย่างมีประสิทธิภาพของ TabICL แล้วนำความคิดทั้งสองมารวมกันและฝึกในขนาดที่ใหญ่กว่ามาก

คำถามถัดมาคือจะ pre-train โมเดลให้ครอบคลุมตารางทุกแบบได้อย่างไร คำตอบในคลิปคือ "สร้างขึ้นเอง" TabFM ถูกฝึกบนข้อมูลสังเคราะห์หลายร้อยล้านชุดที่สร้างจาก structural causal model พร้อมฟังก์ชันสุ่ม ซึ่งผู้พูดบอกว่าเลี่ยงปัญหาข้อมูลขาดแคลนและเรื่องความเป็นส่วนตัวไปทั้งหมด

ข้อที่ควรเข้าใจให้ตรง

หมายเหตุจากผู้จัดทำ: คำบรรยายอัตโนมัติสะกดชื่อผิดหลายจุด: "Tab SEAL" และ "TabSEO" (ที่ 1:38 และ 3:08) หมายถึง TabICL ซึ่ง blog ของ Google ระบุว่าเป็นหนึ่งในสองงานที่ TabFM ต่อยอด; "dation model" (0:45) คือ foundation model

4. สถาปัตยกรรม 3 ขั้นของ TabFM (~2:05–3:39)

ผู้พูดเรียกมันว่า hybrid transformer 3 ขั้น ภาพรวมคือตารางเข้าที่ด้านล่าง ขั้นแรก attention ทำงานข้ามทั้งคอลัมน์และแถว ขั้นที่สองบีบแต่ละแถวให้เป็นเวกเตอร์หนาแน่นหนึ่งเส้น ขั้นสุดท้ายมี transformer เฉพาะที่ทำ in-context learning บนเวกเตอร์เหล่านั้นแล้วอ่านผลทำนายออกมา

ขั้น 1 (2:33–2:52). สลับ attention สองแบบ column attention ให้ feature ปะทะกันเอง จับความสัมพันธ์ที่ปกติต้องออกแบบเป็น feature ด้วยมือ ส่วน row attention ให้ตัวอย่างเทียบกันเอง การสลับไปมาสร้างตัวแทนข้อมูลที่รับรู้โครงสร้างตาราง

ขั้น 2 (2:52–3:06). บีบแต่ละแถวจากตารางของเซลล์ให้เป็นเวกเตอร์หนาแน่นเส้นเดียว ลดสิ่งที่ขั้นถัดไปต้องประมวลผลลงมาก และผู้พูดบอกว่านี่คือกุญแจที่ทำให้ TabFM เร็วแม้บนตารางที่ใหญ่ขึ้น

ขั้น 3 (3:06–3:24). ตามแนวทางของ TabICL (ในคำบรรยายสะกดเป็น "TabSEO") transformer ทำ attention บนเวกเตอร์แถวที่บีบแล้ว ไม่ใช่ตารางดิบ ซึ่งลดการคำนวณลงมาก บล็อกแบบนี้ 24 บล็อกให้แถวบริบทส่งข้อมูลถึงทุกแถวที่ต้องทำนายก่อนจะอ่านผลออก

ในเชิงรูปนัย (3:24) ผู้พูดบอกว่าผลทำนายแต่ละตัวคือ posterior ของ label ที่มีเงื่อนไขเป็นทั้งชุดข้อมูล และกลไกที่ขับมันคือ scaled dot-product attention ซึ่งใช้ query, key, value ที่ normalize ด้วย softmax

5. ตอน inference และการเตรียมข้อมูล (~3:39–4:11)

ตอนใช้งานจริง TabFM ต่อแถว train กับแถว test เข้าด้วยกันเป็น prompt ก้อนใหญ่ก้อนเดียวแล้วรัน forward pass ครั้งเดียว ไม่มีการแบ่ง fold ไม่มี tuning loop ผู้พูดสรุปว่า "บริบทคือการเทรน" และคำตอบออกมาตรง ๆ

ตารางจริงรก และผู้พูดบอกว่าขั้นเตรียมข้อมูลของ TabFM รับมือกับความรกนั้น มันตรวจชนิดคอลัมน์ (categorical, numeric, datetime) เอง ทำ encoding และ scaling เติมค่าที่ขาด และตัดค่าโด่ง ทั้งหมดนี้ก่อนข้อมูลเข้าเครือข่าย

เสริมจากผู้จัดทำ

ส่วนการเตรียมข้อมูลนี้เรายืนยันจากแหล่งที่อ่านได้เพียงบางส่วน: README ของ GitHub กล่าวถึงเพียงว่า fit เตรียม ordinal encoder และ numerical scaler ส่วนการเติมค่าขาดและตัดค่าโด่งไม่พบคำอธิบาย (ดูตารางตรวจข้อเท็จจริง) จึงควรถือเป็นคำบอกเล่าของผู้ทำคลิปไว้ก่อน

6. Ensemble: มุมมองหลายแบบและ TabFM ตัวเต็ม (~4:11–4:48)

เพื่อความแม่นเพิ่ม TabFM ไม่ดูตารางเพียงรอบเดียว มันสร้างมุมมองที่หลากหลายของตารางเดียวกัน ด้วยการสลับลำดับ feature เลื่อนป้ายคลาส และเปลี่ยนวิธี normalize แล้วเฉลี่ยผลทำนาย ผู้พูดเรียกว่าเป็น bagging แต่ทำกับการแทนข้อมูลแทนที่จะทำกับตัวโมเดล

TabFM ensemble ตัวเต็มไปไกลกว่านั้น: เพิ่ม feature cross ที่ออกแบบขึ้น และองค์ประกอบ SVD ใช้ ensemble 32 ทาง ผสมสมาชิกด้วย non-negative least squares และใช้ Platt scaling ปรับความน่าจะเป็นของคลาสให้ตรงกับความเป็นจริง (calibrate)

เสริมจากผู้จัดทำ

ตามที่ blog ของ Google อธิบาย (และที่คลิปที่ 2 ในชุดนี้ย้ำ) TabFM-Ensemble เป็นอีกการตั้งค่าหนึ่งที่ใช้ประเมินใน benchmark ไม่ใช่ค่าเริ่มต้นของแพ็กเกจ ผู้ทำคลิปนี้ไม่ได้แยกสองอย่างนี้ให้ชัด

7. โค้ด: หน้าตาเหมือน scikit-learn (~4:48–5:41)

ผู้พูดบอกว่าส่วนที่ดีที่สุดคือโค้ดน้อยมาก เพราะหน้าตาเหมือน scikit-learn ทุกอย่าง การจัดประเภทใช้หกบรรทัด: โหลดโมเดลที่ pre-train แล้ว หุ้มด้วย TabFM classifier เรียก fit แล้ว predict และย้ำว่า fit ไม่ทำ gradient training มันแค่เตรียม encoder และจำแถวของเราไว้เป็นบริบท

งานถดถอยเป็นเรื่องเดียวกัน: เปลี่ยนชนิดโมเดลเป็น regression ใช้ TabFM regressor แล้ว fit กับ predict API เดียวกัน เปลี่ยนแค่หัว (head)

TabFM มาพร้อม backend สองแบบที่สลับกันได้คือ JAX กับ PyTorch และดาวน์โหลด weights ที่ pre-train แล้วจาก Hugging Face Hub อัตโนมัติเมื่อโหลดครั้งแรก ผู้พูดบอกว่าบน GPU การทำนายใช้เวลาไม่กี่วินาที

เสริมจากผู้จัดทำ

โค้ดบนสไลด์ (5:00–5:10) ใช้การ import แบบ from tabfm import TabFMClassifier, tabfm_v1_0_0_jax แล้วเรียก model = tabfm_v1_0_0_jax.load(model_type="classification"), clf = TabFMClassifier(model=model), clf.fit(X_train, y_train) และ proba = clf.predict_proba(X_test) สไลด์เน้นว่าบรรทัด fit เป็น "NO gradient training" นี่เป็นเนื้อหาที่เห็นเฉพาะบนสไลด์ ผู้พูดไม่ได้อ่านชื่อฟังก์ชันออกเสียง

8. ผลทดสอบ Titanic และ Bike Sharing (~5:41–6:32)

ผู้พูดทดสอบกับชุดข้อมูลคลาสสิกสองชุด: Titanic (จัดประเภทการรอดชีวิต) และ Bike Sharing (ถดถอยปริมาณความต้องการรายวัน) เทียบ TabFM แบบ zero-shot กับ baseline ที่แข็งบน split เดียวกัน

บน Titanic ผู้พูดบอกว่า TabFM ได้ accuracy 80.3% และ AUC 0.852 เหนือ gradient boosting และ logistic regression เล็กน้อย โดยไม่เคยถูกเทรนบน Titanic เลย

บน Bike Sharing ผู้พูดบอกว่า TabFM ทำนายความต้องการรายวันได้ที่ root mean squared error ประมาณ 562 การเช่า และ R² 0.92 ชัดเจนว่านำหน้า gradient boosting และ ridge regression อีกครั้งที่เป็น zero-shot

เสริมจากผู้จัดทำ

ตัวเลขจากสไลด์ที่ผู้พูดไม่ได้อ่านออกเสียง: Titanic accuracy ของ gradient boosting 0.789 และ logistic regression 0.776, AUC 0.802 และ 0.842; Bike Sharing RMSE ของ gradient boosting 667 และ ridge 814, R² 0.884 และ 0.828 ข้อสังเกตของผู้จัดทำ: AUC ของ TabFM นำ logistic regression เพียง 0.010 บน split เดียว และคลิปไม่ระบุ seed หรือจำนวนแถวทดสอบ จึงยังสรุปไม่ได้ว่าชนะอย่างมีนัยสำคัญ

9. Benchmark ที่ Google รายงาน และงานที่เหมาะ (~6:32–7:08)

ผู้พูดบอกว่าสองชุดข้อมูลเป็นเพียงตัวอย่างรสชาติ บน TabArena (ในคำบรรยายสะกดเป็น "Tabularina") benchmark ที่ปรับปรุงต่อเนื่องซึ่งมี 38 ชุดจัดประเภทและ 13 ชุดถดถอย ขนาดตั้งแต่ 700 ถึง 150,000 แถว Google รายงานว่า TabFM ชนะอัลกอริทึมมาตรฐานของอุตสาหกรรมที่จูนมาอย่างหนักอย่างสม่ำเสมอเมื่อวัดด้วยคะแนน Elo

ที่ที่มันช่วยได้มากที่สุดตามคลิป: baseline ที่แข็งทันที งานต้นแบบเร็ว และตารางขนาดเล็กถึงกลางที่การตั้ง training pipeline เต็มรูปแบบไม่คุ้ม ได้โมเดลที่แข่งขันได้ในไม่กี่วินาที

เสริมจากผู้จัดทำ

เมื่อเทียบกับ blog ต้นทาง ข้ออ้างเรื่อง Elo ตรงกับแผนภูมิของ Google (ดูตารางตรวจข้อเท็จจริง) แต่คำว่า "ชนะอย่างสม่ำเสมอ" มาจาก benchmark ที่ Google เป็นผู้รายงานเอง ไม่ใช่การทดสอบอิสระ

10. ข้อจำกัดและบทสรุป (~7:08–7:48)

ผู้พูดย้ำว่า "มันไม่ใช่เวทมนตร์" รุ่นที่ปล่อยรองรับสูงสุด 10 คลาส และจำกัดจำนวน feature กับแถวที่อ่าน ตารางใหญ่มากจึงถูกสุ่มย่อย และเหมือนโมเดล pre-train ทั่วไป พฤติกรรมของมันสะท้อน prior สังเคราะห์ที่ได้เรียนมา ควรรู้ขอบเขตก่อนนำไปใช้จริง

สรุปของคลิป: TabFM อ่านตารางแล้วทำนายโดยไม่ต้องเทรน รวม row และ column attention กับ in-context learning ที่มีประสิทธิภาพ ใช้ง่ายแบบ scikit-learn และสู้ baseline ที่จูนแล้วได้ ผู้พูดเรียกมันว่า foundation model สำหรับข้อมูลตารางตัวจริง

เสริมจากผู้จัดทำ

ข้อมูลที่คลิปไม่ได้พูดแต่ควรรู้ก่อนใช้งาน: weights ตั้งต้นของ TabFM ใช้ license ที่ไม่อนุญาตเชิงพาณิชย์และ production (code เป็น Apache-2.0) และ GitHub README ระบุค่าเริ่มต้น max_num_rows 100 ซึ่งหมายถึงแถวบริบทต่อการประมาณหนึ่งครั้ง (ตามที่เครื่องมืออ่านเว็บรายงาน) ตรวจเงื่อนไขล่าสุดที่หน้า repo ก่อนใช้

Key Takeaways

1.TabFM ทำนายโดยไม่ปรับน้ำหนักบนตารางของเรา: แถวที่มี label เป็นบริบท แถวทดสอบถูกอ่านต่อท้าย แล้วได้คำตอบใน forward pass ครั้งเดียว
2.โครงสร้างสามขั้น (สลับ attention คอลัมน์/แถว → บีบแถวเป็นเวกเตอร์ → ICL transformer 24 บล็อก) คือตัวทำให้เร็วและเข้าใจโครงสร้างตาราง ผู้พูดบอกว่าขั้นบีบแถวเป็นกุญแจของความเร็วบนตารางที่ใหญ่ขึ้น
3.ถูกฝึกบนข้อมูลสังเคราะห์หลายร้อยล้านชุด จึงเลี่ยงปัญหาข้อมูลขาดแคลนและความเป็นส่วนตัวตามที่ผู้พูดบอก แต่พฤติกรรมสะท้อน prior สังเคราะห์นั้น
4.ผลที่คลิปโชว์ (Titanic, Bike Sharing) เป็นการรันเองครั้งเดียว ส่วนข้ออ้างเหนืออัลกอริทึมที่จูนหนักมาจาก benchmark ของ Google และตรงกับแผนภูมิใน blog
5.ก่อนใช้: รุ่นที่ปล่อยรองรับไม่เกิน 10 คลาส มีเพดานจำนวน feature และแถว และ weights ตั้งต้นไม่อนุญาตเชิงพาณิชย์ (คลิปไม่ได้พูดเรื่อง license)
