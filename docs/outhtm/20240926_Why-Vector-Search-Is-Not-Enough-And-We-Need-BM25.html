บทสรุปย่อ

Diffbot อธิบายว่าทำไม vector search (การค้นโดยแปลงข้อความเป็นชุดตัวเลขแล้วหาชุดที่อยู่ใกล้กัน) จึงทำงานไม่ดีกับการคำนวณ การเรียงลำดับ และการกรอง ต้นเหตุคือ embedding วางตัวเลข คำบอกเวลา และคำทั่วไปตามบริบทที่เคยเห็น ไม่ได้วางบนเส้นจำนวนหรือเส้นเวลา และยังขยับตามบริบทจนผลค้นกว้างเกินไปได้ ครึ่งหลังของคลิปจึงแนะนำ BM25 ซึ่งใช้ sparse vector จับคำตรงตัว แล้วให้คะแนนด้วยสามกลไก คือความถี่ที่อิ่มตัว ความหายากของคำ (IDF) และการปรับตามความยาวเอกสาร เพื่อใช้เสริม vector search

สรุปเชิงลึก

ผู้สอนเปิดด้วยข้อสังเกตว่า vector search เองทำงานได้ไม่ดีกับงานคำนวณ การเรียงลำดับ และการกรอง แล้วไล่เหตุผลเป็นสามชั้น ชั้นแรกคืออาการ คนเราเห็น 50, 100 และ 150 แล้วรู้ว่าห่างกันช่วงละ 50 แต่ LLM (โมเดลภาษาขนาดใหญ่) วางตัวเลขตามบริบทที่เลขนั้นถูกใช้ ตำแหน่งของ 100 จึงไม่จำเป็นต้องอยู่กลางระหว่าง 50 กับ 150 และ 50 อาจไปอยู่ใกล้คำอย่าง half ส่วน 100 อาจอยู่ใกล้ full หรือ century โมเดลอาจรู้ว่า "100-day challenge" โดยทั่วไปยาวกว่า "30-day challenge" แต่ทิศของผลต่างอาจเก็บความหมายอย่าง "ความมุ่งมั่น" หรือ "ระยะเวลา" มากกว่าผลต่าง 70 วันจริง ผลคือ ChatGPT หรือ Claude คูณเลขยาวที่ไม่ค่อยเห็นแล้วพลาด แต่ตอบ 150 − 100 ถูกเพราะจำได้จากตอนฝึก คำบอกเวลาก็เช่นกัน latest อาจอยู่ใกล้ newest หรือ current เพราะมักใช้คู่กัน ไม่ใช่เพราะโมเดลรู้ลำดับเวลา และการหาค่าสูงสุดหรือต่ำสุดต้องเทียบเวกเตอร์จำนวนมาก จึงอาจค่อนข้างกินการคำนวณเมื่อข้อมูลโตขึ้น

ชั้นที่สองคือต้นเหตุ ซึ่งผู้สอนให้ไว้สองข้อ:

  • ตัวเลขที่ไม่ค่อยพบ เช่น 3458723098 ถูกตัดเป็นชิ้นข้อความหลายชิ้นเหมือนคำทั่วไป และตัดได้หลายแบบ แบบไหนขึ้นกับการฝึกของโมเดลมาก และไม่มีอะไรรับประกัน
  • embedding ของข้อความขยับตามบริบท ความยืดหยุ่นนี้ช่วยหาแนวคิดที่เกี่ยวข้องได้โดยไม่ต้องมีคำตรงกัน แต่บางครั้งก็ทำให้ผลไม่แม่น คำค้น apple pie อาจได้สูตร cherry pie, peach pie หรือแม้แต่ meat pie กลับมา

ชั้นที่สามคือทางเสริม dense vector ทุกช่องมีค่าและรวมกันบอกตำแหน่งความหมาย ส่วน sparse vector ของ BM25 เกือบทุกช่องเป็นศูนย์ มีค่าเฉพาะช่องของคำที่ปรากฏ จึงเหมาะกับการจับคำตรงตัว BM25 ยังให้คะแนนด้วยสามกลไกที่แก้จุดอ่อนบางข้อของ TF-IDF:

  1. ความถี่อิ่มตัว: หลังเกินจุดหนึ่ง เอกสารที่พูดคำ RAG 50 ครั้งจะไม่ได้เปรียบเอกสารที่พูด 10 ครั้ง การยัดคำซ้ำจึงไม่ช่วย
  2. IDF: คำที่พบแทบทุกเอกสารอย่าง the หรือ system ได้น้ำหนักต่ำ ส่วนคำเฉพาะอย่าง hybrid search ได้น้ำหนักสูง
  3. ความยาวเอกสาร: BM25 ปรับคะแนนตามความยาว เพราะเอกสารยาวไม่จำเป็นต้องให้ข้อมูลมากกว่า และเอกสารสั้นอาจได้คะแนนสูงกว่าเมื่อความถี่คำเท่ากัน

สิ่งที่ตรวจแล้ว: ตรวจ 8 ข้อ ยืนยัน 7 · ยืนยันบางส่วน 1 · ไม่พบ 0 · ขัดแย้ง 0 ข้อที่ยืนยันบางส่วนคือเรื่องตัวเลข งานวิจัยพบว่า embedding ยังเก็บขนาดของตัวเลขไว้ได้คร่าว ๆ เส้นจำนวนจึง "หยาบ" มากกว่า "ไม่มี" (ผู้จัดทำ: คลิปเองก็พูดอย่างระวังว่า "ไม่จำเป็นต้อง" อยู่กลาง) ส่วนเรื่องที่คลิปไม่ได้พูดแต่ควรรู้ คำอธิบายคลิประบุว่า metadata filtering เป็นทางแก้การเรียงและกรองที่ใช้ได้แต่ไม่ได้อธิบายในคลิป และ Anthropic ใช้ embedding คู่ BM25 ใน Contextual Retrieval

(ผู้จัดทำ) สำหรับระบบค้นอย่าง ZVect (โปรเจกต์บทเรียนเรื่อง vector search พร้อมไลบรารี JavaScript ด้าน embedding, BM25 และ hybrid search) หรือ RAG (ระบบที่ดึงเอกสารมาให้ LLM ใช้ตอบ) ข้อสรุปที่ใช้ได้ทันทีคือ ให้ vector search หาความหมาย ให้ BM25 จับคำเฉพาะ รหัส และชื่อ แล้วรวมอันดับสองทาง ส่วนคำถามที่ต้องเรียง กรอง หรือคำนวณ ให้ส่งไปที่ฟิลด์ข้อมูลหรือเครื่องมือคำนวณแทนการหวังให้เวกเตอร์ทำ

ผังภาพรวม

ในภาพนี้:

  1. กล่องแรกคืออาการที่คลิปเปิดไว้ คือ vector search ทำงานได้ไม่ดีกับการคำนวณ การเรียงลำดับ และการกรอง (หัวข้อ 1–2)
  2. กล่องที่สองบอกเหตุผลของอาการ คือ embedding วางตัวเลขและคำบอกเวลาตามบริบท ไม่ได้วางบนเส้นจำนวนหรือเส้นเวลา
  3. กล่องที่สามคือต้นเหตุสองข้อ ได้แก่ การตัดเลขยาวที่ไม่ค่อยพบเป็นหลายชิ้น และตำแหน่งที่ขยับตามบริบท ซึ่งทำให้ผลค้นกว้างเกินไปในกล่องที่สี่ (หัวข้อ 3)
  4. กล่องที่เน้นสีคือ sparse vector ซึ่งมีค่าเฉพาะคำที่ปรากฏ จึงเป็นจุดเปลี่ยนจากปัญหาไปสู่ทางแก้ (หัวข้อ 4)
  5. กล่องคะแนน BM25 รวมสามกลไกเพื่อจัดอันดับ และกล่องสุดท้ายคือการใช้ BM25 เสริม vector search (หัวข้อ 5)

ภาพนี้บอกว่า คลิปเดินจากอาการ ไปหาต้นเหตุ แล้วจึงเสนอ BM25 เป็นตัวเสริม ไม่ใช่ตัวแทน vector search

ใจความ: ผู้สอนเปิดคลิปว่า vector search (การค้นที่แปลงข้อความเป็นชุดตัวเลข แล้วหาเอกสารที่ชุดตัวเลขอยู่ใกล้กัน) ทำงานได้ไม่ดีกับการคำนวณ การเรียงลำดับ และการกรอง ชุดตัวเลขที่แทนความหมายนี้เรียกว่า embedding และ vector search ใช้มันวัดความใกล้ เพื่ออธิบายว่าทำไม ผู้สอนเริ่มจากตัวเลข คนเราเห็น 50, 100 และ 150 แล้วเข้าใจทันทีว่าแต่ละช่วงห่างกัน 50 เท่ากัน แต่ LLM (โมเดลภาษาขนาดใหญ่อย่าง ChatGPT หรือ Claude) ไม่ได้วางตัวเลขบนเส้นจำนวน มันวางตัวเลขตามบริบทที่ตัวเลขนั้นถูกใช้ ตำแหน่งของ 100 จึงไม่จำเป็นต้องอยู่กลางระหว่าง 50 กับ 150 (ผู้จัดทำ: หมายความว่าคำถามที่ต้องใช้ขนาดของตัวเลขจริง ๆ จะตอบด้วยความใกล้ของเวกเตอร์ได้ไม่ดี)

ตัวเลขสามตัว 50, 100 และ 150 ซึ่งบนเส้นจำนวนห่างกันช่วงละ 50 และคู่วลี "100-day challenge" (ภารกิจ 100 วัน) กับ "30-day challenge" (ภารกิจ 30 วัน) ซึ่งต่างกัน 70 วัน

ในภาพนี้:

  1. เส้นแนวนอนสีขาวคือเส้นจำนวน มีขีดกำกับตัวเลข 50, 100 และ 150 เรียงจากซ้ายไปขวา
  2. ลูกศรสีแดงลูกแรกพาจาก 50 ไป 100 และลูกที่สองพาจาก 100 ไป 150 ทั้งสองยาวเท่ากัน ซึ่งหมายถึงการเพิ่มครั้งละ 50 หน่วย
  3. ระยะบนเส้นนี้คือผลต่างทางเลขคณิตโดยตรง ใครเห็นก็อ่านได้ว่า 100 อยู่กึ่งกลางพอดี

ภาพนี้บอกว่า คนเรามองตัวเลขเป็นจุดบนเส้นที่ห่างกันตามผลต่างจริง ซึ่งเป็นภาพที่ LLM ไม่ได้ใช้ และเป็นจุดตั้งต้นที่ผู้สอนใช้เทียบตลอดหัวข้อนี้

ใน vector space (พื้นที่หลายมิติที่ embedding แต่ละตัวเป็นจุดหรือลูกศรหนึ่งเส้น) ผู้สอนบอกว่าตัวเลขอาจไปจับกลุ่มกับคำที่เกี่ยวข้องตามรูปแบบที่โมเดลเรียนจากข้อมูลฝึก เช่น 50 อาจอยู่ใกล้คำว่า half หรือ midpoint (ครึ่ง, จุดกึ่งกลาง) และ 100 อาจอยู่ใกล้ full หรือ century (เต็ม, ศตวรรษ) ภาพถัดไปวาด embedding จริงของสามตัวเลขนี้ให้ดู

ในภาพนี้:

  1. หัวข้อซ้ายบนเขียนว่า 3D vector space with reduced dimensions หมายถึงพื้นที่เวกเตอร์ที่ถูกย่อเหลือสามมิติเพื่อวาดให้ตาเห็นได้
  2. โค้ดมุมขวาบนโหลดเวกเตอร์คำสำเร็จรูป glove-wiki-gigaword-50 ด้วย gensim (ไลบรารี Python สำหรับโหลดและใช้เวกเตอร์คำ) ดึงเวกเตอร์ของข้อความ "50", "100" และ "150" แล้วใช้ PCA (วิธีย่อมิติที่เก็บทิศที่ข้อมูลต่างกันมากที่สุด) ย่อเหลือ 3 มิติ (ผู้จัดทำ: เลข 50 ในชื่อโมเดลคือจำนวนมิติของเวกเตอร์ ไม่เกี่ยวกับตัวเลข 50 ที่นำมาวาด)
  3. ลูกศรสีฟ้าชี้ไปที่ 50 ทางขวาล่าง ลูกศรสีเขียวที่สั้นกว่าชี้ไปที่ 100 ทางขวาบน และลูกศรสีแดงชี้ไปที่ 150 ทางซ้าย สามเส้นจึงไปคนละทิศ
  4. ไม่มีเส้นใดเรียงต่อกันเป็นแนวเดียวแบบเส้นจำนวน และลูกศรของ 100 ก็ไม่ได้อยู่กลางระหว่างอีกสองเส้น

ภาพนี้บอกว่า ในภาพ 3 มิติที่ย่อมาด้วย PCA นี้ ลูกศรของสามตัวเลขไม่ได้เรียงให้เห็นลำดับ 50 < 100 < 150 (ผู้จัดทำ: การย่อจาก 50 มิติเหลือ 3 มิติทิ้งข้อมูลไปส่วนหนึ่ง ภาพนี้จึงบอกเรื่องลำดับได้จำกัด และกล่อง "ข้อที่ควรเข้าใจให้ตรง" ท้ายหัวข้อนี้เล่าว่างานวิจัยพบว่า GloVe ยังเก็บขนาดของเลขไว้คร่าว ๆ)

ผู้สอนบอกต่อว่าแนวคิดคล้ายกันนี้ใช้กับวิธีที่โมเดลภาษาจัดการคำและความสัมพันธ์ของคำด้วย ในตัวอย่างที่มีชื่อเสียง ทิศของผลต่างระหว่างเวกเตอร์ของ king กับ queen ขนานกันอย่างใกล้เคียงกับผลต่างระหว่าง man กับ woman ทิศนั้นจึงเก็บความหมายเรื่องเพศไว้ ผู้จัดทำเขียนคำพูดนี้เป็นสมการ โดยใช้สัญลักษณ์ E แบบเดียวกับภาพถัดไป

สมการ: ผลต่างของ king กับ queen ชี้ทิศเดียวกับผลต่างของ man กับ woman (ผู้จัดทำเขียนจากคำพูด ~0:54)

สมการ 1E(king)−E(queen)≈E(man)−E(woman)E(\text{king}) - E(\text{queen}) \approx E(\text{man}) - E(\text{woman})E(king)−E(queen)≈E(man)−E(woman)
สัญลักษณ์ความหมายในตัวอย่าง
Eembedding คือเวกเตอร์ที่แทนความหมายของคำในวงเล็บE(king) คือลูกศรของคำ king
kingคำว่า กษัตริย์ (ชาย)จุดเริ่มของผลต่างคู่แรก
queenคำว่า ราชินี (หญิง)ปลายของผลต่างคู่แรก
manคำว่า ผู้ชายจุดเริ่มของผลต่างคู่ที่สอง
womanคำว่า ผู้หญิงปลายของผลต่างคู่ที่สอง

วิธีอ่าน: ลบเวกเตอร์คำที่สองออกจากคำแรกในแต่ละข้าง แล้วเทียบว่าลูกศรผลต่างทั้งสองชี้ทิศใกล้กัน เครื่องหมาย ≈ แปลว่า "ใกล้เคียง" ไม่ใช่เท่ากันพอดี

ในภาพนี้:

  1. บรรทัดบนบอกว่าผลต่างของเวกเตอร์เก็บแนวคิดเรื่องเมืองหลวงไว้ได้
  2. ฝั่งซ้ายของบรรทัดล่างคือเวกเตอร์ของ France (ประเทศฝรั่งเศส) ลบด้วยเวกเตอร์ของ Paris (เมืองหลวงของฝรั่งเศส)
  3. ฝั่งขวาคือเวกเตอร์ของ Poland (ประเทศโปแลนด์) ลบด้วยเวกเตอร์ของ Warsaw (เมืองหลวงของโปแลนด์) และเครื่องหมาย ≈ บอกว่าสองผลต่างนี้ใกล้เคียงกัน

ภาพนี้บอกว่า ความสัมพันธ์ "ประเทศ กับ เมืองหลวง" กลายเป็นทิศหนึ่งในพื้นที่เวกเตอร์ (ผู้จัดทำ: ทิศนี้เกิดจากบริบทที่คำเหล่านี้ถูกใช้ในข้อมูลฝึก)

สมการ: ผลต่างระหว่างประเทศกับเมืองหลวงของมันชี้ทิศใกล้กัน เช่น ฝรั่งเศส–ปารีส กับ โปแลนด์–วอร์ซอ (บนจอ ~1:08)

สมการ 2E(France)−E(Paris)≈E(Poland)−E(Warsaw)E(\text{France}) - E(\text{Paris}) \approx E(\text{Poland}) - E(\text{Warsaw})E(France)−E(Paris)≈E(Poland)−E(Warsaw)
สัญลักษณ์ความหมายในตัวอย่าง
Eembedding ของคำในวงเล็บE(Paris) คือเวกเตอร์ของคำ Paris
Franceชื่อประเทศฝรั่งเศสตัวตั้งของผลต่างคู่แรก
Parisเมืองหลวงของฝรั่งเศสตัวลบของผลต่างคู่แรก
Polandชื่อประเทศโปแลนด์ตัวตั้งของผลต่างคู่ที่สอง
Warsawเมืองหลวงของโปแลนด์ตัวลบของผลต่างคู่ที่สอง

กลับมาที่ตัวเลข ผู้สอนบอกว่า LLM อาจเข้าใจได้ว่า 100-day challenge โดยทั่วไปยาวกว่า 30-day challenge แต่ความเข้าใจนี้ไม่ได้มาจากการรู้ว่า 100 มากกว่า 30 ทิศของผลต่างระหว่างสองวลีนี้อาจจับแนวคิดอย่าง "ความมุ่งมั่น" หรือ "ระยะเวลา" ได้ แทนที่จะเก็บผลต่างจริง 70 วัน

ในภาพนี้:

  1. ข้อความมุมซ้ายบนบอกว่าภาพนี้เป็นภาพประกอบเท่านั้น ตำแหน่งของลูกศรไม่ใช่เวกเตอร์จริง
  2. ลูกศรสีเขียวยาวชี้ขึ้นไปที่ป้าย 30-day challenge ส่วนป้าย 100-day challenge วางอยู่ทางซ้ายของภาพ และลูกศรสีแดงสั้นใกล้พื้นเป็นเวกเตอร์อีกเส้นของคู่นี้ (ผู้จัดทำ: ภาพไม่ได้ลากเส้นโยงป้าย 100-day challenge กับลูกศรไว้ชัด และความยาวของลูกศรในภาพไม่ได้แทนจำนวนวัน ลูกศรของ 30 วันที่ดูยาวกว่าจึงไม่ได้มีความหมายอะไร ให้ดูเฉพาะลูกศรสีเหลืองในข้อถัดไป ซึ่งคือผลต่าง)
  3. ลูกศรสีเหลืองลากจากปลายลูกศรสีเขียวไปที่ปลายลูกศรสีแดง ซึ่งคือผลต่างของสองเวกเตอร์ ทิศของลูกศรนี้คือสิ่งที่ผู้สอนบอกว่าอาจเก็บความหมายอย่าง "ความมุ่งมั่น" หรือ "ระยะเวลา" ไว้

ภาพนี้บอกว่า สิ่งที่โมเดลเก็บจากคู่วลีนี้คือทิศของความหมาย ไม่ใช่ตัวเลข 70 วัน โมเดลจึงอาจตอบได้ว่าอันไหนยาวกว่า โดยไม่ได้รู้ว่ายาวกว่ากันเท่าไร

ผู้สอนเตือนว่าเรื่องนี้อาจทำให้คิดว่า LLM คิดเลขไม่เก่ง แต่สิ่งที่เกิดขึ้นจริงคือตัวเลขถูกประมวลผลเป็นส่วนหนึ่งของภาษา ไม่ได้ถูกใช้เป็นค่าตัวเลขจริง ผลคือโมเดลแบบ Transformer (สถาปัตยกรรมของโครงข่ายที่อยู่เบื้องหลัง LLM ยุคปัจจุบัน) อย่าง ChatGPT หรือ Claude คำนวณได้ไม่ถูกเมื่อเจอตัวเลขสุ่มที่ไม่ค่อยเห็นมาก่อน แต่ถ้าเป็นการคำนวณง่าย ๆ ที่เคยเรียนตอนฝึก เช่น 150 − 100 ก็ดึงคำตอบที่ถูกจากความจำได้เร็ว สองภาพถัดไปเป็นหลักฐานของทั้งสองกรณี

  1. ผู้ใช้ส่งโจทย์คูณเลขยาวสองจำนวน คือ 3587457634354 กับ 123984756
  2. Claude ตอบว่าจะคิดทีละขั้น เขียนผลคูณย่อยออกมาหลายแถว และสรุปว่าคำตอบคือ 444,807,477,290,660,344,704 พร้อมอ้างว่าตรวจกับเครื่องคิดเลขแล้วถูก
  3. กรอบสีแดงล้อมคำตอบนั้นไว้เทียบกับเครื่องคิดเลขจริงด้านล่าง ซึ่งแสดง 4.447900594557179e20 คือราว 444,790,059,455,717,9xx,xxx ตัวเลขต่างกันตั้งแต่หลักที่สี่

ภาพนี้บอกว่า ความใกล้ในพื้นที่เวกเตอร์คือความใกล้ของบริบท ไม่ใช่ความใกล้ของค่าตัวเลข

ข้อที่ควรเข้าใจให้ตรง: ผู้จัดทำตรวจจากงานวิจัยเรื่องตัวเลขใน embedding

คลิปพูดอย่างระวังว่าตำแหน่งของ 100 "ไม่จำเป็นต้อง" อยู่กลาง งานวิจัยยืนยันส่วนนี้เพียงบางส่วน Wallace et al. 2019 พบว่า GloVe และ word2vec (โมเดลเวกเตอร์คำรุ่นเก่าที่ให้คำละหนึ่งเวกเตอร์คงที่) เก็บขนาดของตัวเลขได้แม่นสำหรับเลขไม่เกิน 1,000 และ ELMo (โมเดลรุ่นหลังที่ให้เวกเตอร์ตามบริบทของประโยค) ทำได้ดีที่สุด ส่วน Naik et al. 2019 พบว่า embedding เก็บขนาดได้โดยประมาณแต่ไม่พอสำหรับการนับ จึงควรเข้าใจว่าเส้นจำนวนใน embedding "หยาบและไม่น่าเชื่อถือ" มากกว่า "ไม่มีเลย"

ในระบบ RAG (ระบบที่ดึงเอกสารมาให้ LLM ใช้ตอบ) หรือเอเจนต์ (โปรแกรมที่ให้ LLM เลือกเรียกใช้เครื่องมือเองได้) ให้ส่งงานคำนวณไปที่เครื่องมือ เช่น Python หรือเครื่องคิดเลข แทนการให้โมเดลคิดเอง (คำอธิบายคลิปก็บอกว่าเห็นการพึ่ง Python หรือเครื่องคิดเลขแบบนี้) และถ้ากำลัง fine-tune โมเดล (ฝึกโมเดลต่อด้วยข้อมูลของเราเอง) ให้มีชุดทดสอบเลขสุ่มยาวที่ไม่อยู่ในข้อมูลฝึก แยกจากเลขง่ายที่พบบ่อย เพื่อวัดว่าโมเดล "คำนวณ" หรือแค่ "จำ"

เอาไปใช้ทำอะไร: เมื่อเข้าใจว่า embedding วางตัวเลขตามบริบท ก็จะไม่ใช้ความใกล้ของเวกเตอร์ตอบคำถามเชิงตัวเลข เช่น "ราคาไม่เกิน 100" ใน ZVect (โปรเจกต์บทเรียนเรื่อง vector search พร้อมไลบรารี JavaScript ด้าน embedding, BM25 และ hybrid search) หรือในระบบ RAG แต่จะเก็บตัวเลขไว้ในฟิลด์แยกแล้วกรองตรง ๆ

2. คำบอกเวลาและการจัดอันดับ: "latest", "recent" และ "สูงสุด" ที่ vector วัดได้ยาก (~2:03–3:04)

หัวข้อนี้จะพาดูอะไร: ปัญหาแบบเดียวกับตัวเลขเมื่อคำถามมีคำบอกเวลา หรือต้องการของที่ "สูงสุด" หรือ "ต่ำสุด"

ใจความ: หัวข้อก่อนแสดงว่า embedding วางตัวเลขตามบริบท หัวข้อนี้ขยายไปที่คำบอกเวลา ผู้สอนบอกว่าคำอย่าง latest (ล่าสุด), current (ปัจจุบัน) และ recent (เมื่อเร็ว ๆ นี้) ไม่ได้ถูกวางบนเส้นเวลา แต่จับกลุ่มตามบริบท latest อาจอยู่ใกล้ newest หรือ current เพราะคำเหล่านี้มักใช้คู่กัน ไม่ใช่เพราะโมเดลรู้ลำดับเวลา โมเดลแบบ Transformer จึงไม่ได้รู้ในตัวว่า latest มักหมายถึงสิ่งที่ใหม่กว่า recent ต่อจากนั้นผู้สอนพูดถึงการเรียงลำดับ ความสัมพันธ์ในพื้นที่เวกเตอร์ซับซ้อนและมีหลายมิติ การหาของที่สูงสุดหรือต่ำสุดจึงต้องเทียบเวกเตอร์จำนวนมาก ซึ่งอาจค่อนข้างกินการคำนวณเมื่อข้อมูลโตขึ้น

ตัวอย่างที่ใช้ตลอดหัวข้อนี้ (ผู้จัดทำยกขึ้นเอง จากคำในคลิป)

สมมติคำค้นว่า "บทความ RAG ล่าสุด" vector search จะหาเอกสารที่ความหมายใกล้คำว่า RAG และ latest แต่คำว่า latest ในเวกเตอร์ใกล้ newest และ current เพราะมักใช้คู่กัน ไม่ได้บอกว่าเอกสารไหนเผยแพร่หลังสุด

ผู้สอนสรุปส่วนนี้ด้วยการแยกสองแบบของความหมายออกจากกัน:

  • แนวคิดเชิงเปรียบเทียบ (relative concept) เป็นจุดแข็งของ embedding เช่น good อยู่ใกล้ excellent มากกว่าใกล้ poor (ผู้จัดทำ: เพราะทั้งสองคำมักใช้ในบริบทคล้ายกัน)
  • ลำดับแบบสัมบูรณ์ (absolute ranking) เช่น อะไรใหม่ที่สุด หรืออะไรสูงที่สุด เป็นสิ่งที่ embedding ยังทำได้ยาก (ผู้จัดทำ: เพราะลำดับไม่ได้ถูกเก็บเป็นแกนที่ชัดเจนในเวกเตอร์ แม้งานวิจัยจะพบว่าเก็บขนาดของตัวเลขไว้คร่าว ๆ)
  • การหาค่าสูงสุดหรือต่ำสุดด้วยเวกเตอร์ต้องเทียบเวกเตอร์จำนวนมาก จึงอาจค่อนข้างกินการคำนวณเมื่อข้อมูลโตขึ้น

ในคลิปช่วงนี้มีการ์ดข้อความสั้น ๆ สองใบที่ตั้งชื่อปัญหาให้เห็นชัด ใบแรก (~2:25) เขียนเพียงว่า chronological order (ลำดับตามเวลา) ซึ่งคือสิ่งที่ผู้สอนบอกว่าโมเดลไม่ได้รู้ในตัว เพราะคำอย่าง latest กับ recent ถูกวางตามบริบทการใช้ ไม่ใช่ตามเส้นเวลา ใบที่สอง (~2:37) ถามว่าเรียงลำดับในพื้นที่เวกเตอร์ได้หรือไม่ และคำตอบที่ผู้สอนให้ต่อจากการ์ดคือสองข้อสุดท้ายในรายการข้างบน คือทำได้ยาก และต้องเทียบเวกเตอร์จำนวนมาก แล้วผู้สอนปิดด้วยคำถามว่าข้อจำกัดเหล่านี้มาจากไหน ซึ่งต้องดูว่า embedding ถูกสร้างและทำตัวอย่างไรในพื้นที่เวกเตอร์ (หัวข้อ 3)

ในภาพนี้:

  1. กล่องซ้ายคือสิ่งที่ embedding ทำได้ดี คือบอกว่าคำไหนความหมายใกล้กัน เช่น good กับ excellent หรือ latest กับ newest ความใกล้ของ latest กับ newest ถูกต้องในแง่ความหมาย แต่ไม่ได้บอกว่าเอกสารไหนใหม่กว่า ตัวอย่างเดียวกันนี้จึงกลายเป็นปัญหาเมื่อคำถามต้องการลำดับเวลา
  2. กล่องขวาคือสิ่งที่ embedding ทำได้ยาก คือคำถามที่ต้องรู้ลำดับจริง ทั้งลำดับเวลาและค่าสูงสุดต่ำสุด ข้อแรกที่เน้นสีคือคำถามว่า latest ใหม่กว่า recent หรือไม่ ซึ่งโมเดลไม่ได้รู้ในตัว
  3. ลูกศรตรงกลางไม่ได้แปลว่ากล่องซ้ายนำไปสู่กล่องขวา แต่หมายถึงการเอาความใกล้แบบกล่องซ้ายไปใช้ตอบคำถามแบบกล่องขวา ซึ่งต้องเทียบเวกเตอร์หลายคู่ และค่าคำนวณจะโตตามข้อมูล

ภาพนี้บอกว่า เวกเตอร์ตอบได้ว่า "คล้ายอะไร" แต่ตอบได้ยากว่า "มาก่อนหรือมากกว่า"

คำอธิบายคลิประบุว่า metadata filtering (การกรองด้วยฟิลด์ข้อมูลอย่างวันที่หรือราคา) เป็นทางแก้ที่ใช้ได้ แต่ไม่ได้อธิบายในคลิป ใน ZVect หรือระบบ RAG จึงควรเก็บวันที่และค่าตัวเลขเป็นฟิลด์แยก แล้วทำขั้น "จับคำบอกเวลาและคำเรียงลำดับในคำถาม" ก่อนค้น เช่น เจอคำว่า latest ให้เรียงตามวันที่หลังจากได้ผล vector search แล้ว และควรมีชุดทดสอบคำถามที่มีคำบอกเวลา เพื่อวัดว่าระบบคืนเอกสารล่าสุดจริงหรือไม่

เอาไปใช้ทำอะไร: ใช้แยกคำถามในระบบค้นเป็นสองแบบ คำถามเชิงความหมายส่งให้ vector search ส่วนคำถามเชิงลำดับหรือเวลาส่งให้การกรองและเรียงบนฟิลด์ข้อมูล

3. ต้นเหตุ: การตัดตัวเลขเป็น token และ embedding ที่ขยับตามบริบท (apple pie) (~3:04–4:36)

หัวข้อนี้จะพาดูอะไร: ต้นเหตุสองข้อที่ทำให้ vector search มีข้อจำกัดในหัวข้อ 1 และ 2 และตัวอย่างการค้นสูตร apple pie ที่ได้ผลกว้างเกินไป

ใจความ: ผู้สอนบอกว่าจะเข้าใจข้อจำกัดเหล่านี้ต้องดูว่า embedding ถูกสร้างอย่างไร ข้อแรกคือการตัดข้อความเป็น token (ชิ้นข้อความย่อยที่โมเดลอ่านทีละชิ้น) ตัวเลขถูกมองเป็นส่วนหนึ่งของภาษาเหมือนคำทั่วไป จึงถูกตัดเป็นชิ้นเล็กแล้วแปลงเป็น embedding ข้อที่สอง ซึ่งผู้สอนบอกว่าอาจสำคัญกว่า (ผู้จัดทำ: น่าจะเพราะข้อนี้กระทบทุกคำ ไม่ใช่แค่ตัวเลข และเป็นต้นเหตุของผลค้นที่ไม่แม่นในตัวอย่าง apple pie ข้างล่าง) คือ embedding ของข้อความไม่คงที่ แต่ถูกปรับตามบริบทเพื่อสะท้อนความหมาย ตำแหน่งจึงเป็นแบบสัมพัทธ์และขยับได้ตามการใช้งาน ความยืดหยุ่นนี้ทำให้หาแนวคิดที่เกี่ยวข้องได้โดยไม่ต้องมีคำตรงกัน แต่บางครั้งก็ย้อนกลับมาเป็นผลเสีย คือได้ผลค้นที่ไม่แม่น ข้อนี้คือเหตุผลที่คลิปเริ่มพูดถึง BM25

ตัวอย่างที่ใช้ตลอดหัวข้อนี้ (มาจากคลิป)

สองตัวอย่าง ตัวแรกคือเลข 3458723098 ซึ่งไม่ใช่เลขที่พบบ่อย ตัวที่สองคือการค้นสูตรอาหารด้วยคำค้น "apple pie" ในระบบที่ใช้ embedding

ในภาพนี้:

  1. ด้านบนคือเลข 3458723098 สีฟ้า ซึ่งเป็นเลขยาวที่ไม่ค่อยพบในข้อความทั่วไป และเป็นตัวตั้งของทุกแถวด้านล่าง
  2. แถวแรกตัดทีละหลักเป็น 10 ชิ้น คือ "3" "4" "5" "8" "7" "2" "3" "0" "9" "8"
  3. แถวที่สองถึงสี่ตัดเป็นก้อนหลายหลักที่ยาวไม่เท่ากัน คือ "3458" "723" "098", "34" "587" "230" "98" และ "34" "587" "2309" "8"
  4. แถวที่ห้าตัดเป็นสองก้อนใหญ่ "34587" "23098" และแถวสุดท้ายที่สีจางคือ "345" "872" "3098" ซึ่งแสดงว่ายังมีแบบอื่นอีก

ภาพนี้บอกว่า เลขเดียวกันตัดได้หลายแบบ แต่ทุกแบบในภาพตัดเป็นหลายชิ้น ไม่มีแบบใดเก็บเลขทั้งจำนวนเป็นชิ้นเดียว

ผู้สอนบอกว่าโมเดลจะตัดแบบไหนขึ้นกับการฝึกของมันมาก จึงไม่มีอะไรรับประกันว่ามันจะจัดการกับเลขหนึ่ง ๆ อย่างไร สิ่งที่แน่นอนคือเลขแบบนี้จะถูกตัดเป็นหลายส่วน ไม่ได้ถูกมองเป็นชิ้นเดียว (ผู้จัดทำ: เมื่อเลขถูกแยกเป็น "34587" กับ "23098" ไม่มีชิ้นใดบอกขนาดของเลขทั้งจำนวน โมเดลจึงต้องประกอบค่าจากหลายชิ้นเอง การคำนวณ การเรียง และการกรองตามค่าจึงพลาดได้ง่าย ข้อนี้ใช้กับเลขยาวที่ไม่ค่อยพบ ส่วนเลขสั้นอย่าง 100 มักเป็นชิ้นเดียวอยู่แล้ว เหตุที่ 100 ไม่อยู่กลางระหว่าง 50 กับ 150 จึงมาจากการวางตามบริบทในหัวข้อ 1 มากกว่า)

จากนั้นผู้สอนอธิบายข้อสอง เพราะ embedding ขยับตามบริบท มันจึงหาแนวคิดที่เกี่ยวข้องเจอแม้คำไม่ตรงกัน แต่ในการค้นสูตรอาหาร คำค้น apple pie อาจได้สูตร cherry pie หรือ peach pie กลับมา หรือแม้แต่ meat pie (พายไส้เนื้อ) ความเข้าใจแบบกว้างนี้ช่วยให้ผู้ใช้เจอสูตรใหม่ที่อาจชอบ แต่ก็ทำให้หาสิ่งที่ต้องการได้ยากขึ้น ถ้าผู้ใช้ต้องการสูตร apple pie โดยเฉพาะ ผู้สอนจึงบอกว่า งานที่ต้องจับคำตรงตัวแบบนี้ใช้ BM25 มาเสริม vector search ได้ แล้วจะพูดต่อว่า vector search ทำอะไรได้ดี ตรงไหนไม่ดี และ BM25 ช่วยอย่างไร

ในภาพนี้:

  1. กล่องแรกคือคำค้น apple pie ของผู้ใช้ที่ต้องการสูตรนี้โดยเฉพาะ ไม่ได้ต้องการพายชนิดอื่น
  2. กล่องที่สองคือ embedding ของคำค้น ซึ่งถูกวางตามบริบทที่คำว่า pie ถูกใช้ จึงอยู่ใกล้พายชนิดอื่นด้วย
  3. กล่องที่สามคือผลที่ vector search คืนมา ซึ่งอาจมี cherry pie, peach pie และ meat pie ปนมา
  4. กล่องที่สี่ที่เน้นสีคือผลเสีย ผู้ใช้หาสูตรที่ต้องการได้ยากขึ้น แม้จะได้ประโยชน์จากการเจอสูตรใหม่
  5. กล่องสุดท้ายคือทางแก้ที่ผู้สอนเสนอ คือใช้ BM25 ซึ่งจับคำตรงตัวมาเสริม vector search ไม่ใช่มาแทน

ภาพนี้บอกว่า ความยืดหยุ่นของ embedding เป็นทั้งจุดแข็งและต้นเหตุของผลที่ไม่แม่น เมื่องานต้องการคำตรงตัว

ผลตรวจข้อเท็จจริงชี้ว่า embedding ที่ขยับตามบริบทคือของโมเดลแบบ Transformer ส่วน GloVe ที่ใช้วาดภาพในหัวข้อ 1 เป็นเวกเตอร์คงที่ (คำหนึ่งคำมีเวกเตอร์เดียว ไม่ว่าจะอยู่ในประโยคไหน) ต้นเหตุข้อสองนี้จึงใช้อธิบายภาพ GloVe ไม่ได้ เหตุที่ 50, 100 และ 150 ในภาพนั้นไม่เรียงเป็นเส้นจำนวน จึงน่าจะมาจากเรื่องในหัวข้อ 1 (เวกเตอร์คงที่ก็ถูกเรียนจากบริบทในข้อมูลฝึก) ร่วมกับการย่อมิติด้วย PCA ที่หัวข้อ 1 เตือนไว้ ไม่ใช่จากการขยับตามบริบท ZVect มีส่วนที่เป็นบทเรียน จึงควรบอกผู้เรียนให้ชัดว่าบทเรียนไหนใช้เวกเตอร์คงที่ บทไหนใช้ embedding ตามบริบท และในระบบ RAG ควรทำชุดคำถามที่มีชื่อเฉพาะ รหัสสินค้า หรือตัวเลข เพื่อวัดว่า vector search อย่างเดียวพลาดกี่ข้อ ก่อนตัดสินใจเพิ่ม BM25

เอาไปใช้ทำอะไร: ใช้เป็นเหตุผลออกแบบระบบค้นแบบสองทาง คำค้นที่มีชื่อเฉพาะหรือคำที่ต้องตรงตัวควรผ่าน BM25 ด้วย ไม่ใช่ vector search อย่างเดียว

4. dense vector กับ sparse vector ต่างกันอย่างไร (~4:36–5:37)

หัวข้อนี้จะพาดูอะไร: ความต่างของเวกเตอร์สองแบบที่อยู่เบื้องหลัง vector search และ BM25 และเหตุที่แบบหลังเหมาะกับการจับคำตรงตัว

ใจความ: ผู้สอนบอกว่า vector search ใช้ dense vector (เวกเตอร์หนาแน่น ทุกช่องมีค่า) ส่วน BM25 ใช้ sparse vector (เวกเตอร์เบาบาง ช่องส่วนใหญ่เป็นศูนย์) ใน dense vector คำหรือวลีถูกวางในพื้นที่หลายมิติ แต่ละมิติเก็บแง่มุมหนึ่งของความหมายหรือบริบท และค่าของมิติบอกว่าคำนั้นผูกกับแนวคิดหนึ่งแรงแค่ไหน ส่วน sparse vector เน้นที่การมีหรือไม่มีของคำเฉพาะในเอกสาร ช่องของคำที่ไม่มีเป็นศูนย์ ส่วนช่องของคำที่มีจะเก็บค่าที่ไม่เป็นศูนย์ (ผู้จัดทำ: ค่านั้นบอกได้ด้วยว่าคำมีมากแค่ไหน เช่น จำนวนครั้งในตัวอย่างของผู้จัดทำข้างล่าง ซึ่งหัวข้อ 5 จะใช้ต่อ และความต่างนี้ต่อจากหัวข้อ 3 เพราะ dense vector คือที่มาของความยืดหยุ่นที่ทำให้ apple pie ได้พายชนิดอื่น และ sparse vector คือสิ่งที่ทำให้ BM25 จับคำตรงตัวได้)

ตัวอย่างที่ใช้ตลอดหัวข้อนี้ (มาจากคลิป และผู้จัดทำต่อยอด)

คลิปใช้คำว่า King เป็นตัวอย่างของ dense vector และแสดงเวกเตอร์ตัวอย่างยาว 10 ช่องของทั้งสองแบบ ผู้จัดทำต่อยอดด้วยคำค้น apple pie จากหัวข้อ 3 เพื่อดูว่า sparse vector จับเอกสารอย่างไร

ในภาพนี้:

  1. หัวเรื่อง Sparse vs Dense Vectors บอกว่าจะเทียบเวกเตอร์สองแบบ และภาพนี้แสดงแบบแรกก่อน
  2. ป้าย Dense Vector (Semantic) บอกว่านี่คือเวกเตอร์ความหมายแบบที่ vector search ใช้
  3. กล่องเล็ก 10 ช่องแต่ละช่องคือหนึ่งมิติ มีค่า 0.1, -0.3, 0.7, 0.2, 0.5, -0.1, 0.4, 0.6, -0.2 และ 0.3 ทุกช่องมีค่าไม่เป็นศูนย์ และมีทั้งค่าบวกและค่าลบ

ภาพนี้บอกว่า ใน dense vector ทุกมิติมีส่วนร่วมบอกความหมาย ไม่มีช่องใดว่าง

ผู้สอนยกตัวอย่างว่าใน dense vector ของคำว่า King มิติหนึ่งอาจมีค่าสูงที่ผูกกับความเป็นราชวงศ์ อีกมิติผูกกับความเป็นผู้นำ และอีกมิติผูกกับความเป็นชาย มิติทั้งหมดร่วมกันกำหนดตำแหน่งของคำในพื้นที่ความหมาย ในทางกลับกัน sparse vector สนใจว่ามีหรือไม่มีคำเฉพาะ ช่องส่วนใหญ่เป็นศูนย์ และมีค่าไม่เป็นศูนย์เฉพาะเมื่อคำนั้นปรากฏในเอกสาร

ในภาพนี้:

  1. แถวบนคือ Sparse Vector (BM25) ยาว 10 ช่อง ช่องสีเทาเป็น 0 เจ็ดช่อง
  2. ช่องสีเขียวมะกอกสามช่องมีค่า 3, 2 และ 1 อยู่ตำแหน่งที่สาม ห้า และแปด ซึ่งแทนคำที่ตรงกับคำค้น (ผู้จัดทำ: แต่ละช่องคือคำหนึ่งคำในคลังศัพท์ ภาพไม่ได้ระบุว่าแถวนี้เป็นเวกเตอร์ของคำค้นหรือของเอกสาร ผู้สอนพูดถึงทั้งคำที่ปรากฏในเอกสารและคำในคำค้น และคลิปไม่ได้บอกว่าตัวเลขสามค่านี้คือจำนวนครั้งหรือน้ำหนัก)
  3. ข้อความใต้แถวบอกว่ามีค่าไม่เป็นศูนย์เฉพาะคำที่ตรงกันพอดี (exact keyword match)
  4. แถวล่างคือ dense vector ตัวเดิมจากภาพก่อน วางไว้ให้เทียบว่าทุกช่องมีค่า

ภาพนี้บอกว่า sparse vector มีค่าเฉพาะช่องของคำที่ตรงกันพอดี ช่องอื่นเป็นศูนย์ทั้งหมด (เปรียบเทียบโดยผู้จัดทำ: เหมือนรายการเช็กคำ)

ผู้สอนอธิบายว่าโครงสร้างแบบนี้รองรับการจับคำตรงตัวโดยตรง เพราะค่าไม่เป็นศูนย์แต่ละค่าตรงกับคำเฉพาะหนึ่งคำในคำค้น เวกเตอร์จึงชี้ได้ว่าเอกสารไหนมีคำเหล่านั้น sparse vector จึงเหมาะและได้ผลกับงานค้นที่ต้องการความแม่นยำ ซึ่งเป้าหมายคือจับคำเฉพาะ ไม่ใช่จับบริบทความหมายแบบกว้าง

ในภาพนี้:

  1. แต่ละแถวคือ sparse vector ของเอกสารหนึ่งชิ้น และแต่ละคอลัมน์คือคำหนึ่งคำในคลังศัพท์ ตัวเลขในช่องเป็นจำนวนครั้งที่ผู้จัดทำสมมติขึ้น
  2. ช่องส่วนใหญ่เป็น 0 เพราะเอกสารแต่ละชิ้นมีเพียงไม่กี่คำจากคลังศัพท์ ซึ่งคือความหมายของคำว่า sparse
  3. ช่องที่เน้นคือแถวสูตร apple pie ในคอลัมน์ apple เป็นแถวเดียวที่มีค่าในคอลัมน์นี้ คำค้น apple pie จึงแยกเอกสารนี้ออกจากอีกสองชิ้นได้ทันที
  4. คอลัมน์ pie และ recipe มีค่าในทุกแถว เพราะทุกเอกสารเป็นสูตรพาย คำสองคำนี้จึงช่วยแยกเอกสารได้น้อย

ภาพนี้บอกว่า sparse vector จับเอกสารที่มีคำค้นอยู่จริง ซึ่งเป็นสิ่งที่ dense vector ในตัวอย่าง apple pie ทำได้ไม่ชัด (ผู้จัดทำ: เรื่องที่ pie และ recipe มีค่าอยู่ทุกแถวจนช่วยแยกเอกสารได้น้อย จะกลับมาเป็นเรื่อง IDF ในหัวข้อ 5)

เสริมจากผู้จัดทำ: นำไปใช้ต่อ

ใน ZVect ให้เก็บ sparse vector ของแต่ละเอกสารเป็นคู่ "คำ → ค่า" เฉพาะคำที่ปรากฏ ไม่ต้องเก็บศูนย์ทั้งคลังศัพท์ แล้วรวมทุกเอกสารเป็น inverted index (ดัชนีกลับด้าน ที่ชี้จากคำแต่ละคำไปหารายการเอกสารที่มีคำนั้น พร้อมจำนวนครั้ง) ตอนค้นจึงเปิดดูเฉพาะรายการของคำในคำค้น และทดสอบว่าการตัดคำของ BM25 ตรงกับภาษาที่ใช้ เพราะภาษาไทยไม่มีช่องว่างระหว่างคำ ถ้าตัดคำผิด คำค้นจะไม่ตรงกับช่องใดเลย

เอาไปใช้ทำอะไร: ใช้เลือกว่าส่วนไหนของระบบค้นควรใช้เวกเตอร์แบบไหน dense vector สำหรับหาความหมาย และ sparse vector สำหรับจับชื่อ รหัส หรือคำเฉพาะที่ต้องตรงตัว

5. BM25 ทำงานอย่างไร: ความถี่อิ่มตัว, IDF และการปรับตามความยาวเอกสาร (~5:37–8:14)

หัวข้อนี้จะพาดูอะไร: สามกลไกที่ BM25 ใช้ให้คะแนนเอกสาร นอกเหนือจากการจับคำตรงตัว พร้อมกราฟสามภาพจากคลิปและสูตร IDF บนจอ

ใจความ: ผู้สอนบอกว่าการจับคำตรงตัวเป็นเพียงส่วนหนึ่งของจุดแข็งของ BM25 ในการจัดอันดับข้อมูลที่เกี่ยวข้องที่สุด BM25 ไม่ได้ดูแค่ว่าคำมีหรือไม่มี แต่ดูด้วยว่าคำปรากฏบ่อยแค่ไหน และคำนั้นหายากหรือเฉพาะแค่ไหนเมื่อดูทุกเอกสาร ผู้สอนบอกว่าสองเรื่องนี้เป็นการปรับปรุงที่แก้ข้อจำกัดบางข้อของ TF-IDF (วิธีให้คะแนนแบบเก่าที่คูณความถี่ของคำกับความหายากของคำ) เช่น การจัดการความถี่ของคำและความยาวเอกสารแบบพื้นฐาน (ผู้จัดทำ: TF-IDF มีส่วนความหายากอยู่แล้ว สิ่งที่ BM25 เพิ่มขึ้นจริงคือเพดานของคะแนนความถี่และการปรับตามความยาวเอกสาร ส่วน IDF ของ BM25 เป็นสูตรที่ปรับรูปจาก IDF เดิม) กลไกที่ผู้สอนอธิบายทีละข้อจึงมีสามข้อ คือความถี่ ความหายาก และความยาวเอกสาร (ผู้จัดทำ: แต่ละข้อตอบคำถามว่า "ข้อมูลแบบไหนไม่ควรได้คะแนนเพิ่ม") และเมื่อรวมกันแล้ว BM25 จึงให้คะแนนความเกี่ยวข้องแก่แต่ละเอกสารและจัดอันดับได้

ตัวอย่างที่ใช้ตลอดหัวข้อนี้ (มาจากคลิป)

คำค้นคือ "วิธีสร้างระบบ RAG ที่ได้ผลด้วย hybrid search และเทคนิค reranking" โดย RAG คือการดึงเอกสารมาให้ LLM ใช้ตอบ hybrid search คือการค้นแบบผสมหลายวิธี และ reranking คือการจัดอันดับผลใหม่อีกรอบ มีเอกสารหนึ่งที่พูดคำว่า RAG ซ้ำไปซ้ำมา

กลไกทั้งสามที่ผู้สอนอธิบาย มีดังนี้:

  1. ความถี่อิ่มตัว (term frequency saturation) ตั้งจุดที่การพูดคำซ้ำเลิกเพิ่มคะแนน เพราะถ้าพูดซ้ำแล้วคะแนนขึ้นเรื่อย ๆ ใครก็ยัดคำลงเอกสารเพื่อดันอันดับได้
  2. IDF (inverse document frequency) วัดว่าคำหนึ่งพบบ่อยหรือหายากแค่ไหนในทุกเอกสาร แล้วลดน้ำหนักคำที่พบทั่วไป จึงทำให้คำเฉพาะมีน้ำหนักมากกว่า
  3. การปรับตามความยาวเอกสาร (document length normalization) ทำให้เอกสารยาวไม่ได้เปรียบเพียงเพราะยาว เพราะเอกสารยาวไม่จำเป็นต้องให้ข้อมูลมากกว่า

ความถี่อิ่มตัว

ในตัวอย่างนี้ ดูผ่าน ๆ ก็สมเหตุสมผลที่โมเดลจะจัดเอกสารที่พูด RAG บ่อยไว้สูง แต่ผู้สอนถามกลับว่าการพูดซ้ำทำให้เอกสารเกี่ยวข้องขึ้นจริงหรือ ถ้าใช่ ใครก็ "game the system" ได้ด้วยการยัดคำที่ต้องการลงไป BM25 จึงตั้งจุดอิ่มตัว ซึ่งผู้สอนเรียกว่าเกณฑ์ความไวแบบหนึ่ง (sensitivity threshold คือจุดที่คะแนนเลิกไวต่อการพูดซ้ำ ผู้จัดทำ: ในสูตรเต็มท้ายหัวข้อนี้ ตัวเลข k₁ คือตัวกำหนดว่าจะถึงจุดนี้เร็วหรือช้า) เพื่อให้รู้ว่าเมื่อพูดซ้ำถึงระดับหนึ่งแล้วจะไม่เพิ่มคุณค่า เช่น หลังเกินเกณฑ์ไปแล้ว เอกสารที่พูด RAG 50 ครั้งจะไม่ได้เปรียบเอกสารที่พูด 10 ครั้ง

ในภาพนี้:

  1. แกนนอนคือความถี่ของคำ (TermFrequency) คือจำนวนครั้งที่คำปรากฏในเอกสาร จาก 0 ถึง 28 ส่วนแกนตั้งคือคะแนนที่ได้จากความถี่นั้น (TFScore) จาก 0 ถึง 6
  2. เส้นสีแดง Classic TF score ขึ้นต่อเนื่องไม่หยุด จนราว 5.3 ที่ความถี่ 28 หมายความว่ายิ่งพูดซ้ำยิ่งได้คะแนน (ผู้จัดทำ: ค่านี้ใกล้ √28 ≈ 5.29 จึงน่าจะเป็นคะแนนรากที่สองของความถี่ แบบ classic ของ Lucene (ไลบรารีค้นหาข้อความแบบโอเพนซอร์สที่ Elasticsearch ใช้เป็นแกน) คลิปไม่ได้บอกสูตร)
  3. เส้นสีฟ้า BM25 TF Score ขึ้นเร็วช่วงแรกเหมือนกัน แต่แบนลงราว 2.5 และแทบไม่เพิ่มอีก
  4. กรอบเส้นประสีเหลืองคำว่า Saturation ครอบช่วงความถี่ราว 5–13 ซึ่งเส้นสีฟ้าเริ่มแบน ขณะที่เส้นสีแดงยังขึ้นต่อ คือช่วงที่คะแนน BM25 เริ่มอิ่มตัว

ภาพนี้บอกว่า BM25 ให้รางวัลการพูดคำซ้ำแค่ช่วงแรก หลังจากนั้นการพูดซ้ำแทบไม่เพิ่มคะแนน

IDF: น้ำหนักตามความหายากของคำ

เมื่อจัดการความถี่แล้ว ผู้สอนถามต่อว่า BM25 ตัดสินอย่างไรว่าคำไหนควรได้ความสำคัญมากกว่า คำตอบคือ IDF ซึ่งวัดว่าคำพบบ่อยหรือหายากเพียงใดในทุกเอกสาร คำทั่วไปอย่าง the หรือ system อาจพบได้ทุกที่และไม่เพิ่มความหมายมาก BM25 จึงลดผลของมัน ในทางกลับกัน คำที่หายากแต่เฉพาะกว่า อย่าง hybrid search หรือ reranking techniques ได้น้ำหนักมากกว่า เพราะช่วยแยกผลที่เกี่ยวข้องจริงออกจากสิ่งรบกวน

ในภาพนี้:

  1. แกนนอนคือ document frequency คือจำนวนเอกสารที่มีคำนั้น จาก 0 ถึง 100,000 ส่วนแกนตั้งคือค่า IDF ซึ่งใช้สเกลลอการิทึม แต่ละขีดต่างกัน 10 เท่า จาก 10⁻² ถึง 10²
  2. เส้นสีแดงพุ่งสูงมากเมื่อคำพบในเอกสารน้อย แล้วลดลงเร็วและแบนยาวไปทางขวา
  3. จุดสีเขียว hybrid search อยู่ใกล้ซ้ายสุดและได้ IDF สูงที่สุดในสามคำ จุดสีเหลือง system อยู่ราว 30,000 เอกสาร และจุดสีแดง the อยู่ราว 90,000 เอกสาร ได้ IDF ต่ำที่สุด
  4. มุมขวาบนคือสูตร IDF พร้อมคำอธิบายว่า N คือจำนวนเอกสารทั้งหมด และ dfₜ คือจำนวนเอกสารที่มีคำนั้น (กลางภาพมีอักษรเพี้ยนเล็ก ๆ ซึ่งไม่มีความหมาย)

ภาพนี้บอกว่า ยิ่งคำพบในเอกสารมาก น้ำหนักของคำยิ่งต่ำ คำเฉพาะจึงชนะคำทั่วไป

การปรับตามความยาวเอกสาร

ผู้สอนถามต่อว่า ความยาวเอกสารมีผลต่อความเกี่ยวข้องด้วยหรือไม่ เอกสารยาวอาจมีข้อมูลมากกว่า แต่ไม่ได้แปลว่าจำเป็นต้องให้ความรู้มากกว่า บางครั้งข้อความที่สั้นและกระชับกลับให้ข้อมูลที่มีค่ากว่า BM25 จึงปรับคะแนนตามความยาวเอกสาร (ผู้จัดทำ: คำเดียวกัน 4 ครั้งในเอกสารยาวเป็นสัดส่วนที่เล็กกว่าของเนื้อหา จึงบอกได้น้อยกว่าว่าเอกสารนั้นพูดเรื่องนี้เป็นหลัก สูตรเต็มท้ายหัวข้อจึงเทียบความยาวของเอกสารกับความยาวเฉลี่ยของทั้งคลัง)

ในภาพนี้:

  1. แกนนอนคือความถี่ของคำ 0 ถึง 24 ครั้ง และแกนตั้งคือคะแนนจากความถี่ 0 ถึง 2.0 เหมือนกราฟความอิ่มตัวก่อนหน้า
  2. เส้นสีม่วงบนสุดคือเอกสารที่ยาว 1/5 ของความยาวเฉลี่ย ที่ความถี่ราว 4 ได้ราว 1.5 และขึ้นไปเกิน 2.0
  3. เส้นสีส้มตรงกลางคือเอกสารที่ยาวเท่าค่าเฉลี่ย ที่ความถี่เดียวกันได้ราว 1.1 และแบนลงราว 1.4
  4. เส้นสีเหลืองล่างสุดคือเอกสารที่ยาว 5 เท่าของค่าเฉลี่ย ได้ราว 0.5 และแทบไม่ขึ้นอีก
  5. ข้อความใต้กราฟบอกว่า BM25 ปรับตามความยาวเอกสาร และเอกสารที่สั้นกว่าอาจได้คะแนนสูงกว่าเมื่อความถี่คำเท่ากัน

ภาพนี้บอกว่า ความถี่ 4 ครั้งในเอกสารสั้นมีน้ำหนักมากกว่าความถี่ 4 ครั้งในเอกสารยาว

สุดท้าย หลังจากพิจารณาทั้งความถี่ของคำ ความสำคัญของคำ และความยาวเอกสารแล้ว BM25 ให้คะแนนความเกี่ยวข้องแก่เอกสารแต่ละชิ้นและจัดอันดับ ผังนี้วางสามกลไกให้เห็นว่ามารวมกันอย่างไร

ในภาพนี้:

  1. กล่องแรกคือการจับคำตรงตัว ซึ่งเป็นจุดเริ่มที่ sparse vector ทำได้ (หัวข้อ 4)
  2. กล่องที่สองคือความถี่อิ่มตัว ซึ่งนับว่าคำปรากฏกี่ครั้ง แต่หยุดให้คะแนนเพิ่มหลังเกินเกณฑ์
  3. กล่องที่สามคือ IDF ซึ่งถ่วงน้ำหนักตามความหายากของคำในทุกเอกสาร
  4. กล่องที่สี่คือการปรับตามความยาว ซึ่งกันไม่ให้เอกสารยาวได้เปรียบเพียงเพราะยาว
  5. กล่องสุดท้ายที่เน้นสีคือผลรวม คะแนนความเกี่ยวข้องหนึ่งค่าต่อเอกสาร ที่ใช้จัดอันดับ

ภาพนี้บอกว่า คะแนน BM25 ไม่ได้มาจากการนับคำอย่างเดียว แต่ผ่านการปรับสามชั้นก่อนจัดอันดับ (ผู้จัดทำ: ผังเรียงตามลำดับที่ผู้สอนอธิบาย ไม่ใช่ลำดับการคำนวณ ในสูตรเต็มด้านล่าง การปรับความยาวอยู่ในส่วนความถี่ แล้วจึงคูณด้วย IDF)

คลิปไม่ได้แสดงสูตร BM25 เต็ม ผู้จัดทำจึงเสริมสูตรมาตรฐานจากแหล่งที่ใช้ตรวจข้อเท็จจริง (Robertson & Zaragoza; Stanford CS276) เพื่อให้เห็นว่าสามกลไกอยู่ตรงไหนในสูตร

ตารางนี้ (ผู้จัดทำคำนวณ) ตอบตัวอย่าง RAG 50 ครั้งกับ 10 ครั้งของคลิปเป็นตัวเลข ในเอกสารยาวเท่าค่าเฉลี่ย 10 ครั้งได้ 1.96 และ 50 ครั้งได้ 2.15 ต่างกันราว 10% คะแนนจึงยังขึ้นเล็กน้อยแต่แทบไม่ได้เปรียบ ใน ZVect ให้เขียนเทสต์สามข้อสำหรับ BM25: (1) ที่ความถี่ 50 ส่วนความถี่ของคะแนนไม่เกิน k₁ + 1 (คะแนนเต็มของคำนั้นคือค่านี้คูณ IDF) (2) คำที่อยู่ในทุกเอกสารได้ IDF ใกล้ 0 (3) คำเดียวกันจำนวนครั้งเท่ากัน เอกสารสั้นได้คะแนนสูงกว่าเอกสารยาว และเปิดให้ปรับ k₁ กับ b เป็น config เพราะผลตรวจบอกว่าค่าที่ใช้กันอยู่ในช่วง 1.2–2 และราว 0.75

เสริมจากผู้จัดทำ: ใช้ BM25 คู่กับ vector search

คำอธิบายคลิปบอกว่า hybrid search ซึ่งรวม dense vector กับ sparse vector อย่าง BM25 ช่วยให้ค้นได้ดีขึ้น และจะพูดแบบขั้นสูงในคลิปหน้า ผลตรวจข้อเท็จจริงยืนยันว่า Contextual Retrieval ของ Anthropic ที่ใช้ embedding คู่ BM25 ลดอัตราที่ชิ้นเอกสารที่ต้องการไม่ติด 20 อันดับแรกได้ 49% และ 67% เมื่อเพิ่ม reranking เมื่อเทียบกับ embedding แบบเดิม (ตามที่ Anthropic รายงาน อ่านผ่าน InfoQ) (ใช้ Contextual Embeddings อย่างเดียวลดได้ 35%) ใน ZVect ขั้นถัดไปที่สร้างได้คือ รัน vector search กับ BM25 แยกกัน แล้วรวมอันดับด้วย RRF (Reciprocal Rank Fusion) ซึ่งให้คะแนนเอกสารแต่ละชิ้นเท่ากับผลรวมของ 1 ÷ (k + อันดับของเอกสารนั้น) จากทุกรายการ โดย k มักตั้งไว้ราว 60 ตามเปเปอร์ต้นแบบของ RRF (Cormack และคณะ 2009) เอกสารที่ติดอันดับต้นในทั้งสองรายการจึงได้คะแนนรวมสูงสุด และเพราะใช้แค่อันดับ จึงไม่ต้องปรับสเกลคะแนนสองแบบให้เท่ากัน

เอาไปใช้ทำอะไร: ใช้เป็นสเปกของตัวให้คะแนน BM25 ในไลบรารีค้นหาหรือระบบ RAG ทั้งสามกลไกต้องมีครบ และค่าที่ได้ใช้เป็นอันดับฝั่ง sparse ก่อนรวมกับอันดับฝั่ง vector search

Key Takeaways

1.vector search ใช้ embedding ที่วางตัวเลข คำบอกเวลา และคำทั่วไปตามบริบทที่เคยเห็น ไม่ใช่ตามเส้นจำนวนหรือเส้นเวลา จึงทำงานได้ไม่ดีกับการคำนวณ การเรียงลำดับ และการกรอง
2.LLM คำนวณเลขสุ่มยาวที่ไม่ค่อยเห็นพลาดได้ แต่ตอบเลขง่ายที่เคยเห็นอย่าง 150 − 100 ได้ถูกจากความจำ (ผู้จัดทำ: งานคำนวณจึงควรส่งให้เครื่องมืออย่าง Python หรือเครื่องคิดเลข)
3.ต้นเหตุมีสองข้อ คือตัวเลขที่ไม่ค่อยพบถูกตัดเป็นหลายชิ้น และ embedding ขยับตามบริบท ข้อหลังทำให้คำค้น apple pie อาจได้พายชนิดอื่นกลับมา
4.sparse vector ของ BM25 มีค่าเฉพาะคำที่ปรากฏ จึงจับคำตรงตัวได้ และ BM25 ให้คะแนนด้วยความถี่อิ่มตัว IDF และการปรับตามความยาวเอกสาร
5.ทางที่คลิปเสนอคือใช้ BM25 เสริม vector search ส่วนการเรียงและกรองตามค่า คำอธิบายคลิปชี้ไปที่ metadata filtering
