บทสรุปย่อ

คลิปตอนที่ 16 ของเพลย์ลิสต์ RAG สำหรับมือใหม่ อธิบายว่า hybrid search คือการค้นสองทางพร้อมกัน ทางแรกคือ vector search ที่จับ "ความหมาย" ทางที่สองคือ keyword search แบบ BM25 ที่จับ "คำตรงตัว" แล้วรวมสองรายการอันดับเป็นรายการเดียวด้วย reciprocal rank fusion (RRF) ที่ใส่น้ำหนักได้ ผู้สอนเล่า BM25 ด้วยสองปัจจัยบนสไลด์ คือ TF กับ IDF (ไม่มีสูตร) สาธิตใน notebook ด้วย LangChain (Chroma แบบ cosine, BM25Retriever, EnsembleRetriever น้ำหนัก 0.5 / 0.5) แล้วใช้สไลด์ตาราง RRF ถ่วงน้ำหนัก 0.7 / 0.3 ที่ k = 60 และปิดด้วยภาพระบบจริงที่ดึงฝั่งละ 50 chunk รวมแล้วราว 30 chunk จึงต้องมี reranker คัดเหลือ 5 หรือ 10 รายงานฉบับนี้แสดงทุกสูตรเป็นสมการจริง 49 สมการ: ส่วน TF และ IDF ของ BM25 (รูปแบบของ rank_bm25 ที่ LangChain ใช้จริง และแบบ Lucene), สูตร RRF บนสไลด์, RRF ถ่วงน้ำหนักพร้อมการแทนค่าทุกช่องของตาราง, cosine similarity ของฝั่ง vector และจำนวน chunk ในแต่ละขั้นของ reranking นอกจากนี้ผู้จัดทำคำนวณ BM25 บนคลัง 18 chunk ของคลิปเองซ้ำ และพบว่าอธิบายผลบนจอได้ทุกรายการ

สรุปเชิงลึก

ข้อโต้แย้งหลัก. vector search เก่งเรื่องความหมายและบริบท แต่มีจุดบอดที่ทำให้คุณภาพการค้นลดลง ตัวอย่างบนสไลด์: ผู้ใช้ค้น "API key authentication" แต่ได้ผลเรื่อง "user login security" เพราะสองวลีนี้ความหมายใกล้กัน และบางครั้งผู้ใช้รู้แน่ว่าต้องการคำไหน keyword search แก้จุดนี้เพราะหาคำที่ตรงกันทุกตัวอักษร เชื่อถือได้กับชื่อ เลขรุ่น และศัพท์เทคนิค แต่ "โง่" เพราะไม่รู้ว่า car กับ automobile คือสิ่งเดียวกัน สองแบบจึงปิดจุดอ่อนให้กัน (ผู้สอนเปรียบ vector เป็นผู้ช่วยฉลาด keyword เป็นบรรณารักษ์ที่แม่นยำ) ผู้สอนเล่าว่าในงานเอกสารยาที่เต็มไปด้วยชื่อยาซับซ้อน การเติม keyword search ทำให้ความแม่นของระบบเพิ่ม "อย่างน้อยราว 70 %" ซึ่งเป็นประสบการณ์ส่วนตัวที่ไม่มีตัวชี้วัด

BM25 บนสไลด์มีแค่คำบรรยาย ไม่มีสูตร. สไลด์บอกสองปัจจัย: TF คือคำค้นอยู่ใน chunk นี้บ่อยแค่ไหน และ IDF คือคำนั้นหายากแค่ไหนทั้งคลัง ตัวอย่างสามข้อ: (1) chunk A มี Tesla สองครั้งชนะ chunk B ที่มีครั้งเดียว (2) Tesla อยู่ใน 100 chunk แต่ Cybertruck อยู่ใน 5 chunk ห้า chunk นั้นได้ IDF สูงกว่า (3) สำหรับ query "Tesla Cybertruck" chunk "Tesla's Cybertruck production" ชนะ "Tesla Tesla Tesla financial reports" สไลด์ปิดว่า BM25 เป็นเวอร์ชันปรับปรุงของ TF-IDF ที่กันการยัดคำ (keyword stuffing) และจัดการความยาว chunk ได้ดีกว่า ผู้จัดทำเติมสูตรจริงให้ (สมการ 3–11) และแทนค่าตัวอย่างทั้งสามข้อ: กรณี (3) ได้ 8.3282 ต่อ 3.4397 เมื่อสมมติ N = 1,000 (สมการ 16–17) ข้อที่น่าสนใจคือ ถ้าใช้ตัวตัดคำค่าเริ่มต้นของ BM25Retriever ซึ่งแยกด้วยช่องว่างอย่างเดียว คำ "Tesla's" ไม่ใช่ "Tesla" chunk A จึงมี Tesla แค่ครั้งเดียว และ chunk B ที่สั้นกว่าจะชนะแทน (สมการ 15)

โค้ด. คลัง 18 chunk, vector retriever บน Chroma ที่ตั้ง hnsw:space เป็น cosine และ k = 2, BM25Retriever ที่ k = 3 และ EnsembleRetriever น้ำหนัก [0.5, 0.5] ผู้จัดทำคำนวณ BM25 บน 18 chunk ซ้ำแล้วได้ลำดับตรงกับผลบนจอทุก query (รายละเอียดในหัวข้อ 9) และ hybrid คืน chunk เท่ากับ 2 + 3 ลบจำนวนที่ซ้ำ

RRF ถ่วงน้ำหนัก. สไลด์เขียน RRF_score = Σ 1 / (k + rank_position), k = 60 แล้วเปลี่ยนตัวเศษจาก 1 เป็นน้ำหนัก 0.7 (vector) กับ 0.3 (keyword) ผู้จัดทำแทนค่าทุกช่อง: X 0.016314, Y 0.016208, Z 0.015726, W 0.010938, V 0.010769, A 0.004762, B 0.004688 ตรงกับทุกตัวเลขที่มองเห็นบนสไลด์ ส่วนที่กล้องผู้สอนบังไว้ (V, A, B) ผู้จัดทำคำนวณเติม เอกสารที่อยู่ทั้งสองรายการ (X, Y, Z) ได้คะแนนสูงกว่าเอกสารที่อยู่รายการเดียวราว 1.4–1.5 เท่า ด้วยน้ำหนัก 0.5 / 0.5 ของโค้ดสาธิต X กับ Y จะเสมอกันพอดี ผู้สอนยังแก้โค้ดเป็น [0.7, 0.3] ให้ดูที่ ~20:45

ระบบจริงและ reranker. สไลด์ Reality: ฝั่งละ 50 chunk รวมด้วย RRF ได้ราว 30 chunk ผู้สอนเล่าระบบ multi-query hybrid ในผลิตภัณฑ์ของตัวเอง (คำถามแตกเป็น 5 แบบ RRF สองชั้น เหลือราว 25–40) ซึ่งยังมากเกินจะส่ง LLM เพราะเสี่ยงล้น context window และเปลือง token จึงต้องใช้ reranker ที่ "ไม่ใช่ LLM" คัดเหลือ top 5 หรือ 10 ผู้จัดทำชี้ว่า RRF เองไม่ได้ตัดอะไร: สองรายการ 50 อันจะได้ 50 ถึง 100 chunk ไม่ซ้ำ ตัวเลขราว 30 จึงต้องมาจากการตัดที่สไลด์ไม่ได้บอก

ผลตรวจข้อเท็จจริง 13 ข้อ: ยืนยัน 8, ยืนยันบางส่วน 4, ไม่พบแหล่งยืนยัน 1 สิ่งที่คลิปไม่ได้พูด: สูตร BM25 และค่า k1, b; การตัดคำก่อน BM25 (สำคัญมากกับภาษาไทย); วิธีเลือกน้ำหนัก; และวิธีรวมแบบอื่นนอกจาก RRF เอาไปใช้: ถ้าคลังมีชื่อ รหัส หรือตัวเลขที่ผู้ใช้พิมพ์ตรงตัว ให้เพิ่ม BM25 แล้วรวมด้วย RRF k = 60 เริ่มจากน้ำหนักเท่ากัน และเติม reranker เมื่อ candidate มากเกินกว่าที่ LLM รับได้

BM25 = Best Matching 25 และเป็น gold standard ของ keyword searchยืนยันบางส่วนBM ย่อจาก best matching ในระบบ Okapi; "gold standard" เป็นสำนวนของผู้สอนWikipedia (Okapi BM25) ผ่าน WebFetch
BM25 ให้คะแนนจาก TF และ IDFยืนยันสูตรใช้ความถี่คำ, IDF, ความยาวเอกสารและความยาวเฉลี่ย (สมการ 11)ซอร์ส rank_bm25
BM25 เป็นเวอร์ชันปรับปรุงของ TF-IDF ที่กันการยัดคำและจัดการความยาว chunk (สไลด์)ยืนยันk1 ทำให้ TF อิ่มตัว (สมการ 12), b ปรับตามความยาว; คำพูดที่ 7:06 ว่า "ของ TF" แคบกว่าสไลด์ซอร์ส rank_bm25
BM25Retriever ของ LangChain ใช้แพ็กเกจ rank_bm25ยืนยันfrom_texts สร้าง BM25Okapi; ตัวตัดคำค่าเริ่มต้น text.split(); k เริ่มต้น 4ซอร์ส langchain-community bm25.py
EnsembleRetriever รวมได้หลาย retriever และใช้ RRFยืนยันscore += weight / (rank + self.c), c = 60, rank เริ่มที่ 1, ตัดซ้ำด้วย page_contentซอร์ส ensemble.py (อ่านโค้ดจริง)

1. ทำไม hybrid search จึงสำคัญ (~0:00–1:05)

ผู้สอนเปิดว่านี่น่าจะเป็นหนึ่งในคลิปที่สำคัญที่สุดของเพลย์ลิสต์ เพราะ hybrid search กลายเป็นกลยุทธ์ที่เกือบจะเป็นมาตรฐานโดยพฤตินัย (de facto standard) ของการสร้างแอป RAG เขายกตัวอย่างผู้เล่นใหญ่อย่าง Microsoft Copilot ที่ค้นโฟลเดอร์และเอกสารใน SharePoint ว่าใช้ hybrid search และบอกว่าผลิตภัณฑ์ที่เล็กลงมาก็ใช้เช่นกัน

แผนที่ของรายงาน: หัวข้อ 2–6 คือทฤษฎีบนสไลด์ (พร้อมสูตร BM25 ที่ผู้จัดทำเติม), หัวข้อ 7–11 คือโค้ดใน notebook ทีละ cell พร้อมผลบนจอ, หัวข้อ 12–13 คือ RRF ถ่วงน้ำหนักทีละตัวเลข และหัวข้อ 14–15 คือระบบขนาดจริงกับ reranker

2. จุดบอดของ vector search ล้วน (~1:05–2:30)

สไลด์ "Problem with the pure vector search" ขึ้นทีละบรรทัด ห้าข้อ (ถอดจากภาพ ใจความตรงตามสไลด์):

  1. vector search เก่งเรื่องเข้าใจความหมาย (semantic meaning) และบริบท
  2. แต่มีจุดบอดบางอย่างที่ทำให้คุณภาพการค้น (retrieval quality) เสีย
  3. มีปัญหากับการจับคำตรงตัว เช่นผู้ใช้ค้น "API key authentication" แต่ได้ผลเรื่อง "user login security"
  4. อาจพลาดคำสำคัญที่ผู้ใช้เอ่ยถึงโดยเจาะจง
  5. บางครั้งผู้ใช้รู้แน่ชัดว่าต้องการหาคำไหน

ผู้สอนอธิบายสาเหตุว่า embedding ดูความหมายของประโยคหรือกลุ่มคำ "user login security" มีความหมายใกล้ "API key authentication" chunk นั้นจึงถูกดึงมา ข้อนี้เรารู้กันอยู่แล้ว แต่ถ้าผู้ใช้รู้ว่าในเอกสารมีคำนี้อยู่จริงและต้องการเฉพาะ "API key authentication" vector search จะ "fumble" คือพลาดเป้า ตรงนี้เองที่ keyword search แบบคลาสสิกเข้ามา

เสริมจากผู้จัดทำ: ทำไม vector ถึงพลาดคำตรงตัว

embedding อัดทั้งประโยคเป็นเวกเตอร์เดียว คำหายากหนึ่งคำ (รหัส ชื่อยา เลขรุ่น) จึงมีน้ำหนักเล็กน้อยในเวกเตอร์รวม ขณะที่คำทั่วไปรอบ ๆ ดึงเวกเตอร์ไปหา chunk ที่ "เรื่องเดียวกัน" ส่วน BM25 ให้คำหายากมีน้ำหนักสูงโดยตรงผ่าน IDF (หัวข้อ 4) สองวิธีจึงพลาดกันคนละแบบ

3. Keyword search แบบคลาสสิก: จุดแข็งและจุดอ่อน (~2:30–4:05)

ครึ่งล่างของสไลด์เดียวกัน (ภาพในหัวข้อ 2) หัวข้อ "This is where Keyword Search comes in (The Classic Approach)" มีสี่บรรทัด:

  • keyword search หาคำที่ตรงกันทุกตัว (exact word matches) ใน chunk
  • มีมานานมากแล้ว (ให้นึกถึง Google ในช่วงต้นทศวรรษ 2000)
  • เชื่อถือได้สูงมากในการหาคำเฉพาะ ชื่อ เลขรุ่น (model numbers) และศัพท์เทคนิค
  • แต่ "โง่" คือไม่เข้าใจว่า "car" กับ "automobile" หมายถึงสิ่งเดียวกัน

ผู้สอนเรียกว่าแบบคลาสสิกเพราะ Google ยุค 2000 ใช้ keyword search และบอกว่าแม้ตอนนี้ช่องค้นของ Amazon ก็ยังใช้ keyword search เพราะต้องการการจับคำตรงตัว ใช้ vector ที่นั่นไม่ได้ (ส่วนของ Google ยืนยันบางส่วน ส่วน Amazon ผู้จัดทำไม่ได้ตรวจ ดูตารางตรวจข้อเท็จจริง) เมื่อรวม keyword กับ vector จะได้ hybrid search ที่ "แม่นขึ้นมาก" ผู้สอนบอกว่าความแม่นของแอป RAG จะ "พุ่งทะลุหลังคา"

ประสบการณ์ของผู้สอน: ในสองสามโปรเจกต์ล่าสุดเขาทำงานกับเอกสารยา ที่มีศัพท์เทคนิคและชื่อยาซับซ้อนซึ่ง vector embedding อย่างเดียวจับไม่ได้ เขาจึงต้องเติม keyword search และความแม่นของระบบเพิ่มขึ้น "อย่างน้อยราว 70 %" (ไม่มีตัวชี้วัดหรือชุดทดสอบในคลิป) ปิดช่วงนี้ด้วยการย้ำว่า keyword search "โง่" แต่เมื่อจับคู่กับ vector search จะเป็นคู่ที่ทรงพลังมาก

(1) น้ำหนัก 0.5 / 0.5 ให้อันดับเดียวกับ RRF ไม่ถ่วงน้ำหนัก เพราะคะแนนแค่หารสองทั้งหมด X กับ Y จึงยังเสมอกันพอดี ต้องมีกติกาตัดสินเสมอ (LangChain เรียงตามลำดับที่พบก่อน) (2) น้ำหนัก 0.7 / 0.3 ทำลายการเสมอของ X กับ Y และทำให้ W, V ที่อยู่เฉพาะ vector แซง A, B ที่อยู่เฉพาะ keyword ซึ่งในแบบน้ำหนักเท่ากัน A อยู่อันดับ 4 (3) แม้ถ่วง 0.7 ให้ vector Z ที่อยู่ทั้งสองรายการก็ยังได้มากกว่า W ราว 1.44 เท่า การ "อยู่ในทั้งสองรายการ" มีผลแรงกว่าน้ำหนักในช่วงนี้

หลังสไลด์ ผู้สอนกลับไปที่ notebook และแก้ cell เป็น weights=[0.7, 0.3] แล้วรันใหม่ (คอมเมนต์ "Equal weight…" ยังเป็นของเดิม) ตามที่พูดไว้ว่า "เปลี่ยนแบบนี้ได้" ผลของสาม query ในหัวข้อ 11 รันด้วย 0.5 / 0.5 ก่อนการแก้นี้

14. Reality: ขนาดจริงและ multi-query hybrid (~20:23–23:20)

ผู้สอนบอกว่าที่ผ่านมาเป็นโปรเจกต์ของเล่นใน Jupyter แต่แนวคิดทั้งหมดยังใช้ได้ใน production ต่างกันที่ขนาด งานที่เขาเคยเป็นที่ปรึกษามีเอกสารระดับ 10,000 ถึง 20,000 จึงไม่ได้ดึงฝั่งละ 3 chunk แต่ดึง 30 หรือ 50 หรือ 60 ต่อฝั่ง สไลด์ "Reality" สรุปเป็นภาพ: ฝั่ง vector 50 chunk ฝั่ง keyword 50 chunk รวมด้วย RRF ได้ "~30 chunks"

RRF เป็นแค่การให้คะแนนใหม่แล้วเรียง สองรายการ รายการละ 50 จะได้ chunk ไม่ซ้ำ 50 (ถ้าซ้ำกันหมด) ถึง 100 (ถ้าไม่ซ้ำเลย) เสมอ ตัวเลขราว 30 บนสไลด์จึงต้องมาจากการตัด top-N หลัง RRF ซึ่งสไลด์และคำพูดไม่ได้บอก (ใน EnsembleRetriever ของ LangChain ไม่มีการตัดนี้ ผลที่ได้คือทั้งหมด)

ระบบในผลิตภัณฑ์ของผู้สอน (Open Slate) มีกลยุทธ์ "multi-query hybrid search": คำถามของผู้ใช้หนึ่งข้อถูกแปลงเป็น 5 แบบ แต่ละแบบไปทำ hybrid search ของตัวเอง ฝั่ง vector 50 ฝั่ง keyword 50 รวมด้วย RRF ผู้สอนยอมรับว่า "เริ่มซับซ้อน" แบบแรกได้ราว 30 chunk แบบที่สองได้ 25, 30 หรือ 35 แล้วทำ RRF อีกชั้นข้ามทุกแบบ (เหมือนในคลิป multi-query) สุดท้ายยังเหลือ 30, 25 หรือ 40 chunk

15. Reranking: ขั้นสุดท้ายหลัง RRF (~23:20–27:42)

ผู้สอนทวนทั้ง pipeline ด้วยแผนภาพหกขั้น (ถอดจากภาพ): 1 คำถาม "What is the capital of France?" → 2 retriever หลายตัว (Dense, Sparse, Hybrid) → 3 แต่ละ retriever จัดอันดับของตัวเอง → 4 RRF Fusion → 5 อันดับรวม → 6 สร้างคำตอบจาก top docs เขาอธิบายว่า dense คือ vector search และ sparse คือ keyword search ขั้นที่ 3 retriever ทำเอง เช่น vector คืน 50 chunk เรียงจากเกี่ยวข้องมากไปน้อย keyword ก็เช่นกัน ขั้นที่ 4 คือ RRF จากคลิปก่อน chunk ที่อยู่สองรายการจะถูกรวมเป็นหนึ่งและได้อันดับตามคะแนน

ถ้า RRF ให้มาราว 30 chunk ยังส่งทั้งหมดให้ LLM ไม่ได้ ผู้สอนให้สองเหตุผล: อาจเกิน context window และ "แพงอยู่บ้าง" เพราะ LLM ต้องประมวลผล token จำนวนมาก จึงต้องเลือกแค่ top K เช่น top 5 ทางแก้คือ re-ranking model ที่ผู้สอนอธิบายว่า:

  • เป็นโมเดลที่ "ฉลาด" ไม่ได้ "โง่" อย่างอัลกอริทึมธรรมดา
  • ไม่ใช่ LLM ไม่แพงเท่า LLM อยู่ "ตรงกลาง" ระหว่างสองอย่าง
  • ดูคำถามกับ chunk ทั้ง 30 แล้วจัดอันดับใหม่ เช่น chunk ที่ 3 ตรงกับคำถามที่สุดก็ย้ายขึ้นบนสุด จึงเรียกว่า reranker
  • เป็น "ตัวกรองเพิ่มเติม" หลังดึง chunk มาแล้ว จากนั้นค่อยเลือก top 5 หรือ top 10 อย่างมั่นใจ

Key Takeaways

1.Hybrid search = vector search (ความหมาย) + keyword search แบบ BM25 (คำตรงตัว) รวมอันดับด้วย RRF แต่ละฝั่งปิดจุดอ่อนของอีกฝั่ง: vector พลาด "API key authentication" ส่วน keyword ไม่รู้ว่า car = automobile
2.สไลด์ BM25 มีแค่ TF กับ IDF เป็นคำบรรยาย สูตรจริงคือ Σ IDF × ส่วน TF ที่อิ่มตัวและปรับตามความยาว (สมการ 11, ผู้จัดทำ) ทำให้คำหายากชนะคำที่ถูกยัดซ้ำ: 8.3282 ต่อ 3.4397 ในตัวอย่าง Combined (ผู้จัดทำคำนวณ)
3.การตัดคำเป็นส่วนหนึ่งของ BM25: ตัวตัดคำค่าเริ่มต้นของ BM25Retriever ทำให้ "Tesla's" ไม่ใช่ "Tesla" และพลิกผลตัวอย่าง TF ของสไลด์ (ผู้จัดทำคำนวณ)
4.RRF ถ่วงน้ำหนัก = Σ w / (60 + rank) ตรงกับโค้ด LangChain; ตาราง 0.7 / 0.3 ของสไลด์คำนวณซ้ำได้ทุกช่อง X 0.0163, Y 0.0162, Z 0.0157 … และเอกสารที่อยู่สองรายการชนะเสมอในตัวอย่างนี้
5.น้ำหนัก 0.5 / 0.5 ให้อันดับเดียวกับ RRF ธรรมดา (X เสมอ Y) ต้องกำหนดกติกาตัดสินเสมอเอง (ผู้จัดทำ)
6.ระบบจริง: ฝั่งละ 50, RRF ราว 30, multi-query เหลือ 25–40 แล้ว reranker คัดเหลือ 5–10 ส่วน RRF เองไม่ตัดรายการ (ผู้จัดทำ)
