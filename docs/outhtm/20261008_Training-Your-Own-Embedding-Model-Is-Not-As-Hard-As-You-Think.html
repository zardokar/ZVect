Training Your Own Embedding Model Is Not As Hard As You Think — Prompt Engineering

✍️ Prompt Engineering (YouTube)📅 เผยแพร่ 2026-10-08⏱ 12:36🎞 caption อังกฤษอัตโนมัติ (ASR)📝 เรียบเรียงใหม่ด้วยคำของผู้จัดทำ ครบทุกประเด็นและตัวเลข🔎 ตรวจข้อเท็จจริง 8 ข้อ (2026-10-11) 🔗 คลิปต้นฉบับ (YouTube)

📋 บทสรุปย่อ

บทสรุปย่อ: ผู้สอนแสดงว่า embedding model สำเร็จรูปรู้แค่ข้อมูลทั่วไป ไม่รู้จักเอกสาร ชื่อสินค้า หรือเสียงที่แอปของเราสนใจ แต่ fine-tune ได้ไม่ยาก ต่างจากการ fine-tune LLM ตรงที่ไม่มี "เวกเตอร์คำตอบที่ถูก" ให้เป็นเป้า สิ่งที่บอกโมเดลได้มีอย่างเดียวคือ อะไรควรอยู่ใกล้อะไร ข้อมูลฝึกจึงเป็นคู่ (คำถาม, ข้อความที่ตอบ) ใช้ in-batch negatives (MultipleNegativesRankingLoss) ต้องกันข้อความซ้ำในแบตช์ด้วย no-duplicates sampler ใช้ prompt ตอนฝึกให้ตรงกับตอนค้น และฝึกแค่ LoRA (ในการรันของผู้สอน < 2% ของน้ำหนัก) ผลบน EmbeddingGemma 2: เสียง ESC-50 จากราว 1 ใน 4 เป็นราว 2 ใน 3 (สไลด์: top-1 24.5% → 65.8%) ใน ~7.5 นาที และค้น transcript YouTube ของตัวเองจาก ~2 ใน 3 → 3 ใน 4 แต่โมเดลเรียนป้ายที่ให้ ไม่ได้เรียน "การฟัง" ทั่วไป และค้นข้อความทั่วไปลดลงราว 4 คะแนน

โหมดของเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ (license มาตรฐานของ YouTube, ตรวจ 2026-10-11) ครบทุกประเด็นและตัวเลขตามลำดับคลิป ไม่เปลี่ยนความหมาย · คลิปใหม่กว่าความรู้ของผู้จัดทำ จึงตรวจข้อเท็จจริง 8 ข้อด้วยการค้นเว็บ (ส่วนที่ 9)

🧭 สรุปเชิงลึก

ทำไมต้อง fine-tune: โมเดลสำเร็จรูปรู้เฉพาะข้อมูลทั่วไปที่ฝึกมา ผู้สอนโชว์เดโมที่ fine-tune EmbeddingGemma 2 บน transcript ของช่องตัวเอง: พิมพ์คำถามแล้วได้ช่วงเวลาในคลิปที่พูดเรื่องนั้นพร้อม timestamp คำถามของคลิปคือ "fine-tune ไม่กี่นาทีทำให้ดีขึ้นชัดเจนกับข้อมูลของเรา โดยไม่ทำของเดิมพังได้ไหม"

ต่างจาก LLM อย่างไร: LLM มีข้อความคำตอบที่ถูกเป๊ะเป็นเป้า แต่ embedding model แค่เปลี่ยน input เป็นรายการตัวเลข ซึ่งมีความหมายเมื่อเทียบกันเท่านั้น จึงไม่มีรายการตัวเลขที่ถูกให้เขียนเป็นเป้า บอกได้แค่ว่าอะไรควรใกล้กัน ข้อมูลฝึก = คู่ (คำถามลูกค้า, ข้อความที่ตอบ) ไม่ต้องมีคะแนนหรือป้ายคำตอบผิด แต่ดึงคำถามเข้าหาคำตอบอย่างเดียวไม่พอ เพราะโมเดลอาจวางทุกอย่างไว้จุดเดียวแล้วยังได้คะแนนดี

In-batch negatives: ในแบตช์หนึ่ง เช่น 32 คู่ คำตอบของตัวเองคือข้อถูก ข้อความอื่นทุกชิ้นในแบตช์ถือเป็นข้อผิด จึงได้ "คำตอบผิดฟรี" ไม่ต้องติดป้าย คิดเหมือนข้อสอบปรนัยที่ตัวเลือกผิดมาจากคู่อื่น ใน Sentence Transformers ชื่อ MultipleNegativesRankingLoss และเป็นแนวคิดเดียวกับที่ CLIP ใช้รวมภาพกับข้อความ กับดัก: ถ้าสองคำถามมีคำตอบเดียวกันอยู่ในแบตช์เดียว ข้อความที่ซ้ำจะถูกนับเป็นข้อผิด → สอนว่าคำตอบที่ถูกคือผิด แก้ด้วย no-duplicates sampler

Prompt และ LoRA: EmbeddingGemma 2 ต้องมี task prompt สั้น ๆ หน้าคำค้น และรูปแบบ title/text สำหรับเอกสาร รูปแบบตอนฝึกควรเหมือนตอนใช้งานทุกประการ ส่วนที่ฝึกคือ LoRA (เมทริกซ์เล็กข้างชั้นเดิม น้ำหนักเดิมแช่แข็ง) ในการรันของผู้สอนน้อยกว่า 2% ของน้ำหนัก จึงเซฟเป็นไฟล์ adapter เล็ก ๆ ได้ อีกเรื่องหนึ่งคือ ข้อความ ภาพ วิดีโอ เสียง ผ่าน backbone เดียวกัน ฝึกด้วยเสียงจึงกระทบส่วนที่ใช้กับภาพและข้อความด้วย ต้องวัดผลกระทบ และวัดบนข้อมูลที่ไม่เคยเห็น โดยแบ่ง train/test ตามแหล่ง (บทความ คลิป หรือการบันทึก)

ผล: ESC-50 (เสียง 50 ชนิด) ก่อนฝึก top-1 ราว 1 ใน 4 (ผู้สอนพูดว่าราว 25%; สไลด์: 24.5%) prompt สำหรับ classification ของโมเดลแย่กว่าเขียนป้ายเป็นคำค้นด้วยซ้ำ ฝึก ~7.5 นาทีบน A100 ได้ราว 2 ใน 3 (สไลด์: 65.8%, top-5 57.0 → 92.3) บางเสียงที่ไม่เคยถูกเลยกลับถูกเกือบทุกครั้ง (สไลด์: brushing_teeth 0% → 100%, toilet_flush 0% → 88%) แต่เมื่อซ่อน 10 เสียงจากการฝึก 10 เสียงนั้นไม่ดีขึ้น → โมเดลเรียนป้ายที่ให้ ไม่ได้เรียนการฟังทั่วไป ผลข้างเคียง: ค้นภาพและค้นด้วยเสียงไม่ขยับ แต่ข้อความทั่วไปลดราว 4 คะแนน (สไลด์: NanoBEIR nDCG@10 59.2 → 55.6) ครั้งแรกค้นด้วยเสียงตกเกือบศูนย์ เพราะ processor ที่เซฟมากับ adapter ตัดเสียงเหลือไม่กี่มิลลิวินาที แก้หนึ่งบรรทัดโดยใช้ processor ของโมเดลฐาน ข้อความ: transcript 120 คลิป ตัดเป็นช่วงสั้น ให้ Gemini 3.8 Flash เขียนคำถามหนึ่งข้อต่อช่วง (สไลด์: 1,971 pairs) แบ่งตามคลิป ฝึก < 3 นาที ได้ 2 ใน 3 → 3 ใน 4 (คำอธิบายคลิป: 66.3% → 75.0%)

สรุปของผู้สอน: ถ้าจะ fine-tune EmbeddingGemma 2 ผู้สอนจะเน้น 3 อย่าง — คู่ข้อมูล + ไม่มีซ้ำในแบตช์, ทดสอบบนข้อมูลที่ไม่เคยเห็นโดยแบ่งตามแหล่ง, และตรวจสิ่งอื่นที่เปลี่ยนเพราะ backbone ใช้ร่วมกันทุก modality โยงกับ ZVect (ผู้จัดทำ): in-batch negatives คือการดันคู่ที่ไม่ใช่ให้ห่าง ต่อยอดบท 3.7 "ตารางมาจากการฝึก" และบท 6.1 Bi-Encoder ได้

1. ทำไมต้อง fine-tune และเดโม (~0:00–1:02)

ผู้สอนเปิดว่า EmbeddingGemma 2 เป็นโมเดลเปิดที่ดีสำหรับการค้นหลายสื่อ แต่ที่ทำให้ดีขึ้นอีกคือ fine-tune ด้วยข้อมูลของเราเองได้ เหตุผลคือโมเดลสำเร็จรูปรู้แค่ข้อมูลทั่วไปที่ฝึกมา ไม่รู้จักเอกสารของเรา ชื่อสินค้า หรือเสียงที่แอปของเราสนใจ

เดโม: เวอร์ชันที่ fine-tune บน transcript ของช่องผู้สอนเอง พิมพ์คำถามแล้วได้ช่วงเวลาในคลิปที่พูดเรื่องนั้น พร้อม timestamp ที่กดได้ คำถามหลักของคลิป: fine-tune ไม่กี่นาทีทำให้โมเดลดีขึ้นอย่างเห็นได้ชัดกับข้อมูลของเรา โดยไม่ทำของที่ทำได้ดีอยู่แล้วพัง ได้หรือไม่ แผนคือเล่าวิธีทำงานก่อน แล้วเปิด notebook ที่ fine-tune กับตัวอย่างของผู้สอนสองชุด (เสียง และ transcript)

ข้อสังเกต (ผู้จัดทำ): ASR ได้ยินชื่อโมเดลช่วงแรกเป็น "Embedding Gemini 2" แต่สไลด์และคำอธิบายคลิปเขียน EmbeddingGemma 2

2. Fine-tune embedding ต่างจาก LLM (~1:03–2:26)

เวลา fine-tune LLM เราให้ input พร้อมข้อความที่อยากให้เขียนตอบแบบคำต่อคำ ข้อมูลฝึกจึงมีคำตอบที่ถูกอยู่แล้ว แต่ embedding model ไม่ได้เขียนอะไร มันแปลง input เป็นรายการตัวเลข และตัวเลขเหล่านั้นมีประโยชน์เมื่อเทียบกันเท่านั้น (ที่เรียกกันว่า embedding space) จึงไม่มีรายการตัวเลขที่ถูกให้เขียนเป็นเป้า สิ่งเดียวที่บอกโมเดลได้คืออะไรควรจบลงใกล้กัน

ตัวอย่าง: ทำซัพพอร์ตให้บริษัท smart home อยากได้ช่องค้นที่ตอบคำถามลูกค้าจาก help center ข้อมูลฝึกแต่ละตัวเป็นคู่ คำถามลูกค้า + ข้อความที่ตอบ ไม่ต้องมีคะแนนหรือป้ายคำตอบผิด แต่การดึงคำถามเข้าหาข้อความของมันอย่างเดียวไม่พอ เพราะโมเดลอาจวางทุกอย่างไว้จุดเดียวแล้วยังได้คะแนนดี

3. In-batch negatives และกับดักข้อความซ้ำ (~2:27–4:05)

ระหว่างฝึก โมเดลเห็นทีละแบตช์ เช่น 32 คู่ สำหรับแต่ละคำถาม ข้อความของตัวเองคือคำตอบที่ถูก และข้อความอื่นทุกชิ้นในแบตช์ถือเป็นคำตอบผิด จึงไม่ต้องเก็บตัวอย่างผิดเอง ได้มาโดยอัตโนมัติเมื่อมีคู่ loss จะดึงคำถามเข้าหาข้อความของตัวเองและผลักออกจากข้อความอื่น ภาพที่จำง่ายคือข้อสอบปรนัยที่ตัวเลือกผิดมาจากคู่อื่นในแบตช์ ใน Sentence Transformers ชื่อ MultipleNegativesRankingLoss และเป็นแนวคิดเดียวกับที่ CLIP ใช้รวมภาพกับข้อความไว้ในปริภูมิเดียว

กับดัก: ถ้าลูกค้าสองคนถามเรื่องวิธี reset เดียวกัน และทั้งสองคู่อยู่ในแบตช์เดียว loss จะถือว่าข้อความชิ้นที่สองเป็นคำตอบผิดของคำถามแรก = สอนว่าคำตอบที่ถูกคือผิด (false negative) วิธีแก้คือ batch sampler ที่ไม่ใส่ข้อความเดียวกันสองครั้งในแบตช์ Sentence Transformers เรียกว่า no duplicates sampler

สูตรแบบย่อ (ความรู้ทั่วไป / ผู้จัดทำเลือก): สำหรับคำถาม qi ในแบตช์ขนาด B: lossi = −log( es(qi,pi) / Σj=1..B es(qi,pj) ) โดย s คือ cosine คูณ scale — คลิปไม่ได้แสดงสูตรนี้ ใส่ไว้ให้เห็นว่าทำไมข้อความซ้ำ (pj = pi) จึงทำร้ายการฝึก

4. Prompt ต้องเหมือนกันตอนฝึกและตอนค้น (~4:06–4:36)

เรื่องที่สองที่ต้องทำให้ถูกคือ prompt: EmbeddingGemma 2 คาดหวังtask prompt สั้น ๆ หน้าคำค้น และรูปแบบ title กับ text สำหรับเอกสาร รูปแบบที่ใช้ตอนฝึกคือรูปแบบที่โค้ดค้นหาต้องใช้ ผู้สอนเทียบกับ prompt template ของ LLM: template ตอนฝึกควรเหมือนกันทุกประการกับตอน production หรือ inference

เหตุผล (ผู้จัดทำอธิบายเพิ่ม): embedding ของ "task: search result | query: …" กับของข้อความเดียวกันที่ไม่มี prompt ไม่ใช่เวกเตอร์เดียวกัน ถ้าฝึกแบบหนึ่งแล้วค้นอีกแบบ คำถามจะไปตกคนละที่กับที่ฝึกไว้

ผลตรวจ (ส่วนที่ 9): model card ของ EmbeddingGemma 2 ระบุ prompt ของคำค้นเป็น task: search result | query: {query} และของเอกสารเป็น title: {title} | text: {content} (ไม่มีชื่อเรื่องให้ใช้ title: none)

5. LoRA บน backbone ที่ใช้ร่วมกันทุกสื่อ และการวัดผล (~4:37–6:20)

แทนที่จะอัปเดตน้ำหนักทั้งหมด ใช้ LoRA: เพิ่มเมทริกซ์เล็กที่ฝึกได้ไว้ข้างชั้นเดิม แล้วแช่แข็งน้ำหนักเดิม ฝึกเร็วมาก ไม่ต้องฝึกทั้งเครือข่าย ในการรันของผู้สอนส่วนที่ฝึกน้อยกว่า 2% ของน้ำหนัก จึงเซฟเป็นไฟล์ adapter เล็ก ๆ แทนสำเนาโมเดลทั้งก้อน

คลิปก่อนหน้าแสดงว่าข้อความ ภาพ วิดีโอ และเสียงของ EmbeddingGemma 2 ผ่าน backbone เดียวกัน ดังนั้นถ้าฝึก backbone ด้วยเสียง ก็เปลี่ยนส่วนที่ดูแลภาพและข้อความไปด้วย ต้องเช็กว่าแลกมาด้วยอะไร

การวัดผล: loss ที่ลดลงบอกแค่ว่าเก่งขึ้นกับตัวอย่างที่ฝึก สิ่งที่ควรสนใจคือคุณภาพการค้นกับคำถามที่ไม่เคยเห็น ไม่อย่างนั้นก็แค่ overfit ให้กันชุดทดสอบไว้และแบ่งตามแหล่ง: ถ้าบทความเดียวกันมีข้อความทั้งใน train และ test โมเดลก็เหมือนเห็นคำตอบแล้ว จึงแบ่งตามบทความ ตามคลิป หรือตามการบันทึก และคำถามสำหรับการทดลองคือ โมเดลเรียนทักษะทั่วไป หรือแค่ป้ายของเรา

ผลตรวจ (ส่วนที่ 9): model card ระบุ 740M พารามิเตอร์ = text backbone 270M + vision encoder 170M + audio encoder 300M ส่งเข้าปริภูมิร่วม 768 มิติ สไลด์ของคลิปเอง (ส่วนที่ 7) ก็วาด vision encoder และ audio encoder แยก ป้อนเข้า EmbeddingGemma 2 ตรงกลาง คำว่า "backbone เดียวกัน" จึงหมายถึงส่วนกลางที่ทุกสื่อผ่าน

6. Notebook: เสียง ESC-50 และการซ่อน 10 เสียง (~6:21–9:11)

Notebook สร้างบน notebook EmbeddingGemma 2 ของ Unsloth รันทั้งหมดบน A100 ใน Colab (ลิงก์อยู่ในคำอธิบาย) ตัวอย่างแรกแก้จุดอ่อนจากคลิปก่อน: เสียงในชีวิตประจำวัน ใช้ชุด ESC-50 ที่มีคลิปสั้นของเสียง 50 ชนิด เช่น หมาเห่า ฝน เลื่อยยนต์ ชื่อเสียงแต่ละชนิดกลายเป็นประโยค เช่น "the sound of a chainsaw" การจัดหมวดจึงกลายเป็นการค้น: โมเดล embed คลิปเสียง embed ประโยคป้าย แล้วเลือกป้ายที่ใกล้สุด

ก่อนฝึก เลือกเสียงถูกเป็นอันดับแรกได้ราว 1 ใน 4 (ผู้สอนพูดว่าประมาณ 25%) และ prompt สำหรับ classification ที่มากับโมเดลยังแย่กว่าการเขียนป้ายเป็นคำค้นด้วย แปลว่า prompt ที่ดีกว่าแก้ไม่ได้ ต้องฝึก คู่ฝึกคือ (ประโยคป้าย, คลิปเสียง) ตรงนี้กับดักข้อความซ้ำสำคัญมาก เพราะแต่ละป้ายมีหลายคลิป ไม่มี no-duplicates sampler ป้ายเดียวกันจะลงแบตช์เดียวกัน ใส่ LoRA ที่ audio encoder และ backbone ฝึกราว 7 นาทีครึ่งบน A100

หลังฝึก (ดูอันดับแรกของคลิปที่โมเดลไม่เคยได้ยิน) จากราว 1 ใน 4 เป็นราว 2 ใน 3 และบางเสียงที่ไม่เคยถูกเลยกลับถูกเกือบทุกครั้ง เช่น เสียงแปรงฟัน ผู้สอนสรุปว่าการฝึก LoRA adapter บนน้ำหนักเดิมช่วยเพิ่มความแม่นยำได้มาก ทดสอบว่าเรียน "การฟัง" หรือแค่ "ป้าย": รันใหม่โดยซ่อน 10 เสียงจากการฝึกทั้งหมดแล้วทดสอบบน 10 เสียงนั้น เสียงที่ฝึกดีขึ้นเหมือนเดิม แต่ 10 เสียงที่ไม่เคยเห็นไม่ดีขึ้น ข้อสรุปของผู้สอน: โมเดลเรียนป้ายที่เราให้ ไม่ใช่การฟังทั่วไป ถ้า fine-tune แอปของตัวเอง ทุกป้ายที่สนใจต้องอยู่ในข้อมูลฝึก มันขยายไปเองไม่ได้

7. ผลข้างเคียงกับสื่ออื่น และบั๊กตอนโหลด adapter (~9:12–10:24)

ผู้สอนโหลดโมเดลเต็มทั้งแบบมีและไม่มี adapter แล้ววัด 3 อย่าง: ค้นภาพ ค้นด้วยเสียงพูด และค้นข้อความทั่วไป ค้นภาพกับค้นด้วยเสียงไม่ขยับเลย แต่ค้นข้อความทั่วไปลดลงราว 4 คะแนน ซึ่งเป็นราคาของการเปลี่ยน backbone ที่ใช้ร่วมกัน ถ้าแอปพึ่งการค้นข้อความทั่วไปด้วย ผู้สอนแนะนำให้ทดสอบหลัง fine-tune ทุกครั้ง

บั๊ก: ครั้งแรกที่วัด การค้นด้วยเสียงตกเกือบศูนย์ ดูเหมือนโมเดลลืมเสียงพูด ผู้สอนไล่ทีละขั้นแล้วพบว่าน้ำหนัก adapter โหลดถูกต้อง ปัญหาอยู่ที่ processor ที่เซฟมากับ adapter ในกรณีของผู้สอนมันตัดคลิปเสียงทุกคลิปเหลือไม่กี่มิลลิวินาที ทุกเสียงจึงดูเหมือนกันสำหรับโมเดล แก้หนึ่งบรรทัดโดยใช้ processor ของโมเดลฐาน คำแนะนำ: ถ้าเซฟแล้วโหลด audio adapter กลับมา อย่างน้อยกับเวอร์ชันที่ผู้สอนใช้ ให้ทดสอบใหม่หลังโหลด

ตัวเลขบนสไลด์ (อ่านจากภาพ): photo R@1 86.3 → 86.0 · voice→photo R@1 95.0 → 96.0 · voice→photo R@5 99.0 → 99.0 · NanoBEIR nDCG@10 59.2 → 55.6 (−3.6, ที่ผู้สอนพูดว่า "ราว 4 คะแนน")

8. ตัวอย่างข้อความ: transcript ของช่อง และสรุป 3 ข้อ (~10:25–12:36)

ตัวอย่างข้อความในเดโม: เอา transcript 120 คลิปของผู้สอนมาตัดเป็นช่วงสั้น ไม่มีคำถามของแต่ละช่วง จึงให้ Gemini 3.8 Flash เขียนคำถามแบบผู้ชมหนึ่งข้อต่อช่วง ได้คู่ (คำถาม, ข้อความที่ตอบ) ตามรูปแบบที่พูดไว้ (สไลด์: 1,971 pairs) แล้วแบ่งตามคลิป คำถามทดสอบจึงมาจากคลิปที่โมเดลไม่เคยเห็นตอนฝึก

ก่อนฝึก ข้อความที่ถูกขึ้นเป็นอันดับแรกราว 2 ใน 3 หลังฝึกไม่ถึง 3 นาที เป็น 3 ใน 4 (คำอธิบายคลิป: 66.3% → 75.0% top-1) การค้นข้อความทั่วไปลดลงราว 4 คะแนนเหมือนตัวอย่างเสียง ถ้าจะใช้กับข้อมูลของตัวเอง ต้องมีแค่ไฟล์คำถามกับข้อความในรูปแบบเดียวกัน

คำตอบของคลิป: ใช่ fine-tune ไม่กี่นาทีทำให้ดีขึ้นชัดเจนกับเสียงและคลิปของผู้สอน แต่โมเดลเรียนป้ายของผู้สอน ไม่ใช่ทักษะทั่วไป และเสียคะแนนค้นข้อความทั่วไปไปบ้าง ถ้าจะ fine-tune EmbeddingGemma 2 ผู้สอนจะเน้น 3 อย่าง: (1) แปลงข้อมูลเป็นคู่และกันซ้ำออกจากแบตช์ (2) ทดสอบบนข้อมูลที่ไม่เคยเห็น แบ่งตามแหล่ง (3) ตรวจว่าอะไรเปลี่ยนไปบ้างหลังฝึก เพราะ backbone ใช้ร่วมกันทุกสื่อ ผู้สอนมองว่านี่เป็นสิ่งที่ใช้งานได้จริงที่สุดอย่างหนึ่งกับ embedding model "อย่างน้อยในการทดลองของผู้สอน"

9. ผลตรวจข้อเท็จจริง (เสริมจากผู้จัดทำ, 2026-10-11)

คลิปเผยแพร่หลังความรู้ของผู้จัดทำ จึงให้ผู้ตรวจแยกค้นเว็บจากแหล่งต้นทาง 8 ข้อ: ยืนยัน 7 · บางส่วน 1 · ไม่พบ 0 · ขัดแย้ง 0

Key Takeaways

  1. embedding model ไม่มีเวกเตอร์คำตอบที่ถูก สอนได้แค่ อะไรควรใกล้อะไร → ข้อมูลฝึก = คู่ (คำถาม, ข้อความที่ตอบ)
  2. in-batch negatives ให้ข้อผิดฟรี แต่ต้องกันข้อความซ้ำในแบตช์ (no-duplicates sampler) ไม่งั้นสอนว่าคำตอบที่ถูกคือผิด
  3. prompt ตอนฝึกควรเหมือนตอนค้นทุกประการ
  4. LoRA (ในการรันของผู้สอน < 2% ของน้ำหนัก) ฝึกไม่กี่นาที: ESC-50 (สไลด์) 24.5% → 65.8%, transcript (คำอธิบาย) 66.3% → 75.0%
  5. โมเดลเรียนป้ายที่ให้ ไม่ใช่ทักษะทั่วไป · แบ่ง test ตามแหล่ง · วัดผลข้างเคียง (ข้อความทั่วไปลดราว 4 คะแนนทั้งสองตัวอย่าง; สไลด์ ESC-50: NanoBEIR −3.6) · ทดสอบใหม่หลังโหลด adapter
