บทสรุปย่อ

คลิปนี้ (ตอนที่ 17 ของเพลย์ลิสต์ RAG สำหรับมือใหม่) อธิบายว่า reranker คือโมเดล AI ที่ทำหน้าที่ "ความเห็นที่สอง" ต่อผลค้นหาชุดแรก: รับ query กับ chunk ทีละคู่เข้าโมเดลพร้อมกัน (cross-encoder) แล้วให้คะแนนความเกี่ยวข้องใหม่เพื่อเลือก chunk ที่ดีที่สุดไม่กี่อันส่งให้ LLM ผู้สอนเริ่มจากภาพรวม multi-query hybrid search (vector + keyword, รวมด้วย RRF สองชั้น) แล้วอธิบายกลยุทธ์สองขั้น (embedding เร็วและกว้าง, reranker แม่นและโฟกัส) เทียบ bi-encoder กับ cross-encoder จากนั้นสาธิตด้วยโค้ด LangChain + Cohere Rerank บนคลัง chunk ขนาดเล็ก ข้อสังเกตของผู้จัดทำ: ตัวเลข 50 / 35 / 25 chunk และคะแนน 0.82 / 0.79 / 0.78 / 0.12 ในคลิปเป็นตัวเลขสมมติเพื่ออธิบาย ผลโค้ดจริงมีเพียงตัวอย่างเดียวบนคลังเล็กที่ผู้สอนคาดไว้เองก่อนรันว่าผลน่าจะต่างไม่มาก

โหมดเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ แบบวิเคราะห์เชิงลึกพร้อมตรวจข้อเท็จจริง (license มาตรฐานของ YouTube; คำบรรยายเป็น ASR อังกฤษ)

สรุปเชิงลึก

ข้อโต้แย้งของคลิป. ผู้สอนบอกว่าสุดท้ายต้องการเพียงราว 10 chunk ส่งให้ LLM จึงถามว่าทำไมไม่หยิบ top 10 จากผล hybrid + RRF เลย คำตอบคือ embedding เป็นการ "ประมาณราคาถูก" ที่ให้ chunk ซึ่งมีโอกาสเกี่ยวข้องสูง แต่ลำดับที่แน่นอนยังเชื่อไม่ได้ในงานที่ต้องการความแม่น (องค์กร กฎหมาย ยา) เพราะ embedding ของ query กับ chunk ถูกคำนวณแยกกัน โมเดลไม่เคยเห็นสองอย่างนี้ด้วยกัน

ภาพรวมของ pipeline. query ถูกขยายเป็น 5 แบบ (ผู้สอนพูดว่า 5 หรือ 3) แต่ละแบบทำ vector search และ keyword search อย่างละ k = 50 (สมมติ ผู้สอนบอกว่าอาจเป็น 30 หรือ 80) รวมสองรายการด้วย RRF เหลือราว 35 chunk ต่อ query แล้วรวมห้ารายการด้วย RRF อีกรอบเหลือราว 25 chunk ก่อนเข้า reranker ซึ่งอ่าน query กับ chunk ทั้ง 25 อันแล้วคัด top n = 10 อันส่งต่อให้ LLM ผู้สอนบอกว่าจำนวน 35 และ 25 เป็นตัวเลขสมมติ และอาจเป็นอื่นได้ถึง 100

กลไก. Bi-encoder (embedding) แปลง query และ chunk เป็นเวกเตอร์ในเวลาต่างกันแล้วเทียบ cosine (ตัวอย่างบนสไลด์ query "apple stock price" กับ chunk "Apple trees grow in orchards" ได้ 0.78) ส่วน cross-encoder รับสตริงเดียวที่ต่อ query กับ chunk ด้วยตัวคั่น [SEP] แล้วตอบคะแนนความเกี่ยวข้อง (ตัวอย่างเดียวกันได้ 0.12 ซึ่งสไลด์กำกับว่าจับความไม่ตรงได้ถูกต้อง ผู้สอนพูดเพียงว่าแม่นกว่าจึงได้คะแนนต่ำ) ต้นทุนอยู่ตรงกลางระหว่าง embedding กับ LLM จึงใช้กับ chunk ประมาณ 10 ถึง 100 อันเท่านั้น ผู้สอนเปรียบเทียบกับการสัมภาษณ์คัดกรองตามด้วยการสัมภาษณ์เทคนิค

การสาธิต. โค้ดใช้ BM25 + vector ใน EnsembleRetriever น้ำหนัก 70 : 30 (ผู้สอนให้เหตุผลว่า vector search ฉลาดกว่าเล็กน้อย) ดึงอย่างละ 15 chunk ได้ผลรวม 18 chunk เพราะ RRF รวมรายการซ้ำ จากนั้นใช้ CohereRerank รุ่น rerank-english-v3.0 ด้วย top_n = 10 ผลก่อนและหลัง rerank ต่างกันเล็กน้อย: chunk ที่เป็นตัวเลขการเงินขึ้นมาอยู่สูงขึ้น ส่วนประโยคทั่วไปเรื่องแผนขยายโรงงานตกลงมา ผู้สอนคาดไว้ก่อนรันว่าคลังเล็กจึงน่าจะผลต่างไม่มาก และบอกว่าถ้ามี chunk เหลือเพียง 5 ถึง 10 อันก็ไม่ต้องมี reranker

ถูก ผิด และขาด (ผลตรวจของผู้จัดทำ). แนวคิดหลักถูกต้องตามเอกสาร Sentence-Transformers (retrieve แล้ว re-rank ด้วย cross-encoder ที่ให้คะแนนต่อคู่) ตรวจข้อเท็จจริง 12 ข้อ: ยืนยัน 6, ยืนยันบางส่วน 3, ไม่พบแหล่งยืนยัน 2, ขัดแย้ง 1 ข้อที่ควรแก้คือ "tsvector เป็น extension" ที่จริงเป็นชนิดข้อมูลในตัวของ PostgreSQL และ ts_rank ไม่ใช่ BM25 ข้อควรระวังอื่น: ตัวเลข 0.78 กับ 0.12 เป็นคนละมาตรวัด (cosine เทียบกับคะแนน reranker) ห้ามเอามาเทียบกันตรง ๆ, ข้อความ "Top 3" ในผลโค้ดแสดงรายการ 5 อัน, และคลิปไม่มีการวัดคุณภาพหรือเวลาหน่วง (latency) จริงของ reranker เลย

เอาไปใช้ต่อ (ข้อเสนอของผู้จัดทำ). ถ้าหลัง RRF ยังมี chunk มากกว่าจำนวนที่จะส่งให้ LLM (เกิน 5 ถึง 10 อันตามคลิป) และความแม่นสำคัญ ให้เติม reranker หลัง RRF; ถ้าคลังเล็กหรือ chunk เหลือน้อยอยู่แล้ว ข้ามได้

ตรวจข้อเท็จจริง

ข้ออ้างในคลิปผลตรวจรายละเอียดอ่านจาก
Reranker (cross-encoder) อ่าน query กับ chunk พร้อมกันแล้วให้คะแนนความเกี่ยวข้องยืนยันเอกสาร Sentence-Transformers: ป้อน query กับเอกสารเข้า transformer พร้อมกัน ได้คะแนนเดียวระหว่าง 0 ถึง 1sbert.net ผ่าน WebFetch
Bi-encoder เข้ารหัส query กับ chunk แยกกัน แล้วเทียบเวกเตอร์ยืนยันเอกสารเดียวกัน: bi-encoder เข้ารหัส query แล้วหาเวกเตอร์เอกสารที่ใกล้ที่สุดsbert.net ผ่าน WebFetch
ขั้นแรกดึง candidate จำนวนมาก ขั้นสองให้ reranker เรียงใหม่ (pipeline สองขั้น)ยืนยันตัวอย่างในเอกสารดึงราว 100 candidate ด้วย retriever (lexical หรือ bi-encoder) แล้วให้ cross-encoder ให้คะแนนsbert.net ผ่าน WebFetch
Cross-encoder แพงกว่า จึงใช้กับ chunk หลักสิบถึงร้อยเท่านั้นยืนยันบางส่วนเหตุผลถูก (ต้องรันโมเดลต่อคู่ ทำกับหลายล้านคู่ไม่ไหว) แต่ช่วง 10 ถึง 100 เป็นข้อสังเกตของผู้พูด ไม่ใช่ข้อกำหนดsbert.net ผ่าน WebFetch
Reranker อยู่ระหว่าง embedding กับ LLM ด้านต้นทุนและความแม่นไม่พบแหล่งยืนยันทิศทางสมเหตุสมผลและไม่มีตัวเลขในคลิป; ไม่พบแหล่งที่วัดเทียบสามแบบตรง ๆ ในรอบนี้—
LangChain EnsembleRetriever รวมสองรายการด้วย RRF จึงเหลือ 18 จาก 15 + 15ยืนยันซอร์สใช้ weighted RRF: คะแนน = weight / (rank + c) โดย c = 60, ตัด chunk ซ้ำตาม page_content แล้วเรียงตามคะแนนรวมซอร์ส ensemble.py ผ่าน WebFetch (สรุป)
น้ำหนัก 70 % vector / 30 % BM25ยืนยันน้ำหนักเป็นพารามิเตอร์ของ EnsembleRetriever (ค่าเริ่มต้นเท่ากันทุกตัว = 1/จำนวน retriever) ค่า 0.7 / 0.3 เป็นการตั้งของผู้สอนซอร์ส ensemble.py ผ่าน WebFetch (สรุป)
Cohere rerank-english-v3.0 รองรับเอกสารภาษาอังกฤษ และมี top_nยืนยันบางส่วนหน้าเอกสารของ Cohere ระบุ rerank-english-v3.0 เป็นรุ่น English ของตระกูล 3.0 และตัวอย่างใช้ top_n=5; ปัจจุบันมีรุ่นใหม่กว่า (rerank-v3.5, rerank-v4.0-pro / fast)docs.cohere.com ผ่าน WebFetch

1. คลิปนี้ตอบคำถามอะไร และภาพรวม pipeline ก่อนถึง reranker (~0:00–6:17)

ผู้สอนบอกว่าคลิปนี้โฟกัส reranker ทั้งคลิป: คืออะไร ใช้ทำไม ใช้ในสถานการณ์ไหนและไม่จำเป็นเมื่อไร ทำงานเบื้องหลังอย่างไร และต่างจาก embedding กับ LLM ตรงไหน (reranker ก็เป็นโมเดล AI เช่นกัน) ก่อนเข้าเรื่อง ผู้สอนทวนภาพรวมของ multi-query hybrid search ที่เคยสอนมาแล้วด้วยแผนภาพที่วาดไว้

ลำดับที่ผู้สอนไล่ให้ดู: เริ่มจากคำถามของผู้ใช้ สร้างคำถามแปลงรูป (ผู้สอนพูดว่า 5 แบบหรืออาจ 3 แบบ) แต่ละคำถามทำ hybrid search คือมีทั้งส่วน vector และส่วน keyword สมมติให้ vector retrieval แต่ละครั้งดึง k = 50 ซึ่งผู้สอนเรียกว่าการ "ทอดแหกว้าง" ตั้งแต่ต้นแล้วค่อยบีบให้แคบ โดยเฉพาะกับเอกสารระดับองค์กรหลักหมื่นฉบับ (10,000 ถึง 20,000) ที่ข้อมูลกระจายอยู่ในหลายเอกสาร ผู้สอนย้ำว่า 50 เป็นเพียงตัวเลขสมมติ จริงอาจเป็น 30 หรือ 80

สองรายการ (vector 50 และ keyword 50) มี chunk ซ้ำกันได้ จึงรวมแบบต่อกันเฉย ๆ ไม่ได้ ต้องใช้ reciprocal rank fusion (RRF) ผลสมมติคือ 35 chunk หากสองรายการไม่ซ้ำกันเลยจะได้ 100 ผู้สอนเรียก RRF ว่าอัลกอริทึมที่มีประโยชน์หลายสถานการณ์: ทุกครั้งที่มีสองรายการใน RAG ให้ใช้ RRF รวมแทนการต่อกันเฉย ๆ เมื่อได้ห้ารายการ (query ละหนึ่งรายการ) ก็ใช้ RRF รวมอีกชั้น สมมติเหลือ 25 chunk (ผู้สอนบอกว่าอาจเป็น 100, 40 หรือ 75) แล้ว "ตรงนี้เองที่ reranking เข้ามา" โดย reranker จะอ่าน query กับ chunk ทั้ง 25 อัน จัดลำดับใหม่ให้ chunk ที่แม่นที่สุดอยู่บนสุด และตัดด้วยพารามิเตอร์ top n เหลือ 10 chunk "สมบูรณ์แบบ" ส่งให้ LLM พร้อมคำถามเพื่อสร้างคำตอบ

ผู้สอนตั้งคำถามแทนผู้ชมเองว่า ในเมื่อมีรายการ 25 chunk แล้วต้องการแค่ 10 ทำไมไม่หยิบ 10 อันบนสุดเลย คำตอบคือทำได้ แต่การมี reranker ช่วยในบางสถานการณ์ และเกินความจำเป็นในอีกบางสถานการณ์ ซึ่งเป็นสองเรื่องที่คลิปจะไล่ต่อไป

เสริมจากผู้จัดทำ: RRF ในที่นี้เป็นเพียงตัวรวมรายการ

คลิปนี้ไม่ได้อธิบายสูตร RRF (เป็นเนื้อหาของคลิปก่อนหน้าในเพลย์ลิสต์) สูตรที่ EnsembleRetriever ของ LangChain ใช้ (ตามที่ตอนที่ 16 แสดงบนสไลด์) คือคะแนนของเอกสาร = ผลรวมของ น้ำหนัก / (อันดับ + 60) ในทุกรายการที่เอกสารนั้นปรากฏ ดูรายละเอียดในรายงานของคลิปตอนที่ 16 (Hybrid Search)

2. Reranker คืออะไร และทำไม hybrid + RRF ยังไม่พอ (~6:54–9:40)

นิยามของผู้สอน: reranker คือโมเดล AI เฉพาะทางที่ทำตัวเหมือน "ผู้ตรวจคุณภาพ" ช่วยปรับผลค้นหาชุดแรกโดยเรียงใหม่ตามความเกี่ยวข้องเชิงความหมายกับ query คิดได้ว่าเป็นระบบ "ความเห็นที่สอง" ผลค้นหาชุดแรกอาจมาจาก hybrid search + RRF จำนวน 100, 50 หรือ 25 chunk แล้ว reranker นำมาวิเคราะห์ละเอียดขึ้นและดัน chunk ที่เกี่ยวข้องที่สุดไว้บนสุด

คำถามที่ผู้สอนตั้ง: ถ้ามี vector embedding, hybrid search และ RRF แล้ว ทำไมต้องเพิ่มความซับซ้อนอีกชั้น ผลที่ได้ไม่ดีพอหรือ เพื่ออธิบายเรื่องนี้ ผู้สอนยกข้อจำกัดของ embedding ด้วยตัวอย่าง query "How to fix a leaky faucet?" กับสอง chunk สมมติ

  • chunk A ตอบคำถามตรง ๆ (ปิดน้ำ ถอดด้ามจับ เปลี่ยนแหวนยางที่สึก)
  • chunk B ยังเกี่ยวข้องอยู่ แต่ไม่ได้ตอบว่าจะแก้อย่างไร (ความเสียหายจากน้ำและเชื้อรา)
  • คะแนนความคล้ายสมมติบนสไลด์: A ได้ 0.82 และ B ได้ 0.79 ซึ่งห่างกันเพียงนิดเดียว ทั้งที่ A ตอบตรงกว่า

ผู้สอนสรุปว่า embedding และคะแนนความคล้ายช่วยดึง chunk ที่มี "โอกาสดีที่จะเกี่ยวข้อง" แต่ "ดี" บางครั้งยังไม่ดีพอสำหรับระบบ RAG ที่ต้องการความแม่นสูง เช่น องค์กร หรือบริษัทด้านกฎหมายและยา ซึ่งต้องเดินต่อไปอีกก้าวเพื่อให้ได้ความแม่นเพิ่ม

เสริมจากผู้จัดทำ: ตัวอย่างนี้มีรายละเอียดที่ควรรู้

คะแนนบนสไลด์เป็นตัวเลขสมมติ ไม่ได้มาจากการรันโมเดลจริง และผู้สอนบอกเองว่าเป็นสมมติ (hypothetical) ประเด็นที่ตัวอย่างต้องการให้เห็นคือ "ลำดับ" ของสอง chunk อาจสลับหรือห่างกันน้อยเกินกว่าจะเชื่อได้ ซึ่งตัวอย่างนี้ A ยังนำ B อยู่ แต่ส่วนต่างเล็ก

3. กลยุทธ์สองขั้น: เร็วและกว้าง แล้วแม่นและโฟกัส (~9:40–13:25)

ขั้นที่ 1 คือ embedding ซึ่งผู้สอนเรียกว่า "เร็วและกว้าง" และเป็นสิ่งที่ทำมาแล้วทั้งเพลย์ลิสต์: เทียบ query กับเวกเตอร์ในฐานข้อมูลที่มีได้ 1 ล้าน 5 ล้านหรือ 10 ล้าน chunk (ตามตัวอย่างของผู้สอน) เพราะเป็นเพียงการเปรียบเทียบเชิงคณิตศาสตร์แบบง่ายจึงทอดแหกว้างได้ถูก ดึง 50, 80 หรือ 100 chunk ต่อ query จุดประสงค์คือ "การประมาณราคาถูก" ข้อดีที่ผู้สอนไล่ให้: เร็ว (ค้นหลายล้าน chunk ได้เร็ว), กว้าง (เก่งหา chunk ที่อยู่ในย่านที่ถูก), ถูก (ต้นทุนคำนวณต่อการเปรียบเทียบต่ำ), และเชื่อถือได้ (ให้ chunk ที่มีโอกาสเกี่ยวข้องดี) แต่สุดท้ายเป็นแค่การประมาณ "คุณคงไม่กล้าเดิมพันเงินกับอันดับที่แน่นอน"

จากตรงนี้ผู้สอนตั้งคำถามว่า น่าจะดีถ้ามีโมเดล AI ที่แพงไม่เท่า LLM แต่แม่นกว่า embedding และคะแนนความคล้ายธรรมดา และเรียง chunk สุดท้ายราว 20 ถึง 30 อันให้ถูกต้องตาม query ได้ นั่นคือขั้นที่ 2 "แม่นและโฟกัส" ที่ใช้ reranker

วิธีทำงานตามที่ผู้สอนอธิบาย: นำ query กับ chunk ที่ 1 ส่งเข้า reranker (หรือ cross-encoder) แล้วได้คะแนนความเกี่ยวข้องที่แม่น ทำซ้ำกับ chunk ที่ 2, 3, 4 และต่อไป ทุกครั้งได้คะแนนใหม่ จุดประสงค์คือเพิ่มโอกาสให้ top 10 เป็น "ดีที่สุดจริง" คุณสมบัติที่ผู้สอนให้: แม่น (อ่าน query กับ chunk ด้วยกัน), รู้บริบท (เข้าใจเจตนาและความสัมพันธ์), แต่แพงกว่า (ต้นทุนคำนวณสูงกว่า) จึงใช้กับ chunk ราว 10 ถึง 100 อันเท่านั้น ผู้สอนบอกว่าตัวอย่างใช้ 25 อัน และ "ไม่เกิน 100" ถือว่าสมเหตุสมผล

เหตุผลที่แนวทางสองขั้นได้ผล ผู้สอนเปรียบว่าเหมือนมีการสัมภาษณ์คัดกรองก่อน แล้วตามด้วยการสัมภาษณ์เชิงเทคนิคอย่างละเอียด แต่ละขั้นปรับให้เหมาะกับหน้าที่ของตน และผู้สอนวางตำแหน่ง reranker ไว้ "ตรงกลาง" ระหว่าง embedding (ถูกแต่ผู้สอนว่าแม่นต่ำมาก) กับ LLM (แพงแต่แม่นสูง) คือไม่แพงเท่า LLM แต่ให้ความแม่นมากกว่า embedding "อีกเล็กน้อย"

4. Bi-encoder เทียบ cross-encoder: ต่างกันที่เห็น query กับ chunk พร้อมกันหรือไม่ (~13:25–16:40)

ผู้สอนยกคำถามใหญ่ว่า reranker หรือ cross-encoder ทำสิ่งนี้ได้อย่างไร และต่างจาก embedding model และ LLM อย่างไร โดยเริ่มจากทบทวนว่า embedding model เรียกว่า bi-encoder ส่วน reranker เรียกว่า cross-encoder

ตัวอย่างบนสไลด์: query "apple stock price" (หมายถึงบริษัท Apple) กับ chunk "Apple trees grow in orchards" ในแบบ bi-encoder ทั้งสองถูกแปลงเป็นเวกเตอร์ของตัวเอง แล้วทำ cosine similarity ได้ 0.78 สาเหตุที่เรียก bi-encoder (ไม่ใช่ cross-encoder) คือการเข้ารหัสเกิดแยกกันสำหรับ query กับ chunk: การเข้ารหัส chunk เกิดไว้ก่อนในเวลาหนึ่ง แล้วภายหลังเมื่อผู้ใช้ถาม query จึงถูกเข้ารหัสและเทียบกัน ผู้สอนมองว่านี่คือปัญหา เพราะโมเดล "ไม่เคยเห็น query กับ chunk ด้วยกัน" มันประมวลผลแยกแล้วเทียบกันด้วยคณิตศาสตร์ตอนทำ cosine เท่านั้น

ฝั่ง reranker (cross-encoder หรือแนวทางประมวลผลร่วม) ต้องป้อนทั้ง query และเนื้อหา chunk เข้าไป โมเดลจะรวมสองอย่างเป็นสตริงเดียวคั่นด้วยคำพิเศษ [SEP] โดยโมเดลถูกฝึกมาให้มอง query และ chunk ด้วยกันเพื่อเข้าใจว่าสัมพันธ์กันแค่ไหน ตอบคำถามหรือไม่ แล้วให้คะแนนความเกี่ยวข้อง ในตัวอย่างเดียวกันได้ 0.12 ซึ่งผู้สอนอธิบายว่าคะแนนต่ำกว่ามากเพราะแม่นกว่า (ตรวจพบว่าไม่ตรงกัน) สไลด์เขียนกำกับว่า "correctly identifies mismatch"

ข้อสรุปของผู้สอนในหัวข้อนี้: reranker ถูกสร้างมาเพื่อมอง query กับค่าของ chunk พร้อมกัน จึงแม่นกว่า embedding มาก

เสริมจากผู้จัดทำ: อย่าเทียบคะแนน 0.78 กับ 0.12 ตรง ๆ

ตัวเลขทั้งสองมาจากคนละมาตรวัด: 0.78 คือ cosine similarity ของเวกเตอร์ ส่วน 0.12 คือคะแนนความเกี่ยวข้องจาก cross-encoder ช่วงค่าของคะแนนแบบหลังขึ้นกับโมเดล (เอกสาร Sentence-Transformers อธิบายตัวอย่างว่าให้คะแนนระหว่าง 0 ถึง 1) จุดที่ควรจำคือโครงสร้างต่างกัน ไม่ใช่ตัวเลขสองตัวนั้น และเนื้อหาข้างต้นเป็นตัวอย่างสมมติของผู้สอน อีกข้อ: ข้อได้เปรียบเชิงต้นทุนของ bi-encoder มาจากการคำนวณเวกเตอร์ของ chunk ไว้ล่วงหน้าได้ ส่วน cross-encoder ต้องรันโมเดลใหม่ต่อคู่ (query, chunk) ทุกคู่ จึงใช้กับ candidate จำนวนน้อย (ตรวจจากเอกสาร Sentence-Transformers ดูในตารางตรวจข้อเท็จจริง)

5. โค้ดตอนแรก: เตรียม hybrid retriever บนคลังที่ใหญ่ขึ้น (~16:40–20:30)

ผู้สอนเริ่มส่วนโค้ดด้วยการบอกว่าจะใช้ Cohere reranker โดยอ่านคำโปรยในหน้าเว็บของ Cohere ว่า Rerank ส่งเฉพาะ chunk หรือเอกสารที่เกี่ยวข้องที่สุดเข้า pipeline RAG และ workflow แบบ agent ช่วยลดการใช้ token ลดเวลาหน่วง (latency) และเพิ่มความแม่น (เป็นคำของผู้ขาย คลิปไม่ได้วัด) แล้วบอกว่าไฟล์ reranker ที่สร้างไว้คล้ายกับไฟล์ hybrid search ที่เขียนไว้แล้ว: เดิมมี keyword กับ vector ผสมกันด้วย ensemble retriever แล้วดึงมา 3 หรือ 5 chunk ตอนท้าย แต่ "reranker ไม่สมเหตุสมผลถ้าดึงมาแค่ 5 chunk" ถ้าเหลือ 5 หรือ 10 chunk อยู่แล้วก็ส่งให้ LLM ตอบได้เลย จะต้องใช้ reranker เมื่อมี chunk มากขึ้นและต้องการกรอง

ดังนั้นไฟล์ใหม่จึงสร้าง chunk เพิ่มเป็นราว 100 อัน เนื้อหาเกี่ยวกับ Tesla, การพัฒนาและการซื้อกิจการของ Microsoft, AI และฮาร์ดแวร์ของ Nvidia, AI และคลาวด์ของ Google และมี chunk รบกวนที่เกี่ยวข้องน้อยปนเข้าไปเพื่อเพิ่มความสับสน

ขั้นตอนในโค้ด:

  1. นำเข้า BM25 retriever, ensemble retriever, embedding, Chroma vector store, Document ของ LangChain และ CohereRerank จาก langchain cohere (ต้องติดตั้งแพ็กเกจ langchain-cohere เพิ่ม) จากนั้นแปลง chunk เป็นเอกสารของ LangChain
  2. สร้าง retriever สามแบบเหมือนที่ทำไว้ก่อนหน้า: vector retriever, BM25 retriever และ hybrid retriever ที่รวมสองอย่าง โดยตั้งจำนวนที่ดึงต่อฝั่งเป็น 15 (เพิ่มขึ้นเล็กน้อย)
  3. ตั้งน้ำหนักของ hybrid retriever เป็น vector 70 % และ BM25 30 % เหตุผลที่ผู้สอนให้คือ vector search ฉลาดกว่าเล็กน้อย ส่วน BM25 มีไว้เพื่อลบจุดอ่อนของ vector search
  4. เรียกใช้ด้วย query "Tesla financial performance and production updates" ได้ผลรวม 18 chunk 11 อันแรกพูดถึง Tesla ทั้งหมดตามที่ query ถาม ที่ได้ 18 ไม่ใช่ 30 เพราะ vector ดึง 15 และ keyword ดึง 15 แต่ RRF รวมรายการซ้ำเข้าด้วยกัน

ผู้สอนบอกว่าคลังนี้เล็ก embedding จึงทำได้ดีอยู่แล้ว (top 10 พูดถึง Tesla ทั้งหมด) จะหยิบ top K ส่งให้ LLM ตรง ๆ ก็ได้ แต่ยังจะสาธิตว่า reranker ทำให้ดีขึ้นได้อีก เพราะบางครั้ง LLM ให้ผลดีกว่าเมื่อ chunk ที่เข้าเกณฑ์มากกว่าอยู่บนสุด

เสริมจากผู้จัดทำ: น้ำหนัก 70 : 30 คืออะไรในโค้ด

ซอร์สของ EnsembleRetriever ใน LangChain ใช้ weighted RRF: คะแนนของเอกสารหนึ่งอัน = ผลรวมของ น้ำหนักของ retriever นั้น หารด้วย (อันดับ + c) โดย c ค่าเริ่มต้นคือ 60 และอันดับเริ่มที่ 1 (ตรวจจากซอร์สผ่าน WebFetch) ดังนั้น 70 : 30 ไม่ใช่การเอาคะแนน vector กับคะแนน BM25 มาถ่วงรวมกันโดยตรง แต่ถ่วงที่ตัวเศษของ RRF เท่านั้น

6. ใช้ Cohere Rerank และดูผลก่อน/หลัง (~20:30–26:25)

ผู้สอนบอกว่าจะส่ง chunk ทั้ง 18 อันเข้า reranker แล้วขอให้จัดลำดับใหม่ตาม query ให้แม่นขึ้น ขั้นที่ 2 คือ "apply Cohere ranking" ด้วย CohereRerank ของ LangChain ซึ่งรับเอกสาร LangChain ได้ "ช่วยแบกงานหนักให้" (ใช้แพ็กเกจต้นฉบับของ Cohere ก็ได้เช่นกัน) โมเดลที่เลือกคือ rerank-english-v3.0 ผู้สอนบอกว่ามีหลายโมเดล และมีโมเดลโอเพนซอร์สที่ดีกว่า Cohere ด้วย แต่เลือก Cohere เพราะเป็นคลาวด์และมีโควตาฟรีค่อนข้างใจดี โมเดลที่ใช้ตามคำอธิบายของ Cohere ในคลิปคือโมเดลสำหรับ rerank เอกสารภาษาอังกฤษและข้อมูลกึ่งโครงสร้าง

เมธอดรับพารามิเตอร์ "จำนวนเอกสารที่จะคืน": ถ้าไม่ระบุก็จะได้ทั้ง 18 อันที่เรียงใหม่ แต่ผู้สอนต้องการแค่ top 5 หรือ top 10 จึงระบุ (ในโค้ดคือ top 10) เมธอด compress_documents รับ chunk ทั้งหมดพร้อม query แล้วภายในมันจะเทียบ query กับ chunk ที่ 1, 2, ... สร้างคะแนนทุกอัน เรียงลำดับ และคืน 10 อันที่แม่นที่สุด ผู้สอนยังพิมพ์ผลก่อน rerank (ผลของ hybrid search) ออกมาดูเทียบด้วย

ผลเทียบก่อนและหลังตามที่แสดงบนจอ (~24:40 ผู้จัดทำอ่านจากเฟรม ผู้สอนพูดถึงเฉพาะอันดับ 1, chunk Gigafactory และ chunk รายได้ 25.2 พันล้าน) ก่อนรัน ผู้สอนคาดว่าคลังเล็กจึงน่าจะผลต่างไม่มาก แต่หวังว่าจะเห็นการสลับลำดับบ้าง

อันดับก่อน rerank (hybrid)หลัง rerank (Cohere)
1กระแสเงินสดอิสระ 7.5 พันล้านดอลลาร์กระแสเงินสดอิสระ 7.5 พันล้านดอลลาร์ (คงเดิม)
2แผนขยายกำลังการผลิตของ Gigafactoryรายได้ไตรมาสสูงสุด 25.2 พันล้านดอลลาร์ใน Q3 2024
3รายได้ 25.2 พันล้านดอลลาร์อัตรากำไรขั้นต้นยานยนต์ 19.3 %
4ราคาหุ้นทำจุดสูงใหม่หลังประกาศกำไรแผนขยายกำลังการผลิตของ Gigafactory
5อัตรากำไรขั้นต้นยานยนต์ 19.3 %ธุรกิจกักเก็บพลังงานโต 40 % ต่อปี

ผู้สอนอธิบายเฉพาะสิ่งที่พูดถึง: chunk Gigafactory จากอันดับ 2 ตกไปอันดับ 4 และ chunk ที่ 3 (รายได้ 25.2 พันล้าน) ขึ้นเป็นอันดับ 2 เหตุผลที่ผู้สอนให้คือ query ถามเรื่อง "financial performance" และ "production updates" ดังนั้น chunk ที่เป็นตัวชี้วัดการเงินถูกดันขึ้นบนสุด ส่วนประโยคทั่วไปเช่น "ประกาศแผนขยายกำลังการผลิตของ Gigafactory" ถูกดันลงเล็กน้อย ผู้สอนสรุปว่า "ยังมีการสลับลำดับเกิดขึ้น"

ขั้นตอน API key ที่ผู้สอนขอโทษที่ลืมพูด

ต้องตั้งตัวแปร env ชื่อ CO_API_KEY ด้วยคีย์ของ Cohere: สมัครแล้วเข้า API keys ที่แถบด้านข้างแล้วสร้าง trial key ผู้สอนบอกว่า trial key ใช้เชิงพาณิชย์ไม่ได้เพราะถูกจำกัด rate แต่เรียนรู้ใช้ได้เท่าที่ต้องการ แล้วต้องรีสตาร์ท Jupyter เคลียร์ output เพื่อให้ตัวแปรใช้ได้ในเซลล์ ตัวเลขข้อจำกัดจริงดูในตารางตรวจข้อเท็จจริง

เสริมจากผู้จัดทำ: ผลลัพธ์ที่ผู้สอนไม่ได้เอ่ยถึง

จากตารางที่อ่านจากจอ: chunk ราคาหุ้นอันดับ 4 ก่อน rerank ไม่อยู่ใน 5 อันดับแรกหลัง rerank และ chunk ธุรกิจกักเก็บพลังงานซึ่งไม่อยู่ใน 5 อันดับแรกก่อนหน้า ขึ้นมาเป็นอันดับ 5 (ผู้จัดทำอ่านจากเฟรม ผู้สอนไม่ได้พูดถึงสองจุดนี้) อีกข้อคือป้ายในโค้ดเขียน "Top 3" แต่พิมพ์รายการ 5 อัน ซึ่งเป็นป้ายที่ไม่ตรงกับจำนวน ตัวอย่างนี้เป็นการรันครั้งเดียวบนคลังเล็กและไม่มีเกณฑ์ตัดสินว่าลำดับใหม่ "ดีกว่า" ในเชิงวัดผล จึงใช้เป็นภาพประกอบมากกว่าหลักฐานของประสิทธิภาพ

7. ส่งให้ LLM และก้าวต่อไปสู่งาน production (~26:26–28:52)

ขั้นสุดท้ายเหมือนตอนก่อนหน้า: นำ 10 chunk ที่แม่นที่สุดส่งให้ LLM พร้อมคำถามของผู้ใช้เพื่อสร้างคำตอบ โค้ดเดียวกับที่เห็นในคลิปก่อน เมื่อรันจะได้คำตอบเช่น "Tesla demonstrated a strong financial performance" โดยส่งเอกสารที่ rerank แล้วทั้งหมดเป็น context

ผู้สอนปิดเพลย์ลิสต์ว่าออกแบบสำหรับมือใหม่แต่ครอบคลุมแนวคิดขั้นสูงเกือบทั้งหมดที่ต้องรู้เพื่อเรียน RAG และยังมีหัวข้อขั้นสูงกว่านี้ เช่น การใช้ LangGraph และ agent สร้างต่อยอด ผู้สอนบอกว่าในงาน production จริง ที่มีข้อมูลในฐานข้อมูลและตารางเชิงสัมพันธ์อยู่แล้ว ทีมไม่น่าจะใช้ LangChain หรือเฟรมเวิร์กเหล่านี้ แต่จะใช้เทคโนโลยีระดับ production เช่น PG vector ซึ่งเป็นส่วนขยาย vector search ของ PostgreSQL และสำหรับ keyword search มี ts vector ซึ่งผู้สอนเรียกว่าส่วนขยาย keyword search ของ PostgreSQL เพื่อนำแนวคิดเหล่านี้ไปผสมในผลิตภัณฑ์ที่มีอยู่ (ส่วนโฆษณาคอร์สและพอร์ตโฟลิโอท้ายคลิปถูกตัดออกจากรายงานนี้)

ข้อที่ควรเข้าใจให้ตรง: ผู้จัดทำแก้ให้ตรง: ts vector

tsvector เป็นชนิดข้อมูลในตัวของ PostgreSQL สำหรับ full-text search (ไม่ต้องติดตั้ง extension) และฟังก์ชันจัดอันดับ ts_rank อิงความถี่ของคำที่ตรงโดยไม่ใช้สถิติทั้งคลัง จึงไม่ใช่ BM25 ถ้าต้องการ BM25 ใน Postgres ต้องใช้ส่วนเสริมหรือบริการแยกต่างหาก ส่วน pgvector เป็น extension จริง และ README ของมันแนะนำให้ใช้ร่วมกับ full-text search เพื่อทำ hybrid (มีตัวอย่าง RRF)

Key Takeaways

1.Reranker คือโมเดลที่อ่าน query กับ chunk พร้อมกัน (cross-encoder) แล้วให้คะแนนความเกี่ยวข้องต่อคู่ ใช้เป็นขั้นที่ 2 ที่คัดจาก candidate หลักสิบถึงร้อยอัน ไม่ใช่ขั้นที่ค้นทั้งคลัง
2.Embedding (bi-encoder) แปลง query กับ chunk แยกกันแล้วเทียบ cosine จึงเร็วและถูกแต่เป็นการประมาณ ส่วน reranker แพงกว่าแต่แม่นกว่า ผู้สอนวางตำแหน่งไว้ระหว่าง embedding กับ LLM
3.Pipeline ที่แนะนำ: multi-query → hybrid (vector + keyword) ต่อ query → RRF → RRF → reranker (top n = 10) → LLM โดยตัวเลข 50 / 35 / 25 เป็นตัวอย่างสมมติ
4.ไม่ต้องใช้ reranker ถ้าเหลือ chunk เพียง 5 ถึง 10 อันอยู่แล้ว และบนคลังเล็กผลต่างมีน้อย (ผู้สอนพูดเอง) ผลในคลิปเป็นการรันครั้งเดียว ไม่มีการวัดความแม่นหรือเวลาหน่วง (ข้อสังเกตของผู้จัดทำ)
5.ข้อควรตรวจก่อนเชื่อ: ตัวเลขคะแนนบนสไลด์เป็นสมมติและคนละมาตรวัด, rerank-english-v3.0 ไม่ใช่รุ่นล่าสุดของ Cohere, และ tsvector ไม่ใช่ extension ที่ให้ BM25 (ข้อสังเกตของผู้จัดทำ)
