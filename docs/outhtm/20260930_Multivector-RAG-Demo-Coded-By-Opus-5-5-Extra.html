📋 บทสรุปย่อ

บทสรุปย่อ: ผู้สอนให้ Claude Opus 5.5 (โหมด Extra) เขียนเดโม RAG แบบ multi-vector ที่ทำงานในเบราว์เซอร์ทั้งหมด ตามไอเดียของ Antoine Chaffin บนหน้า GitHub Pages: เข้ารหัสคำถามด้วย pylate-rs (WASM) และโมเดล ColBERT ขนาด 33M (answerai-colbert-small-v1, 96 มิติ) ค้นบล็อก 3,417 ส่วนจาก 187 โพสต์ ด้วย MaxSim ที่เอกสารเก็บเป็นเวกเตอร์ 1 บิต แต่คำถามเป็น float (asymmetric quantization) แล้วส่งผลให้ Pleias-RAG-350M ตอบบน WebGPU ครึ่งหลังของคลิปเปิด DevTools ไล่ข้อมูลจริง: คำถาม = 32 token × 96 มิติ, ตาราง lookup 32 × 12 × 256 = 98,304 ค่า, index 435,383 token vector = 5,224,596 ไบต์

โหมดของเนื้อหา: เรียบเรียงใหม่ด้วยคำของผู้จัดทำ (license มาตรฐานของ YouTube, ตรวจ 2026-10-11) ครบทุกประเด็นและตัวเลข ไม่เปลี่ยนความหมาย · ตัวเลขหลายตัวมาจากตารางบนจอ (กำกับไว้) · คลิปใหม่กว่าความรู้ของผู้จัดทำ จึงตรวจข้อเท็จจริง 7 ข้อ (ส่วนที่ 9)

🧭 สรุปเชิงลึก

ที่มา: ผู้สอนถามคนในวง late interaction ว่ามีโปรเจกต์ข้างเคียงไหนที่ก่อนหน้านี้ทำไม่ทัน แต่ตอนนี้ AI เก่งพอจะช่วยทำได้ Antoine ตอบว่าอยากทำเดโม RAG แบบ multi-vector ที่รันบนเว็บทั้งหมดด้วย pylate-rs และโมเดลเล็กสำหรับ RAG ของ Pleias ผู้สอนจึงลองให้ Opus 5.5 ทำ ตอนนี้ index บล็อกของตัวเองด้วย answerai-colbert-small-v1 แล้ว

เดโม: หน้าเว็บโหลด index และดาวน์โหลดโมเดลเพื่อเข้ารหัสคำถามตอนค้น ถาม "What does the cavern represent?" ได้ตาราง MaxSim ต่อ token ของคำถามของ 5 อันดับแรก อันดับ 1 รวมสูงสุด (246.41) และคอลัมน์ cavern ของอันดับ 1 (7.25) สูงกว่าอันดับอื่นราว 1.5–2 เท่า (3.59–4.71) ขณะที่คำอื่นใกล้กันมาก อันดับ 1 คือโพสต์ allegory เรื่อง cavern ซึ่งมีโพสต์เดียว ผลถัดไปจึงด้อยลงเร็ว กด Generate answer → ดาวน์โหลด Pleias-RAG-350M (448 MB) รันบน WebGPU ช้าบน MacBook 2019 แต่ผู้สอนทึ่งที่โมเดล 350 ล้าน พารามิเตอร์วิเคราะห์คำถาม ประเมินแหล่ง แล้วตอบว่า cavern แทน "space of solutions" ตรงกับโพสต์ และ "ไม่ค่อย hallucinate"

ทำกับ Opus อย่างไร: ให้ URL ของ pylate-rs บน npm และบล็อก asymmetric quantization ของ Mixedbread: เก็บคำถามละเอียด (FP32) แต่เอกสารเป็น int8 หรือ binary (binary = แต่ละมิติเหลือบวกหรือลบ) Opus ทดลองคุณภาพบน SciFact ก่อน: int8 ไม่เสียอะไร (74.51 vs 74.18) แต่เอกสาร binary ลด NDCG@10 ราว 3.6 คะแนน (70.56) และ binary ทั้งคู่ลด 14 คะแนน ขนาด index 533 MB → 16.7 MB (บนจอ) เลือก คำถาม FP32 × เอกสาร binary เพราะเป็นเดโม และทดสอบกับคำถามบนบล็อก 7 ข้อ: อันดับ 1 ตรงกับ FP32 ทุกข้อยกเว้นหนึ่ง สถาปัตยกรรม: HTML ไฟล์เดียวบน GitHub Pages, pylate-rs จาก jsDelivr, น้ำหนักโมเดลจาก Hugging Face, index.bin + docs.json

ใต้ฝากระโปรง: เพราะเอกสารเป็น ±1 ผลคูณจุด q · d = 2 × (ผลรวม q ตรงที่บิตเป็น 1) − (ผลรวม q ทั้งหมด) ส่วนแรกเปิดตารางทีละไบต์: สำหรับทุกเวกเตอร์คำถามและทุกตำแหน่งไบต์ มีตาราง 256 ช่องเก็บผลรวม q ของทุกรูปแบบ 8 บิต (32 × 12 × 256 = 98,304) แล้วหาค่ามากสุดต่อ token คำถามในแต่ละ passage ก่อนแปลงเป็นคะแนน ผู้สอนยอมรับว่ายังไม่เข้าใจทุกบรรทัด และติดชื่อตัวแปร bits ที่จริงเก็บเป็นไบต์

ข้อควรรู้ (ผู้จัดทำ): ในตารางบนจอ คอลัมน์ "Other 26" ([CLS], ตัวบอก query, [SEP] และ [MASK] ที่เติมจนครบ 32 token — คำถามนี้มีคำจริง 6 token จึงเติม 23 ตัว) รวมได้ราว 200 จาก ~246 คะแนน คะแนนส่วนใหญ่จึงมาจาก token พิเศษและ token เติม ไม่ใช่คำในคำถาม · โยงกับ ZVect: บท 5.3 เวกเตอร์ 1 บิต (XOR + popcount) เป็นอีกวิธีของแนวคิดเดียวกัน และบท 6.2 Late interaction

1. ที่มาของเดโม (~0:00–1:27)

ผู้สอนจะเดินผ่านเดโม multi-vector RAG ที่ "vibe code" กับ Opus 5.5 และบอกว่าไม่ใช่ไอเดียของตัวเอง: เคยทวีตถามคนในวง late interaction ว่ามีโปรเจกต์ข้างเคียงอะไรที่อยากทำแต่ทำไม่ทัน ก่อนที่ AI จะเก่งขนาดนี้ Antoine ตอบว่าอยากผลักเดโม RAG ที่ทำงานบนเว็บทั้งหมดด้วย pylate-rs และ multi-vector โดยใช้โมเดลของ Pleias (ผู้สอนไม่แน่ใจการออกเสียง) ซึ่งมีโมเดลขนาดเล็กที่ออกแบบมาสำหรับ RAG ผู้สอนเห็นเป็นโอกาสลองว่า Opus 5.5 กับตัวเองจะทำได้ไหม

สถานะตอนนี้ยัง "พื้นฐานมาก": index บล็อกของผู้สอนด้วยโมเดล answerai-colbert-small-v1 แล้ว ผู้สอนเปิดในหน้าต่าง incognito เพื่อให้เห็นตั้งแต่เริ่ม: หน้าเว็บโหลด index ก่อน แล้วดาวน์โหลดโมเดลเพื่อใช้เข้ารหัสคำถามตอนค้น

ตามคำอธิบายคลิป: pylate-rs ใช้ index เอกสาร Pleias-RAG-350M ใช้สร้างคำตอบจาก context ที่ค้นได้ ไฟล์ index.bin ~5 MB คำถามคงเป็น FP32

3. สร้างคำตอบด้วย Pleias-RAG-350M บน WebGPU (~3:30–6:35)

กด Generate answer หน้าเว็บใช้โมเดล Pleias-RAG-350M บน WebGPU ต้องดาวน์โหลดราวหนึ่งนาที (บนจอ: ครั้งแรก 448 MB) ผู้สอนไม่ตัดต่อคลิปเพราะอยากปล่อยเร็ว inference ช้ามาก ผู้สอน "ค่อนข้างแน่ใจ" ว่าเพราะใช้ MacBook ปี 2019 ถ้ามีเครื่องอย่าง M3 ผู้สอน "มั่นใจ" ว่าจะเร็วกว่า แต่บอกว่าผลนี้ "น่าทึ่ง" สำหรับโมเดล 350 ล้าน พารามิเตอร์ที่สร้างและฝึกมาเพื่อ RAG

เห็นการให้เหตุผลของโมเดล: ส่วน query analysis บอกว่าต้องหา cavern ในแหล่ง ส่วนใหญ่เป็นเรื่องเทคนิคและโมเดล แต่ source 1 พูดถึง cavern, source 5 เป็นเรื่อง negative prompting (ผู้สอนบอกว่าเป็นตัวหลอก ไม่เป็นไร) โมเดลยังมีข้อสงสัยว่าแหล่งไม่ได้บอกรูปร่างทางกายภาพของ cavern แล้วจัดคำถามเป็น trivial (ผู้สอนคิดว่ามีหมวดราว trivial / answerable / infeasible อาจมีอีกหมวด) จากนั้นตอบว่า ตามแหล่ง cavern แทน "space of solutions" ซึ่งตรงกับโพสต์ อธิบายว่า cavern เป็นเครือข่ายอุโมงค์และที่โล่งเชื่อมกัน กว้างใหญ่ แม้ไม่ถึงกับไม่มีที่สิ้นสุด แต่ใหญ่พอที่ไม่มีใครคนเดียวทำแผนที่ได้ทั้งหมด ผู้สอนบอกว่ามัน "ไม่ค่อย hallucinate" ทำได้ดี — ครบวงจร: R (retrieval) ด้านบน แล้วส่งให้โมเดล RAG ทำ AG ให้

ผลตรวจ A4: model card ยืนยัน 350M, อ้างอิงแหล่งในคำตอบ, มีขั้น query analysis (ตอบปกติ / trace สั้นสำหรับคำถาม trivial / reformulation / ปฏิเสธ) และ source analysis และรองรับฝรั่งเศส เยอรมัน อิตาลี สเปน (โปแลนด์ ละติน โปรตุเกส น้อยกว่า)

4. ทำงานกับ Opus: asymmetric quantization และแผนภาพระบบ (~6:36–11:21)

ผู้สอนเริ่มด้วยการให้ URL ของแพ็กเกจ pylate-rs บน npm แล้วให้บล็อก asymmetric quantization ของ Mixedbread (ผู้สอนแนะนำให้อ่าน) Opus อธิบายสมการให้คะแนนและประโยชน์ด้านพื้นที่ ความหมายคือ quantize คำถามกับเอกสารไม่เท่ากัน: คำถามเป็น FP32 เอกสารเป็น int8 หรือ binary ขึ้นกับว่าผลค้นแย่ลงแค่ไหน binary คือแต่ละมิติของ token เอกสารเหลือแค่บวกหรือลบ (1 = บวก, 0 = ลบ) จากนั้นถามคำถามต่อ และให้ทวีตของ Antoine เพื่อดูว่าทำในเซสชันเดียวได้ไหม — ได้ และ "ไม่ได้เกินตัว"

ขอแผนภาพระบบ (ผู้สอนบอกว่าจากนี้ไม่มีอะไรใหม่ เดโมจบแล้ว ที่เหลือคือไล่โค้ด): ขั้นแรก Opus ทำสคริปต์ eval quality เทียบเอกสาร FP32 / int8 / binary บนชุดข้อมูลเล็ก พอเลือกระดับได้ก็สร้าง index เซฟเป็น index.bin และ docs.json สร้าง index.html ดึง pylate-rs ผ่าน jsDelivr ดึงน้ำหนักโมเดลจาก Hugging Face และทำเป็น HTML ไฟล์เดียวเพราะอยากโฮสต์บน GitHub Pages ผู้สอนชอบโมเดล Answer ColBERT ที่สุดเพราะ 33 ล้านพารามิเตอร์ เล็กและดีมาก เหมาะกับงานนี้

ลำดับข้อมูล: พิมพ์คำถาม → น้ำหนักโมเดลเข้ารหัสเป็น 32 เวกเตอร์ ด้วย pylate-rs → binary MaxSim ใน score.js ที่ Opus เขียน ใช้เอกสารที่เตรียมและโหลดไว้แล้ว (ผู้สอนคิดว่าราว 6 MB เลือก binary เพราะพอสำหรับเดโม) → จัดอันดับ ตอนแรกไม่ได้ตั้งใจใส่โมเดล RAG แต่ "ทุกอย่างเร็วมาก" จึงให้ Opus ทำต่อจนเสร็จ ใช้บล็อกของตัวเองเพราะมีในเครื่องและคุ้นเคย

5. การทดลองก่อนเลือกระดับ quantization (~11:22–14:27)

สิ่งที่ผู้สอน "คิดว่า" น่าสนใจรองลงมา คือ Opus ทำชุดประเมินเล็ก ๆ ก่อนเลือกระดับ quantization บนชุดข้อมูล SciFact เทียบ: ทั้งคู่ FP32, ทั้งคู่ int8, คำถาม FP32 × เอกสาร binary, คำถาม int8 × เอกสาร binary และ binary ทั้งคู่ (ตารางเต็มในส่วนเปรียบเทียบด้านบน) เพราะคำถามมีอันเดียวแต่เอกสารมีมาก เมื่อเอกสารเป็น binary ขนาดรวมแทบเท่าเดิมในทุกแบบ ที่สำคัญคือขนาดของคลังเอกสาร คำถามมีมากสุดแค่ 32 token จึงไม่มีผล

ผล: FP32 กับ int8 ได้ค่าเท่ากัน binary ทั้งคู่ลดลงมาก จึงเลือกคำถาม FP32 × เอกสาร binary การลดจากเอกสาร FP32/int8 ไป binary ยัง "มีนัย" (74 → 70) แต่เป็นเดโมจึงรับได้

6. เปิด DevTools: embedding ของคำถาม และสูตร asymmetric (~14:28–17:42)

ผู้สอนรีเฟรช เปิด inspect ใส่คำถาม และตั้ง breakpoint ที่ renderGrid (ตำแหน่งที่ Opus แนะนำ) สิ่งแรกที่ดูคือ embedding จริงของคำถาม: กด submit แล้วเข้ารหัสด้วย answerai-colbert-small-v1 ได้ 32 token แต่ละตัว 96 มิติ (มิติของโมเดล Answer) เป็นตัวเลข float — "ดูข้อมูลของคุณเสมอ"

ต่อไปคือ lookupTables ที่ผู้สอนบอกว่ายังไม่เข้าใจเต็มที่ จึงลองไล่ไปพร้อมกัน คอมเมนต์ในโค้ดบอกว่า: ให้คะแนนทุก passage ด้วย MaxSim แบบตรงด้วยเวกเตอร์คำถาม float กับเวกเตอร์เอกสาร binary แต่ละค่าของเอกสารเป็น +1 หรือ −1 ดังนั้น q · d = 2 × (ผลรวม q ตรงที่บิตของเอกสารเป็น 1) − (ผลรวม q ทั้งหมด) นี่คือ asymmetric quantization ผู้สอนอธิบายว่ารวม q ทั้งหมดไว้ก่อนได้ แล้วสำหรับแต่ละเอกสารแค่รวม q ตรงที่บิตเป็น 1 แล้วคูณสองลบผลรวมทั้งหมด — การลบมาจากค่า −1 ("ค่อนข้างแน่ใจ อ่านมาเมื่อสัปดาห์ก่อน")

ส่วนแรกเปิดตารางทีละไบต์: สำหรับทุกเวกเตอร์คำถามและทุกตำแหน่งไบต์ มีตาราง 256 ช่องเก็บผลรวม q ของทุกรูปแบบ 8 บิตที่เป็นไปได้ ผู้สอน "ไม่แน่ใจ 100%" ว่าจำเป็นไหม แต่คิดว่าทำเพื่อไม่ต้องคำนวณซ้ำ: เปิดตารางแทนการบวก

7. ขนาดของตาราง lookup และ index (~17:43–30:15)

ส่งเข้า lookupTables คือคำถามที่แผ่เป็นแถวเดียว และจำนวนมิติ: ความยาว 3,072 (ASR ได้ยินเป็น "372") = 32 × 96 · มิติ 96 → จำนวนเวกเตอร์ = 3,072 / 96 = 32 · ไบต์ต่อเวกเตอร์ = 96 / 8 = 12 · ตาราง = 32 × 12 × 256 = 98,304 ค่า (ASR "98,34") คือ 32 token คำถาม × 12 ไบต์ × 256 รูปแบบของ 8 บิต ผู้สอน "คิดว่า" ลูปเลื่อนทีละ 8 ค่า (0–8, 8–16 …) ตลอด 96 ค่าของแต่ละเวกเตอร์คำถาม และบอกว่าเป็นความเข้าใจของตัวเอง ยังไม่ได้ไล่ทีละขั้นครบ ไม่ถนัด bit operation จึงไม่ลงลึก ค่าในตารางเริ่มที่ 0

scorePassages ทำ MaxSim ของทุก passage รับ tables, bits และ offsets: offsets มาจาก index ผู้สอนเดาว่า index ทีละส่วนของบล็อก 180 กว่าโพสต์ "คิดว่ามีราว 3,418 ส่วน" ส่วนแรกยาว 76 token ส่วนถัดไปจาก 76 ถึง 129 … ค่าสุดท้ายของ offsets คือ 435,383 = จำนวน token vector ทั้งหมด (JavaScript ใช้ index −1 ไม่ได้ จึงพิมพ์เลขตำแหน่งสุดท้ายตรง ๆ)

เสริมจากผู้จัดทำ: บนจอเขียน 3,417 passages ดังนั้น offsets มี 3,418 ช่อง (n + 1) ตัวเลข 3,418 ที่ผู้สอนพูดน่าจะเป็นความยาวของ offsets ไม่ใช่จำนวนส่วน

bits ยาว 5,224,596 = 435,383 × 12 ไบต์ ผู้สอนเคยคิดว่า 5,224,596 คือจำนวนบิต แต่ค่าแรกเป็น 80 (ซึ่งน่าจะแทน 8 บิต) จึงถาม Opus ได้คำตอบว่า 5,224,596 คือจำนวนไบต์ ไม่ใช่บิต จำนวนบิตจริงราว 41 ล้าน (435,383 × 96 = 41,796,768) ผู้สอนบ่นว่าชื่อ bits แย่ ควรชื่อ bytes

ตัวอย่างรูปธรรม (ผู้จัดทำ): ไบต์ค่า 80 (เลขฐานสิบ) = 0101 0000 → มิติที่ 2 และ 4 ของ 8 มิตินั้นเป็น +1 อีก 6 มิติเป็น −1 (อ่านบิตสูงสุดก่อนตามคอมเมนต์ในโค้ด)

8. bestSums, คะแนนสุดท้าย และโมเดลที่น่าสนใจ (~30:16–39:22)

bestSums: สำหรับแต่ละ passage (from–to ตาม offsets) และแต่ละเวกเตอร์คำถาม (ผู้สอน "เชื่อว่า" nq = 32 คือจำนวน token ของคำถาม) เติม best ด้วยผลรวมจากตารางที่สูงที่สุดตลอด token vector ของ passage ผู้สอน "สันนิษฐาน" ว่าแต่ละ token ของเอกสารดึงหน้าต่าง 12 ไบต์จาก bits ผู้สอนบอกว่าโค้ดอ่านยาก ("ไม่อยากเถียงเรื่องชื่อตัวแปร") และยังไม่เข้าใจทุกบรรทัด — "ไว้ค่อยดู" ("famous last words") จากนั้นเป็น asymmetric quantization: เอาผลรวม q ตรงบิต 1 คูณสองลบผลรวมทั้งหมด = MaxSim ด้วยเวกเตอร์ binary ซึ่งถูกกว่า เก็บคะแนนของ passage แล้วไป passage ถัดไป ต่อด้วยส่วนที่ผู้สอน "คิดว่า" แค่จับเวลาเป็นมิลลิวินาที, topPosts ที่ผู้สอน "สันนิษฐาน" ว่าเรียง passage ตามคะแนน และส่วนส่งค่าต่อ token ของคำถาม ซึ่งผู้สอน "เดาว่า" ใช้กับตารางด้านบน

ผู้สอนยอมรับว่ามีรายละเอียดหลายอย่างที่ยังไม่เข้าใจ ต้องอ่านทั้ง syntax ของ Opus และ JavaScript ที่ไม่ได้เขียนตั้งแต่ราวปี 2018 แต่เห็นว่าเป็น proof of concept ที่ดี จะแชร์ลิงก์และ repo บน X และ LinkedIn ให้คนช่วยปรับ และบอกว่าอาจทำคลิปต่อถ้ายังพัฒนาต่อ

ท้ายคลิปค้นวิธีออกเสียง Pleias ("เพล-อัส") แล้วเปิดหน้าโมเดล: ประเมินว่าแหล่งมีข้อมูลพอให้ตอบอย่างมีหลักฐานไหม (trivial / answerable / reformulate / refused และการวิเคราะห์เอกสาร extensive / basic / incomplete / infeasible — ผู้สอนไม่แน่ใจ 100%) ผู้สอนตื่นเต้นที่โมเดล 350M "ชนะ" หลายโมเดล ดูกราฟประสิทธิภาพที่ลดลงในภาษาที่ไม่ใช่อังกฤษบน HotpotQA และสัดส่วนคำตอบถูก ที่ "ชนะโมเดล 7 พันล้านพารามิเตอร์" ผู้สอนยอมรับว่าไม่รู้จัก Pleias มาก่อนและจะไปศึกษา แล้วพูดถึง ModernColBERT ที่ต้องไปดูด้วย และ Reason-ModernColBERT ที่เดาว่าราว 100 ล้านพารามิเตอร์ ไฟล์ราว 600 MB ("อาจจะ ไม่แน่ใจ 100%") และคิดว่าอาจเพราะเก็บเป็น F32 ขอบคุณ Antoine สำหรับแรงบันดาลใจ

ข้อที่ควรเข้าใจให้ตรง (ผลตรวจ ส่วนที่ 9): model card ของ Pleias บอกว่าดีกว่า SLM ส่วนใหญ่ที่ ≤ 4B บน HotpotQA / 2wiki และเป็นทางเลือกที่คุ้มกว่า Qwen-2.5-7B / Llama-3.1-8B แต่ไม่ได้อ้างว่าชนะโมเดล ~7B โดยรวม · Reason-ModernColBERT ระบุ 150M (ไม่ใช่ ~100M) · บล็อก Mixedbread เก็บคำถามเป็น int8 ส่วนเดโมนี้ใช้ FP32 สูตรเหมือนกัน

9. ผลตรวจข้อเท็จจริง (เสริมจากผู้จัดทำ, 2026-10-11)

Key Takeaways

  1. RAG แบบ multi-vector รันในเบราว์เซอร์ทั้งหมดได้: pylate-rs (WASM) + ColBERT 33M + index 1 บิต ~5 MB + Pleias-RAG-350M บน WebGPU
  2. asymmetric quantization: คำถามละเอียด เอกสาร ±1 → q · d = 2 × Σ(q ที่บิต 1) − Σq และเปิดตาราง 256 ช่องทีละไบต์แทนการบวก
  3. บน SciFact: int8 ไม่เสียอะไร · เอกสาร binary −3.6 NDCG@10 แต่เล็กลงราว 32 เท่า (ผู้จัดทำคำนวณ) และ Recall@100 แทบไม่ตก · binary ทั้งคู่ −14
  4. ตาราง MaxSim ต่อ token ช่วยเห็นว่าคำไหนตัดสินอันดับ (cavern) · ผู้จัดทำสังเกต: คอลัมน์ Other 26 ([CLS], [unused0], [SEP] และ [MASK] 23 ตัว) คิดเป็นราว 82% ของคะแนนรวม
  5. ดูข้อมูลจริงใน DevTools: 32 × 96, 32 × 12 × 256 = 98,304, 435,383 token × 12 ไบต์ = 5,224,596
